# 2026-04-09 PTY WebSocket 化与卡顿治理计划（再次修订）

## 1. 背景与终态

当前 PTY 主链路：
1. 输入：`POST /pty/:id/input`
2. 输出：`GET /pty/:id/stream`（SSE）

终态目标：
1. PTY 输入与输出统一为 WebSocket。
2. 升级完成后彻底移除旧 HTTP/SSE PTY 通道。
3. 计划必须分阶段推进，每阶段都有可验收交付条件。

## 2. 约束与范围

1. 阶段性推进是硬要求，禁止“一步到位但不可验收”。
2. 不优先做通用输入防抖；仅允许微批合帧，且不得改变终端交互语义。
3. 本轮不展开平台差异设计讨论；Rust + Tauri 的跨平台实现按统一方案推进。
4. **不做 runtime fallback**：
   - 不做“WS 失败自动退回 HTTP input”的实现。
   - 阶段性保留旧通道，仅用于未迁移链路仍需存在的过渡，不作为错误处理兜底。
5. 终态是 WS-only，但阶段性允许“输入已迁移、输出未迁移”的混合拓扑。

## 3. 与 Issue #894 的关系

Issue：<https://github.com/exomind-team/exomind/issues/894>

映射关系：
1. `#894` 对应本计划 `阶段 S1（Plan-S1）`。
2. 由于本计划明确“不做 fallback”，在开始执行 `S1` 之前，应先把 `#894` 的标题、目标行为、验证溯源方法、完成条件同步为：
   - 输入默认走 WS
   - 输出暂时保留 SSE
   - 不实现自动 fallback
   - 失败态为显式错误 + 手动 `retry/reconnect`
3. `#894` 的关闭不等于 WS-only 完成；WS-only 以 `S3` 验收为准。
4. `#894` 关闭依赖 `S0` 已完成，但 `S0` 不计入 `#894` 交付物本身。
5. `#894` 的关闭口径以本计划 `DoD-S1` 的明文条款为准，不保留另一套相互冲突的 checklist。

### 3.1 发布顺序与兼容矩阵

在“不做 runtime fallback”的前提下，阶段迁移必须遵守以下兼容矩阵：

1. `旧前端 + 旧 runtime`
   - 状态：支持
   - 含义：当前基线
2. `旧前端 + 新 runtime`
   - 状态：支持
   - 含义：过渡态；`S1/S2` 期间 runtime 仍需兼容旧前端所依赖的旧路由
3. `新前端 + 旧 runtime`
   - 状态：不支持
   - 含义：禁止发布；因为新前端要求 WS 输入主路径
4. `新前端 + 新 runtime`
   - 状态：支持
   - 含义：目标组合

唯一允许的发布顺序：
1. `S1/S2` 先发 runtime，再发 frontend
2. `S3` 仅在确认不存在受支持旧前端仍依赖旧路由后，才允许硬删旧通道

### 3.2 版本能力协商与支持边界

1. 新前端在启用 PTY 输入前必须完成传输能力协商；若 runtime 不满足当前阶段要求，前端进入“版本不兼容/需升级 runtime”的阻断态：
   - 不发送 PTY 输入
   - 不自动 fallback 到旧 HTTP/SSE 通道
2. `S1` 所需最小能力：
   - 支持 PTY WS 输入
3. `S2` 所需最小能力：
   - 支持 PTY WS 输入
   - 支持 PTY WS 输出
   - 支持同会话重连与重绑
4. `S2` 期间，旧 `POST/SSE` 仍是“已发布旧前端”的受支持兼容面：
   - 这不是 runtime fallback
   - 仅用于旧前端与新 runtime 的兼容
5. 进入 `S3` 前，必须先明确“受支持旧前端”的边界：
   - 以最小受支持前端版本或截止日期写入发布说明/issue
   - 只有该支持边界内的前端都不再依赖旧路由时，才允许物理删除旧通道
   - 超出支持边界的旧客户端访问需要记录，但不构成 `S3` 阻塞条件

## 4. 兼容性继承清单

本次迁移默认继承以下既有行为，不在本计划内重写，但必须保持不回归：

1. 会话身份不变：
   - 回退到旧版本、重连、换通道都不得凭空新建替代会话。
2. 生命周期语义不变：
   - `running / waiting_input / ended / completed` 等既有状态机不因传输层变化而漂移。
3. 终端工作台绑定关系不变：
   - 已绑定 PTY 的窗格/视图不应因通道切换串绑或误绑。
4. 历史回放语义不变：
   - 不允许出现可见输出重复、缺段或历史缓冲被意外清空。
5. 传输层错误是副状态：
   - WS 输入失败等错误只能表现为 transport/UI 错误态，不得覆写 PTY 主生命周期状态。

## 6. 分阶段计划（含交付条件）

### 阶段 S0（Plan-S0）：基线、协议与兼容口径定稿

目标：先把“怎么测、怎么判、哪些旧语义必须保持”写死。

交付物：
1. 指标定义：
   - 输入延迟（含前端排队/微批等待）
   - 重连恢复时间
   - 丢键率
   - 失败率
   - UI 冻结判定
   - 长输出期间可输入性
2. PTY WS 协议说明：
   - `input`, `resize`, `ping`, `ready`, `output`, `eof`, `ack`, `error`
3. 错误兼容表：
   - 鉴权失效
   - 会话不存在
   - 权限不足
   - 会话已结束
   - 临时网络失败
4. 兼容性继承清单与关联 issue 矩阵。
5. 版本能力协商与不兼容阻断合同。
6. 附着/输入所有权合同：
   - 同一 `pty:id` 是否允许多附着
   - 谁拥有输入权
   - 输入 owner 如何切换
   - 后来连接是否顶替先前连接
7. 输入序号与不确定态合同：
   - `input_seq`
   - `ack` 对应规则
   - “已写入 PTY，但客户端未收到 `ack` 就断连”的不可判定输入如何处理

交付条件（DoD-S0）：
1. 明确“输入到回显延迟”测量口径：
   - 起点：前端收到终端控件输入事件、进入本地缓冲/微批队列前时间戳
   - 终点：对应输出字节完成渲染时间戳
2. 明确“断连恢复时间”测量口径：
   - 起点：客户端收到活动 WS 的 `close/error`
   - 终点：同一会话的新 WS 收到 `ready`，且紧随其后的探针输入收到成功 `ack`，并出现可见 PTY 输出或提示符刷新
3. 明确采样规则：
   - 每场景 >= 1000 样本
   - 固定负载模板、会话时长、环境指纹字段
4. 明确 `ack` 语义：
   - 固定为：`指定 input_seq 已写入 PTY`
   - 不允许使用“仅已入队”作为成功口径
5. 明确混合期输入-输出关联规则：
   - 需要有序号或关联字段，能证明输入批次、`ack`、回显输出的对应关系
   - `S1` 期间至少由 `WS input_seq + ack + 前端本地 telemetry` 形成可导出的证据链；不要求改造 SSE 对外协议
6. 明确 `丢键率 / 失败率 / UI 冻结 / 长输出期可输入性` 的判定口径：
   - 普通输入场景的 `ack` 超时阈值固定为 500ms；恢复场景按 `3 秒恢复` 单独计
   - `丢键率`：在普通输入场景中，500ms 内未收到 `ack`，且 1000ms 内未出现预期可观察结果的输入字节或输入批次占比
   - `失败率`：输入批次在普通输入场景中 500ms 内出现显式 `error`、`ack` 超时、版本不兼容阻断、或未恢复 transport 故障的占比
   - `UI 冻结`：4KB 粘贴场景中，出现连续 > 200ms 主线程卡顿，或用户后续探针输入在 500ms 内无法进入输入队列
   - `长输出期间可输入性`：长输出场景下，每次探针输入都必须在 500ms 内收到 `ack`，并在 1000ms 内出现对应可见结果
7. 明确微批默认值选择规则：
   - 在 `8-16ms` 范围内，选择满足收益门槛、且不破坏控制键语义的最小窗口值
8. 明确术语：
   - `验证批次` = 一次完整执行 `§8.2` 场景集 + 对应自动化底线 + 用户叙事/日志归档
   - `完整验证窗口` = 新前端默认版发布后连续 72 小时，且覆盖至少 3 个独立自然日
9. 明确“不确定态输入”处理原则：
   - 若服务端可能已写入 PTY，但客户端未收到 `ack` 就断连，则该输入标记为“不可判定”
   - 不自动重放不可判定输入，只允许显式人工重试

晋级门（S0 -> S1）：
1. 协议语义评审通过。
2. 指标口径、采样模板、证据格式可复现。
3. `#894` 文案已同步为“无 fallback”的阶段性目标。

### 阶段 S1（Plan-S1）：输入改为 WS，输出仍保留 SSE

目标：先解决逐键 HTTP 输入开销，不同时重写输出链路。

交付物：
1. 新增 `GET /pty/:id/ws`，承载输入与控制消息。
2. 前端输入**默认**走 WS，不再逐键 `POST /pty/:id/input`。
3. 输出暂时仍走 SSE。
4. 输入微批策略生效：
   - 范围 `8-16ms`
   - 默认值由 `S0` 基线决定
   - `Enter`、`Ctrl+C`、`Escape`、方向键即时 flush
5. WS 输入失败时，呈现明确 transport 错误状态，不自动 fallback 到旧 input 通道。
6. `S1` 失败态兼容合同：
   - 会话保持原身份，不新建替代会话
   - 若 SSE 输出仍存活，则继续只读输出，不因输入 WS 失败而立即中断
   - 若 SSE 输出也不可用，则进入显式阻断态，不伪装为可继续输入
   - PTY 与窗格/视图绑定保持不变
   - 用户可显式执行 `retry/reconnect`，但不走自动 fallback
   - 不自动重放不可判定输入

交付条件（DoD-S1）：
1. 前端默认走 WS 输入、输出暂保 SSE、不自动 fallback，且与已同步后的 `#894` 文案一致。
2. shell/vim/tmux/控制键语义不回归。
3. 会话身份与生命周期语义不回归：
   - 不新建替代会话
   - 不改变 `running / waiting_input / ended / completed` 语义
4. 关键交互指标达标：
   - 连续输入 30 秒无丢键
   - 粘贴 4KB 文本不出现 UI 冻结
5. 失败态合同经诱发验证通过：
   - 人工诱发 WS 输入失败
   - 错误态明确可见
   - 若 SSE 仍存活，则维持同会话只读输出
   - 不自动 fallback
   - 不自动重放不可判定输入
6. 至少一份“旧链路 vs S1”的量化对比证据：
   - 同一负载模板
   - 同一采样口径
7. S1 收益门槛：
   - 输入到回显延迟 `p95` 相比旧链路改善 >= 20%，或
   - 输入失败率相比旧链路下降 >= 50%
8. `S1-S3` 公共自动化底线与 `S1` 额外测试类别通过（见 `§9.2`）。

晋级门（S1 -> S2）：
1. 连续 3 个验证批次无 P1 回归。
2. 上述收益门槛稳定达成。

### 阶段 S2（Plan-S2）：输出改为 WS，WS 成为新前端唯一主路径

目标：输入输出统一到同一 WS 主路径，但此时旧路由代码仍可短暂保留，作为“已发布旧前端”的兼容面，尚未物理删除。

交付物：
1. 输出改走 WS `output/eof` 消息。
2. 前端停止消费 SSE 主路径。
3. 旧 `POST/SSE` 路由继续仅服务已发布旧前端，不作为新前端 fallback。
4. 实现同会话重连与重绑。
5. 按 `S0` 合同落实附着/输入所有权规则。
6. 多实例/多窗格场景验证补齐。

交付条件（DoD-S2）：
1. 核心指标达标：
   - 输入到回显：`p95 < 50ms`、`p99 < 100ms`
2. 可靠性达标：
   - 断连恢复时间 <= 3 秒（按 `S0` 口径）
3. 关键交互与兼容性达标：
   - 连续输入 30 秒无丢键
   - 粘贴 4KB 文本不出现 UI 冻结
   - 长输出期间可持续输入
   - 不出现可见输出重复、缺段或历史缓冲意外清空
   - 同会话重连后会话身份、绑定关系保持不变
   - 多 PTY 视图并存时不串绑、不误绑
4. 兼容边界达标：
   - 已发布旧前端 + 新 runtime 仍可使用旧 `POST/SSE` 兼容面
   - 新前端 + 旧 runtime 会进入显式“版本不兼容/需升级 runtime”阻断态
5. 自动化达标：
   - `S1-S3` 公共自动化底线通过
   - `S2` 额外测试类别通过（见 `§9.2`）
   - Tauri MCP 用户叙事 `A-F` + `G` 验收通过

晋级门（S2 -> S3）：
1. 指标连续通过。
2. 无 P1 回归。
3. 运行态证据显示旧 input/output 通道已不再被主路径使用。

### 阶段 S3（Plan-S3）：物理删除旧 HTTP/SSE PTY 通道

目标：达到 WS-only 终态，不留残留。

交付物：
1. 删除 runtime 旧路由：
   - `/pty/:id/input`
   - `/pty/:id/stream`
2. 删除前端旧实现：
   - `sendPtyTextInput`
   - SSE 读取与解析链路
3. 删除兼容枚举与文档旧路径描述。

交付条件（DoD-S3）：
1. 残留扫描全绿（见第 9.1）。
2. 运行态反证成立：
   - 主动探针访问旧 endpoint 返回 `404` 或 `410`
   - 一个完整验证窗口内不存在“来自受支持前端版本”的旧通道自然业务命中证据
   - 数据源固定为 runtime 路由访问日志 + frontend transport telemetry
3. `S1-S3` 公共自动化底线通过，且 `S3` 额外测试类别通过（见 `§9.2`）。
4. Tauri MCP 用户叙事 `A-F` + `G` 在旧通道删除后再次通过，且证据归档。

## 7. 关键设计决策

1. 不做自动 fallback，这一条是主动减复杂度决策。
2. 阶段性交付与终态清理分离验收，避免混淆关闭口径。
3. WS-only 终态必须通过“代码扫描 + 运行态反证”双证据确认。

## 8. 验收指标与测量定义

### 8.1 核心指标

1. 输入到回显延迟：
   - `p95 < 50ms`
   - `p99 < 100ms`
2. 连续输入 30 秒无丢键：
   - `S1` 起即为硬指标
3. 粘贴 4KB 文本不出现 UI 冻结：
   - `S1` 起即为硬指标
4. 长输出期间可持续输入：
   - `S2` 起即为硬指标
5. 断连恢复时间 <= 3 秒：
   - `S2` 起即为硬指标

### 8.2 测量定义

1. 样本量：
   - 每场景 >= 1000
2. 场景集：
   - 逐键输入
   - 连续输入 30 秒
   - 连续粘贴
   - 控制键混合输入
   - 长输出期间探针输入
   - 断连后恢复
   - 版本错配阻断
   - 输入 WS 失败态
3. 证据产物：
    - 原始 CSV/JSON
    - 汇总报告（`p50/p95/p99/失败率`）
    - 环境指纹
    - `commit SHA`
    - 时间戳
4. 恢复成功附加证据：
    - `close/error` 时间戳
    - 新 WS `ready` 时间戳
    - 探针输入 `ack` 时间戳
    - 首个恢复后可见 PTY 输出或提示符刷新时间戳
5. 运行态反证附加定义：
   - `主路径使用` = 新前端默认用户流程在未显式切换 transport 的情况下实际使用的输入/输出通道
   - `自然业务命中` = 非主动探针、非 CI、非人工兼容测试、且来自受支持前端版本的旧 endpoint 访问

3. `S2` 额外最小测试类别：
   - WS 输出分帧、顺序、历史连续性
   - 同会话重连与重绑
   - 多 PTY 焦点/绑定隔离
   - 长输出期间持续输入
4. `S3` 额外最小测试类别：
   - 旧 endpoint 返回 `404/410`

   - 版本错配阻断仍然成立

### 9.3 Tauri MCP 验证总流程

不在本计划中写死工具级点击细节。
实际执行时遵循：

2. 下述“全过程 + 测试项 + 验收标准”

#### 9.3.1 执行顺序（必须按序）

1. 环境准备：
   - 清理失败实例、残留 PTY、重复桌面实例。
   - 记录当前桌面实例 `hostId`、`startedAt`、RT 端口、前端端口。
   - 先做一次旧 endpoint 主动探针，记录 `/pty/:id/input`、`/pty/:id/stream` 的返回码。
2. 会话准备：
   - **只允许通过真实 UI 创建会话**，禁止直接写 DB、脚本注入、伪造 session。
   - 最少准备 `3` 个活跃 PTY，会话类型至少包含 `1 个 Claude + 1 个 Codex`。
   - 每个会话都要发送一条唯一 token，确认它在终端真实出现，并记录：
     - `session id`
     - `pty id`
     - `inner_session_id`
     - `agent type`
     - `workdir`
3. 基线链路：
   - 先在 `网络/会话` 页面验证右侧终端窗格。
   - 再验证全屏终端。
   - 最后进入 `网络/平铺`。
4. 主验收面：
   - **`网络/平铺` 是主验收页。**
   - 后续大部分操作量、并发量、恢复量、日志观察量都在 `平铺` 完成。
5. 中断恢复：
   - 在 `平铺` 页面保持多个 PTY 活跃时执行 embedded runtime 重启或短时断连。
   - 重启后先看 `平铺` 恢复，再回查 `会话` 与右侧窗格是否一致。
6. WS-only 反证：
   - 在完整验证窗口内确认前端无旧 transport 调用。
   - 再次主动探针旧 endpoint，确认 `404/410`。
7. 证据归档：
   - 完成日志、截图/录屏、session/pane 对照记录与 pass/fail 结论。

#### 9.3.2 单轮验证批次闭环要求

只有同时满足以下条件，这一轮验证才算“有效批次”：

1. 执行前：
   - 代码版本固定，记录 `commit SHA`。
   - 自动化底线已跑完，且结果已记录。
   - 当前桌面实例信息已记录。
   - 旧 endpoint 主动探针已记录。
2. 执行中：
   - `A-H` 每个叙事都必须当场记录 pass/fail，不允许事后凭印象补写。
   - `网络/平铺` 的 pane 与 PTY 绑定表必须在进入压力测试前先记一版，在 runtime 重启后再记一版。
   - 控制台日志必须持续开启，至少覆盖：
     - 建连
     - `ready`
     - `close/error`
     - 重新附着/恢复
3. 执行后：
   - 对照 `DoD-S1 / DoD-S2 / DoD-S3` 做阶段结论。
   - 明确标注本轮结果只能是 `pass / fail / no conclusion` 三种之一。
   - `no conclusion` 不得按通过处理，也不能用于关闭阶段或 issue。

#### 9.3.3 失败处理与重测规则

1. 任一叙事失败后，必须先保留失败证据，再允许修复。
2. 只要代码、runtime 配置、桌面实例或验证前提发生变化，上一轮验证不得继续累加视为同一批次。
3. 若失败发生在 `平铺` 页，则至少必须重跑：
   - `叙事 C`
   - `叙事 D`
   - `叙事 E`
   - `叙事 F`
   - `叙事 H`
4. 若失败发生在 runtime 重启/恢复链路，则重测时必须重新记录：
   - 重启前 `hostId` / `startedAt`
   - 重启后 `hostId` / `startedAt`
   - 每个活跃 pane 的恢复结果
5. 若只能复现到“看起来不对”但证据不足，则结论必须写为 `fail` 或 `no conclusion`，禁止写 `pass with concern`。

### 9.4 Tauri MCP 用户叙事（S2/S3 必须）

#### 叙事 A：`网络/会话` 创建 Claude / Codex 并立即输入

1. 用户进入 `网络/会话`。
2. 用户通过真实 UI 分别创建 Claude 或 Codex 终端，而不是自定义 shell 占位。
3. 用户在右侧终端或底部统一输入框立刻发送一条短提示。
4. 预期：
   - 输入即时送达。
   - 无逐键卡顿。
   - 无错误状态闪烁。
   - 当前输入目标与实际输出 PTY 一致。

#### 叙事 B：突发粘贴

1. 用户向当前 PTY 一次性粘贴大段文本。
2. 预期：
   - UI 不冻结。
   - 文本完整送达。
   - 无明显乱序或截断。
   - 不把不可判定输入自动重放到别的 PTY。

#### 叙事 C：`会话` 右侧窗格与全屏终端来回切换

1. 用户在 `网络/会话` 右侧窗格打开某个 Claude/Codex PTY。
2. 用户切到全屏终端，再返回 `网络/会话`。
3. 预期：
   - 始终绑定同一会话与同一历史身份。
   - 不出现重复终端面。
   - 不串到其他 PTY。
   - 返回后底部统一输入框仍指向正确 PTY。

#### 叙事 D：运行时短暂中断后恢复

1. 用户在会话仍存活前提下经历 runtime 重启或短时断连。
2. 预期：
   - `3 秒内恢复交互`。
   - 不新建替代会话。
   - 生命周期语义不漂移。
   - 若只剩 transcript，可读历史会显式进入断开/恢复链路，而不是停留在“输出看似活着、输入已死”的中间态。

#### 叙事 E：多 PTY 并存

1. 用户同时打开两个以上 PTY 视图或窗格。
2. 用户在不同 PTY 间切换焦点并输入。
3. 预期：
   - 输入只进入当前聚焦 PTY。
   - 不串绑、不误绑。
   - 关闭一个 PTY 不影响其他 PTY 的输出与输入。

#### 叙事 F：长输出与历史连续性

1. 用户让 PTY 产生明显超过一屏的长输出。
2. 如发生断连/重连，再继续观察。
3. 预期：
   - 不出现可见输出重复。
   - 不出现缺段。
   - 历史缓冲不意外清空。
   - 同一会话在不同 view（右侧窗格 / 全屏 / 平铺）中的历史连续。

#### 叙事 G：输入 WS 失败态

1. 用户在会话仍存活前提下遭遇输入 WS 建连失败或中途失败。
2. 预期：
   - 出现明确 transport 错误状态。
   - 不自动 fallback 到旧 HTTP input。
   - 不自动重放不可判定输入。
   - 若 WS 输出仍存活，则保持同会话只读输出。
   - 用户只能显式执行 `retry/reconnect`，或等待恢复链路收敛。

#### 叙事 H：`网络/平铺` 高强度压力测试

1. 用户切到 `网络/平铺`，并把最少 `3` 个活跃 PTY 绑定到多个 pane。
2. 至少包含：
   - `1 个 Claude`
   - `1 个 Codex`
   - `1 个额外 PTY`
3. 在同一验证窗口内至少完成以下操作量：
   - 连续 `20` 次聚焦切换并发送输入。
   - 至少 `2` 个 pane 同时持续输出时，在另一个 pane 继续输入。
   - 至少 `5` 次 pane 关闭 / 重新绑定 / 替换。
   - 至少 `1` 次从 `平铺` 切回 `会话` 或全屏，再返回 `平铺`。
   - 至少 `1` 次在 `平铺` 保持多 PTY 活跃时执行 runtime 重启。
4. 预期：
   - `平铺` 中每个 pane 的 PTY 身份始终稳定。
   - 焦点、输入目标、pane 标题、终端输出四者一致。
   - 不出现 pane 空白挂死、串绑、误绑、重复输出、历史错位。
   - 右侧窗格与 `平铺` 不互相污染状态。
   - runtime 重启后优先恢复 `平铺` 中的活跃 pane，而不是只恢复单窗格。

### 9.5 验收标准（逐项 + 整体验收）

#### 9.5.1 单项通过标准

1. 任一测试项只有在以下条件全部成立时才算通过：
   - UI 可继续交互，无明显冻结。
   - 当前输入目标与实际输出 PTY 一致。
   - 无串绑、误绑、错 pane 输出。
   - 无重复终端实例或幽灵 pane。
   - 无旧 HTTP/SSE PTY fallback 行为。
   - 日志中无持续 reconnect storm。

#### 9.5.2 `平铺` 页特别阻断条件

1. `网络/平铺` 是后续高频主页面，因此采用更严格阻断口径。
2. 以下任一情况出现一次，即判定本轮 `S2/S3` 验收失败，必须修复后重测：
   - 任一 pane 输入进入错误 PTY。
   - 任一 pane 输出串到其他 pane。
   - 任一 pane 在正常网络/本机条件下出现可感知卡死或持续空白。
   - runtime 重启后只恢复 `会话` 页而未恢复 `平铺` 主链路。
   - 控制台对同一 `ptyId` 出现连续 `3` 次及以上无收敛的 open/close 循环。
   - 出现 `before ready` / `read_only history mode for live terminal` 后，未在恢复链路中收敛到正确终态。

#### 9.5.3 中断恢复通过标准

1. 对有历史绑定的 recoverable 会话：
   - `3 秒内恢复交互`。
   - 不新建替代 session id。
   - 不把旧 PTY 的只读 transcript 误判为“已恢复可交互”。
2. 对不可恢复会话：
   - 必须显式进入只读/断开态。
   - 不允许虚假可输入态。
   - 不允许输入 silently 丢失。

#### 9.5.4 整体验收标准

1. `A-H` 全部通过，且必须在同一轮验证记录中闭环。
2. `平铺` 压力测试必须通过，不能用 `会话` 页通过来替代。
3. 日志、截图/录屏、session/pane 对照记录齐全。
4. 任一测试项失败，都阻塞 `S2/S3` 关闭。

#### 9.5.5 分阶段验收门

1. `S1` 验收至少要求：
   - `§9.2` 公共自动化底线通过。
   - `叙事 A / B / C / G` 通过。
   - `DoD-S1` 中的收益门槛与失败态合同有对应证据。
2. `S2` 验收至少要求：
   - `§9.2` 公共自动化底线通过。
   - `叙事 A-H` 全通过。
   - `平铺` 压力测试通过，且 runtime 重启恢复通过。
   - `DoD-S2` 的指标、恢复时间、绑定稳定性都有实测证据。
3. `S3` 验收至少要求：
   - 先完整满足 `S2` 的所有验收条件。
   - `§9.1` 残留扫描全绿。
   - 旧 endpoint 主动探针返回 `404/410`。
   - 旧 transport 在真实用户流程中无自然业务命中证据。
