## 反馈相关性标签

对每条记录先判定“是否与外心有关”，再决定是否进入 Beta 规划。不能因为记录出现在外心档案里就默认它是外心缺陷。

| 标签 | 含义 | 处理方式 |
|---|---|---|
| `exomind-product` | 外心自身的功能、交互、数据或可靠性 | 进入对应反馈簇并回到源码/运行证据核验 |
| `exomind-integration` | 外心与 OS、网络、输入法、文件系统等交界处的问题 | 保留为调查线索；区分外心责任和外部依赖 |
| `external` | 其他应用、工具或服务自身的问题，外心只是记录载体 | 从 Beta 修复候选中排除；需要时仅作外部依赖背景 |
| `personal` | 睡眠、精力、生活安排、研究或其他个人记录 | 不进入外心产品材料 |
| `mixed` | 同一条记录包含多类内容 | 只摘录与外心有关的原意，逐项保留 event ID；其余不复制 |
| `unresolved` | 现有材料无法判断是否指向外心 | 保留待核状态，不自动并入 Beta 缺陷或派工 |

## Agent 自动化集成：handoff 持久授权与明确访问结果

> **用户明确表示这是目前最烦的问题，规划时应作为高优先级的 Agent 工作流/外心集成议题处理。** 本节来自 T3「外心β开始日用：实测」中的直接反馈，不属于 Beta typed feed；不能伪造 `local_seq` 或 `event_id`。

用户报告，过去在 0.5 的使用体验中，定期巡检时给 Agent 一个 `/exomind-monitor` Skill，就能自动找到对应外心实例并顺畅完成读写；用户希望 0.6 延续这种“授权一次，之后自动复用”的体验。端口变化、外心重启或版本变化等运行环境变动，不应反复要求用户寻找、重发或确认已经授权的 handoff。只要用户没有撤销授权，Agent 每次都应给出可理解的访问结果并继续获准操作；若授权确实失效、撤销或范围不足，则明确报告具体结果和可行下一步。

本次巡检暴露的具体断点：定时触发的新运行没有当前消息附带的 handoff，Agent 先因此停下并请求用户提供；用户指出此前授权已在常驻汇报线程给过。用户进一步明确，后续不允许卡在 handoff 上，也不应每次查别的线程或刻意搜索；应由 Skill 的脚本自动复用本机持久保存的既有授权。来源为本线程 user items `9f3e6382-b438-4107-b200-ce87ae378f37`、`a4c4c24e-7b45-41cd-bdff-8222782a6db7`、`58c45e52-1253-4397-9aa6-42c46def92df`。这些是同一问题逐步澄清，不应拆成多个缺陷或反复向用户确认。

需要解决的是“授权上下文未被 Skill 稳定持有和复用”，不能把它误判成端口扫描问题，也不能用更宽松的身份校验绕过。规划与实现需满足以下体验合同：

1. 用户在某台受信任主机上完成一次明确授权后，Skill/CLI 将 handoff 安全保存在本机 Git 忽略的私有状态位置；后续由固定入口自动读取，无需依赖本轮消息、其他 T3 线程或用户记忆文件路径。凭据不进入仓库、命令行参数、日志、普通报告或聊天。
2. 授权逻辑绑定稳定的 profile/grant 与能力范围；`api_base_url`/端口只作为路由提示。脚本可动态发现当前实例 endpoint，并对授权绑定的 profile 执行 hello、`access/check` 与所需能力检查。仅端口变化、进程重启或兼容的版本/runtime 变化，不应让既有授权丢失；实际 profile 不匹配、grant 撤销、能力不足或协议不兼容时必须拒绝并解释。
3. 每次调用都返回明确状态：当前实例是否发现、连接/协议是否可用、授权是否有效及范围、操作是否完整、是否部分成功。至少区分实例不可达、未发现 endpoint、授权缺失/损坏、授权拒绝/撤销、profile 不匹配、版本/协议不兼容和读取/写入不完整；不得把“没有 handoff”“网络失败”与“权限拒绝”混成一个状态。
4. 用户撤销授权后，后续 Skill 调用须停止访问，并说明已撤销/不可用；重新授权只在确实需要建立新授权时发生。不要通过查找其它 profile、匿名访问、旧 0.5 Runtime 回退或放宽 grant 来伪造连续性。
5. `doctor`/访问结果与业务操作结果分开：诊断成功不代表历史读取完整或 Note 写入成功；分页读取仍以 `coverage.full_history_complete` 为准，写入仍须按回执和回读合同确认。

现有 `exomind-monitor` Skill 已规定 Windows 下按 `exomind.exe` 的 loopback listener 动态发现 endpoint，并校验 handoff 授权；这覆盖了端口/进程路由变化的一部分。缺口是：当前入口在持久 handoff 不在标准位置/本轮上下文没有时仍可能转而询问用户，且跨运行如何稳定复用授权必须由本地安全存储与 Skill 脚本共同闭环。后续复用已有动态发现和访问校验，不另造实例发现系统。此项是 Agent tooling 与 ExoMind 访问集成的可靠性/可用性问题，不自动等于 Beta 终端用户产品缺陷；但它会直接影响自动化巡检、读写任务和用户对 Agent 的信任，应进入 β27/β28 战略讨论。

**验收场景**：用户只做一次授权；随后轮换 endpoint 端口、重启 ExoMind、升级到兼容版本并触发定时巡检。每轮脚本都自动发现当前授权范围内的实例，准确返回访问/业务结果，不询问用户、不访问其他档案；真实撤销授权后则立即停止并报告撤销。另覆盖无实例、过期/损坏 handoff、profile 不符、grant 缺能力、旧/不兼容协议和分页中断，检查它们都有彼此可区分的明确结果。此验收证明 Skill 集成连续性，不代替 ExoMind 的跨设备同步验收。

## 自动化建议：把人工巡检变成可回溯的候选索引

目标是自动完成重复检索、归并和交叉引用，让人只处理不确定分类与产品决策。分类自动化不能靠“出现外心关键词”一条规则，也不自动把候选变成任务。

1. **读取与覆盖**：沿用进程优先的本机 endpoint 动态发现、当前 handoff 绑定 profile 的 `access/check`、固定 highwater 分页；把 generated time、through、feed counts 和 `full_history_complete` 写入每轮结果。
2. **稳定去重**：以 `event_id` 为主键；`local_seq` 只作为档案内定位号。状态分开记录 `reviewed`（人工核对）、`reported`（线程回读确认）、源码/测试/候选/设备验收；旧 `processed` ledger 项先标待复核，不能自动当成已审核。
3. **自动预分类**：按记录类型、作者、正文和来源关系生成相关性标签（上表）及主题标签（输入/附件/同步/提醒/性能等），输出简短理由和置信度。混合、低置信或可能私密内容默认进入人工复核，不转发无关正文。
4. **自动关联但不自动定因**：把相关 seq 与已有 issue/开发线程 item/验收计划段落对照，列出“新增、重复、后续修正、正面验收、待确认”候选；只能通过稳定 event ID 或明确引用关联，不凭关键词自动关闭问题。
5. **按需源码对照**：仅在知道现场版本时追 UI → client/IPC/API → Host/Core；否则标 `source version unverified`。结论用 `consistent / possible explanation / diverges / unverified`，保留现场与代码差异。
6. **生成轻索引**：每轮只更新“新增/变化/需确认”的短索引，并链接到详细台账、源事件和代码链；不重复写完整历史，不把 token、邀请材料、私密生活内容或未经 hash 校验的原件写入报告。
7. **人类决策边界**：自动化可只读发现、分类建议、去重、生成草案和覆盖检查；启动版本、确定优先级、派工、提交/推送、发布或对外发送仍按用户明确授权范围执行。

现有落地基础：本机 [exomind-dev-patrol](C:/Users/56506/.claude/skills/exomind-dev-patrol/SKILL.md) 的 `patrol.mjs` 现通过显式 handoff 的动态连接流程读取完整 history，按 event_id 生成无正文相关性索引；输出 `through` 与 `last_record_seq` 分开显示。人工 `reviewed` 与线程回读确认后的 `reported` 分开记入 profile ledger，只有明确状态命令可生成待提交提案。分类规则是启发式，已做少量合成样例验证；生产运行时覆盖与跨档案迁移仍需后续巡检观察。无需另造第二套巡检系统。
