# 本地参考源维护章程

本文件服务于 `cross-analysis` skill 的“维护态”。

它不是单独 skill，而是入口 `SKILL.md` 的附属参考文档，用来指导 Agent 如何新增、补充或整理本地参考源。

## 目标

维护本地参考源时，重点不是堆积资料，而是持续完善一套“本地化搜索指南”。

这套指南的作用是：

- 帮助 Agent 更快找到合适参考源
- 提供主题到参考源之间的链接性语义
- 给出后续检索路线，而不是代替检索本身

## 什么时候进入维护态

当出现以下情况时，进入维护态：

- 用户明确要求新增一个本地参考源
- 现有参考源不足以覆盖某个常见目的
- 某个参考源已经存在，但入口、边界或检索路线明显不完整
- 需要整理参考源索引，使其更容易被 Agent 复用

## 维护态的基本原则

### 1. 先判断是否值得纳入

不是所有对象都值得成为本地参考源。

优先纳入这些对象：

- 在多个主题上会被反复参考
- 对某一类目的有稳定代表性
- 能提供清晰的检索入口
- 具有较明确的产品边界或实现边界

如果只是一次性提到、缺乏持续复用价值，不要急着纳入。

### 2. 本地参考源是“入口资产”，不是“知识正文资产”

新增参考源时，要优先写：

- 这个对象适合回答什么目的
- 它不适合回答什么问题
- Agent 应该先去哪里检索
- 若要继续深挖，应优先看哪些入口

不要把维护重点放在复制大段百科式介绍。

### 3. 优先补“链接性语义”

一份好的本地参考源档案，应优先告诉 Agent：

- 什么时候想到它
- 为什么想到它
- 从哪里开始看
- 下一步往哪里延伸

### 4. 粒度以“够用”为准

新增参考源时，不必默认写到源码文件级细节。

默认目标是写到“足以让运行态 Agent 找到正确入口并决定下一步”的粒度即可。

通常情况下：

- 产品导向参考源：写到官网、帮助文档、论坛、showcase 这一层就够
- 实现导向参考源：写到官方文档、API、GitHub 仓库、包目录、examples 这一层通常就够

只有在某类目的反复要求更细的源码定位时，才继续下探到具体源码文件级别。

## 维护流程

### 1. 确认对象

先确认这个对象：

- 名称是否稳定
- 是否具备持续复用价值
- 与哪些主题强相关

### 2. 生成独立档案

新增参考源时，优先基于：

- [template.md](./template.md)

生成独立档案。

新档案应尽量保持模板结构，不要随意删改成不可复用的散文。

### 3. 更新索引

在：

- [index.md](./index.md)

中补登记条目。

索引里重点写：

- 主题标签
- 适用目的
- 适用问题
- 档案位置
- 检索入口
- 外部补充优先路线

### 4. 检查“运行态”是否真的能用

维护完成后，自检这条参考源是否真的能在运行态中帮助 Agent：

- 更快联想到该对象
- 更快找到起始入口
- 更快判断其适用边界

如果做不到这三点，说明档案还不够好。

## 维护时的反模式

不要这样做：

- 把参考源档案写成百科介绍
- 只写“这个产品很强”，不写适用目的
- 只给一个官网链接，没有检索路线
- 不写边界，导致 Agent 误把它当万能参考
- 新增了独立档案，却不更新索引

## 最小检查清单

- 已确认该对象值得纳入本地参考源
- 已基于模板生成独立档案
- 已在索引中登记
- 已补上适用目的与不适用边界
- 已补上检索入口与外部延伸路线
- 已确认运行态真的能利用这条参考源
