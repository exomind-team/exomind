# 2026-04-17 goal-system：任务为边、目标为节点的新架构整理与关联分析

## 范围

这份文档先做两件事：

1. 把当前讨论中的新想法整理成一个可复述、可继续迭代的结构化方案。
2. 把这个方案与仓库里已有的目标系统 issue、spec、实现计划做关联分析，判断哪些是继承，哪些是冲突，哪些需要重新定名或升版。

这不是正式 spec，也不是实现计划。它更像一份过桥文档：把“脑中模型”落成能被后续 issue / spec / RT 迁移继续使用的分析稿。

## 原始想法（全文摘录）

> ①目标是任务系统的新视图，但基于视图还有更多的东西，就是将任务从节点看成边、随后引入新的「节点」类型——目标
>
> ②每个任务都必然指向一个目标节点，但每个任务指向的目标节点是可变的——可以多个任务指向一个目标节点，也能一个目标节点发出多个任务
>
> ③任务的依赖关系天然表现在目标的连接关系中，因为其本质就是「任务指向目标」——一个任务若有上游任务，那这个任务必然基于所有上游任务节点的目标节点（不论直接还是间接），而一个任务没有上游任务（是根），则其表示为从Me节点（目标节点的根）到其终点的边。
>
> ④目标节点依托任务存在，任务不存在了，目标节点就会少一条依托，而正常时候不会存在没任务作为连边的目标节点。一条边（或者有多个起点、一个终点的超边？）唯一对应一个任务，而不会有多余冗余存在。
>
> ⑤任务之间可以用「共同目标」相关联，任务之间原本不同的目标可以经过操作变成是相同的，这时候有多个任务指向同一个目标，而这些任务的下游依赖则都表现为从这个「共同目标节点」所发出的边
>
> ⑥这时候「目标节点」其实就是先前在issue中讨论过的「随着任务自动完成的任务」，而现在这份语义恰好给「目标」承载了
>
> ⑦这个新的「目标系统架构」强化了与任务系统的联系，降低使用的认知负荷（因为更不需要维护两套任务系统了，目标系统不需要绑定任务，而只需专注目标本身，匿名目标节点会因为任务的增加而自动生成）
>
> ⑧这个新的目标系统设计，应该是与先前的目标系统设计是兼容的

## 新想法整理

### 一句话版本

把“目标系统”从“任务系统之外的独立图”改写成“任务系统的一种目标视图”：

- 任务不再主要被看作节点，而被看作从某个起点指向某个目标的边。
- 目标成为新的一等节点类型。
- `Me` 是全图根节点；没有上游任务的根任务，表现为 `Me -> 目标`。
- 任务之间的依赖，不再主要表现为“任务节点之间的箭头”，而表现为“某条任务边从哪个目标节点出发，又指向哪个目标节点”。

### 结构化表述

#### 1. 基本实体

- `MeNode`：根节点，表示“自我 / 当前主体”。
- `GoalNode`：目标节点，表示任务所指向的目的地、阶段性达成态或共同目标。
- `Task`：连接节点的边，语义是“通过这个行动，从某个前提状态走向某个目标”。

#### 2. 基本约束

- 每个任务都必须指向一个目标节点。
- 任务的目标节点可变，任务重规划本质上就是“改边的终点”或“改边所依托的目标结构”。
- 多个任务可以指向同一个目标节点，这表示“不同手段汇聚到同一目标”。
- 一个目标节点可以发出多条任务边，这表示“达成这个目标后，可以进一步展开多个下游任务”。
- 正常状态下不应存在完全脱离任务的目标节点。目标节点依托任务网络而存在。

#### 3. 依赖关系的重写

- 如果一个任务没有上游任务，它就是从 `Me` 发出的根边。
- 如果一个任务有上游任务，它的起点应当落在“上游任务已经抵达的目标节点”上。
- 如果多个上游任务共同构成某个后续任务的前提，那么应优先把这些前提收敛成一个“共同目标节点”，再从该共同目标节点发出新的任务边。

这里隐含一个关键倾向：

- 你提出的模型虽然提到了“多个起点、一个终点的超边”可能性，但更自然、也更兼容现有图模型的做法，是优先使用“共同目标节点归一化”，而不是一开始就引入超边。

#### 4. 目标节点的语义来源

- 目标节点不是额外维护的一套对象树。
- 它更像是原先讨论过的“会随着任务完成而自动完成的任务”被重新命名、重新安放之后的承载体。
- 也就是说，原本漂浮在任务系统旁边的“自动完成层”现在被目标节点吸收了。

#### 5. 这套模型想解决的问题

- 不再维护两套彼此松耦合的系统：任务系统一套，目标系统一套。
- 让目标系统成为任务系统的高层语义视图，而不是平行功能。
- 让“共同目标”“边拆解”“匿名占位边”“目标自动完成”这些旧概念收口到同一张图里。

### 术语对照提醒

当前仓库旧资料里，并没有直接把这个概念正式命名为“共同目标”。

最接近的旧表达有三类：

- v0.1 概念稿里的“复合目标”。
- v0.3 逻辑稿里的“多入边目标 + completionRule”。
- `#721` / `splitEdge` 语义里的“拆边时复用已有中间目标”。

所以后续如果要继续推进，比较稳妥的做法不是假定“共同目标”已经是旧术语，而是明确写成：

- 这是对旧语义的重新命名与收口，不是简单复述原词。

## 这个想法和现有设计的继承关系

### 1. 与 v0.1 / v0.2 的关系：大体继承，不是推翻

[SPEC-goal-system-design.md](../specs/SPEC-goal-system-design.md) 和 [SPEC-goal-system-design-v0.2.md](../specs/SPEC-goal-system-design-v0.2.md) 最核心的世界观本来就是：

- `Me` 是中心。
- 目标是节点。
- 任务是边。
- `source -> target` 表示“通过该任务贡献于达成 target”。

所以从图论外形上看，你的新想法不是偏航，反而更接近这个系列最早的主张。它强化的不是“新拓扑”，而是“旧拓扑的任务语义”。

### 2. 与 v0.3 的关系：外形兼容，语义重心变化

[SPEC-goal-system-v0.3-logic.md](../specs/SPEC-goal-system-v0.3-logic.md) 已经把 `GoalGraph` 收口成：

- `GoalGraph = { me, goals, edges }`
- `TaskEdge.source`
- `TaskEdge.target`
- `taskNodeRef`

并明确：

- 边状态派生自任务状态
- 目标完成由入边规则推导
- `Me` 是独立实体

这说明 v0.3 的图壳本身已经足够接近你现在的想法。真正的差别在于：

- v0.3 把 `TaskEdge` 定义成“任务槽位”，不等于任务本身。
- 你现在想把“任务就是边”重新推回主语义，而不是“边只是一条指向真实任务的引用槽位”。

所以兼容性的关键判断是：

- 图结构兼容。
- 实体命名大体兼容。
- 任务与边的同一性，需要重新定义。

### 3. 与 `Me -> 目标` 匿名边设计的关系：直接继承

[#718](https://github.com/exomind-team/exomind/issues/718) 和 v0.2 / v0.3 的 C5 都明确要求：

- 新目标应自动有一条 `Me -> 目标` 的边。
- 不允许孤立目标。

你的新想法直接继承了这一点，而且把它从“为目标系统补一条匿名占位边”升级为：

- 根任务本来就应当被视为 `Me -> Goal`。

也就是说，`Me -> 目标` 不再只是 UI 引导技巧，而变成整个语义体系的根形式。

### 4. 与“边拆解为中间目标”的关系：高度一致

[#721](https://github.com/exomind-team/exomind/issues/721) 讨论的是：

- 原来一条 `A -> B` 的边，可以拆成 `A -> C -> B`。
- 新增 `C` 作为中间目标。
- 另一段补匿名占位边。

这和你现在的想法几乎是同一方向。它说明现有体系已经默认接受：

- 任务不是只能直达终点。
- 中间目标可以从一条边中析出。
- 图上“边与目标节点可以互相转化层级”。

你的新想法只是把这种局部操作提升成整体解释框架。

### 5. 与“目标完成纯由入边推导”的关系：一致，但可再收紧

[#719](https://github.com/exomind-team/exomind/issues/719) 和 v0.3 都强调：

- 目标不能手动完成。
- 目标完成由入边状态和完成规则推导。

你现在的提法更进一步：

- 目标节点本质上就是任务网络在某个阶段上的“自动完成承载体”。

这和 v0.3 并不冲突，反而给了 v0.3 一个更清晰的解释：为什么目标应该由入边推导，而不是自己存储状态。因为目标就是“任务通向何处”的节点表达。

### 6. 与任务事件桥接的关系：从“可选增强”变成“必备主链路”

[#737](https://github.com/exomind-team/exomind/issues/737) / [#766](https://github.com/exomind-team/exomind/issues/766) 当前把 Task -> Goal 事件联动视作一个后续 bridge：

- 任务状态变了
- 找到关联边
- 重算目标

如果接受你这套新想法，这条链路的地位会变化：

- 它不再是“目标系统与任务系统的集成增强”
- 而是“同一系统内部的主状态传播”

换句话说，`task.statusChanged -> goal recompute` 不该再被视为外挂桥接，而应当成为目标语义的基础设施。

## 这个想法和现有设计的冲突点

### 1. 最大冲突：#234 的“与 Task 系统解耦”

[#234](https://github.com/exomind-team/exomind/issues/234) 的标题和正文，明确把目标系统定义为：

- 独立系列
- 与 Task 系统解耦
- 目标是上游规划来源，不与任务执行视图混用

而你现在的想法明确在做相反方向的事：

- 不解耦，反而更强耦合。
- 不把目标系统当成任务系统之外的规划层，而把它当成任务系统的一种结构视图。

所以这里必须明确一句：

- 这个新想法和 #234 的原始 framing 有直接张力。

但这种张力不一定意味着完全推翻。更准确的说法是：

- #234 想解决的是“不要把目标页做成任务页的复制品”。
- 你现在想解决的是“不要让目标系统变成任务系统旁边的第二套事实源”。

二者反对的是不同问题。

因此更合理的升级路径不是简单否定 #234，而是把它改写为：

- 目标系统在交互视图上可以独立。
- 但在事实层和语义层上，应尽量回到任务系统同一张图。

### 2. `TaskEdge = 槽位` 与 `Task = 边本体` 的冲突

v0.3 当前的一个关键抽象是：

- `TaskEdge` 不是任务本体，而是任务槽位。
- 空槽位边不占用任务系统资源。
- 真正任务通过 `taskNodeRef` 外接。

你的新想法更像是：

- 每条边唯一对应一个任务。
- 目标节点依托任务存在。
- 边不是“占位引用”，而是任务在目标图里的直接存在方式。

这意味着 v0.3 的 `taskNodeRef` 抽象需要被重估：

- 如果保留 `taskNodeRef`，它更像“边与任务域实体之间的外键”。
- 如果不保留，就需要让任务域事实本身迁入这张图。

这不是 UI 层改名，而是数据模型级决策。

### 3. 单起点边模型与“多上游任务”问题

你在想法里自己也指出了一个真正的结构问题：

- 当一个任务依赖多个上游任务时，它看起来更像“多个起点，一个终点”的超边。

而现有 `TaskEdge` 模型是单 `source`、单 `target`。

这里有两条路：

#### 路线 A：引入超边

- 每个任务可以引用多个 source goal。
- 图从普通有向图升级成超图。

优点：

- 表达直接。

代价：

- 布局、交互、规则推导、RT 接口、现有 spec 全部变复杂。

#### 路线 B：共同目标节点归一化

- 先把多个上游任务汇聚成一个共同目标节点。
- 再从这个共同目标节点发出后续任务边。

优点：

- 保持现有单 `source` / 单 `target` 有向边模型。
- 与 #721 的“边拆解为中间目标”完全一致。
- 与现有 ReactFlow / 力导向 / completionRule 更兼容。

代价：

- 图上会多出一些“结构性目标节点”。

当前更推荐路线 B。不是因为它最优雅，而是因为它能最大程度继承已有 issue 和代码方向。

### 4. “目标节点依托任务存在”与“显式创建目标”的张力

你提出：

- 正常情况下不会存在没有任务作为连边依托的目标节点。

这和现有系统也基本一致，因为 C5 要求自动补边，避免孤立目标。

但现有 UI 又允许用户显式“添加目标”，然后系统自动补一条 `Me -> 目标` 空槽位边。

所以二者并不真冲突，只是表达顺序不同：

- 旧表达：先创建目标，再补边。
- 新表达：目标一旦被创建，必须立刻被解释为边网络中的一个落点。

这可以通过文案和 API 重写统一起来，而不一定要改用户操作本身。

## 一个更清晰的兼容性判断

### 可直接继承的部分

- `Me` 是独立根节点。
- 目标是节点，任务是边。
- `Me -> Goal` 是根形式。
- 目标完成由入边推导。
- 匿名边 / 空槽位边表达“尚未落成具体任务”。
- 边拆解成中间目标。
- 共同目标收敛多个手段。

### 需要重释的部分

- `TaskEdge` 到底是“任务本体”还是“任务槽位”。
- `taskNodeRef` 是必要桥接字段，还是过渡期遗产。
- completionRule 是目标域独立规则，还是任务网络天然结构的投影。

### 需要升版才能处理的部分

- 多上游任务是否真的需要超边。
- 目标节点是否允许纯规划态存在，还是必须总由任务边托底。
- RT 中 goal 与 task 的事实源如何统一。

## 建议的解释框架

如果要尽量兼容旧资产，又把你的新想法推进下去，最合理的 framing 不是“重做目标系统”，而是：

- 把它定义成 `goal-system v0.4` 的语义重心调整。
- 保留现有 `GoalGraph = { me, goals, edges }` 外壳。
- 改写 `TaskEdge` 的官方解释，从“任务槽位”转成“任务在目标图中的主表达；空槽位只是尚未绑定任务事实的退化态”。

可以把这件事拆成三层：

### 第 1 层：语义层收口

- 把目标页重新定义为任务系统的目标视图。
- 把 `Task -> Goal` 联动从“bridge”改成“主链路”。
- 把 `Me -> Goal`、边拆解、共同目标这些旧设计放回统一叙事。

这一层主要改 spec、issue framing、命名。

### 第 2 层：数据层收口

- 决定 `TaskEdge` 与真实任务对象的关系。
- 决定 `taskNodeRef` 是长期接口还是迁移桥。
- 决定 completionRule 是否继续保留为显式字段，还是更多由目标汇聚结构隐式表达。

这一层会影响 [#744](https://github.com/exomind-team/exomind/issues/744) 的 RT 化方式。

### 第 3 层：结构扩展

- 若单 source 不够，再讨论多 source / 超边。
- 在这之前，优先用“共同目标节点归一化”解决多数多上游场景。

这一层不应抢在前两层前面做。

## 建议的后续 issue / spec 方向

### 1. 先补一份新的设计文档，而不是直接改代码

优先新增一份 v0.4 设计分析或 spec 草案，聚焦回答下面四个问题：

- 目标系统是否还应被定义为“与 Task 系统解耦”。
- `TaskEdge` 是否仍是槽位抽象。
- 多上游任务是走超边，还是走共同目标节点归一化。
- completionRule 在新框架下是保留、弱化，还是重定义。

### 2. 把 #234 的 epic framing 重新写清

建议不是关掉 #234，而是修正文案，把它从：

- “目标系统独立系列（与 Task 系统解耦）”

改成更接近下面这种意思：

- “目标系统独立视图系列（交互独立，但事实层尽量与 Task 系统同图）”

否则后续所有子 issue 会默认沿着“再造一套目标事实源”继续走。

### 3. 让 #737 / #766 升级为架构主链路议题

如果接受新想法，`task.statusChanged -> goal recompute` 不应再被视为“有空再接的桥”，而应成为：

- RT 任务域
- goal graph
- UI 展示状态

三者之间的主状态传播链。

### 4. #744 要以“统一事实源”而不只是“把 localStorage 搬进 RT”为目标

[#744](https://github.com/exomind-team/exomind/issues/744) 现在的 framing 已经比前面更接近正确方向，因为它在问：

- 目标系统的核心数据模型与规则是否应进入 RT。

但如果新想法成立，#744 还需要再加一句：

- RT 化不是把目标图单独存起来，而是要决定 task 与 goal 到底谁是主事实，谁是派生视图。

## 当前判断

一句话结论：

- 这套新想法在图结构上与 v0.1 / v0.2 / v0.3 高度连续。
- 它真正冲击的不是“目标是节点、任务是边”这件事，而是 #234 那种“目标系统作为独立于任务系统的另一套事实源”的 framing。
- 它最值得保留的价值，不是超边设想本身，而是把“共同目标”“自动完成”“边拆解”“Me 根边”“任务事件重算”收回到一张任务-目标统一图里。

如果只保留一个建议，那就是：

- 先不要急着引入超边。
- 先把“共同目标节点归一化 + 任务即边的主语义 + Task/Goal 同图事实层”写成 v0.4 的正式问题陈述。
