## 1. 计划摘要

本轮先收口基础设施主线，不把九大主题一次性混做一轮。逻辑前提固定为：

- 外心是去中心化系统，不强制中心化的用户服务器或注册服务器
- 网络传输首先发生在 `RT` 之间，档案是 `RT` 内的逻辑租户
- 个人档案与集体档案在身份层同型，都以不可变 `archive_id` 为主键
- 当前的“激活档案”模型升级为“多档案会话管理”

实例锚点：

- 一个 `RT` 可同时运行多个个人档案和集体档案
- 用户前台切到另一个档案时，只切换 UI 接入和前台独占资源，不默认杀掉旧档案
- 集体档案有自己的运行会话，但前台接入的是“某成员对该集体的座席”
- 邀请通过公开标识定向到某个具体个人档案，经提案批准后带外送达，对方在自己的个人档案里接受

## 2. 核心对象模型

### 2.1 Archive

统一表示个人档案与集体档案。

- 主键为不可变 `archive_id`
- 密码、token、邀请码只是接入材料，不是档案身份本身
- 个人档案与集体档案在身份层同型，只在治理与成员关系上分化

### 2.2 ArchiveSession

表示某个 `RT` 上某个档案的本地运行时对象。

- 作用域完全本地于 `RT`
- 不跨 `RT` 同步
- 状态至少为：
  - `running`
  - `suspended`
  - `stopped`

### 2.3 ForegroundAttachment

表示当前 UI 与前台独占资源接入到哪个 `ArchiveSession`。

- 普通“切换档案”默认只切前台接入
- 不默认停掉切出的档案
- 前台切换事务必须保证单例资源原子无双占

### 2.4 MemberSeat

表示成员进入集体档案时的前台接入座席。

- 集体档案有自己的 `ArchiveSession`
- 但前台进入它时，接入的是 `MemberSeat`
- 所有集体行为都记录为“某成员在某集体中的动作”

### 2.5 PublicArchiveIdentifier

表示个人档案的对外公开标识。

- 映射到内部 `archive_id`
- `v1` 仅个人档案可拥有
- 需显式开启后才生成
- `v1` 先只支持一个主公开标识
- 第一阶段可采用“内部 ID 压缩封装”的简单方案，不明文暴露 `archive_id`

### 2.6 InviteCredential

表示集体批准后生成的加入材料。

- 绑定到目标个人档案
- 默认通过带外方式传递
- 由被邀请者在自己的个人档案中接受

### 2.7 PublicCard

表示给人类看的最小公开名片。

- 独立于公开标识与邀请码建模
- 由公开标识解析得到
- `v1` 最小承载：
  - `display_name`
  - `slug`
  - 可选 `avatar_hint`
- 只承担最小自述与人工确认职责，不承担防伪承诺

### 2.8 KnownArchiveEntry

表示已建立关系后的档案级长期关系记忆。

- 只在真实关系建立后沉淀
- 正式关系的稳定主键为 `archive_id`
- 同时保存最近看到的名片快照与本地备注 / 别名
- 在同一档案的各 `RT` 间同步

## 3. 多档案会话与前台切换

### 3.1 多档案并活

- 同一 `RT` 上允许多个 `ArchiveSession` 并活
- 同一档案可在不同 `RT` 上各自前台，各 `RT` 自治
- `ArchiveSession` 持久化落在各 `RT` 本地会话存储，不挂进档案共享数据

### 3.2 前台独占资源

以下资源默认前台独占：

- 主窗口焦点
- 全局快捷键
- 麦克风入口
- 托盘主入口

后台档案默认可继续运行，但默认静默，不主动抢前台。

### 3.3 挂起与停止

`suspended` 的本质是：

- 失去前台接入权
- 失去前台独占资源占用权
- 核心服务仍可继续运行

“切出时是否自动挂起”作为切出档案自己的设置。

### 3.4 “硬切换”的新含义

此前讨论中的“硬切换”不再理解为“停旧启新”的唯一主路径，而重定义为：

- 前台接入
- 前台独占资源

在档案之间的原子切换事务。

如果用户明确想把切出的档案停掉或挂起，则作为显式附加动作处理，而不是普通切换默认语义。

## 4. Settings 分层合同

### 4.1 个人档案级 settings

- 默认采用广义档案态
- 个人 UI/交互偏好先默认跟档案走
- 后续再微调哪些设置回落到平台/设备层

### 4.2 集体本体级 settings

持有集体公共规则：

- 提案门禁
- 成员策略
- route 编辑门禁
- 其他治理级开关

这些设置跨 `RT` 同步。

### 4.3 成员 × 集体视角级 settings

表示某成员进入某集体时的工作面偏好。

- 默认继承该成员个人档案偏好
- 可做少量局部覆写
- 覆写在该成员各 `RT` 间同步
- 采用“继承 + 覆写”，不维护两套完全独立工作面

### 4.4 route table

- route table 归属于档案级持久配置
- 不归属于会话级临时状态

## 5. 集体档案与治理

### 5.1 基本原则

- 集体档案与个人档案在身份层同型，都有自己的 `archive_id`
- 集体档案有自己的 `ArchiveSession`
- 前台进入集体档案时，接入的是 `MemberSeat`
- `v1` 不引入固定的“管理员 / 创建者”角色

### 5.2 元治理

- 元治理变更按变更前旧规则裁决
- 治理设置本身也走提案
- 不做通用规则引擎，先用少量策略开关和预设表达

### 5.3 邀请与成员生命周期

任何现有成员都可发起邀请新成员的提案。

成员生命周期最少显式区分：

- `inviting`
- `approved_pending_accept`
- `active_member`
- `exited`

加入流程固定为：

1. 现有成员发起邀请提案
2. 集体按当前治理规则批准
3. 生成绑定目标个人档案的 `InviteCredential`
4. 邀请材料带外传递给对方
5. 被邀请者在自己的个人档案中接受
6. 状态流转为 `active_member`

退出与移出：

- 都保留为显式成员生命周期动作
- 默认都按治理动作处理并留下审计
- “退出”可视作成员对自己发起的移出动作

### 5.4 审计浏览表面

第一阶段默认采用：

- **对象局部历史**

也就是说：

- 优先让事件、任务、提案、成员关系等对象各自可回看历史
- 不先做厚重的全局审计总控台

## 6. 提案门禁粒度与默认可见性

集体档案默认策略收口为：

- 结构与治理经提案
- 执行与协调少量直写

### 6.1 EventLog

- 集体 `eventlog` 默认允许成员直接写入
- 但必须强审计

### 6.2 时间块

- 计划 / 安排走提案
- 执行态开始 / 暂停 / 结束记录直写并审计

### 6.3 任务

- 新建 / 删除 / 重排 / 责任边界变更走提案
- 执行反馈 / 进度回报直写并审计

### 6.4 提案可见性

- 提案默认对所有 `active_member` 可见
- 成员可见性不自动等于 Agent 可见性

### 6.5 `blackboard`

- 默认可直接写入
- 但必须强审计

### 6.6 route / edge 编辑

- 在集体档案中默认走提案

### 6.7 例外类别

- 允许少量枚举例外类别
- 由集体 settings 配置开关
- 不做自由规则矩阵

## 7. Blackboard、Network v1 与集体 Agent

### 7.1 Blackboard

`blackboard` 的最小合同：

- 每档案一个持久 `blackboard`
- 不按每次会话重建
- `v1` 仅承载：
  - 共享工作记忆
  - 协调便笺
  - 交接摘要
- 不作为：
  - 任务、时间块等业务真相数据库
  - 公共长期记忆总池

在集体档案中：

- 默认对所有 `active_member` 可读
- 默认长期保留
- 清理 / 归档先采用手动方式
- 应作为靠近 node / workbench 的特殊访问方式出现
- 不先做厚重独立页面
- 直写时必须记录成员身份、来源与审计信息

### 7.2 Network v1

- 采用“固定节点 + 可配路由”
- route table 是档案级持久配置
- `edge` 对用户表达“输出后默认发给谁”
- `v1` 没有连边就不能发消息
- 无边发信必须硬失败并提示先建边
- topic 先采用预注册集合
- 通配 `*` 只用于前端观察 / 诊断
- 禁用 route 投递记为 `skipped`
- 目标缺失或不可用投递记为 `failed`
- 人类可直接改边；Agent 改边默认通过提案或明确授权流程

### 7.3 集体 Agent 默认权限

集体 Agent 第一阶段默认采用：

- **最小权限读面**

进一步收口为：

- 每个 Agent 的可读范围单独配置
- tools 层显式区分读权限与写权限
- 写权限按角色输出受限，不默认等同成员的广泛写权限
- 审计需要同时记录：
  - Agent 身份
  - delegating / source member

当前仍未定的内容：

- 集体 Agent 具体跑在哪个 RT
- 调度 / 派工 / 驻留机制如何实现

这些不进入 `v1` 关闭条件。

## 8. 去中心化找人与档案 bootstrap

本节的“找被邀请者”子题已细化到：

- [2026-04-06-invitee-discovery-public-identifier-and-known-archives-plan.md](./2026-04-06-invitee-discovery-public-identifier-and-known-archives-plan.md)

### 8.1 固定前提

- 不依赖中心化用户服务器或注册服务器
- `v1` 不做全网搜人
- 系统只负责解析用户已经拿到的公开标识

### 8.2 找人与邀请

- 邀请目标粒度是“某个具体个人档案”
- `v1` 只给个人档案开放公开标识
- 公开标识默认长期稳定，仅在用户手动停用或重置时变化
- 公开标识、`PublicCard`、`InviteCredential` 明确分离
- 集体档案 `v1` 不做公开发现对象
- 首次找人只支持带外导入公开标识，如复制、扫码、文件、聊天等
- 导入后先解析最小名片，供人类人工确认目标
- 邀请发起与批准阶段不要求目标当前在线
- 被邀请者只能用被绑定的那个个人档案接受邀请

### 8.3 已知档案与关系沉淀

- 正式关系只在接受成功后沉淀
- 个人关系沉淀为 `KnownArchiveEntry`
- 集体新增成员首先落在成员表，不自动写入发起成员的私人关系簿
- `KnownArchiveEntry` 的稳定主键为 `archive_id`
- 旧公开标识失效时，关系对象保留但标记待更新
- 关系新鲜度默认通过“再次接触 + 手动校验”更新，不做后台主动探测

### 8.4 档案 bootstrap

- 新 `RT` 接入已存在档案，默认走显式配对 / 导入
- 现有“同名同密码自动相认”逻辑直接废弃，不做过渡兼容
- 公开标识是外部标识层，不直接明文暴露内部 `archive_id`

## 9. 实施顺序

> 注：本节描述的是 **archive-first 主线内部** 的拆题顺序，不等于全局产品路线顺序。全局先后次序以 [2026-04-06-roadmap-sequencing-personal-sync-baseline-plan.md](./2026-04-06-roadmap-sequencing-personal-sync-baseline-plan.md) 为准。

建议按以下顺序继续拆题：

1. `ArchiveSession` 本地状态机与持久化
2. 前台接入事务与前台独占资源切换器
3. settings 三层分域与继承 / 覆写规则
4. 集体成员生命周期与邀请材料合同
5. 集体治理开关与提案门禁预设
6. `blackboard` 最小合同与访问表面
7. `network v1` route / edge / output 合同
8. 集体 Agent 读写权限合同与审计字段
9. 个人公开标识与 archive bootstrap 合同
10. 档案会话管理器 UI 规格

## 10. 测试与验收基线

至少覆盖以下场景：

- 单 `RT` 同时运行多个 `ArchiveSession`，切前台不杀后台
- 同一档案在两个 `RT` 上同时前台，各自独立
- 前台切换时，主窗口 / 快捷键 / 麦克风不出现双占
- 切出档案配置为自动挂起时，只失去前台接入权，不丢运行态
- 个人档案 UI 偏好随档案恢复
- 集体视角默认继承个人偏好，局部覆写后仅在该成员自己的 `RT` 间同步
- 集体治理设置跨 `RT` 保持一致
- 邀请全链路走通：提案批准、生成加入材料、带外传递、个人档案接受、成员状态流转
- 导入公开标识后，只显示最小名片，不提前创建正式 `KnownArchiveEntry`
- 旧公开标识失效时，旧邀请接受失败；既有关系保留并标记待更新
- 接受成功后，关系以 `archive_id` 稳定化，后续可直接选已知档案再次邀请
- 集体 `eventlog` 可直接写并留下强审计
- 任务结构变更走提案，执行反馈直写并审计
- 时间块计划走提案，执行记录直写并审计
- 提案默认对所有 `active_member` 可见
- `blackboard` 默认对 `active_member` 可读，并保留成员身份、来源、审计
- `blackboard` 清理 / 归档采用手动动作
- route table 按档案恢复；集体改边默认走提案
- 无连边节点发信失败，并能提示先建边
- 禁用 route 记录 `skipped`；目标缺失 / 不可用记录 `failed`
- 集体 Agent 的读面 / 写面可分别配置，且审计能同时看到 Agent 与来源成员
- 未开启公开标识的个人档案不可被定向邀请
- 新 `RT` 不能再靠“同名同密码”自动归并已有档案
