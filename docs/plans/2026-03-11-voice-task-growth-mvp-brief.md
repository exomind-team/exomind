# ExoMind 周五可发布版本需求摘要

> 状态：需求收束稿  
> 日期：2026-03-11  
> 目标：在本周五前收敛出一个能真实帮助用户、可分享、可演示的最小闭环版本

---

## 1. 问题定义

ExoMind 这周不应该发布成“更复杂的看板”或“更多的 Agent”。

它要解决的核心问题是：

1. 用户脑子里会不断冒出很多想法、任务、担忧、计划，但来不及整理。
2. 用户不知道自己现在到底有多少时间、多少精力，以及此刻最适合做什么。
3. 用户不想再手动维护一堆静态任务卡片，因为那会增加额外的心智负担。
4. 用户进入专注前不清楚目标，结束后也不知道如何验收成果。
5. 用户和 Agent 协作时，不知道哪些该自己做，哪些可以让 Agent 在后台辅助推进。

一句话说：

> ExoMind 要做的，是把用户脑中的混乱和远大的目标都接住，整理成此刻能落实的下一步，并帮助用户把当下这件事做到位。

---

## 2. 用户痛点与共鸣场景

这不是一个“任务记录工具”的问题，而是一个“生活与执行被压垮”的问题。

典型场景包括：

### 2.1 深夜焦虑

用户晚上脑子停不下来，想到很多事：

- 明天要推进什么
- 哪些事情很重要
- 哪些只是担心，不是立刻要做
- 哪些可以先交给 Agent 去整理

如果这些东西不被接住，就会继续焦虑。

### 2.2 早上坐下来，不知道先做什么

用户明明有两个小时能坐下来，但真正难的是：

- 先做哪一件
- 为什么是这件
- 现在的状态适不适合做难任务

很多人不是没有任务，而是不知道如何从大量任务里切出“现在能做的一个动作”。

### 2.3 不想维护任务系统

传统 Todo List 最大的问题不是不能记，而是：

- 需要手动整理
- 需要手动分类
- 需要手动调整时间
- 不更新就会变成一潭死水

用户并不想把精力用在“维护任务系统”上，而是想把精力用在“完成事情”上。

### 2.4 做完没有沉淀

一天过去了，用户可能做了很多事，但：

- 没有被总结
- 没有被复盘
- 没有转成明天能继续推进的结构

于是第二天还是从混乱开始。

---

## 3. 产品定位

本周五可分享版本的定位建议：

> ExoMind 是一个语音驱动、以人为中心、由 Agent 在后台持续接住输入、整理任务、辅助执行、帮助复盘的生命成长工作流系统。

它不是：

- 通用任务管理软件
- 通用 AI 看板
- 纯自动化 Agent 平台

它是：

- 一个接住用户输入的系统
- 一个帮助用户聚焦当下的系统
- 一个把远大目标逐步落实到今天、再落实到现在的系统
- 一个帮助用户与 Agent 共同完成事情的系统

---

## 4. 周五版本的唯一主场景

### 主场景

> 我只管说话，ExoMind 帮我记住、整理、更新任务、给出现在能做的事项建议，并在我做完后帮我复盘。

### 场景故事

用户不想打开一堆软件去手动整理自己。

他只需要对 ExoMind 说：

> “这周我要把 Phase 3 做出来，周五还要分享，上午我可能有两个小时能坐下来。核心设计我自己做，资料整理和背景梳理可以让 Agent 帮我。今天先把最重要的一步做出来。”  

然后系统完成：

1. 接住这段输入并落到事件日志。
2. 在后台把内容整理成结构化信息。
3. 识别哪些是任务、哪些是状态、哪些是复盘线索、哪些是对已有任务的补充。
4. 把这些输入不断补充到任务对象里，而不是只生成一张新的静态卡片。
5. 给出“现在能做的事项建议”，而不是泛泛地列一个“今天能做清单”。
6. 让用户选择一个或多个任务进入专注时间块。
7. 在时间块结束时帮助用户验收、总结，并生成下一步。

## 5. 用户价值

这个版本对用户的价值，不是“AI 很聪明”，而是以下几点：

### 5.1 想法被接住

用户只管说。

系统先记下来，再整理，而不是要求用户一开始就自己整理。

这会直接降低：

- “我怕忘”
- “我不知道从哪里开始整理”
- “我脑子里东西太多”

### 5.2 不需要自己维护任务系统

ExoMind 不该把任务管理变成新的负担。

用户不需要自己去做这些额外工作：

- 手动分类
- 手动写长描述
- 手动维护每一条任务状态
- 手动记住这件事什么时候又被提到

这些应该尽量由 Agent 在后台辅助完成。

### 5.3 任务是活的，不是死的

任务不是一张创建后就不再变化的卡片。

任务应该是一个持续更新的对象：

- 会不断吸收新的语音输入
- 会记录什么时候又被提到
- 会更新当前描述
- 会更新当前执行现状
- 会随着时间和上下文变化而调整建议

这让系统不是一潭死水，而是一团源头活水。

### 5.4 聚焦“现在能做什么”

系统最重要的帮助，不是告诉用户“今天总共有多少任务”，而是告诉用户：

> 现在能做什么。

因为真正决定行动的，是用户当下的：

- 时间
- 精力
- 身体状态
- 情绪状态
- 当前上下文

### 5.5 帮助把远大目标落实下来

用户不只是要完成几个小任务。

用户可能想：

- 做出一个产品
- 改变自己
- 改造世界

ExoMind 的价值不在于替用户梦想，而在于：

> 它能把这些宏大的目标兜住，再一步步拆成当下可执行的动作。

### 5.6 做完之后有沉淀

完成事情之后，系统还能帮助用户留下：

- 做了什么
- 没做什么
- 为什么没做完
- 下一步是什么
- 今天的情绪、状态、感受如何

这会降低第二天重新开始时的焦虑。

## 6. 需求总结

### 6.1 输入原则

用户的默认交互方式是“说话”。

要求：

1. 用户只管说，不强迫用户先结构化思考。
2. 所有输入先进入事件日志。
3. 结构化整理、分类、任务化都在后台完成。
4. 用户输入给 Agent、输入给事件日志、输入给任务系统，本质上应该先汇入一条统一的内部流。

### 6.2 任务对象原则

任务不应该是静态卡片，而应该是动态更新对象。

要求：

1. 新输入可以补充已有任务，而不是机械地不断新增任务。
2. 任务要能链接到“用户什么时候又提到过它”。
3. 任务描述和现状应随着输入与执行不断更新。
4. 如果任务在预期时间内没有完成，系统应能顺延、提醒用户反思，或自动调整安排。

### 6.3 建议原则

系统要给建议，但不能替用户决定一切。

要求：

1. 建议重点是“现在能做的事项”，不是泛泛的“今天能做清单”。
2. 建议要考虑时间、精力、身体状态、情绪状态和当前上下文。
3. 用户始终拥有最高调整权。

### 6.4 时间块原则

时间块是从“整理”进入“执行”的桥。

要求：

1. 用户可以从建议中选择一个或多个任务进入专注时间块。
2. 时间块结束后，系统自动触发验收和复盘。
3. 验收结果能重新影响任务状态和下一步建议。
4. 时间块相关体验需要尽量顺滑，包含必要的倒计时与悬浮提示能力。

### 6.5 人与 Agent 协作原则

Agent 是后台协作者，不是替代人类的主人。

要求：

1. Agent 可以长期在后台处理任务。
2. Agent 做完的结果，应该先回流成用户可理解、可验收的内容。
3. 真正进入用户主任务列表的，应该是“用户要确认的结果”或“用户下一步要做的事”。
4. 用户可以否决、修改、覆盖 Agent 的判断。
5. Agent 应保持一定独立性，能明确指出自己的判断，但也能在实践证明用户更对时修正自己的理解。

## 7. 本周五 MVP 边界

### 必须做到

1. 语音输入后，内容能稳定落到事件日志。
2. 后台能把输入整理成结构化内容。
3. 至少能识别出任务类输入，并生成或更新任务。
4. 系统能给出“现在能做的事项建议”。
5. 用户能选择任务进入专注时间块。
6. 时间块结束后有可见的复盘/验收结果。

### 配套体验应尽量补齐

1. 语音相关悬浮窗体验继续优化。
2. 时间块倒计时 / 时间块悬浮窗体验尽量打磨顺滑。

### 可以弱化

1. 不需要一开始就有复杂的多 Agent 自治。
2. 不需要先做通用看板。
3. 不需要复杂优先级算法。
4. 不需要一次性做完整人生管理系统。

### 不应该做

1. 不要让用户面对太多配置。
2. 不要让 Agent 逻辑压过人的理解。
3. 不要先追求“系统很复杂”，而忽略“用户今天能不能用”。

---

## 8. 现阶段最关键的后端闭环

根据当前代码库现状，周五版本最值得收敛的不是 UI，而是这条闭环：

`语音输入 -> 事件日志 -> 分类 -> 任务生成/更新 -> 现在能做的事项建议 -> 时间块 -> 复盘`

当前最关键的缺口是：

1. 统一输入归一化入口
2. 稳定的分类结果协议
3. 任务与时间块之间的统一状态流

---

## 9. 最终结论

本周五可发布版本，不该强调“我们有很多 Agent”，而应该强调：

> ExoMind 能通过语音，把用户脑子里不断涌现的内容接住，自动整理成结构化的任务与记录，帮助用户在当下聚焦、执行、验收，并持续推动自己的成长与目标落地。

这是当前最强、最真实、也最容易被外部用户感知的价值。
