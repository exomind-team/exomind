# ExoMind 官网「任务系统与时间块平级表达」文案草稿

> 日期：2026-04-10  
> 用途：作为官网后续信息架构、文案与设计稿更新的指导稿  
> 范围：只提供文案与页面更新建议，不改网页源码

---

## 1. 结论

`任务系统` 应该正式进入官网主表达层，并且应当与 `时间块` 平级呈现。

同时，官网的对外描述顺序建议固定为：

**事件 → 时间块 → 任务**

原因不是“任务也算一个功能”，而是：

- `任务系统` 管的是“现在最该推进什么”
- `时间块` 管的是“现在如何开始执行”
- 两者共同构成 ExoMind 成长闭环里最具体、最可感知的行动层

如果官网继续只把任务系统藏在概括性句子里，用户会更容易理解：

- ExoMind 有记录
- ExoMind 有 Agent
- ExoMind 有同步

但不容易理解：

- ExoMind 如何把“真实发生过的事”收敛成“下一步行动”

而这恰恰是外心和普通笔记、普通 AI 助手、普通待办工具拉开差异的关键部分。

---

## 2. 推荐对外判断

### 2.1 任务系统在官网中的身份

官网不应把 `任务系统` 写成“附带的待办能力”，而应写成：

**把线程收敛成下一步行动的系统。**

它对外负责回答三个问题：

1. 现在最值得推进什么
2. 任务之间是什么关系
3. 做完之后如何继续推进，而不是重新开始

### 2.2 时间块在官网中的身份

`时间块` 不只是计时器，而是：

**把行动接入真实执行时段的系统。**

它对外负责回答三个问题：

1. 什么时候开始做
2. 做了多久
3. 结束后怎样留下反馈与可回看的执行证据

### 2.3 两者之间的关系

官网最应该说清楚的，不是一条单线流程，而是两套不同层面的顺序：

- `对外呈现顺序`：事件 → 时间块 → 任务
- `动作依赖关系`：任务 → 时间块 → 事件

也就是说：

- 用户第一眼先理解“留下了什么”
- 第二眼理解“怎么开始做”
- 第三眼理解“如何把这些动作编排成可继续推进的任务结构”

也可以写成更偏用户收益的话：

**先留下线索，再开始一段时间，最后把它组织成能继续推进的任务。**

## 3. 官网推荐表达总纲

### 3.1 不推荐的旧写法

- `任务系统：不只是待办清单。AI 帮你拆解目标、追踪进度、回顾完成情况。`
- `时间块：专注计时器 + 能量管理。知道自己的时间花在哪里，找到最佳工作节奏。`

问题在于：

- 太像通用生产力工具
- 没把 ExoMind 的“线程感”和“闭环感”讲出来
- 没有体现任务和时间块之间的互相咬合

### 3.2 推荐的新写法原则

- 少讲“功能名词”，多讲“行动结果”
- 少讲“待办 / 计时器”，多讲“推进 / 承接”
- 少讲抽象能力，多讲闭环关系

### 3.3 建议固定的官网句式

建议在官网里反复稳定使用下面几类句子：

#### A. 任务系统定义句

`任务系统把模糊目标收敛成此刻最值得推进的一步。`

#### B. 时间块定义句

`时间块把这一小步接进真实可执行的时段。`

#### C. 两者关系句

`事件留下线索，时间块负责开始，任务把行动编排成可继续推进的结构。`

#### D. 成长闭环句

`记录留下上下文，时间块承接执行，任务把动作组织成可继续推进的结构，复盘沉淀策略。`

## 4. 可直接使用的文案草稿

本节给的是可直接进入设计稿或后续页面实现的中文草稿。

### 4.1 首页中段总标题

可选标题 A：

`把记录变成下一步行动，而不是堆成一堆信息`

可选标题 B：

`外心不只帮你记住，还帮你继续推进`

可选标题 C：

`从留下线索，到开始执行，再把动作编排成任务`

推荐副标题：

`事件日志留下真实语境，时间块承接真实执行时段，任务系统把这些动作组织成可继续推进的结构，让一条工作线程继续往前，而不是每次重新整理。`

### 4.2 首页平级能力卡文案

建议把 `时间块` 和 `任务系统` 明确拆成两张平级卡，而不是继续合并在一句里带过。

在首页成长期的描述顺序里，建议固定为：

`事件日志 → 时间块 → 任务系统`

#### 时间块

标题：

`时间块`

一句话描述：

`把当前这一小步接进一段真实可执行的时间里。`

展开描述：

`不是孤立计时器，而是把开始执行、投入时长和结束反馈接入同一条工作线程。`

要点文案：

- `先开始，再记录时长`
- `执行时段与当前动作直接相连`
- `结束后留下反馈与证据`

#### 任务系统

标题：

`任务系统`

一句话描述：

`把已经开始的动作编排成可继续推进的任务结构。`

展开描述：

`不是平面待办清单，而是能表达当前根节点、依赖关系、推进状态与下一步行动的任务结构。`

要点文案：

- `从动作收束成可推进的任务`
- `任务关系可展开，不再只有一列清单`
- `推进后还能接上复盘与后续动作`

### 4.3 首页关系说明条

适合放在事件、时间块、任务系统这一组卡片下方的一句短说明：

`事件先留下线索，时间块负责开始，任务再把这些动作组织成可继续推进的结构。`

### 4.4 功能页任务系统卡文案

标题：

`任务系统`

描述候选 1：

`把目标、依赖关系与推进状态放进同一张任务图里，让你始终知道下一步该做什么。`

描述候选 2：

`不是只会越堆越多的待办清单，而是能持续收敛、推进和接续的任务结构。`

描述候选 3：

`从当前根节点到依赖关系，再到状态推进，任务系统让工作线程有明确的下一步。`

### 4.5 功能页时间块卡文案

标题：

`时间块`

描述候选 1：

`把任务接入真实时段，开始执行、记录投入，并在结束时留下反馈。`

描述候选 2：

`不是单独存在的专注计时器，而是行动闭环里的执行容器。`

### 4.6 Getting Started 引导文案

这里不建议继续用一棵严格的树来描述卡片关系，而应拆成两层：

- `页面呈现顺序`
- `动作依赖关系`

推荐把 `Getting Started` 的根目录固定为 `page-top`，并在根目录放 3 张平级入口卡，顺序按“从微观到宏观”排列：

1. `先记下一件事`
2. `先开一个时间块`
3. `先建一个任务`

其中，`任务系统` 依然必须是根目录卡片，而不是其他卡的子卡。

原因是：

- 用户可以直接创建任务
- 创建任务没有前置依赖
- 不需要先写记录
- 也不需要先开时间块

### 4.7 Getting Started 推荐顺序与依赖图

页面呈现顺序建议固定为：

```text
page-top = 先记下一件事 | 先开一个时间块 | 先建一个任务
```

动作依赖关系则建议写成下面这张图，而不是强行收成树：

```text
编排任务 -> 开时间块 -> 记录事件
开时间块 -> 回看总结
事件日志 -> 接入设备
```

如果要写成卡片间的推荐跳转，可直接展开为：

```text
task -> timeblock
timeblock -> capture
timeblock -> review
capture -> pairing
capture -> task
```

### 4.8 每张根卡应该怎么写

#### 根卡 1：先记下一件事

适用人群：

- 还没想清楚
- 只想先留下线索
- 暂时不想组织任务结构

推荐摘要：

`先把脑子里的这件事留下来，再决定要不要继续整理。`

完成后推荐去向：

- `直接说出来`
- `把刚才这件事收敛成任务`
- `如果需要换设备继续，就去接入设备`

#### 根卡 2：先开一个时间块

适用人群：

- 已经准备开始做事
- 不想再整理
- 只差一个开始动作

推荐摘要：

`如果你现在就想开始做，就先开一个时间块。`

推荐引导句：

`时间块不是结果页，而是当前动作真正开始发生的地方。`

完成后推荐去向：

- `做完后回看一下`
- `把这段动作收敛成任务`
- `结束后记一条事件`

#### 根卡 3：先建一个任务

适用人群：

- 已经知道要推进什么
- 想直接进入行动组织
- 不需要先记一条再整理

推荐摘要：

`已经知道要推进什么，就直接建一个任务。`

推荐引导句：

`任务系统在这里是零依赖入口。你不需要先写记录，也不需要先开时间块。`

完成后推荐去向：

- `立刻开始一个时间块`
- `继续补充任务描述 / 关系`
- `建完先回看一下`

### 4.9 可直接使用的起步页引导文案

页首总说明建议改成：

`先选你现在最接近的一步。你可以先记一条、马上开一个时间块，或者直接建任务。页面上的顺序是事件、时间块、任务；但卡片之间会按动作依赖互相跳转。`

任务根卡建议文案：

标题：

`先建一个任务`

摘要：

`已经知道要推进什么，就直接建任务。这里不依赖先记记录，也不依赖先开时间块。`

完成说明：

`当你看到任务已经创建，并能继续补充描述、关系或状态时，就算完成。`

下一步按钮建议：

- `立刻开始一个时间块`
- `继续补充任务关系`
- `建完先回看一下`

## 5. 各页面应如何更新

本节是指导性建议，不要求一次全部上线。

## 5.1 首页 `website/src/pages/index.astro`

### 当前问题

- 首页已经提到“时间块与任务”，但仍是合并表达
- 用户知道它们存在，但看不出二者分工
- 首页当前更偏“基础设施与线程哲学”，行动层不够具体

### 推荐更新方向

不要改 Hero 的总定位，Hero 仍然讲：

- 外心是什么
- 为什么不是普通 AI 工具
- 为什么它能持续接续

 但在 Hero 之后的第一层结构化展开里，应该新增或重写为：

1. `记录`
2. `时间块`
3. `任务系统`
4. `Agent 执行`

其中：

- `任务系统` 与 `时间块` 必须拆开
- 二者用一条关系说明文字重新扣在一起

### 首页设计指导

- `任务系统` 建议配任务列表 + 当前根节点或 DAG 关系截图
- `时间块` 建议配时间块输入 / 计时中 / 结束反馈中的任一真实界面
- 两张卡最好风格一致，形成“行动层双支柱”
- 不建议把它们继续埋在“成长层”的一张大卡里

### 首页优先新增模块

建议新增一个模块标题：

`把线程变成可推进的行动`

模块内部放两张主卡：

- `任务系统`
- `时间块`

底部再放一句桥接文案：

`事件先留下线索，时间块负责开始，任务把动作组织成可继续推进的结构。`

## 5.2 功能页 `website/src/pages/features.astro`

### 当前问题

- 现在是 6 张平铺功能卡
- `任务系统` 虽然有独立卡，但文案太泛
- `时间块` 与 `任务系统` 没形成明显平级关系

### 推荐更新方向

功能页应该从“平铺功能卡”升级成“分层能力结构”。

建议至少分三层：

1. `成长闭环层`
   - 事件日志
   - 时间块
   - 任务系统
   - 复盘
2. `Agent 执行层`
3. `基础设施层`

如果暂时不改结构，最低限度也应做到：

- 重写 `任务系统` 文案
- 重写 `时间块` 文案
- 在两张卡的说明里写出二者关系

### 功能页设计指导

- 任务系统卡的视觉重点是“结构”和“推进”
- 时间块卡的视觉重点是“开始”和“执行时段”
- 两张卡应靠近摆放，而不是被其他卡打散

## 5.3 新手开始页 `website/src/pages/getting-started.astro`

### 当前问题

- 当前路径更偏“先记一条”与“开一个时间块”
- 没有明确为“已经知道要推进什么的人”提供任务根入口
- 入口树没有把各卡之间的流转关系说清楚

### 推荐更新方向

在保留现有轻量入口的前提下，新增一条并列起手路线：

- `先建一个任务`

建议把新手入口改成三种起手方式，并按下面顺序呈现：

1. `先记下一件事`
2. `先开一个时间块`
3. `先建一个任务`

这里要明确：

- `先建一个任务` 是根目录卡
- 不是 `先记下一件事` 的子卡
- 也不是 `先开一个时间块` 之后的补充卡

### 推荐卡片顺序与依赖图

这里不建议再用树模型约束页面，而应拆成“根目录顺序 + 动作依赖”。

```text
page-top = capture | timeblock | task
```

动作依赖建议直接写成：

```text
task -> timeblock -> capture
timeblock -> review
capture -> pairing
```

### 新手页文案原则

- 任务入口面向“我已经知道要推进什么，但还没开始”
- 时间块入口面向“我不想整理了，我要立刻开始”
- 二者不能互相替代，但应互相跳转
- 根目录三张卡必须分别对应三种不同起手状态，而不是只做功能罗列

### 页面关系指导

建议加入这样的互链：

- 从任务入口跳到时间块：`已经编排好任务了，就开始一段时间块`
- 从时间块入口跳到记录入口：`结束后记一条事件`
- 从时间块入口跳到回看入口：`做完后回看一下`
- 从记录入口跳到设备入口：`如果要换设备继续，就去接入设备`
- 任务卡的返回文案不要写成“回去先记一条”，而应写成 `回到入口重新选`

### 设计指导

- 根目录三张卡视觉上应完全平级
- `先建一个任务` 不应缩成次级文本链接
- 任务卡建议使用更明确的“行动组织”视觉暗示，例如任务条目、状态点、关系线
- 时间块卡建议使用“开始执行”视觉暗示，例如时间块标题、时长或开始按钮

## 5.4 文档首页 `website/src/pages/docs.astro`

### 当前问题

- 文档首页描述里提了“记录、语音输入、时间块、设备配对与排障”
- 任务系统没有进入文档主题描述

### 推荐更新方向

文档首页描述应升级为：

`按主题浏览外心文档：记录、时间块、任务、语音输入、设备配对与排障。`

如果文档导航支持主题卡，也建议把 `任务系统` 独立成主题入口。

## 5.5 版本日志 / 下载页 `website/src/pages/changelog.astro`

### 当前问题

- 该页主要承担下载与版本记录
- 不适合承载完整任务系统叙事

### 推荐更新方向

这里不需要大改，只建议在版本更新摘要或发行说明摘要里，逐步把下列能力当作稳定产品面持续露出：

- 任务系统
- 时间块
- Agent 工作台

目的不是讲完整故事，而是让用户知道这不是只有下载入口的空页。

## 5.6 关于页 `website/src/pages/about.astro`

### 当前问题

- About 更偏理念、命名、哲学
- 还没有把“为什么外心需要任务系统与时间块”讲成理念的一部分

### 推荐更新方向

建议在 About 中补一小段“为什么不是只记录就够了”的解释：

`外心不只记录发生过什么，还要把这些线索接进真实会发生的时段，并进一步组织成可继续推进的任务结构。时间块与任务系统，就是这条闭环在产品中的两个关键表面。`

### About 页作用

About 不需要详细解释任务功能，但应解释：

- 为什么“记录”之后必须有“推进”
- 为什么“推进”之后必须进入“真实执行时段”

### 文档页

负责回答：

- 如果我要深挖时间块或任务系统，去哪里看
