# 代码评审规范

> 本规范定义 ExoMind 项目的代码评审流程、维度和标准

---

## 1. 评审触发条件

以下情况必须进行代码评审：

| 触发条件 | 说明 |
|----------|------|
| 功能开发完成 | 特性开发完成后 |
| PR 提交前 | 合并到主分支前 |
| 安全相关代码 | 认证、授权、加密等 |
| 架构变更 | 模块重构、接口变更 |
| 修复 Bug 后 | 验证修复是否彻底 |

---

## 2. 评审维度

### 2.1 六大核心维度

| 维度 | 权重 | 说明 |
|------|------|------|
| **功能完整性** | 25% | 需求覆盖度、功能点完整性 |
| **安全性** | 25% | 输入验证、认证授权、数据安全 |
| **代码质量** | 20% | 可读性、可维护性、DRY原则 |
| **架构设计** | 15% | 模块划分、依赖关系、设计模式 |
| **性能** | 10% | 资源使用、算法效率、扩展性 |
| **测试覆盖** | 5% | 单元测试、集成测试、E2E测试 |

### 2.2 专项评审维度

| 维度 | 适用场景 |
|------|----------|
| **UI/UX** | 前端组件、用户交互 |
| **后端接口** | API 设计、数据传输 |
| **数据库** | 存储设计、查询优化 |
| **移动端** | 响应式、性能优化 |
| **安全** | 认证、加密、漏洞 |

---

## 3. 评分标准

### 3.1 总体评分

| 分数 | 等级 | 说明 |
|------|------|------|
| 90-100 | A | 优秀，可直接合并 |
| 75-89 | B | 良好，小修改后合并 |
| 60-74 | C | 中等，需较多修改 |
| <60 | D | 差，需重大重构 |

### 3.2 问题严重程度

| 标记 | 级别 | 说明 | 处理时限 |
|------|------|------|----------|
| 🔴 P0 | 阻塞 | 阻断性问题，必须修复 | 立即 |
| 🟠 P1 | 严重 | 重要功能缺陷，应修复 | 24h |
| 🟡 P2 | 中等 | 一般问题，建议修复 | 1周 |
| 🟢 P3 | 轻微 | 优化建议，可延后 | 任意 |

## 4. 评审输出格式

### 4.1 文件命名规范

```
agent-output/review/YYYY-MM-DD-{commit:6}/[文件类型].md
```

**示例**：
```
agent-output/review/2026-02-04-745ee4d/
├── 综合评审.md              # < 2500 token 时使用
├── 功能-需求-流程评审.md     # > 2500 token 时拆分
├── 安全评审.md
├── UI-UX评审.md
└── 模块-接口设计评审.md
```

### 4.2 单文件结构（< 2500 token）

```markdown
# XXX 评审报告

**评审分支**：`xxx`
**Commit Hash**：`xxx`
**评审日期**：YYYY-MM-DD

## 执行摘要
- 总体评分
- 核心问题列表

## 问题清单
- 按严重程度分类

## 改进建议
- 按优先级排序

## 已实现模块
- 完整功能列表

---

`★ Insight ─────────────────────────────────────`
**关键发现**：
1. xxx
2. xxx
`─────────────────────────────────────────────────`
```

### 4.3 多文件结构（> 2500 token）

每个文件不超过 2500 token，包含：

```
## 1. 执行摘要
## 2. 详细发现
## 3. 问题列表
## 4. 改进建议
```

## 5. 评审流程

### 5.1 准备阶段

```
1. 确认评审范围和分支
2. 获取 commit hash
3. 收集相关文档（SPEC、PRD）
```

### 5.2 执行阶段

```
1. 功能完整性评审
2. 代码质量评审
3. 安全评审
4. 架构设计评审
5. 性能评审
6. 测试覆盖评审
```

### 5.3 输出阶段

```
1. 整理问题清单
2. 计算总体评分
3. 生成评审报告
4. 归档到 agent-output/review/
```
