# Beta15：覆盖网络地址与加入恢复

起点`dev-0.6@8fdf2e66`。用户在Beta13的同档案、同EasyTier网络中发现平板新文字不到PC，随后以另一个档案邀请加入仍失败。当前只定位地址/连接接缝，不把它归因于旧档案证明，也不重写同步协议。任务编号不是档案事件ID。

## 现场与边界

- PC实际运行已知Beta13候选，peer TCP监听所有IPv4接口，HTTP API另在loopback。只读库查询确认旧档案的已保存平板路由仍为旧Wi-Fi地址，用户给出的消息节选在PC未匹配；未读取其他记录正文、原件或凭据。
- 通过与已装GUI同版、官方digest校验的临时EasyTier CLI，只读取得平板节点虚拟IP；PC到其peer端口TCP连接成功。此项只证明端口可达，尚非TLS身份、加入、复制或投影通过。原始非凭据诊断留仓库外。
- 用户的新档案邀请截图只列Wi-Fi、代理TUN与loopback，没有EasyTier地址。没有复制、记录或复用截图内的邀请secret，后续验证使用新生成的合成邀请。
- 初读源码只看到启动时枚举地址，曾提出缓存过期假设；完整worker循环实际每2秒重枚举，`route-refresh-red`运行了1项且通过，未证明该缺陷，已撤回“只在启动快照”的根因口径。邀请实际缺少可达的覆盖地址；没有虚拟网卡的覆盖网络也可能不出现在`if_addrs`，不能靠重复刷新解决所有情况。平板当前接口枚举尚未取证。
- 本机原生窗口控制接口返回native pipe不可用；平板ADB未连接。不能把无法操作现场界面写作恢复通过，也不让用户反复代查本机可取得的信息。

## 保持的合同

拨号地址只是到某个设备的线索，不授予档案权限、不替换设备身份或重签邀请。备用地址不能绕过原邀请的协议/schema、签名、有效期、TLS指纹、当前成员/代次/撤销及claim幂等。旧档案、草稿和已落库事实不清空；没有直接暴露owner HTTP API到覆盖网络。

本轮补充邀请之外的拨号路由及明确恢复路径。自动发现、网络变更后的路由学习/退避/优先级、常连事件提示及全设备总览，需要在Luna证据及当前可复现问题上形成后续切片，不直接照搬T3的客户端—服务端数据所有权。
