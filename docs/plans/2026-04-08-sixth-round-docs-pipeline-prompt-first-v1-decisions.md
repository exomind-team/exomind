## 1. 本轮主题总览

这轮没有继续扩展 `/docs` 首版内容合同本身，而是开始收口：

1. 这条未来文档生产工作流的 **v1 止步层**
2. 它的 **机器真相源**
3. 它的 **最先自动化环节**
4. 它与 `#847`、`#865` 两条现有 issue 线的衔接关系
5. prompt-first 阶段的最小输入、输出与 review 拓扑

本轮新增的核心判断是：

- 当前 v1 **不先做完整自动流水线**
- 当前 v1 **先不做正式脚本入口**
- 当前 v1 **先让 Agent 跑通**
- 当前 v1 **先写一版可复用提示词 / 提示词文档**

也就是说，这条线当前最应该先做的不是“代码直出官网”，而是：

- 先把 **prompt-first 的人工运行协议** 做出来
- 再看是否值得封装成脚本、命令或 GitHub Actions

## 2. 本轮新增已定决策

### 2.1 工作流的 v1 止步层

这条未来文档生产工作流当前 v1 明确收口为：

- **只到草稿生成**

不进入 v1 关闭条件的内容包括：

- 自动推进到 canonical 正文
- 自动推进到 website 页面
- 从代码直接贯通到官网的端到端流水线

换句话说：

- v1 先解决“草稿怎样稳定产出”
- 暂不解决“草稿何时正式晋升为 canonical / 上站”

### 2.2 第一机器真相源

当前最先作为机器真相源的不是：

- 代码注释
- 全仓自动扫描
- website 页面内容

而是：

- **issue 汇总包**

更具体地说，prompt-first 阶段最合适的输入包固定为：

- **issue + 对应计划文档 + 必要证据链接**

不要求：

- Agent 自己全仓乱扫再猜主题
- 只给 issue 列表不带计划文档

### 2.3 第一自动化目标

这条工作流第一阶段最值得自动化的环节固定为：

- **草案打包**

不优先做：

- 站点镜像
- 全链直通

并且一次运行最值得先产出的组合固定为：

- `#847` 用的 **里程碑评论草案包**
- `#865` 用的 **待提取章节清单**

### 2.4 `#847` 与 `#865` 的衔接方式

这两条线的第一阶段衔接方式明确收口为：

- `#847` 负责：
  - 已验证里程碑
  - 对外草案包
  - 证据与边界整理
- `#865` 负责：
  - 用户手册章节 review
  - canonical 正文的集中收敛

两者之间的第一阶段衔接动作固定为：

- **生成待提取清单**

不采用：

- `#847` 直接承载完整用户手册正文
- `#847` 与 `#865` 完全松散手工转写、没有中间衔接对象

### 2.5 草稿粒度

自动化“草案打包”第一阶段的最小粒度固定为：

- **章节级草稿**

不采用：

- 只生成摘要骨架
- 直接生成完整可发布长文

这意味着第一阶段自动化的目标是：

- 帮助人类快速进入章节 review
- 而不是跳过 review 直接替人完成最终写作

### 2.6 用户手册线的 review 拓扑

`#865` 这条用户手册线第一阶段的 review 拓扑固定为：

- **中心挂点**

也就是说：

- 继续集中在 `#865` 做章节草稿 review
- 不为每一章单开 issue
- 不以 website 页面作为正文主 review 面

### 2.7 canonical 正文的收敛表面

当自动化开始介入后，真正的 canonical 正文内容第一阶段默认收口在：

- **仓库 Markdown**

而不是：

- issue 评论本身
- website 页面本身

对应关系固定为：

- issue 评论负责：
  - 草稿 review
  - 证据讨论
  - 边界澄清
- 仓库 Markdown 负责：
  - canonical 正文收敛

### 2.8 每个章节草稿的最小合同

每个自动生成的章节草稿，第一阶段至少必须带：

- 用户路径
- 操作步骤
- 来源证据
- 范围边界
- 排障信息

不采用：

- 只给正文 + 来源链接
- 只给结构化元数据，不给面向用户的章节文本

### 2.9 实验性内容进入用户手册的规则

当某功能核心路径已可用，但边缘场景尚未完全验证时，第一阶段默认：

- **允许进入用户手册**

但必须：

- 显式标记为 `实验`
- 写清边界
- 写清风险

不采用：

- 一律不进普通用户手册
- 只能丢进 FAQ，不能进主正文

### 2.10 v1 中间产物的落点

prompt-first v1 生成出来的中间产物，第一阶段固定先落在：

- **本地临时文件**

不默认：

- 一生成就直接发到 `#847 / #865`
- 直接把中间草稿入库跟踪

当前阶段的最小语义是：

- 先本地生成
- 先本地检查
- 再决定是否发到 issue 或回写正文

### 2.11 触发方式的最新判断

关于“这条 v1 工作流最适合由什么方式触发”，用户本轮没有采用此前给出的：

- 本地命令
- GitHub 手动派发
- issue 状态自动触发

而是新增了一个更靠前的阶段判断：

- **先让 Agent 跑通，先写一个提示词**

因此本轮真正收口的是：

- 当前 v1 甚至还不到“先做正式命令入口”的阶段
- 当前应先做 **prompt-first 的人工运行协议**

### 2.12 prompt-first 阶段的输入包

这版 prompt-first 工作流第一阶段最适合喂给 Agent 的输入包固定为：

- **issue + 计划文档**

更完整地说包括：

- 指定 issue
- 对应计划文档
- 必要证据链接

### 2.13 prompt-first 阶段的输出组合

这版 prompt-first 工作流，一次运行最值得先产出的组合固定为：

- **`#847` 草案包**
- **`#865` 提取清单**

当前明确不先产出：

- 完整用户手册正文
- website 页面草稿

### 2.14 prompt-first 阶段的第一落点

这版 prompt-first 的第一落点固定为：

- **仓库内提示词文档**

不优先做成：

- 中心 issue 的评论模板
- 脚本内置常量

这说明当前最适合先落的不是代码，而是：

- 一份仓库内可复用、可迭代、可由人和 Agent 共读的提示词 / 操作说明文档

## 3. 当前明确未收口的点

以下内容本轮刻意没有强行定稿：

“草稿进入 canonical / 上站链”的正式门禁，本轮明确：

- **留作后续讨论**

因此当前尚未锁定：

- 是否以评论确认作为正式门禁
- 是否以 issue 关闭作为正式门禁
- 是否以 release / build 标签作为正式门禁

### 3.2 正式脚本或命令入口

本轮没有锁定：

- 最终是否做成本地命令
- 是否接入 GitHub Actions
- 是否做 issue 状态自动触发

当前只锁定：

- 先用 prompt-first 跑通

### 3.3 提示词文档的最终仓库路径

本轮只锁定了：

- **仓库内提示词文档**

尚未锁定：

- 最终应落在 `docs/plans/`
- 还是独立 prompt 目录
- 还是后续提升为 skill / references
