# 跨项目 Issue 追踪迁移章程（通用版）

> 目标：把 ExoMind 的 issue 追踪治理能力抽象成跨项目可复用的方法，让 Agent 能把用户的自然语言反馈稳定转成“查重 → 现状核查 → 新建/追加 → 建依赖 → 回报”的标准动作，而不被单个项目的分支命名、标签体系或日志入口绑死。

## 0. 迁移原则

不要机械复制 ExoMind 的专有约定，要先做语义映射：

| ExoMind 原字段 | 跨项目迁移后的通用语义 |
|---|---|
| `dev` 分支 | 当前集成分支 / 默认开发分支（如 `dev`、`main`、`trunk`、`develop`） |
| `dev` 短 hash | 当前核查分支的短 hash |
| `UI / Web / Tauri / 移动端` | 目标仓库已有的平台或模块标签 |
| `P0 / P1 / P2` | 目标仓库已有的优先级标签；若没有则用宿主系统原生优先级字段 |
| 设置页日志 / Tauri 日志 | 目标项目现有的调试、日志、诊断、监控、Sentry、控制台或系统日志入口 |
| GitHub GraphQL `blockedBy / subIssue` | 宿主平台原生依赖模型（GitHub / Jira / Linear / Azure DevOps 等） |

迁移时只保留“不变量”，不要照搬实现细节。

## 1. 适用范围

- Bug / 回归 / 体验缺陷
- 功能请求
- 架构或产品讨论
- 设计原则澄清
- 技术债追踪

## 2. 强制原则（不可跳过）

1. **自主执行，不向用户索要结构化表单信息**
   - 收到自然语言描述后，立即开始查重、检索、核查。
   - 不要求用户补“预期/实际/复现步骤/平台/影响范围/关联 issue 编号”等表单字段。
   - 所有结构化字段由 Agent 通过仓库、分支、历史 issue、PR、日志与代码检索自行补齐。
   - 只有在完成检索后仍无法判断核心分歧时，才允许提出一个最小澄清问题。
2. **无则创建，有则追加**
   - 先查重，再决定新建 issue、追加评论、更新旧 issue，还是标记为回归。
3. **必须核查当前实现**
   - 创建或追加前，必须查看当前集成分支的实现现状。
4. **必须包含“预期 / 实际”**
   - 任何追踪对象都必须显式呈现目标行为与当前行为的张力。
5. **必须写明验证方法**
   - 不只写“应该怎样”和“现在怎样”，还要写“当前如何验证”和“实现后如何验收”。
6. **实际必须带实现定位**
   - 写明当前核查分支、短 hash、关键文件路径或服务入口；关键路径要保持仓库相对路径语义，在 issue / 评论正文中应以可点击 Markdown 链接展示，保证后续可溯源。
7. **强制关联**
   - 与已有 issue、PR、文档、设计决策相关时，必须互相引用。
8. **严格去重**
   - 只有在“几乎同一个问题”时才追加；否则新建，并通过关联表达上下文。
9. **多问题强制拆分**
   - 一个 issue 只追踪一个原子问题；一个反馈里包含多个问题时必须拆分。
10. **先追踪层，后细化层**
   - 先让问题进入可追踪状态，再逐步升级为可执行合约；不要因为信息未完全收敛而阻塞 issue 落地。
11. **链接降噪后再发布**
    - 在 issue / 评论中禁止裸贴 URL、禁止把 URL 直接当作链接文本、禁止保留本地绝对路径。
    - 仓库内文件、文档、工作流、报告引用应优先转换为简短命名的 Markdown 链接。

## 3. 执行 SOP

1. 抽取问题原子点
2. 查重检索
   - 搜 open + closed issues
   - 搜相关 PR、commit、release note、文档
3. 核查当前实现
   - 检查当前集成分支代码、开关、默认值、入口路由、调用链
   - 需要时运行最小验证命令或查看现成日志/监控
4. 决策动作
   - 新建
   - 追加
   - 标记回归
   - 更新已过时描述
5. 先写追踪层
   - `背景`
   - `预期`
   - `实际`
   - `关联/依赖`
6. 建立原生依赖关系
   - 优先使用宿主平台原生依赖能力，不要只靠正文或评论模拟
7. 适时补全细化层
   - `已定决策`
   - `边界`
   - `完成条件`
8. 发布前正文复核
   - 本地回读临时正文文件
   - 检查是否残留裸 URL、URL 直出式链接文本、不可点击的仓库路径、本地绝对路径
   - 宿主项目若提供 issue body 检查脚本或统一 grep/正则命令，优先使用
   - 必要时先统一改写，再发布
9. 回报用户
   - 决策说明
   - 当前状态
   - 下一步建议
10. 输出追踪报告
   - 说明查了什么、证据来自哪里、还有哪些未验证项

## 3.1 验证优先的细化方法

追踪不是“帮用户润色需求”，而是把一个模糊反馈压缩成可验证、可接力、可回溯的对象。

每个 issue 至少回答两件事：

1. 当前情况如何被验证
2. 目标情况在实现后如何被验证

建议按四层取证：

- 现象层：用户看到了什么、没看到什么
- 操作层：在哪个页面、接口、命令、设备、状态下能复现或验收
- 证据层：日志、报错、截图、监控、代码路径、issue/PR/文档
- 边界层：哪些已验证，哪些未验证，哪些仍待补证据

## 3.2 Bug / 回归类问题的默认路径

Bug 追踪优先“先取证，再定性”：

1. 优先复现问题
2. 优先使用现有日志、监控和诊断入口
3. 仅当现有入口不足时，才追加最小调试信息
4. “实际”只能写已观察到的现象与证据
5. 推测原因只能放在 `未验证` 或后续讨论区

对 bug 的“实际”建议至少包含：

- 当前实现 / 现状定位
- 观察到的现象
- 验证溯源方法
- 已验证 / 未验证 / 待补证据

## 4. Issue 合约分层

### 4.1 追踪层（创建/追加时必备）

用于把用户自然语言反馈变成标准追踪对象。至少覆盖：

- `背景`
- `预期`
- `实际`
- `关联/依赖`

特点：

- 面向事实、现状、定位、关联
- 适用于 bug、功能、讨论、回归、设计澄清等所有入口
- 不要求一开始写满完整方案

### 4.2 细化层（问题收敛后补齐）

当方向、边界和验收方式足够清晰时，补充：

- `已定决策`
- `边界`
- `完成条件`

特点：

- 把 issue 从“追踪对象”升级成“可执行合约”
- 支持渐进补全
- 完成条件优先写成外部可验证行为

## 5. 通用 Issue 模板

```md
## 背景
- 用户反馈：
- 影响范围：

## 预期
### 目标行为
### 验证溯源方法

## 实际
### 当前实现 / 现状定位
- 分支：<integration-branch>
- commit: <short-hash>
- 关键路径：
  - [src/xxx.ts](<repo-blob-url>)
  - [docs/xxx.md](<repo-blob-url>)
- 上下文检索：
  - Issues:
    - #123
  - PRs:
    - #456
  - Docs:
    - [设计文档](<repo-blob-url>)
  - Code:
    - [src/xxx.ts](<repo-blob-url>)
### 观察到的现象
### 验证溯源方法
### 已验证 / 未验证 / 待补证据

## 已定决策（问题收敛后补）
- 决策 1

## 边界（问题收敛后补）
### 要做
- 范围 1

### 不做
- 非目标 1

## 完成条件（问题收敛后补）
- [ ] AC1
- [ ] AC2

## 关联/依赖
- 关联：
  - #123
- 阻塞：
  - #456
- 子问题：
  - #789
```

## 6. 依赖关系迁移规则

### 6.1 总原则

- 优先使用宿主平台原生依赖关系
- 阻塞关系优先于“模糊相关”
- 父子关系只在范围真正包含时使用
- 若平台支持，父子与阻塞可以同时存在

### 6.2 GitHub 项目的默认做法

- 使用 GraphQL 的 `blockedBy / blocking / subIssue`
- 若 mutation 失败：
  1. 在正文 `关联/依赖` 保留 Markdown 列表
  2. 追加评论记录失败原因与待补命令

### 6.3 非 GitHub 项目的迁移要求

- Jira：用原生 issue links / parent-child / epic 结构
- Linear：用 dependency / parent-child 关系
- Azure DevOps：用 work item link types
- 若宿主平台完全不支持原生依赖，才退化为正文 + 评论留痕

## 7. 标签与优先级迁移规则

- 平台标签：映射到目标仓库已有的平台、端、模块标签
- 领域标签：映射到目标仓库已有的模块、子系统、业务域标签
- 优先级：
  - 默认使用目标仓库现有优先级体系
  - 若无既有体系，再引入 `P0 / P1 / P2`
- 只有在影响主线、数据安全、系统可用性或明确业务要求时，才提升到最高优先级

## 8. 迁移前检查清单

把这份章程落到新项目之前，先确认：

1. 当前集成分支是什么
2. issue 平台是什么
3. 标签体系是什么
4. 已有日志、监控、诊断入口有哪些
5. 默认验证链路是什么
6. 需要在 issue 中固定写哪些仓库特定字段

## 9. 回报用户格式（必须）

- 决策说明：新建 / 追加 / 回归 / 覆盖
- 当前状态：issue 编号、标题、状态
- 下一步建议：最小可执行动作

## 10. 链接与正文降噪规则

- 宿主平台支持 Markdown 链接时，优先使用 `[短名](链接)` 而不是裸 URL
- 对仓库内文件、文档、工作流、报告，链接文本优先使用文件名、标题或简短语义名
- 若文件名重复或语义不清，链接文本应加最小必要前缀（如 `docs/overview.md`）
- 在本地仓库 Markdown 文档中优先使用相对路径链接；在 issue / 评论中优先使用宿主平台可访问的命名链接
- 若仓库相对路径本身就是必要定位信息，可直接把 `src/...`、`docs/...` 作为链接文本，但不要裸写成普通文本
- 禁止把本地绝对路径暴露到 issue / 评论正文中
