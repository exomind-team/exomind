# 2026-04-06 Agent 能量与资源双计量第一阶段计划

> 状态：已收口阶段判断
>
> 目的：把 `Theme D` 中已经形成稳定共识的部分从聊天中摘出，避免后续继续把“运行能量”“token 成本”“生命叙事”混成一个主题。

---

## 1. 计划摘要

`Agent` 的能量系统在第一阶段不作为完整生命叙事，也不追求把所有资源压成一个统一数值，而先收口为：

- 一个面向 `Agent` 的**运行调度模型**
- 一套**双账本同界面**的资源表达
- 一个先落在**诊断面 / Agent workbench**的治理表面
- 一套**人工手动补能 / 唤醒优先**的干预机制

---

## 2. 方法论前提

后续文档统一按以下原则表述：

- `actor` 与 `Agent` 都是**方法论概念**
- 它们都不是对底层程序本体的硬分类
- 外心系统关注的是“用什么视角组织它、监控它、治理它”，而不是先规定“这种程序天生必须有哪些特征”

在这个前提下：

- `actor` 更偏向：
  - 消息参与
  - 关系
  - 收发
  - 连边
- `Agent` 更偏向：
  - 调度
  - 记忆
  - 提案
  - 资源治理

因此，`Agent` 相对 `actor` 的差别，不应写成“底层程序天然不同”，而应写成：

- **外心在这一层对它额外关注并持续追踪了更多治理变量**

---

## 3. 双计量的第一阶段结构

第一阶段明确采用：

- **双账本，同界面**

也就是说：

- 运行资源与模型资源是两套不同计量
- 允许在同一产品表面解释
- 不强行压成一个总分值或单一电池

### 3.1 运行资源

对任何被放入外心运行与观测表面的运行体，第一层都至少可以从两个运行资源维度去看：

- **时**
  - CPU 时间
  - 计算资源
  - 调度频率
- **空**
  - 存储占用
  - 内存占用

这些是运行时层面普遍存在、且可被系统观测和治理的资源维度；它们不用于把某类程序先验地定义成 `actor` 或 `Agent`。

### 3.2 `Agent` 视角额外关注的资源

当外心以 `Agent` 视角组织某个运行体时，还会额外纳入更强的控制面变量：

- token 消耗
- 调用额度
- 成本
- 心跳 / 唤醒节律等调度维度

这里的重点不是把它们立即折算成统一值，而是承认：

- 这些维度是在 `Agent` 视角下需要被系统性追踪和治理的
- 这不是因为底层程序先天不同，而是因为外心在该层选择了不同的监控变量与治理责任

### 3.3 模型账本粒度

模型资源账本第一阶段默认按以下方式记账：

- **单次 invocation 为主粒度**
- **按 turn 聚合为主要汇总粒度**

也就是说：

- 先把每次模型调用记清
- 再在 turn 级别做汇总观察
- 之后再讨论设备级 / 档案级聚合

---

## 4. 第一阶段显化表面

第一阶段最先显化在：

- 诊断面
- `Agent workbench`
- 开发 / 治理表面

不直接作为普通用户主界面的强叙事核心。

第一阶段默认要求：

- 人类能看到相关告警
- Agent 也能读取到自身资源状态

---

## 5. 告警与干预策略

### 5.1 告警落点

低能量 / 高频唤醒 / 模型资源异常等告警，第一阶段默认落在：

- diagnostics
- `Agent workbench`

而不是先落到：

- 普通用户首页
- 强提醒消费面

### 5.2 补能 / 唤醒

第一阶段默认采用：

- **人工手动补能**
- **人工手动唤醒**

后续可以继续讨论：

- 通过提案触发的补能 / 续命流程

但这不进入第一阶段关闭条件。

---

## 7. 接入主线的时机

这条线不与信号网络 `v1` 同批推进，而收口为：

1. 先完成**个人同步基线**
2. 再完成**信号网络 v1**
3. 再完成**单 Agent 时间块闭环**
4. 然后把能量双计量接成新的治理 / 调度层

这样做的原因是：

- 先让信号、节点、单 Agent 用户叙事稳定
- 再给 `Agent` 层加更强的资源治理壳体
- 避免过早把资源模型压进基础网络语义里

---

## 8. 第一阶段明确不做的内容

以下内容不进入这份子计划的关闭条件：

- 把运行资源与 token 成本折算成单一总能量值
- 完整生命体叙事产品化
- 自动提案式补能 / 唤醒
- 多 Agent 阶段的全局配额编排
- 最终版统一公式

---

## 9. 最小验收方向

至少应能稳定回答并验证：

- diagnostics / `Agent workbench` 能显示运行资源与模型资源的基本状态
- 低能量与模型资源异常先在治理表面告警
- 人类可以手动执行补能 / 唤醒
- 模型账本按 invocation 记录，并能按 turn 聚合观察
- `Agent` 与 `actor` 的差别文档化为治理变量差异，而不是程序本体差异

---

## 10. 一句话总结

`Agent` 能量系统第一阶段不是“做一个更华丽的电池比喻”，而是“**先把 Agent 这一方法论视角下的运行调度、告警干预和双账本资源治理变量收口出来，并把它们落在 diagnostics / workbench 这样的治理表面**”。
