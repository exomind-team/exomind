## 3. 问题与建议

### 3.1 阶段划分问题

| 问题 | 详情 | 建议 |
|------|------|------|
| **阶段一二强耦合** | Agent 框架依赖 ExoBuffer，但阶段二是单独的 | 合并阶段一、二，或明确依赖关系 |
| **记忆系统前置** | 记忆系统放在阶段三，但 Agent 基类需要状态管理 | 状态持久化应与 Agent 框架同步 |
| **健康监控后置** | 健康监控放在阶段四，但应该在开发过程中持续构建 | 健康监控应该是贯穿全程，而非独立阶段 |

**建议调整**：

```
原计划：
阶段一 → 阶段二 → 阶段三 → 阶段四 → 阶段五 → 阶段六

建议计划：
阶段一 (1-2周): Agent 核心 + ExoBuffer 基础
阶段二 (3周): 记忆系统 + 健康监控
阶段三 (5周): 语音集成
阶段四 (6周): 多代理协作 + 测试
```

### 3.2 技术栈问题

| 问题 | 详情 | 建议 |
|------|------|------|
| **Rust 后端定位** | 文档说 Rust + Axum，但 exomind 已有 Tauri 2.0 + Rust | 复用 Tauri 的 Rust 后端，避免重复 |
| **Python 迁移** | wzy-agents 是 Python，迁移到 TS 工作量大 | 考虑保留 Python Agent，用 IPC 通信 |
| **SSE 实现** | 已有 SSE 客户端实现，但需要适配新架构 | 先复用，再优化 |

**关键决策点**：

> **问题**: wzy-agents 的 Python Agent 是否需要迁移到 TypeScript？
>
> **选项 A**: 完全迁移 → 工作量大，但架构统一
> **选项 B**: 保留 Python，用 IPC 通信 → 复用现有代码，但架构分裂
> **选项 C**: 重写核心，保留 Python 子 Agent → 折中方案

**建议**: 采用选项 C，主 Agent 用 TypeScript，子 Agent 保留 Python

### 3.3 数据流问题

| 问题 | 详情 | 建议 |
|------|------|------|
| **循环依赖** | Agent → ExoBuffer → 前端，但 Agent 也需要读取 Fact | 明确数据流向，避免循环 |
| **实时性要求** | SSE 实时广播，但 Claude Code 响应可能很慢 | 区分实时消息和批量数据 |

### 3.4 验收标准问题

| 问题 | 详情 | 建议 |
|------|------|------|
| **缺少集成验收** | 各阶段有验收标准，但缺少集成测试 | 增加阶段间的集成测试 |
| **指标缺少基线** | "稳定"、">90%" 等缺少当前基线 | 添加当前值和目标值 |
| **缺少用户验收** | 都是技术指标，缺少用户满意度 | 增加用户验收标准 |

## 4. 风险补充

### 4.1 文档未识别的风险

| 风险 | 影响 | 应对 |
|------|------|------|
| **Python→TS 迁移** | wzy-agents 是 Python，迁移成本高 | 渐进式迁移，先核心功能 |
| **依赖项目失活** | wzy-agents/exomind-model 可能停止维护 | 锁定版本，分支管理 |
| **API 兼容** | ExoBuffer API 设计与现有系统可能冲突 | 适配层设计 |
| **数据迁移** | 现有项目的记忆数据如何迁移 | 设计迁移工具 |

### 4.2 架构风险

| 风险 | 详情 | 应对 |
|------|------|------|
| **Tauri IPC 延迟** | 前端→Rust→Python 多跳 | 异步处理，避免阻塞 |
| **状态一致性** | 多端状态同步 | 单一数据源，事件溯源 |
