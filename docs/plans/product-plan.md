## 一、产品愿景

> **一句话**：认知生命科学原型 - 基于大模型的自主生命体，像生物一样有生老病死，具备持续运行、自主决策、真实责任能力。

### 1.1 核心定位

ExoMind 是一个 **以 Claude Code 为核心的跨平台自主生命体系统**，帮助用户主动地掌控自己的生命过程。

### 1.2 核心理念

| 理念 | 说明 |
|------|------|
| **生命-认知一体化** | 不把感知和学习作为后加功能，而是从单细胞阶段就作为存活优势存在 |
| **可存活区间** | 生命主体的硬判据：能量与资源有限、边界明确、不可逆裁决 |
| **失败不可回滚** | 死亡不是 episode reset，错误会留下不可抹平的后果 |
| **伤疤机制** | 失败产生不可逆退化，压缩未来行动空间 |
| **环境裁决** | 边界不可协商，由环境执行约束 |

```

├─────────────────────────────────────────────────────────────┤

│  ├── 关机仪式（模板存在，未执行）                            │
```

## 二、四个 Agent 职责定义

### 2.1 外心 (ExoMind Core / Governor)

**角色**：系统调控中枢，方向盘 + 刹车

**核心职责**：
- 🌅 **开机调度**：决定今天偏推进 / 修复 / 学习 / 校准
- 🚦 **输出治理**：拦截副作用（羞耻、控制感、负担）
- 🌙 **关机校准**：总结有效 / 无效建议，调整明天策略
- 🧱 **防膨胀**：保持主循环极简

**关键接口**：
- 接收各 Agent 的输出并评估副作用
- 调度其他 Agent 的优先级和活跃度
- 维护系统整体"可持续性"

### 2.2 任务系统 (Task Recommendation Agent)

**角色**：状态 × 需求 × 项目 × 兴趣的智能匹配引擎

**核心职责**：
- 推荐此刻最值得做的 1 个任务 + 1 个备选
- 解释取舍：为什么适合你现在的状态与长期方向
- 🧭 **用户主导**：建议可拒绝，你做最终选择
- 与 Governor 配合：低状态时自动收缩任务强度

**数据依赖**：
- 当前状态（能量、焦虑度、时间可用性）
- 项目列表（来自 PARA/Projects）
- 历史偏好（从 Review Agent 获取）
- 目标优先级（从 Growth Coach 获取）

### 2.3 目标身心觉察 (Growth Coach)

**角色**：意识 × 潜意识的成长教练

**核心职责**：
- 🪞 **证据三角**：行为证据 + 感受证据 + 叙事证据
- 🌊 **潜意识模式识别**：回避、完美主义、拖延、羞耻循环
- 🔧 **最小改写练习**：3-5 分钟，可拒绝
- 📍 **插槽位置**：任务选择时、复盘之后

**输出形式**：
- 成长洞察（基于证据，不贴标签）
- 练习建议（短、低风险、可坚持）
- 状态匹配（帮助任务系统做推荐）

### 2.4 行动反馈 Agent (Review Agent)

**角色**：极简复盘，沉淀可复用策略

**核心职责**：
- 每次尝试后只产出四行：
  - ✅ **哪里有效**
  - 🧱 **哪里卡住**
  - 🔧 **下次改一条策略**
  - 🚫 **避免一条做法**

**数据流向**：
- → Governor：提供有效性反馈
- → 任务系统：提供任务偏好数据
- → Growth Coach：提供行为证据

## 三、核心闭环设计

### 3.1 最小闭环定义

```
最小闭环 = 能跑通一个"观察→判断→执行→反馈"循环
├── 观察：获取外部信息（语音 / 图像 / 文字）
├── 判断：理解信息意图（任务 / 记账 / 聊天）
├── 执行：调用对应 Agent 处理
└── 反馈：返回结果给用户
```

### 3.3 MCP 验收接口

**为什么需要 MCP 服务器作为验收接口？**

- 文件操作是"破坏性"的，接口可以验证、审计、幂等
- MCP 是标准化协议，后续换平台不用改逻辑
- 验收流程本身也是一种"信息流"，需要被记录和追踪
- Agent 不能直接改任务状态，需要人确认后才能生效

**验收流程**：

```
┌─────────────────────────────────────────────────────────────┐
│  任务验收闭环                                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 任务创建（Agent）                                        │
│     Agent → MCP: create_task(description)                   │
│     MCP → 返回: task_id (状态: pending)                     │
│                                                             │
│  2. 任务执行（人）                                           │
│     人 → 完成任务 → 标记"待验收"                            │
│                                                             │
│  3. 任务验收（人）                                           │
│     人 → APP/MCP → confirm_task(task_id)                   │
│     MCP → 验证 → 更新状态: completed                        │
│     MCP → 触发: 任务完成事件 → 更新 now.md                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**验收状态机**：

```
draft → pending → in_progress → pending_review → completed
           ↑                              |
           └──────────────────────────────┘
                      (拒绝验收)

pending:      任务已创建，等待开始
in_progress:  任务执行中
pending_review: 待验收（人完成任务后手动标记）
completed:    已验收（人确认后自动更新）
```

**最小关机仪式（5 分钟）**：

```
┌─────────────────────────────────────────────────────────────┐
```

## 五、场景设计

### 5.1 场景一：语音 / 文字任务输入

```
流程：手机语音 → Tasker → HTTP(:2601) → 意图识别 → Agent 执行

示例对话：
用户（手机）: "整理 human 目录"
     ↓
Tasker 发送: {"type": "voice", "content": "整理 human 目录", "source": "mobile"}
     ↓
消息路由器 → 意图识别 → 任务类型
     ↓
调用任务规划师 Agent → 生成任务建议 → 更新 now.md
     ↓
返回: "已创建任务 T-2026-01-xxx，建议今天完成"
```

### 5.2 场景二：拍照记账

```
流程：手机拍照 → 发送图片路径 → 桌面 OCR → 财务 Agent 记账

┌─────────────────────────────────────────────────────────────┐
│  手机端（轻量）                                             │
│  ├── 拍照 / 选择图片                                         │
│  ├── 可选：本地 OCR（Google ML Kit）                        │
│  └── 发送：图片 Base64 / 路径 + 金额（用户输入）            │
├─────────────────────────────────────────────────────────────┤
│  桌面端（重量）                                             │
│  ├── 接收图片                                               │
│  ├── 调用云端 OCR API（阿里 / 腾讯 / Google）               │
│  ├── 识别金额 / 商家 / 品类                                 │
│  ├── 调用财务 Agent 记账                                     │
│  └── 返回结果                                               │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 场景三：日常聊天 / 灵感

```
流程：手机文字 → Tasker → HTTP → 小荷 Agent → 返回

这是最简单的场景，也是信息量最大的场景
小荷 Agent 可以直接处理，无需路由
```

## 六、实施路线图

### 6.1 核心原则

- ✅ 默认短：仪式不超过 10 分钟
- ✅ 默认可跳过：不做强制
- ✅ 失败不羞辱：失败不记录为"失败"，只记录"未执行"
- ✅ 只改一条：每次复盘只改一条
- ✅ 建议可拒绝：推荐只是建议
- ✅ 最小干预：宁可少做，不制造负担

### 6.2 第 1 周：手动模拟验证闭环 (Wizard-of-Oz)

**目标**：不写代码，先验证闭环是否有效

| 日期 | 任务 | Agent | 输出物 | 验收标准 |
|------|------|-------|--------|----------|
| **Day 1** | 恢复仪式模板 | Governor | `template-boot-morning.md`<br>`template-boot-night.md` | 开机 5 分钟内，关机 10 分钟内 |
| **Day 2** | 手动跑一次主循环 | 任务系统 + Review | 今日任务选择记录<br>极简复盘（4 行） | 能推荐 1 个任务 + 1 个备选 |
| **Day 3** | 证据三角练习 | Growth Coach | 行为 / 感受 / 叙事记录<br>1 条洞察 + 1 个练习 | 基于真实数据，不空话 |
| **Day 4** | 整合仪式闭环 | 全部 | 完整一天的闭环记录 | 开机 → 主循环 → 关机无中断 |
| **Day 5-7** | 连续 3 天验证 | 全部 | 3 天日记记录 | 每天执行，记录体感 |

### 6.3 Day 7 验证问题（只问 6 题）

1. ✅ 我更少无谓点开了吗？
2. ✅ 我更快开始做事了吗？
3. ✅ 我更容易恢复上下文了吗？
4. ✅ 我开始复用下次方案 / 避免项了吗？
5. ✅ 我更清楚自己的状态 / 触发器 / 模式，并更快回到可行动了吗？
6. ✅ 我睡前更能放下，手机更可控了吗？

**决策点**：
- 如果体感变好 → 进入第 2 周（插件化）
- 如果变负担 → 立刻减法：删步骤，不加功能

### 6.4 第 2 周：Obsidian 插件 MVP

**前提**：第 1 周验证通过

#### 6.4.1 Agent 1：任务系统插件

**功能范围**：
- 正计时 / 倒计时功能
- 自动保存为 EventLog 格式
- 简易任务推荐（基于当前状态）

#### 6.4.2 Agent 2：Review Agent（复盘助手）

**功能范围**：
- 极简复盘模板（4 行）
- 自动插入到任务记录末尾
- 汇总到日记文件

#### 6.4.3 Agent 3：Growth Coach（成长助手）

**功能范围**：
- 证据三角模板
- 插槽位置：关机仪式时触发
- 可选模式（默认关闭）

#### 6.4.4 Agent 4：Governor（系统调控）

**功能范围**：
- 检查仪式完成情况
- 拦截过长输出（超过 200 字提醒）
- 失败不羞辱记录

### 6.5 第 3 周：手机外部缓冲区 App

**前提**：第 2 周插件基本可用

#### 6.5.1 核心功能

1. **信息捕获**
   - 微信分享接入
   - 快速笔记
   - 语音转文字（可选）

2. **本地存储**
   - SQLite 数据库
   - Markdown 预览

3. **Git 同步**
   - 定时推送到个人仓库
   - 增量同步
   - 冲突提示（手动解决）

#### 6.5.2 移动端策略（关键决策）

**决策**：不做 Tasker，直接做轻量 Android APP

| 方案 | 问题 | 选择 |
|------|------|------|
| Termux + Claude | 需要 root，需要安装，不通用 | ❌ |
| Tasker | 需要学习配置，用户体验差 | ❌ |
| 轻量 APP | 需要开发，但简单、统一 | ✅ **直接做** |

### 6.6 MVP 最小技术栈

#### 6.6.1 轻量 APP + HTTP（本周完成）

```
输入层：
├── 轻量 Android APP
│   ├── 拍照按钮 → 发送图片 Base64
│   ├── 录音按钮 → 本地 STT → 发送文本
│   └── 文字输入 → 发送文本
│
└── Happy Coder（桌面对话）

├── Node.js + Express (:2601)
│   ├── 消息路由器（简单的 if-else 路由）
│   └── MCP 服务器（任务验收接口）
└── Claude API（调用各 Agent）

存储层：
├── Obsidian Vault（事实层）
└── SQLite（任务状态缓存）

输出层：
├── 返回文本到 APP（HTTP Response）
└── 更新 Obsidian 文件（通过 MCP）
```

#### 6.6.2 拍照记账（下周完成）

```
新增：
├── 图片接收接口 (:2602)
├── OCR 调用模块（阿里云 OCR API）
└── 财务 Agent 集成
```
