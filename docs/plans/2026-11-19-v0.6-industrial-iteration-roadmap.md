用户要求先把反复返工转成可证明的约束，再逐步引入意图编排和自动检查。

余项。工业化检查服务于这条主线，不以「框架完工」阻塞产品修复。

## 分期任务与成功判据

| 阶段 | 状态 | 可评审产物 | 通过判据 |
|---|---|---|---|
| A：单一不变量试点 | 本地/远端通过；非候选验收 | 1 条已确认需求、1 份合同、薄门禁、源码 CI | 真执行 3 个 Native 场景及选定 UI 回归；可拦截回归；保留红绿证据 |
| B：核心缺陷按所有者扩展 | 待办 | 同步/原件的需求、失败案例和合同 | 先复现对应故障；区分文字/块状态/原件；旧档案阻塞不伪造成功 |
| C：候选与设备证据接入 | 待办 | 来源/配置/hash/设备矩阵与接受状态 | 同一候选新装/升级、断连重连、EasyTier 路由、系统文件打开分别可查 |
| D：视觉/交互及资源预算 | 待办 | 用户原则 + ARC + Alpha 人审与度量合同 | 键鼠/触摸/短屏/软键盘通过；先有能源基线再制定预算，测面板自身成本 |
| E：完整意图编排框架 | 路线图 | 需求变化分析、任务 DAG、风险选测、证据汇总、人工接受 | 未接受意图不能自动扩权；冲突/失败停在真实边界，旧证明不得冒用 |

完整框架还需：来源与信任分级、合同版本/失效传播、跨模块依赖编排、
隔离数据与凭据策略、受限恢复与取消、可观测队列、证据保留/GC、人工批准
接缝。每个模块先用真实工作证明价值，再决定自动化程度；不先造统一大平台。

## Beta26 环境与多连接主线

用户于 2026-11-21 批准采用增量方案 B：以“稳定外心环境 + 可多条连接 +
档案 membership”替换当前把 route 直接挂在 `(profile, device)` 上的单层模型。
详细设计见
[Beta26 环境与多连接设计](2026-11-21-beta26-environments-connections-design.md)。

实施顺序：

1. 状态闭包、邀请候选、自动复制、主动扫描和 Windows 任务栏身份；
2. 环境、连接、端点、邀请投递和同步尝试持久层；
3. 双侧连接启停、显式拒绝、手动测试和同步路径日志；
4. 一键邀请/接受以及无复制主路径；
5. PC 双 Host、EasyTier、Android 模拟器，最后再做物理平板矩阵。

### 长期选项 C：完整连接督导器

只有在上述真实模型通过后，才评估 T3 式单一 supervisor、持续 route 预检、
抖动退避、优先后台探测和自动回切。该长期选项要求：

- 多路真实故障矩阵和移动端后台数据；
- 连接测试、同步拨号和 discovery 的成本分别预算；
- 前后台/切网唤醒不产生竞争重连；
- 连接失败可定位到 transport、identity、membership 或数据阶段；
- 用户主动关闭始终优先于自动恢复。

本轮不照搬 T3 的 provider/thread/project/MCP OAuth 或整个客户端架构，只学习
稳定环境身份、可变路线、显式授权和唯一重连所有者的工程规律。
