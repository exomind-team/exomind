# Beta 迭代：从根因到可执行回归

本轮只建立一个可运行的试点：已有的「呈现独立」约束。它不代表同步、
附件、能源或完整 Beta 已验收。完整框架的分期见
[路线图](../plans/2026-11-19-v0.6-industrial-iteration-roadmap.md)，沿用
[#568](https://github.com/exomind-team/exomind/issues/568)，不另开重复议题。

## 一次修复的最小单位

1. 写下现场事件/候选、触发操作、期望与实际，区分现场事实和待复现假设。
2. 找到被违反的不变量，以及持有状态、命令和生命周期的所有者。
3. 在该所有者边界先得到失败测试，再做最小修复；视图层另测用户动作。
4. 运行相关回归和下面的合同门禁，保留命令、实际执行数量和失败记录。
5. 行为涉及原生桥、打包或设备时，另做精确候选验收；源码绿不能替代现场绿。
6. 更新执行记录，提交后立即推送，回读远端 SHA；结束时工作区干净。

例如「隐藏专注导致浮窗失效」，不能只把轮询从子组件移到主窗：
主窗仍是浮窗的隐含生命线。应在没有 Main 文档/执行器时直接对 Native
进行暂停、继续、结束和反馈。这个测试才在故障所属层证明了独立性。

## 重复缺陷的预防规则

以下用于重复缺陷、共享写入、原生/网络接缝和生命周期变更。纯文本/样式修改
仍按实际风险选测，不机械要求每次走完整设备矩阵。

| 规则 | 必须回答/检查 | 不适用边界与反例 |
|---|---|---|
| 所有者覆盖全部入口 | 同一状态由谁写、谁执行、谁终止；列出视图离场、切档案和在途结果的资格 | 只搬到主窗 effect 仍把主窗当服务器；纯计算无需生命周期框架 |
| 恢复不混用身份和完成层 | 档案/设备/代次/权限/路由分别核对；文字、可解释投影和原件分别验收 | IP 可达不是身份通过；有正文不是有原作者证明；没有测试授权不清用户库 |
| 编辑、提交和确认分别建模 | 草稿写入、固定命令、未知结果和回执清理各有归属；晚结果不能清新稿 | 传输中的编辑不应禁用提交按钮造成抖动；等待断言不等于重发业务命令 |
| 改维护源，核对 fresh 产物 | 图标/manifest/provider/生成补丁改准备脚本并检查最终包；部分补丁明确失败 | 改生成目录会被下一次 init 覆盖；单纯 Web 文字修改无需重建所有平台 |
| 证明必须绑定输入和反例 | 选定测试实际执行、来源范围明确；已知缺陷临时恢复时应被相应测试识别 | 零匹配/skip/模型推断不当通过；数量相等不证明语义覆盖；执行中改源码要重跑 |
| 工作有预算，观察不取得停止权 | 有限命令有时限和自有清理；采样、缓存、重试与证据保留有成本边界 | 心跳不等于业务进展；全局杀镜像/新增冷缓存不是恢复；功耗结论须实测 |
| 历史代码按可达性退休 | 查入口、配置/特性、动态注册、消费者与回归后再删；历史模型可移为具名测试夹具 | 单次零文本命中不是死代码证明；仍在日用的 0.5 与 Beta 隔离并存不可一并删除 |

一例多因可以拆出多条改进，但每条改进须指向责任边界和可验证反例。
报告区分产品缺陷、测试驱动失误、环境/构建失败、用户语义调整及未证假设；
不以 fix 提交数充当独立 Bug 数，也不把更严格的保护误归类为兼容失败。

| 反复出现的症状 | 应保护的所有者/不变量 | 最小证据与仍需的验收 |
|---|---|---|
| 隐藏/卸载使浮窗失效 | Native 工作区；呈现不持有业务生命期 | Native 无 Main 测试 + UI 显隐/主窗离场；实际 EXE 另验 |
| 观察状态不断增加授权 | Host 授权边界；读不产生新授权 | 首次资格建立后多次读取，授权行数不增加 |
| 另一窗口覆盖新草稿 | Host 比较更新；陈旧写者不能覆盖 | 新稿/损坏稿均保留，陈旧更新明确冲突 |
| 搜索导致导出中断 | 原生任务持有导出；消息行只持有观察 | 搜索卸载 UI 回归；大文件原生完成与系统打开另验 |
| 反馈快捷键/按钮随输入变化 | 提交合同与持久化确认；编辑不等于提交 | 显式 UI 测试和输入前后状态；不能只看截图 |
| 文字到达但计时不可解释 | 源事实/证明 → 复制 → 投影逐层核对 | 分别验文字、可解释时间块、原件；当前试点不覆盖 |

根因记录至少包含：破坏了什么、谁拥有它、过去为何漏测、失败测试怎样
排除另一种解释、修复是否增加空闲开销。不能用无边界重试、延时或吞错
来代替所有权与协议修复。历史档案缺源事实/签名证明时仍保留阻塞结论。

## 立即可用的命令

依赖 Bun、Node、Rust/Cargo、Git 和精确的 `agent-spec 1.4.0`。CLI 缺失时
先执行 `cargo install agent-spec --version 1.4.0 --locked`，不自动替换工具。

```text
agent-spec lint-knowledge --knowledge knowledge --gate
agent-spec requirements plan --knowledge knowledge --specs specs --format json --gate
agent-spec contract specs/beta-runtime-invariants.spec.md --format json
bun run test:beta:contract-evidence
bun run verify:beta:contracts --out <仓库外已有父目录下的新绝对路径>
```

输出目录必须全新、在仓库外，保留每次失败的证据。默认 Cargo 缓存是输出
目录的同级 `cargo-target`，多次验证复用同一个缓存；也可显式指定仓库外
`CARGO_TARGET_DIR`。不再为每次验证创建冷缓存。不要放回用户正在删除的
G 盘旧构建目录。

本地默认检查 worktree（含未跟踪文件）。CI 的 `--base <40位SHA>` 检查
该提交到 HEAD 的来源与变更集合，要求工作区干净，防止测试实际使用的代码
与报告提交身份不一致。无 base 时允许本地改动，报告明确为 worktree；它不是
该 HEAD 的纯提交证明。开始和结束会比较 HEAD、tracked diff 与 untracked
内容指纹，持续到结束的变化使结果失效；这不是原子源码快照，不能检测中途
修改后又原样恢复的全部竞态。验证期间不要编辑源。未跟踪输入每文件有
16 MiB 预算，Git 输出也有上限，超限先分类，不为扫描忽然读取巨型产物。

**持续行为约束和单次任务范围分开。** 默认持续执行三条 Native/选定 UI 回归，
记录来源和变更，不把试点任务的 Allowed Changes 当成所有未来 Beta 工作的权限表。
需要核对这份合同的任务范围时显式加 `--check-boundaries`，报告才会标为已检查；
默认 `boundaryScope=not-requested`，`notAssessed` 包含 `task-boundaries`。
真正的新任务应先评审自己的范围；不为通关把 Allowed Changes 放宽为 `**`。
路径检查不是语义约束证明，也不是文件系统沙箱。

门禁固定执行以下工作：

- CLI 的知识 lint、意图计划、合同渲染、规格 lint 和结构检查。
- 单叶试点的已接受需求、work unit 与选定合同场景数必须相等；这能阻止删少
  场景却仍显示 ready，不证明每个场景已经语义覆盖所有要求，合同改动仍需审阅。
- `lifecycle --ai-mode off --review-mode strict`；不请求模型、不发送原件。
- 三个明确绑定的 Native 集成测试；每个必须实际执行一次，零匹配不算通过。
- 四个明确选定的 UI 测试文件；全部断言实际执行通过，空文件/跳过不算通过。
- Windows 下有限 Job 监督：观察到终态、退出码和自有进程清理确认才算完成。

`summary.json` 固定声明 `source-regressions-only`。CLI 的 lint 分数、
启动回执和模型推断都不是行为证据。证明适配器拒绝缺失/未知场景、
不匹配的测试、推断证据、跳过/不确定/待复审、空意图计划以及空 UI 结果。
CLI 内置的路径边界检查独立计数，不冒充第四个业务场景。

规格入口是 [运行约束合同](../../specs/beta-runtime-invariants.spec.md)，
需求入口是 [已确认需求](../../knowledge/requirements/req-beta-runtime-runtime-presentation-independence.md)。
`knowledge/` 的通用说明/模板由 CLI 生成，只有带来源的已确认需求才是本轮
产品约束；模板不构成新产品决策。

## 验收层次与 CI

| 层次 | 证明什么 | 不证明什么 |
|---|---|---|
| 知识/规格/计划 lint | 格式、引用与意图可编排 | 功能正确、需求完整 |
| 源码合同门禁 | 选定 Native/UI 回归及变更范围 | 打包/真实窗口、手机、审美、功耗 |
| 精确候选联调 | 指定 hash 的原生桥/窗口/文件链路 | 其他 ABI/签名/升级态 |
| 真机与人审 | 指定设备/网络/操作的行为与视觉 | 未测档案和完整 Beta |

工作流 `Beta Source Contracts` 只跑源码门禁，失败也保存七天证据；
不构建 APK/EXE，不打标签、不发布。远端实跑结果应单独回读，不能将本地
通过写成 GitHub Actions 已通过。尚未核实为受保护分支必需检查，不能宣称红灯
阻止一切 push/发布。轻量证明检查先于安装 CLI，触发路径包含依赖的 Core 和共享
展示组件；不根据一次源码绿宣称完整跨平台通过。现阶段不设全仓覆盖率或机械性能阈值。

## G 盘空间与构建保留（用户 2026-11-19 确认）

- 最多保留最新和上一版，共两个版本槽。同版不累计多个无用 staging。
  旧版通过精确 Git 提交、依赖锁、配置、ABI、签名来源和构建命令复建；
  可复建不承诺字节相同。必要的小型 hash/版本/复现索引保留。
- 在构建、测试、依赖安装、复制候选等可能增加占用的步骤前检查相关盘，
  不运行定时巡检（用户随后明确取消，已删除调度）。G 盘空闲 **<2 GiB**
  时立即清理确认不用的项目构建/缓存，无法安全回收则上报；正常空间无需
  全盘扫描或通知。
- 构建/测试前检查证据盘、缓存盘、临时盘；门禁低于 2 GiB 拒绝启动，
  不靠新增另一份巨型缓存规避门禁。Windows 同时要求空闲内存至少
  12 GiB 且 35%，单编译任务、单测试线程及有界链接并行。
- 删除前核实绝对目标、归属、活跃 Job/进程、锁和链接。Cargo 缓存可在
  确认未使用后用 `cargo clean --target-dir <精确的外部缓存路径>`。
  不跟随 junction 清理共享依赖，不与用户正在执行的删除互相竞态。
- 保留源码/Git、用户档案/原件、签名密钥和运行中候选。不能核实归属的
  `G:/.gradle` 等目录不清理；不能通过杀未知进程或 `git clean` 腾空间。

用户已经授权对不用的项目产物执行 GC，无需逐次再问。未知所有权、
锁定或没有可安全回收项时，报告剩余空间和阻塞原因，不扩大删除范围。
