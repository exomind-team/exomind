# ExoMind Issue 追踪罗盘（Compass）

> 目标：把用户一句“追踪下 XXXX”稳定转成可执行的 Issue 管理动作：先去重、再归类、再落地（新建或追加），并留下可迭代证据。

> **Agent 追踪权威章程**：`docs/agents/issue-tracking/charter.md`  
> 如与本罗盘有冲突，以章程为准。

## 1. 适用场景

- 用户报告 bug / 回归 / 体验缺陷。
- 用户补充新证据（日志、版本、设备、截图、复现路径）。
- 用户要求“新增 issue”或“看看是否已有 issue”。
- 架构/产品设计讨论。

## 2. 标准输入与输出

输入（最少）：
- 问题描述（原话）。

输入（理想）：
- 版本号、构建号、commit、设备/系统、复现步骤、预期结果、实际结果、影响范围。

输出（必须）：
- 去重结论（复用已有 / 新建）。
- 对应 Issue 编号与链接。
- 已追加的评论内容摘要（若复用）。
- 与相关 Issue 的关联（`related to` / `regression from` / `duplicates`）。
- 现状快照（`dev` 短 hash + 关键路径，项目根目录相对路径）。

## 3. 执行 SOP（6 步）

1. **抽取问题原子点**
   - 把用户描述拆为单个问题，避免把多问题塞进同一个 issue。
2. **去重检索**
   - 以“模块词 + 症状词 + 平台词 + 版本词”搜索 open/closed issue。
3. **核查 dev 现状**
   - 记录 `dev` 短 hash + 关键路径（相对路径）。
4. **决策路由**
   - 同主题且未解决：追加评论。
   - 历史已关闭但同症状复发：新建回归 issue，并链接旧 issue。
   - 主题重叠但根因不同：拆分新 issue，并互相关联。
5. **结构化落地**
   - 标题：`[平台/模块] 症状`，禁止模糊词。
   - 正文至少包含：背景、预期、实际、现状快照、验收标准、关联/依赖。
   - 关键路径必须保持项目根目录相对路径语义；在 issue / 评论正文里，展示形式应为可点击的 Markdown 链接。
6. **正文降噪与发布前复核**
   - issue / 评论里禁止裸贴 URL、禁止 `[https://...](https://...)`、禁止本地绝对路径。
   - 仓库文件、文档、workflow、报告引用必须写成简短命名的 Markdown 链接；若路径本身就是必要定位信息，可直接用相对路径作为链接文本，但仍必须是链接。
   - 发布前必须回读 `--body-file` 的临时 Markdown，检查是否残留不可点击的反引号路径或高噪音链接。
   - 当前仓库可用 `node scripts/check-issue-link-hygiene.cjs <body-file>` 做最小机械检查。
7. **关联图谱**
   - 在新旧 issue 互贴链接；同链路问题统一标注共享上下文（版本、数据链路、迁移窗口）。
8. **回报用户**
   - 明确说明：哪些是复用，哪些是新建，为什么。
   - 必含：决策说明 + 当前状态 + 下一步建议。

## 4. 去重决策矩阵

| 情况 | 动作 | 备注 |
|---|---|---|
| 已有 open issue 完全同问题 | 追加评论 | 不新建，避免分叉 |
| 已有 closed issue，但当前版本复现 | 新建 regression issue | 在标题/正文标注 `Regression` |
| 同模块、不同根因 | 新建 issue + 互链 | 防止单 issue 过载 |
| 多症状混杂、无法定位 | 默认强制拆分 | 信息不足时可先建聚合 issue 作为临时调度 |

## 5. Issue 模板（建议）

```md
## 背景
- 用户反馈：
- 影响版本：
- 设备/平台：

## 实际结果
-

## 期望结果
-

## 现状快照
- dev: <short-hash>
- 关键路径：
  - [src/xxx.ts](<repo-blob-url>)
  - [docs/xxx.md](<repo-blob-url>)

## 验收标准
- [ ] AC1
- [ ] AC2

## 关联/依赖
- 关联：#123 #456
- 阻塞：#789
- 子问题：#234
```

> Bug/回归类可补充：复现步骤、影响评估、初步分析。

## 7. `gh` 最小命令集

```bash
# 1) 检索（先 open，再 closed）
gh issue list --search "关键词" --state open --limit 30
gh issue list --search "关键词" --state closed --limit 30

# 2) 查看详情
gh issue view <id>

# 3) 新建
gh issue create --title "[模块] 问题标题" --body-file /tmp/issue.md

# 4) 编辑正文
gh issue edit <id> --body-file /tmp/issue.md

# 5) 追加评论
gh issue comment <id> --body-file /tmp/comment.md

# 6) 发布前检查正文链接卫生
node scripts/check-issue-link-hygiene.cjs /tmp/issue.md
```

依赖关系（blocked-by / sub-issue）请按章程中的 GraphQL 命令执行。

## 8. 质量红线（Do / Don’t）

Do：
- 一次回复里给出去重依据。
- 每个 issue 有可验证的验收标准。
- 对“数据不兼容/链路切换”类问题，写清时间窗与版本窗。
- 允许并鼓励多级 Markdown 列表与 mermaid 图表（复杂关系）。
- 仓库引用使用简短命名的 Markdown 链接，而不是裸 URL。
- 关键路径若需要保留定位语义，直接把 `src/...` 或 `docs/...` 作为链接文本，但不要裸写成普通文本。

Don’t：
- 不检索就直接新建。
- 一个 issue 混多个独立问题。
- 只写“无法复现”，不记录环境与假设。
- 不把本地绝对路径、裸 URL 或 URL 直出式链接文本发到 issue 正文/评论里。
- 不把 `docs/...md`、`src/...ts`、`.github/workflows/...yml` 只放在反引号里而不加链接。

## 9. 一句话指令（给 Agent）

当用户说“追踪下 XXXX”时，按以下顺序自动执行：
1. 抽取问题原子点。
2. 检索并判重（open + closed）。
3. 核查 dev 现状并记录快照。
4. 决策“追加/新建/回归/拆分”。
5. 在 GitHub 完成动作并互链相关 issue。
6. 回传编号、链接、决策理由、下一步建议。

可直接复用的执行口令：

```text
追踪下 <问题>：先查重（open/closed），核查 dev 现状并记录快照；有则追加并补证据；无则新建（含预期/实际/验收标准/关联依赖），并关联历史 issue。
```
