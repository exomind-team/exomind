# v0.5.x 日常核心能力迭代计划

> **状态**：`0.5.1` 已完成本地实现与隔离端到端验收，等待桌面日用验收；`0.5.2+` 尚未开始
> **规划基线**：计划起点 `dev@16d08627` / `0.5.0`；当前实施起点 `0.5.x@9aa7c5da`，应用版本 `0.5.1`
> **实施分支**：`0.5.x`；后续仍按一个用户可感知功能对应一个 fix 版本推进
> **关联 Issue**：#527、#532、#622、#702、#833、#868、#869、#879、#906、#963、#969
> **执行顺序**：`0.5.1 悬浮工作台` → `0.5.2 EventLog 完整恢复` → `0.5.3 响应式同步与能耗` → `0.5.4 桌面后台生命周期` → `0.5.5 快捷事件记录` → `0.5.6 设置搜索` → `0.5.7 Agent 配置热迭代`
> **版本纪律**：一个用户可感知功能对应一个 fix 版本；前一版本完成发布验收后才开始下一版本。紧急 hotfix 可以插队，但不得把后续功能并入当前 patch。
> **优先级例外**：#868 是 P0、#702 是 P1；`0.5.1` 先于 #868 是本轮唯一获准的 P0/P1 顺序例外，因为缺少 overlay 已经让桌面端无法升级和参与当前版本 dogfooding。`0.5.1` 不得扩展范围，发布后立即转入 #868 的 EventLog P0 子里程碑。

## Context

### 现场事实

计划制定时，桌面端因悬浮工作台缺失仍停留在 `0.4.22`，移动端已经使用 `0.5.0`。这不是一般的版本偏好，而是桌面日常工作流被功能回退阻断：当前时间块、计时状态、暂停/恢复/结束、任务启动、事件快速输入、结束反馈、始终置顶与快速返回主窗口都依赖旧悬浮工作台。截至 `0.5.1` 隔离联调，悬浮工作台已经恢复，用户已在桌面现场确认恢复程度符合预期；正式迁移仍以完整日用验收为准。

近两个月实际使用还暴露出四类高频问题。用户在本轮对话中提供的手机系统耗电截图可作为宏观现场基线：统计窗口总使用时长 `3 小时 27 分`，ExoMind 占应用耗电 `12.91%`（同图微信 `25.45%`、Edge `21.45%`）。截图未标注设备型号、系统版本和精确采集日期，后续基线实验必须补齐这些 provenance。该单次截图不能证明具体后台机制的因果，但足以说明能源治理需要进入正式验收，而不是只做源码推断。

1. 长时间跨度的 EventLog 不能稳定、完整地跨端恢复；这是数据完整性硬伤。
2. 固定 backfill 和重复网络尝试缺少清晰的能源预算，移动端有持续耗电压力。
3. 主窗口被快捷键唤起后仍占 Alt-Tab，关闭又容易退出进程；快捷记录不够“召之即来、用完即退”。
4. Agent 提示词和设置导航的迭代路径偏长：前者往往需要重新打包安装，后者难以快速定位 AI Registry/provider 配置。

因此，本轮不新建 `exomind-minimal` 分叉，也不先做插件平台或 #906 全量迁移。主线 `0.5.x` 直接把已验证的日常能力做尖、做稳，并让桌面与移动端恢复到同一版本。

### 当前迭代与 #906 的阶段关系

当前迭代和 #906 是前后两个阶段：

- **阶段一（本计划）**：在现有 RT SQLite、Mesh/Signal、profile/user scope 和 Tauri/WebView 边界内做小步修复；不先换底层数据结构。
- **阶段二（#906）**：阶段一达到进入条件后，再把已经验证的边界迁移为长期架构。#906 此时扮演架构不变量、迁移债务和目标状态的上位追踪器，而不是当前功能的前置 Epic。

本计划继续遵守 #906 中已经证明有价值的原则：UI 不拥有 runtime 真相或长期后台副作用；RT 是本机 apply 的最终权威；源对象与投影分离；兼容路径必须有限、单向并可删除。暂不实施 DSON、Proposal-first、Blackboard、Archive OS、多档案交互、Reticulum/iroh 或 ScriptHost。

### 迭代目标

1. `0.5.1` 发布后，桌面与移动端安装同一个 `0.5.1` 构建；桌面不再被锁在 `0.4.22`。
2. 长历史、断线、重启和中途失败场景下，EventLog 以稳定 ID 集合收敛，不再依赖每 15 秒全量快照碰运气。
3. 同步由真实事件触发并有界重试；用户可以对指定设备发起“立即同步”。
4. 桌面主窗口、悬浮工作台和快捷记录窗口各自职责清楚，隐藏、关闭到托盘和退出语义可预测。
5. 设置可搜索；内置 Agent 的系统提示词最终可作为配置迭代，而不需要重新编译安装。

### 本轮非目标

- 不建立第三方插件市场、动态脚本权限模型或完整 TypeScript Plugin Host。
- 不迁移到 DSON、Reticulum、iroh、PouchDB/CouchDB 或其他新同步底座。
- 不重做 EventLog/TimeBlock/Task 的领域模型，不主动改动底层 schema。
- 不恢复 `b5d01576` 删除的整批 Me、实时语音、测试页或旧 Workbench 页面。
- 不重新设计多档案；保留内部 scope/archive 能力，近期 UI 维持单档案主路径。

## Release 0.5.1：恢复桌面悬浮工作台

### 1.1 决策与历史理由

悬浮工作台在 `b5d01576` 中由星林随“大范围精简”有意删除，并非迁移遗漏。原决策在当时有合理目标：删除低使用率页面、实验入口和多入口维护成本，降低代码体积。本轮恢复不是否认那次清理，也不是 revert 整个提交。

恢复理由来自删除后的真实使用证据：

- 桌面端因缺失该能力持续停在 `0.4.22`，已经直接阻断版本统一和后续 dogfooding。
- 当前 Action Dock 只是 Windows AppBar/布局 PoC，缺少时间块、任务、EventLog 和反馈闭环，不能替代悬浮工作台。
- 悬浮工作台是可以独立开关、独立验证、未来也可模块化的原子桌面 surface；它不要求恢复被清理的整个 Workbench 产品面。

因此采用“能力回归、实现收敛”：以用户实际依赖的 `v0.4.22@b0e1c35d` 为能力基线，以删除前最后代码 `b5d01576^` 为提取源，保留删除前已经完成的 profile IPC、主窗口数据源和 RT readiness 修复；对接当前 dev 的 RT-first service 和 signal，不带回旧 owner、localStorage 真相或一秒全量刷新。

### 1.3 实施步骤

1. 用 `git show b5d01576^:<path>` 审阅并逐文件恢复上述原子制品；禁止整体 revert/cherry-pick `b5d01576`。
2. 恢复 Tauri window/capability：单实例、初始隐藏、`always_on_top`、`skip_taskbar`、无装饰、不可调整大小；Android/iOS 命令保持安全 no-op。
3. 接回当前 `TimeBlockService`、`TaskService`、`TaskTimerService`、`EventLogService` 和 `useSignalStream`；RT 未满足 `running && port > 0` 时只显示等待态，不挂载业务 controller/SSE。
4. 主窗口继续是 profile 和 runtime endpoint 的权威来源；overlay 不从独立 WebView localStorage 推断 scope，也不选择端口。
5. 恢复当前时间块、运行/暂停状态、剩余时间、开始任务、暂停/恢复/结束、结束反馈、EventLog 输入、最近事件、返回主窗口和位置保存。
6. 删除旧 controller 的每秒 `reloadAll()`；每秒只更新纯视觉倒计时。领域状态通过 RT Signal/跨 WebView 事件增量更新，#702 的正常目标延迟 `<500ms`。
7. 设置页提供可开关入口；关闭表示不显示/不预热该 surface，不改变领域数据和后台 runtime。
8. 保留当前 Action Dock，既不删除也不把它冒充恢复目标。

### 1.4 验证

所有 `0.5.x` 桌面开发、Tauri MCP、自动化端到端和后续人工验收都必须使用隔离档案，禁止直接复用当前 `0.4.22` 日用档案：

- 通过 Tauri dev manager 使用唯一实例名启动，使 app-data、runtime 与 WebView 数据目录落入该实例的独立目录。

### 1.6 当前实施与验收证据（2026-08-24）

实现已在 `0.5.x` 完成并将版本接线更新为 `0.5.1`。恢复采用 `b5d01576^` 的原子文件提取并适配当前 RT-first API，没有整体回滚精简提交；旧 controller 的每秒领域 `reloadAll()` 未恢复，每秒 tick 只更新视觉时钟。

自动验证：

- 悬浮工作台、设置 registry 与 Signal 节流相关的 12 个测试文件：`90 passed`。
- Rust 窗口位置与可见性测试：`5 passed`。
- `bun run build:web`：通过，产物包含独立 `now-workbench-overlay` 入口。
- `cargo check --manifest-path src-tauri/Cargo.toml`：通过，仅有仓库既有 warning。
- `bun run check:android:meta`：通过；悬浮窗口在 Android/iOS command 层保持 no-op。

Windows Tauri MCP bridge 端到端（官方 session 不可用时按 playbook 使用 raw bridge fallback）首先使用隔离实例 `overlay-051`：Web `1640`、HMR `1641`、RT `9344`、bridge `9443`、一次性档案 `profile-overlay051-1787565280330`。脚本在业务写入前验证了 main URL、RT endpoint、broker profile 和 overlay session。该轮功能链路通过，但复核发现 overlay WebView 尚未显式使用 dev-manager 数据目录：测试档案键写入了默认 WebView 目录中仅属于 `http://localhost:1640` origin 的记录。该记录没有覆盖 `0.4.22` 使用的 origin 或档案值，但仍不满足“测试目录完全隔离”的门槛，因此补上了 per-instance/per-window `data_directory` 后重新验收。初轮实测结果：

- 只创建一个 `now-workbench-overlay`，窗口可见且 `alwaysOnTop=true`；Action Dock/voice overlay 保持隐藏。
- overlay 快速记录写入 RT 成功，commit 后草稿清空。
- 主窗口开始时间块 → overlay 更新 `123ms`。
- overlay 暂停 → 主窗口与 RT 更新 `260ms`；继续为 `142ms`。
- overlay 结束并提交反馈 → 主窗口回到 idle `115ms`。
- 隐藏后重新打开复用同一窗口实例。

加固后的最终串行复测使用 `overlay-051-final`：Web `1650`、HMR `1651`、RT `9354`、bridge `9453`。启动写入前的内存门禁为总内存 `39.16 GiB`、可用 `19.04 GiB`（`48.6%`），仅运行一个 Tauri 实例与一个轻量 bridge 驱动，不再并行执行构建或测试。实例目录现场确认：

- app/runtime：`.tmp/tauri-dev-state/overlay-051-final/app-data/`
- main WebView：`.tmp/tauri-dev-state/overlay-051-final/webview/main/`
- overlay WebView：`.tmp/tauri-dev-state/overlay-051-final/webview/overlay/now-workbench-overlay/`

最终写入档案为 `profile-overlay051-final-1787569756740`；本次重试前的档案也带相同一次性前缀，未复用或切换到任何日用档案。main session/store、Rust broker、overlay session/store/broker 六处 profile 真值完全一致。最终实测结果：

- overlay singleton、可见、置顶；Action Dock 与 voice overlay 保持隐藏。
- 快捷事件写入并收到 commit，`17ms` 后可读，草稿随后清空。
- Task 经 RT signal 投影到 overlay：`9ms`。
- 主窗口开始 → overlay：`132ms`；主窗口暂停 → overlay：`154ms`。
- overlay 继续 → 主窗口/RT：`80ms`；overlay 结束并反馈 → 主窗口 idle：`158ms`。
- 隐藏 `2ms`、恢复 `4ms`，恢复后仍只有一个 overlay 窗口。

上述数值均低于本轮 `<500ms` 的跨 WebView 目标。测试过程中宿主机曾因并行验证蓝屏；这暴露的是验证编排缺陷，不是产品通过证据。Windows 验证现已明确改为“先内存门禁、后严格串行”，并写入 Tauri MCP playbook。

全仓 Vitest 基线仍为红：`460 passed / 40 failed / 9 skipped` 个文件，`3078 passed / 99 failed / 34 skipped` 个测试，并有 `236` 个环境/异步错误。按测试分诊规则复跑后，主要是历史 profile mock、旧行为期望、缺失 fixture、设置可见性夹具以及 happy-dom/React scheduler 状态污染；这些失败没有落在本次 overlay 生产文件，且本次 12 个聚焦文件全部通过。本 patch 不夹带这些无关修复，但必须把全仓基线治理作为独立测试债务处理。

## Release 0.5.2：长跨度 EventLog 完整恢复

### 2.1 问题定义

当前 `RtDomainBackfillCoordinator` 固定每 15 秒调用 backfill；EventLog recovery 对每个 peer 导出整个 SQLite snapshot 再 merge。该路径没有可审计的 per-peer EventLog 持久恢复进度，遇到长历史、断线重连、应用重启或中途失败时无法证明完整收敛。

#868 的原始范围还包含 Task、TimeBlock、Proposal 四域恢复。本 release 只交付其中最紧急的 **EventLog P0 子里程碑**，完成后不能关闭整个 #868：Task/TimeBlock 继续使用现有恢复路径，并在 `0.5.3` 接入统一响应式调度；Proposal 当前属于非目标，等恢复真实使用价值后再排期。该切片遵守“一个功能一个 fix”，也避免为满足 Issue 文字范围而把无用域混入数据修复。

本 patch 先修正确性，不先换底层数据结构。Obsidian LiveSync 值得借鉴的是“持久 checkpoint 后可续传、分批与背压、对等端立即同步、缓存 epoch/reset 检测”和“冲突时不猜测、不用 mtime 强行判新旧”的原则，而不是照搬 PouchDB revision tree。EventLog 以追加为主，当前目标是稳定 ID 的并集和保守冲突诊断。

参考：

- [Obsidian LiveSync 0.25：Fast Fetch checkpoint、streaming/backpressure 与 per-peer replication](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/releases/0.25.md)
- [Obsidian LiveSync 冲突规范：保守合并、重验 live leaves、不以 mtime 猜测](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/specs_conflict_resolution.md)

### 2.2 先写可重复失败场景

新增双 Runtime E2E，至少覆盖：

1. A 有 90 天合成 EventLog，B 首次配对后拉齐。
2. B 离线期间，A 同时新增“当前事件”和带旧 timestamp 的补录事件；重连后两者都到达 B。
3. A/B 离线期间分别追加，恢复后双方取得稳定 ID 并集。
4. 每个 batch apply 后故意中断；进程重启后从最后一次已提交 checkpoint 继续。
5. 同一 ID + 同一 payload 重复到达时幂等跳过。
6. 同一 ID + 不同 payload 时不得静默覆盖；保留本地记录并写入有界 conflict diagnostic，等待 #869 处理通用冲突合同。
7. checkpoint 丢失、peer identity 变化或 remote epoch/reset 时进入显式 full bootstrap，不静默跳过旧数据。

验收比较 RT 内的 `id -> canonical payload hash`、总数和 ID 集合，不以 UI 列表是否看见最近若干条作为完成证据。

### 2.3 最小恢复协议

在不主动改变 EventLog 表结构的前提下实现：

- 每个 `peer + profile/user scope + domain` 一个持久 checkpoint，存入现有 runtime config/mesh state；checkpoint 对调用方保持 opaque。
- RT 提供稳定的有界 batch 拉取，返回 `items`、`nextCursor`、`hasMore` 和 `remoteEpoch`。可先评估现有 `(timestamp,id)` keyset 能否满足 backdated event；若不能，必须先用失败测试证明，再单独提出最小 schema 变更，不得直接引入 DSON。
- 只有本地 transaction/batch 完整提交成功后才持久化 next checkpoint；拉取成功但 apply 失败时保持旧 checkpoint。
- 记录 ID 相同且 canonical payload 一致时幂等跳过；不同则拒绝隐式 LWW/overwrite，并写入固定容量的诊断状态。
- 每批有数量和字节上限；有 in-flight lock、取消、指数退避和最大重试窗口。
- 同步页增加指定设备的“立即同步”，显示本设备看到的 last success、last checkpoint、pending/error 和是否正在 full bootstrap。

### 2.4 验证

```powershell
bun run test -- --run tests/e2e/eventlog-backfill-multi-device.issue794.test.ts
bun run test -- --run tests/unit/services/rt-domain-backfill.service.test.ts
bun run test -- --run tests/unit/services/eventlog-backup.service.test.ts
cargo test --manifest-path crates/exomind-runtime/Cargo.toml eventlog
```

实际实施应新增独立的 long-history/restart E2E，并在计划回填中给出两 Runtime 的 exact-ID-set 对比结果。

### 2.5 完成门

- 四类失败场景（长历史、离线补录、中断续传、双端追加）均能确定性收敛。
- 不再靠周期性全 SQLite snapshot 才能恢复；snapshot 只保留为显式 bootstrap/repair 工具。
- “立即同步”可对指定设备发出请求并反馈完成/失败，而不是只刷新 UI。
- #869 的 EventLog 同 ID 冲突/删除合同已经冻结，并有“同 payload 幂等、异 payload 不静默覆盖”的测试证据；这是 `0.5.2` 的内部完成门，不是另一个并行 release。
- 只回填 #868 的 EventLog 子里程碑，保持 #868 OPEN，直到其余已确认需要的领域恢复条件完成或经治理明确移出范围。
- 若现有结构确实无法提供稳定恢复，必须提交可复现测试和边界报告；在报告审议前仍不进入 DSON 或新同步技术。

## Release 0.5.3：响应式同步与移动端能源预算

### 3.1 调度模型

把同步从固定周期拉取改为事件驱动：

- pairing confirmed；
- peer reachable/reconnected；
- 网络从 offline 到 online；
- 应用进入 foreground；
- 本地域对象 commit；
- 时间块结束；
- 用户对指定设备点击“立即同步”。

触发只负责 schedule，不直接并发执行。按 `peer + domain` 合并触发，复用单个 in-flight job；失败采用有界退避和 jitter。后台、前台、发现窗口、连接保活和 batch 大小都必须有明确预算。

### 3.2 删除轮询的条件

只有 `0.5.2` 的恢复测试稳定后，才删除 `src/ui/app/components/RtDomainBackfillCoordinator.tsx` 中 `BACKFILL_INTERVAL_MS = 15_000`。保留 `mount/focus/online` 等响应式入口，但让它们只投递 durable recovery job。

用户 EventLog 不承载网络重试日志；诊断写入固定容量、可清除、可导出的 sync diagnostic。失败不会丢掉 durable checkpoint，也不会无限保持 radio/network 活跃。

### 3.3 测量与验收

- Android 在相同设备、网络、屏幕与正常使用时段下，对比 `0.5.2`/`0.5.3` 的耗电占比、后台时长、唤醒次数和网络请求数；只把系统截图作为宏观参考，不把单次百分比当因果证明。
- 静置且无 peer/无 pending job 时，不出现固定 15 秒 domain backfill。
- 连续 20 次本地提交合并为有界的少量同步轮次，不建立 20 条并行连接。
- 网络断开时退避；网络恢复后立即恢复；应用退后台后遵守平台后台限制。
- PC/手机在长历史、断线和重启 E2E 中继续保持 exact-ID-set 收敛。

## ⚠️ 容易出错的关键点

1. `v0.4.22` 是能力基线，不一定是最佳代码提取点；提取应使用包含后续 profile/RT 修复的 `b5d01576^`，逐文件对比当前接口。
2. #702 不是“浮窗 focus 后刷新”；主窗口和独立 WebView 的 active block 必须靠 runtime signal/版本化事件即时一致。
3. 旧 overlay 的视觉倒计时和领域 reload 都是 1 秒 interval；只能保留前者，不能因为测试方便一起恢复。
4. `RtDomainBackfillCoordinator` 的 `focus/online` 触发本身不是问题，固定 15 秒全量 backfill 才是；重构后这些事件应 schedule 同一个 durable job。
5. EventLog 当前同 ID 写入存在 overwrite 风险；在冲突合同完成前必须保守拒绝异 payload，而不是根据用户 timestamp 推断胜者。
6. backdated EventLog 会破坏把“最大 timestamp”直接当复制进度的假设；checkpoint 必须由恢复协议定义并有 reset/bootstrap 语义。
7. checkpoint 必须在本地 apply commit 之后保存；顺序反过来会造成永久缺口。
8. 移动端不使用悬浮工作台，不代表可以跳过同版本回归；`0.5.1` 仍需 Android Web/Tauri 正常构建和日用验证。
9. “总结至少成功一次”比“绝不重试”更重要；Agent job 要幂等、有界且 durable，不能以单次请求上限制造漏总结。
10. 快捷记录窗口只有收到 canonical EventLog command 的 RT commit ack 才能清草稿并隐藏。
