# CRDT：冲突无关复制数据类型的深度研究报告

---

## 一、纵向分析：从分布式共识的裂缝中诞生

### 1. 问题的原点：为什么"同步"这件事如此之难

要理解 CRDT 为什么会诞生，需要回到一个困扰了分布式系统研究者几十年的根本问题：**在多个节点可以独立修改数据的系统中，如何确保所有节点最终看到一致的答案？**

这个问题看似抽象，实际上与每个使用云端协作工具的人密切相关。Google Docs 允许多人同时编辑一段文字；Figma 允许多个设计师同时操作一个设计文件；你的 iPhone 和 Mac 上的备忘录需要随时同步。这些场景的共同挑战是：**当多个设备或多个用户在没有中央协调者的情况下，同时对同一份数据做了修改，这些修改该如何合并？**

分布式系统研究者很早就发现，这个问题的答案取决于你愿意放弃什么。1998 年，UC Berkeley 的教授 Eric Brewer 提出了后来被证明的 CAP 定理：在一个分布式系统中，你最多只能同时满足**一致性（Consistency）**、**可用性（Availability）**和**分区容错性（Partition Tolerance）**中的两个。对于需要跨互联网协作的应用来说，网络分区是常态而非例外，因此实际的选择只剩两个：**要么牺牲可用性**（等待所有节点达成一致后才能响应），**要么牺牲一致性**（允许各节点暂时不一致，但最终收敛到相同状态）。

20 世纪 90 年代末到 21 世纪初，绝大多数商业系统选择了**强一致性路线**——以 Google Docs 为代表，通过一个中心服务器来"总控"所有操作，确保每个人的改动都经过同一个"仲裁者"的调解。这条路线的代价是：**服务器必须始终在线，所有流量必须经过服务器，用户的数据必须存放在服务商的电脑上**。

然而，一批学术研究者从另一个方向思考：如果我们能设计出一种**特殊的数据结构**，让任何两个副本之间的合并操作都"天然正确"——不需要中央协调者，不需要等待，不需要锁定——那会怎样？

这个问题的答案，最终催生了 CRDT。

---

### 2. 思想先驱：1970 年代末的萌芽

CRDT 的思想根源，可以追溯到 1979 年。彼时，伦敦大学学院的 Brian Randell 在研究**分布式操作系统**时，首次提出了"复制数据类型"（Replicated Data Type）的概念，提出了在多个节点间复制数据的基本问题。

此后，1981 年，Al辟T. Babaoglu 和 Keith Marzullo 在论文中证明了：对于某些**单调递增（monotonic）**的数据结构，复制后的合并可以不需要锁或协调——只要每个节点只追加信息而不覆盖信息，最终状态自然收敛。这一发现为后来的 CRDT 理论奠定了最早的数学直觉。

1991 年，Attiya 和 Welch 在一篇影响深远的论文中，进一步精确化了这些条件，明确了**交换性（commutativity）**——即操作的执行顺序不影响最终结果——是实现无冲突合并的关键性质。这些早期工作，构建了 CRDT 最终所需的概念地基。

---

### 3. 协作编辑之战：OT 与 CRDT 的暗中角力（1990s-2000s）

CRDT 的正式诞生，与**协作编辑（Collaborative Editing）**领域的一场长达二十年的技术战争密不可分。

1989 年，Chong (章嵚) 和 Sun 在 DEC 的研究团队发表了 OT（Operational Transformation，操作转换）算法，被 Google Docs 及其前身（最早是 IBM 的 "Orwell" 项目，后来演变为 Google Wave，再演变为 Google Docs）所采纳。OT 的核心思路是：**当两个用户同时做操作时，服务器会"变换"其中一个操作以适应另一个操作的结果**，从而保持所有客户端看到的文档一致。

Google Docs 的 OT 方案是工程上的巨大成功，但它有一个被人长期批评的**结构性缺陷**：OT 需要一个**中央服务器**来执行操作转换——没有服务器，OT 就无法工作。这不仅是架构上的集中化风险，也是理论上的一个软肋：OT 的正确性证明极其复杂，实践中很容易出现 corner case 导致文档"漂移"（drift），即所有客户端看似正常但实际上已经积累了微小的不一致。

这一痛点，正是 CRDT 研究者的出发点。

---

### 4. 关键突破：Marc Shapiro 与"最终一致性"研究团队（2005-2011）

CRDT 作为一个正式概念和技术体系的诞生，绕不开一个研究团队：**Marc Shapiro**（法国国家信息与自动化研究所 Inria）、**Nuno Preguiça**（葡萄牙 NOVA LINCS / CITI）、**Carlos Baquero**（葡萄牙米尼奥大学）和 **Marek Zawirski**（Inria）。

Marc Shapiro 当时在 Inria 的 REGAL 研究组（后合并为 LIP6 的一部分），同时也在微软研究院 Redmond 有合作关系（他后来在 2015 年前后加入微软研究院巴黎，长期主持微软的分布式系统研究）。Shapiro 的研究主线是**乐观复制（Optimistic Replication）**——一种"先写再说"的复制策略：允许各节点独立修改数据，事后通过某种机制收敛到一致状态，而不要求前台同步等待。

2006-2008 年间，Shapiro 团队与 Preguiça、Baquero 团队开始紧密合作，他们关注的核心问题是：**能否找到一组充分条件，使得任何满足这些条件的复制数据类型，都能保证最终一致性？** 如果能找到这样一组条件，开发者就可以自由设计各种数据类型，只要满足这些条件，就不用担心合并冲突。

2011 年 1 月 13 日，团队发表了具有里程碑意义的研位报告：**《A comprehensive study of Convergent and Commutative Replicated Data Types》**（INRIA RR-7506），由 Marc Shapiro、Nuno Preguiça、Carlos Baquero 和 Marek Zawirski 合著。这份 50 页的技术报告，首次系统性地：

1. **提出了 CRDT 的正式定义**——Conflict-free Replicated Data Types，冲突无关复制数据类型
2. **建立了 CRDT 的完整分类体系**，将所有 CRDT 分为两大类：
   - **CvRDT（Convergent Replicated Data Types，状态型）**：每个节点保存完整状态，合并时取两个状态的"合并"（join），要求状态空间是一个**半格（join-semilattice）**
   - **CmRDT（Commutative Replicated Data Types，操作型）**：节点间传递的是操作而非状态，合并时将操作"应用"到本地副本，要求操作满足**交换性**
3. **给出了多种具体 CRDT 实现**：G-Set（只读集合）、2P-Set（双向集合）、OR-Set（可观察移除集合）、LWW-Register（最后写入获胜寄存器）等

这份报告的下载量超过 **16.8 万次**（截至 2025 年），被引用超过数千次，成为分布式系统领域最广泛阅读的技术报告之一。

> 📄 来源：INRIA HAL, RR-7506, 2011年1月, hal-00902436

### 5. 从理论到实践：工业界的早期探索（2012-2016）

CRDT 走出学术圈进入工业界的第一批"使者"，是几家以分布式系统见长的基础设施公司。

**Basho 的 Riak KV**（约 2012 年）是第一个大规模商业采用的 CRDT 案例。Riak 是一个面向"最终一致性"场景的分布式 key-value 数据库，它引入了 CRDT 作为一等公民：开发者可以使用 G-Counter、PN-Counter、Set 等 CRDT 类型来构建应用，而无需自己处理冲突合并。Riak 的设计哲学与 CRDT 的天然契合度极高：它本来就允许节点之间的数据复制，CRDT 只是让它"合并不确定性"有了理论保障。

**SoundCloud 的 Roshi**（约 2014 年）在其分布式时间线系统中采用了 CRDT 思想来管理用户的时间线数据，实现跨数据中心的最终一致性复制。

**Facebook 的 OpenR**（2017 年开源）是一个用 Rust 写的分布式路由系统，内部使用了 CRDT 来管理路由信息，其论文《Asynchronous BFT and CRDT》详细描述了如何用 CRDT 实现拜占庭容错。

同期，微软的 **Azure Cosmos DB**（2017 年正式发布）宣布支持多主复制（multi-master replication），其底层大量使用了 CRDT 思想（特别是 LWW-Register 和多版本并发控制的变体）。Azure Cosmos DB 的"一致性级别"模型中，最低级别的"最终一致性"背后，就有 CRDT 的身影。

然而，这一阶段的 CRDT 应用，主要局限在**服务器端的基础设施**——没有人在终端用户的应用层面大规模使用 CRDT，直到几个关键产品的出现。

---

### 6. 协作工具革命：Figma 的破局（2015-2017）

在 CRDT 的工业应用史上，**Figma** 是一个不可绕过的重要节点。

Figma 成立于 2012 年，其联合创始人 Dylan Field 和 Evan Wallace 从一开始就想做一款"浏览器里的 Sketch"——一个基于 WebGL 的矢量设计工具，而且必须支持多人实时协作。但早期的 Figma 面临一个艰难的工程选择：协作引擎该用什么技术？

他们在 2016-2017 年的技术演进中，逐步构建了一套**自定义的 CRDT 实现**，专门针对设计文档的特殊语义进行了优化。Figma 的 CRDT 不是通用实现，而是针对"设计对象"（如图层、组件、样式）高度定制的数据结构。这使得 Figma 能够在保持文档复杂语义的同时，实现真正的去中心化协作。

值得注意的是，Figma 在 2019 年的博客文章中，详细描述了他们的技术路线，并明确表示：**他们的方案与 Google Docs 的 OT 有本质不同**——不需要中央服务器来"变换"操作，任何两个节点可以直接合并变更。Figma 的这篇博客，成为工程社区理解 CRDT 实用价值的重要参考文献。

2022 年 9 月，Adobe 宣布以约 **200 亿美元**收购 Figma。尽管这场收购在 2024 年因监管压力告吹（Adobe 支付了 10 亿美元反向解约金），但 Figma 的成功本身，已经证明了 CRDT 在高性能协作工具领域的工程可行性。

---

### 7. JavaScript 生态的 CRDT 爆发：Yjs 的崛起（2015-2021）

如果说 Figma 证明了 CRDT 在专有系统中的可行性，那么 **Yjs** 则证明了 CRDT 在开放生态中的普适性。

Yjs 由 **Kevin Jahns**（GitHub 用户名 dmonad）创建，是一个用 JavaScript/TypeScript 编写的**通用 CRDT 框架**。Jahns 从 2015 年开始开发 Yjs，最初只是个人项目，用于实现一个离线优先的笔记应用。随着项目的发展，他发现 CRDT 在 Web 生态中有巨大需求——每一个想做"像 Google Docs 一样协作"的 Web 应用，都需要一套可靠的冲突合并机制，而当时没有一个好用的开源库能同时满足"高性能"、"易于集成"和"支持多种编辑器"。

Yjs 的核心设计哲学是**"编辑器无关"**：Yjs 不绑定任何特定的编辑器或 UI 框架，而是定义了**Y.Doc**（文档）、**Y.Text**（文本）、**Y.Map**（映射）、**Y.Array**（数组）等基础数据类型，并提供与具体编辑器的适配层。目前 Yjs 支持 CodeMirror、Monaco Editor、ProseMirror、Slate、TipTap 等主流编辑器，覆盖了从代码编辑到富文本编辑的完整场景。

Yjs 的 GitHub 仓库显示（截至 2026 年初）：**约 21.6k Stars，762 Forks**，官方列出的使用方（companies and products using Yjs）超过 **50 家**，包括：

- **AFFiNE**：可替代 Notion 的开源协作工具，由新加坡团队开发
- **GitBook**：知名技术文档平台
- **Evernote**：知名笔记应用的某个版本
- **JupyterLab**：数据科学领域最流行的笔记本环境（通过 yjupyter）
- **AWS SageMaker**：亚马逊的机器学习平台（用于协作笔记本场景）
- **Linear**：被广泛使用的项目管理工具
- **NextCloud**：开源云存储平台
- **Liveblocks**：实时协作 API 服务（商业产品）
- **Hocuspocus**：Yjs 的服务端解决方案

Yjs 的成功还催生了一个**商业生态**。Jahns 本人通过 GitHub Sponsors 提供商业支持合同，多家初创公司（如 Liveblocks、Partykit）以 Yjs 为核心构建商业产品。这使得 CRDT 从一个纯学术概念，变成了一个有可持续商业回报的开放基础设施。

### 8. 学术-工程的桥梁：Automerge 与 Ink & Switch（2017-2023）

与 Yjs 并行推进的另一个重要实现是 **Automerge**，由 **Ink & Switch** 公司（一家专注"本地优先软件"的研究型创业工作室）开发和维护。

Ink & Switch 的创始团队包括 **Martin Kleppmann**（剑桥大学研究员、《Designing Data-Intensive Applications》的作者）、**Adam Wiggins**（Heroku 的联合创始人）等人。Kleppmann 是 CRDT 学术研究的重要贡献者：2016 年，他与 Alastair Beresford 发表了 **《A Conflict-Free Replicated JSON Datatype》**（IEEE TPDS 2017），首次将 CRDT 的数学保证扩展到了 JSON 这种"现实世界中最常用的数据格式"，解决了任意嵌套的 map 和 list 类型的并发修改合并问题。

2017 年，Ink & Switch 基于这篇论文的成果，开发了 Automerge——一个与 Yjs 几乎同时起步的 JavaScript CRDT 实现。Automerge 的定位与 Yjs 有明显不同：

- **Yjs** 追求极致的**性能和内存效率**，文档紧凑，同步速度快
- **Automerge** 追求**完整的类型安全**和**易于调试**，内置了变更历史追踪和快照功能

2019 年 4 月，Kleppmann 联合 Wiggins、Peter van Hardenberg 和 Mark McGranaghan发表了著名的 **"Local-first software: You own your data, in spite of the cloud"**（Onward! 2019 会议论文），系统性地论证了 CRDT 是实现"本地优先软件"——即同时具备"协作能力"和"用户数据主权"——的**基础技术设施**。这篇论文的影响力远超学术界，直接影响了此后数年大量笔记、文档、代码协作工具的产品决策。

2021 年，Ink & Switch 发布了 **Automerge v2**，2023 年进一步发布 **Automerge v3**，实现了约 **10 倍的内存使用量降低**，并正式推出了商业化支持服务。Automerge 的 v3 版本同时支持 WebAssembly 编译，使 Node.js 和浏览器环境的性能差距大幅缩小。

### 9. 2020 年后的 CRDT 生态：爆发与分化（2020-2026）

2020 年新冠疫情引发的远程办公潮，极大地加速了实时协作工具的普及，也将 CRDT 推向了更广泛的开发者认知。

这一阶段，CRDT 生态出现了明显的**分化和深化**：

**框架层面**，形成了几个主要的技术路线：
- **Yjs 路线**：高性能、编辑器无关、以速度和内存效率为核心
- **Automerge 路线**：类型安全、开发者体验、以可调试性和完整性为核心
- **Diamond Types**（2020 年）：专注于**最优操作转换**，试图在 CRDT 的合并保证和 OT 的空间效率之间找到新的平衡点
- **Collabs**（Google）：Google 内部的 CRDT 框架，已在 Google Docs 的某些组件中使用

**数据库层面**，CRDT 的影响已深入主流数据库：
- **Redis 6.2+** 引入了 CRDT 感知的复制机制
- **CouchDB 3.0** 强化了 CRDT 基础的多主复制
- **FoundationDB**、**YugabyteDB** 等 NewSQL 数据库在多区域部署中借鉴了 CRDT 的冲突无关合并思想
- **ElectricSQL**（2022 年）将 CRDT 用于本地优先的 SQLite 同步，构建了"局部 SQLite + 云端 PostgreSQL"的混合架构

**标准层面**，2023-2024 年，IETF 和 W3C 开始关注 CRDT 在**去中心化网络**（ActivityPub 的扩展、WebRTC DataChannel 的 CRDT 层）中的应用。W3C 的 **Mubi** 工作组和 IETF 的 **DCRG**（Decentralized and Collaborative Research）小组均将 CRDT 列为去中心化社交协议的关键候选技术。

**中国市场的采用**方面，字节跳动的飞书文档、腾讯文档等产品的底层协作引擎，虽然官方未完全披露技术选型，但从功能特征（离线编辑、跨设备同步、多人实时协作）判断，内部实现与 CRDT 的设计思想高度一致。Notion 的亚洲竞争者——包括**我来 wolai**（已被字节收购并整合进飞书）、**Craft**（中国团队）——也在内部采用了类似的机制。

### 10. 演进逻辑：为什么 CRDT 最终胜出

回顾 CRDT 从学术概念到工业基础设施的十五年历程，可以清晰地看到三条驱动线索：

**第一条：理论基础是根本**。CRDT 的优势在于，它将"无冲突合并"这个问题从工程实践层面，拔高到了**数学证明层面**。只要一个数据结构的操作满足交换性、结合性和幂等性（对于 CmRDT）或状态空间是半格（对于 CvRDT），就能保证最终一致性，无需任何运行时协调。这不是"碰巧能用"，而是"证明了一定能用"。这种理论保证，是 OT 所不具备的——OT 的正确性依赖复杂的转换函数，历史上多次出现已部署系统因 corner case 而出现文档漂移的问题。

**第二条：去中心化需求是催化剂**。随着终端设备计算能力的增强和用户对隐私、数据主权的意识提升，"服务器是唯一真相来源"的架构越来越不被接受。CRDT 的"无需中央服务器"特性，从一个技术优势变成了商业卖点。

**第三条：Web 生态的开放性是关键催化剂**。Yjs 和 Automerge 的开放生态，使得任何一个前端开发者，不需要懂分布式系统理论，就可以用几行代码将 CRDT 集成到自己的应用中。这种**工程上的民主化**，是将 CRDT 从少数大公司的专有实现变成公共基础设施的关键一步。

## 二、横向分析：CRDT 赛道的版图与竞品

### 1. 赛道的本质判断

在深入对比之前，需要先明确 CRDT 所处的赛道本质。

CRDT 不是一种单一产品，而是一个**技术基础设施层**。它解决的问题是：任何需要在多个节点（设备/用户）之间**同步和合并数据**的应用，都可以基于 CRDT 来构建。这意味着 CRDT 的"竞品"不是某个具体产品，而是不同的**同步技术路线**。

具体而言，CRDT 所在的赛道，可以被定义为**"去中心化数据同步与合并技术"**。在这个赛道上，CRDT 面临的主要竞争路线有三种：

- **Operational Transformation（OT，操作转换）**：Google Docs 等产品使用的路线
- **最终一致性数据库的多主复制（Multi-master replication）**：Riak、CouchDB 等
- **去中心化文件系统/版本控制（Git-like）**：内容寻址存储 + 合并语义

其中，OT 是与 CRDT 关系最复杂、也最值得深入分析的竞争对手。

---

### 2. 核心维度对比：Yjs vs Automerge vs Diamond Types

在 CRDT 开源实现这个子赛道上，真正形成实质性竞争的，主要是三个项目。

#### 2.1 Yjs：速度与生态的双重王者

**创建者**：Kevin Jahns（个人开发者，德国），GitHub 托管
**技术栈**：JavaScript / TypeScript，支持 Node.js 和所有主流浏览器
**Star 数**：约 21.6k（截至 2026 年初）
**最新动态**：活跃维护中，2024-2025 年持续更新

**核心优势**：

Yjs 的首要设计目标是**性能**。在 CRDT 领域，长期存在一个 trade-off：**合并保证越强，内存开销和数据体积通常越大**（因为需要记录所有操作历史以支持任意两个副本之间的合并）。Yjs 在这方面做了大量工程优化：使用基于 LEB128 编码的二进制格式（Yjs 使用的是优化的二进制序列化格式，而非 JSON），对常用操作进行压缩，以及精心设计的数据结构来减少冗余存储。

在实际 benchmarks 中，Yjs 通常比 Automerge 快一个数量级，内存占用也更少。这使得 Yjs 特别适合对性能敏感的 Web 应用场景——比如在线代码编辑器（代码文件可能很大），或者需要同时支持数十个并发用户的实时协作场景。

Yjs 的第二个优势是**生态覆盖广度**。它的"编辑器无关"设计，使其能同时服务于：
- 代码编辑器（CodeMirror 6, Monaco Editor）
- 富文本编辑器（ProseMirror, TipTap）
- 白板（通过自定义 binding）
- 普通数据结构（Y.Doc, Y.Map, Y.Array）

这种"大一统"策略，使得 Yjs 成为事实上的 **Web 协作 SDK 标准**。

**用户口碑与槽点**：

Yjs 在开发者社区享有极高声誉。在 GitHub、Discord 和 Twitter/X 上，开发者对 Yjs 的评价普遍积极：安装简单、API 直观、性能出色。但也有几个公认的槽点：

1. **文档质量参差不齐**。Yjs 的官方文档相对简洁，但对于复杂场景（如自定义 CRDT 类型、处理特定冲突场景）的说明不够充分，开发者经常需要在 Discord 群里提问才能找到答案。

2. **缺少内置的"服务发现"机制**。Yjs 负责 CRDT 本身，但**谁来广播更新、谁来作为节点间的通信桥梁**，完全交给开发者自己实现。Yjs 提供了 `y-websocket`（基于 WebSocket 的同步）等官方"连接器"，但这些连接器的生产环境部署需要开发者自己做决策（单机还是集群，消息如何路由等）。

3. **二进制格式的不透明性**。Yjs 的内部数据格式是高度压缩的二进制，虽然效率高，但当出现问题时，开发者很难直接"看"懂数据状态，调试成本高。这与 Automerge 的"人类可读的 JSON-like"格式形成了对比。

4. **缺少变更历史和快照的内置支持**（直到 2024 年的更新才有所改善）。对于需要"版本回溯"功能的场景，Yjs 需要搭配额外的工具（如 `y-indexeddb` + 外部版本存储）。

#### 2.2 Automerge：类型安全与可调试性的坚守者

**创建者**：Ink & Switch（Martin Kleppmann 等）
**技术栈**：JavaScript / TypeScript，支持 WebAssembly（v3）
**Star 数**：约 7.5k
**最新动态**：2023 年发布 v3，持续活跃

**核心优势**：

Automerge 的设计哲学与 Yjs 形成了鲜明对比。如果说 Yjs 是"让 CRDT 跑得更快"，Automerge 就是"让 CRDT 更容易被正确使用"。

Automerge 的核心创新在于**类型安全的文档模型**：开发者可以定义一个 TypeScript 类型（interface），Automerge 会确保合并过程中类型不丢失、不损坏。这对于构建复杂应用（不只是编辑器，还有协作式数据库、多人表单等）至关重要——你可以在文档中放入任意嵌套的结构，Automerge 会忠实地维护你的类型承诺。

Automerge 的另一个差异化特性是**内置的变更历史和快照**。在 Automerge 中，每一次修改都会生成一个"变更（change）"对象，包含操作的完整信息。这使得：
- 可以随时重建文档在任何时间点的状态（"时间旅行调试"）
- 可以审计每个用户的操作历史
- 可以构建"像 Git 一样"的版本分支和合并

这种完整性保证，是以性能为代价换来的——Automerge v3 声称将内存使用量降低到原来的 1/10，但与 Yjs 相比仍有差距。

**与 Yjs 的关键区别**：Automerge 的同步格式是**可验证的**——你不仅可以合并两个状态，还可以验证某个变更序列是否"正确"（即是否符合 Automerge 的合并语义）。这在需要**审计和合规**的场景中特别有价值，比如医疗记录、金融文档的协作编辑。

**用户口碑与槽点**：

Automerge 在学术圈和"严谨派"开发者中有很高声望——Martin Kleppmann 的影响力为 Automerge 带来了天然的权威性。Automerge 特别受那些"做正确的事情"优先于"快速发布"的团队青睐。

槽点主要集中在：
1. **性能差距明显**。在 Automerge v3 之前，其性能（特别是内存使用）是一个显著问题。v3 虽然大幅改善，但在大规模文档（如大型代码文件、复杂设计文件）场景下，仍然不如 Yjs。
2. **JavaScript-first 的包袱**。Automerge 起源于 Ink & Switch 的 JavaScript 研究项目，其核心数据模型在设计时受 JavaScript 动态类型的限制，虽然后来引入了 TypeScript 支持，但底层架构的适配并不完美。
3. **社区规模远小于 Yjs**。Yjs 的 Stars 数是 Automerge 的近 3 倍，生态系统（第三方 binding、连接器、商业服务等）的丰富度也明显更胜一筹。

#### 2.3 Diamond Types：最小化 overhead 的挑战者

**创建者**：Arthur Peters（个人开发者），GitHub 托管
**技术栈**：Rust（核心）/ JavaScript wrapper
**Star 数**：约 1.2k
**最新动态**：活跃，但项目规模较小

Diamond Types 是 2020 年出现的一个较新的实现，其核心理念是**解决 CRDT 的"存储开销"问题**——传统 CRDT（无论是 Yjs 还是 Automerge）都需要存储完整的操作历史，以便任意两个副本之间可以合并。但 Diamond Types 发现：对于**顺序文档编辑**（最常见的协作场景），其实不需要完整的操作历史，只需要记录**相对顺序关系**，就能实现正确的合并。

Diamond Types 的技术基础是**最小化 CRDT（Minimal CRDT）** 学术研究成果，其核心论文是 2019 年的工作。它在纯文本协作编辑场景下，能将存储空间降低到 Yjs 的约 1/10，同时保持相同的合并正确性。

**局限性**：
- Diamond Types 目前只支持**序列（sequence）数据类型**——即线性文档（文本）。它不能处理任意嵌套的 JSON-like 结构。因此，它的适用场景更窄：主要适合"在线文本编辑器"这个垂直场景。
- 项目规模小，只有 1 个主要维护者，社区支持有限。
- Rust 核心虽然性能优秀，但 JavaScript wrapper 的成熟度不如 Yjs 的原生 JS 实现。

### 3. CRDT vs OT：两条技术路线的深层对比

CRDT 与 OT 的关系，不是简单的"替代"，而更像是"演进"与"并行"。

#### 3.1 技术路线的根本差异

| 维度 | CRDT | Operational Transformation |
|------|-------|---------------------------|
| **协调需求** | 无需中央协调者 | 需要中央服务器执行转换 |
| **理论基础** | 数学证明（交换性/半格） | 工程启发式（操作变换函数） |
| **正确性保证** | 理论上绝对保证 | 工程上依赖实现的正确性 |
| **适用场景** | 点对点、去中心化 | 客户端-服务器架构 |
| **历史存储** | 必须保留（支持任意合并） | 不需要（服务器顺序即权威） |
| **扩展到任意数据类型** | 理论可行（但实现复杂） | 困难（OT 变换函数需针对每种操作设计） |

#### 3.2 Google Docs 的"OT 悖论"

Google Docs 是 OT 最著名的应用，也是最容易被用来"反驳"CRDT 的案例——"Google Docs 用 OT 不是很成功吗？"

然而，深入分析会发现：Google Docs 之所以用 OT，更多是一个**历史路径依赖**，而非 OT 的优越性。

Google Docs 的前身 Google Wave 项目始于 2009 年，当时的技术生态中，CRDT 还只是一个刚被提出的学术概念（2011 年才正式命名），缺乏工业级实现。Google Wave 的团队需要在"现实的时间压力"下构建一个功能完整的协作编辑器，选择 OT 是一个合理的历史决定——他们没有别的选择。

Google Docs 使用 OT 付出的隐性代价是：
1. **服务器必须始终在线且参与每次操作**——没有服务器，Google Docs 的协作功能完全失效。
2. **服务器端需要维护复杂的变换状态**，随着并发用户增加，服务器的计算开销呈非线性增长。
3. **Google 内部多次出现过文档不一致的 bug**（虽然是小概率事件），这些 bug 的根源往往在于 OT 变换函数在 corner case 上的不完整性。

CRDT 路线则完全规避了这些问题。Figma 的实践已经证明，同等复杂度的协作设计文档，使用 CRDT 可以实现**更强的正确性保证，同时完全去中心化**。

**总结判断**：在**新的协作产品**中，CRDT 已经是明显的主流选择。OT 的优势在于**向后兼容性**（Google Docs 等已有系统不会重写），以及在**客户端-服务器模型**下 OT 的实现更简单。对于全新的项目，选择 CRDT 几乎在所有维度上都是更优的决策。

### 4. CRDT 在数据库赛道的竞争版图

CRDT 的另一种竞争，来自**数据库层面的多主复制方案**。

| 产品 | CRDT 定位 | 目标用户 | 核心特点 |
|------|-----------|----------|----------|
| **Riak KV** | 一等公民 | 需要强可用性的分布式系统 | 开源，G-Set/PN-Counter/2P-Set 等内置支持 |
| **Azure Cosmos DB** | 底层机制 | 云原生应用，多区域部署 | 多主复制，CRDT 用于冲突解决 |
| **CouchDB 3.0** | 基础机制 | 需要离线优先的 Web 应用 | 多主复制，但需要手动解决冲突 |
| **ElectricSQL** | 创新者 | 需要本地 SQLite + 云端同步的应用 | CRDT 用于 SQLite 行级同步 |
| **Redis (with CRDT module)** | 实验性 | 需要键值级别最终一致性的系统 | 实验性模块，社区版不支持 |
| **YugabyteDB** | 借鉴思想 | 需要水平扩展的 NewSQL | 多主复制借鉴了 CRDT 的最终一致性保证 |

这一赛道中，**ElectricSQL** 特别值得关注。它于 2022 年正式发布，将 CRDT 的应用边界从"文档/编辑器"扩展到了"关系型数据库的行级同步"。ElectricSQL 的核心洞察是：绝大多数应用不需要协作编辑整篇文档，而是需要**协作编辑某个数据库行**（比如一个任务的状态、一条客户记录）。ElectricSQL 通过让每个 SQLite 数据库行成为一个微型 CRDT，实现了这一目标，同时保留了 SQL 的全部表达能力。

### 5. 生态位分析：谁在用 CRDT，为什么

通过梳理 CRDT 的主要用户，可以将 CRDT 的应用格局分为三个圈层：

**第一圈层：实时协作工具（直接受益者）**

这一圈层的用户，直接将 CRDT 作为产品的核心技术栈。代表产品：
- **Figma**（设计协作）：自定义 CRDT，用于矢量图形对象的并发编辑
- **AFFiNE**（笔记/文档）：基于 Yjs 的富文本和块级协作
- **Liveblocks**（B2B SaaS）：以 Yjs 为核心的实时协作 API
- **JupyterLab**（数据科学）：通过 yjupyter 实现多人同时编辑笔记本

**第二圈层：数据同步基础设施（间接使用者）**

这一圈层的用户，使用 CRDT 来解决"多设备、多节点数据同步"的问题，虽然终端用户不一定感知到。
- **Apple Notes / iWork**：跨设备同步（具体实现未公开，但功能特征高度吻合）
- **Microsoft Outlook "Clutter"功能**：邮箱分类的跨设备同步
- **AWS 的部分服务**：特定场景下的最终一致性保证

**第三圈层：去中心化网络（新兴探索者）**

CRDT 在 Web3 和去中心化协议中找到了新的应用场景，因为 CRDT 的"无需中央协调"特性与去中心化哲学天然契合：
- **Scuttlebutt**（去中心化社交网络）：使用 CRDT 管理用户的时间线和关系图谱
- **Secure Scuttlebutt 协议**：消息同步机制基于 CRDT
- **Element（Matrix 协议）**：端到端加密消息的离线同步
- **ActivityPub 扩展提案**：W3C 正在讨论将 CRDT 作为联邦社交网络（如 Mastodon 的后继协议）的标准数据同步机制

### 6. CRDT 当前竞争格局的综合判断

**CRDT 的"无竞品"本质**

从严格的定义上说，CRDT **没有**一个在"技术路线"层面完全对等的直接竞争者。CRDT 所提供的"数学保证的、无需协调的、最终一致的并发修改合并"，在其他主流技术路线中（OT、传统多主复制、Git-like 合并）都无法完整实现——要么需要中央协调，要么无法保证数学正确性，要么无法处理任意数据类型。

CRDT 的"竞争对手"，更多是**不同抽象层次上的替代方案**：
- **如果你的问题是"我如何让多人协作编辑文本"**：替代方案是 Google Docs API（闭源、中心化），或自己实现 OT（复杂度高，正确性难以保证）
- **如果你的问题是"我如何让数据在多设备间同步"**：替代方案是 Firebase Realtime Database / CloudKit（中心化、有厂商锁定风险）
- **如果你的问题是"我如何做去中心化的数据管理"**：替代方案是 IPFS + 自己设计合并逻辑（复杂度极高）

CRDT 的战略护城河在于：**它同时解决了上述所有问题**，而且是在一个统一的数学框架下。这使得 CRDT 不是一个"可选方案"，而是一个**必要的基础设施层**。

**未来最可能的竞争来源**

CRDT 未来最可能受到挑战的方向，不是来自同类技术路线，而是来自 **LLM（大型语言模型）+ 代理架构**的降维打击。

如果未来出现这样的产品："你的文档/代码由一个 AI 代理管理，它可以理解冲突、解决歧义、自动合并不同人的贡献"——那 CRDT 的价值主张将受到重新审视。但这一场景的实现本身面临巨大挑战（LLM 的推理延迟、Token 消耗、确定性保证），至少在短期内（3-5 年），CRDT 仍将是协作数据同步的首选技术基础设施。

## 三、横纵交汇：CRDT 的现在位置与未来走向

### 1. 十五年回望：CRDT 走过的路

CRDT 从 2011 年的 50 页技术报告，到 2026 年成为数十亿用户日常使用的技术的底层基础设施，走过的路径可以用一个词来概括：**从证明到普及**。

2011-2015 年是**理论验证期**：Marc Shapiro 团队的工作证明了 CRDT 的数学可行性，但工业界普遍持观望态度——"理论上很美，但能用在生产环境吗？"

2015-2019 年是**工程验证期**：Yjs 和 Automerge 的出现，将 CRDT 从"需要分布式系统 PhD 才能实现"变成了"npm install yjs，五行代码集成"。Figma 的成功则证明了 CRDT 在高性能产品中与 OT 相比的优越性。

2019-2023 年是**生态扩张期**：Yjs 生态爆炸，Liveblocks 等商业服务出现，ElectricSQL 将 CRDT 带入关系型数据库，Local-first 运动赋予 CRDT 更宏观的哲学叙事。

2024 年至今是**主流化期**：CRDT 已成为实时协作工具的事实标准。新的协作产品（无论是笔记、文档、代码编辑器还是白板）如果不使用 CRDT，就需要"发明一个新的 CRDT"——这本身就是对 CRDT 作为基础设施地位的最好背书。

### 2. 当前坐标：基础设施层的"隐形冠军"

CRDT 目前在整个软件栈中的位置，是**"隐形冠军"**——它的价值巨大，但普通用户几乎感知不到它的存在。

CRDT 处于三个重要趋势的交汇点：

- **远程办公 + 实时协作常态化**：疫情后的工作模式变革，使得"多人同时编辑同一份文档"从特例变成了常态。
- **数据主权和隐私意识提升**：用户和监管机构越来越不能接受"我的数据存在别人的服务器上"。
- **去中心化和本地优先理念的扩散**：从区块链到 ActivityPub，"不依赖中央服务器"的价值主张正在获得更广泛的认同。

这三个趋势的交汇，使得 CRDT 的战略价值远超其作为一个技术概念的影响力。

### 3. 未竟之路：CRDT 面临的四大挑战

CRDT 虽然已经成为基础设施，但它的演进远未完成。当前 CRDT 面临四个尚未解决的深层挑战：

**挑战一：存储 overhead 问题**。CRDT 为了支持任意两个副本之间的合并，必须保留所有历史操作。这使得 CRDT 的存储需求随时间线性增长。对于大型文档（如数千页的设计文件），这是一个实质性的瓶颈。Diamond Types 试图解决这个问题，但目前只能处理序列类型，适用范围有限。

**挑战二：语义丰富性的天花板**。CRDT 能保证"无冲突合并"，但"无冲突"不等于"语义正确"。例如：两个用户同时将一个图层的颜色从"红色"改为"蓝色"和"绿色"，CRDT 会忠实地记录这两个操作（通过 LWW-Register 选择其中一个），但无论选哪个，都可能不是用户真正想要的——用户可能希望"保留最后一个操作"但这又引入了时间戳依赖的脆弱性。**如何让 CRDT 的语义与人类协作意图对齐**，仍是一个活跃的研究课题。

**挑战三：查询和索引的难题**。CRDT 的合并操作天然适合"追加"类操作，但**范围查询**（"找出所有满足条件 X 的记录"）在 CRDT 模型下变得极其困难——因为你无法在合并前知道哪些记录会被创建。这一挑战在需要"协作式数据库"的应用（如 Figma 的组件库搜索）中尤为突出，目前的解决方案都需要在 CRDT 之上引入额外的索引层，破坏了 CRDT 的纯粹性。

**挑战四：安全性和访问控制**。CRDT 的"任何节点都可以自由合并"的特性，与**权限控制**的需求存在根本矛盾——如果你只想让特定用户修改特定内容，CRDT 的开放合并语义就需要额外的"验证层"来约束每个操作的合法性。目前的实现（如 Yjs 的 `Awareness` 协议）只能做到基本的在线状态广播，无法实现细粒度的 RBAC（基于角色的访问控制）。

### 4. 未来走向：2026-2030 年的五个趋势

基于对 CRDT 发展脉络和当前竞争格局的分析，可以对 CRDT 的未来走向做出以下判断：

**趋势一：CRDT 将成为"协作协议"的标准化组件**。就像 TLS/SSL 成为 HTTP 的标配一样，CRDT（或 CRDT 的某种标准化子集）将成为所有支持实时协作的应用的内部协议层。IETF 和 W3C 已经开始相关讨论，5 年内可能出现 RFC 级别的标准。

**趋势二：Yjs 将主导 Web 生态，Automerge 将主导需要完整性和可审计性的场景**。两者的定位互补而非竞争。Diamond Types 可能在文本编辑的垂直场景中获得一定市场份额。

**趋势三：ElectricSQL 等"CRDT + 关系数据库"的产品将打开企业市场**。目前 CRDT 的使用者主要是 SaaS 和工具类产品，企业级应用（如 ERP、CRM）的协作功能仍然依赖传统的"锁定-协调"模型。如果 CRDT 能与 SQL 深度整合，将打开一个巨大的增量市场。

**趋势四：LLM 协作界面将成为 CRDT 的新战场**。当 AI 代理参与文档编辑时，多方（包括 AI 和人类）同时修改文档的并发问题将以新的形式出现。CRDT 在这个场景下的适用性是一个开放问题，但 Yjs 等框架已经开始探索"AI 感知"的协作扩展。

**趋势五：去中心化协议中的 CRDT 将走向成熟**。Scuttlebutt 已经证明了 CRDT 在去中心化社交网络中的可行性，ActivityPub 的 CRDT 扩展如果被主流去中心化平台（Mastodon、PixelFed 等）采纳，将为 CRDT 打开一个全新的亿级用户市场。

### 5. 终极判断

CRDT 不是一个会"消失"的技术，因为它解决的问题——**如何让多个独立的实体对同一份数据做修改而不产生灾难性的冲突**——是一个**永恒的工程问题**。

CRDT 的伟大之处在于：它不是用更复杂的协调机制来回避冲突，而是**将冲突的可能性内化为数据结构的设计原则**，从而从根本上消灭了冲突。这种思路，与计算机科学中许多最优雅的解决方案一脉相承——从哈希函数到事务内存。

未来，无论软件架构如何演进（从集中式到分布式，从中心化到去中心化，从人类协作到人机协作），**需要协调多个参与方对共享状态的修改**这一基本需求不会消失。CRDT 为这个需求提供了一个数学上严谨、工程上可行的答案——这正是它将长期保持生命力的根本原因。
