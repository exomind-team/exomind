## 结论先行

### 结论 1：要做单向兼容，但只做一次

对旧的空历史任务，应该提供一次性兼容能力，比“完全不兼容”更合理。

但兼容的形式不是：

- 时间线页面加载时临时回退去读 EventLog
- UI 每次打开都现场补历史
- 恢复 `/tasks/timeline` 对 EventLog 的运行期依赖

而是：

- 在任务域内部增加一个 one-shot repair
- 只把旧事件单向重建为 `Task.statusTransitions`
- repair 完成后，时间线继续只认任务域状态历史

### 结论 2：repair 不应新增用户入口

这次兼容不值得为此新增：

- 单独的设置页按钮
- 单独的用户交互弹窗
- 单独的公开 API 端点

最小合理做法是把 repair 接入现有任务域内部链路：

- runtime 启动 / 任务 store 初始化后的内部 repair
- 或“某个 scope 第一次进入任务域读路径时”的内部 ensure-repair
- 以及 legacy 导入完成后的收尾 repair

无论采用哪种细节落点，本质都应是：

- **现有链路内的内部 one-shot 过程**
- 而不是“新增一个用户可见的 repair 入口”

### 结论 3：repair 的“可回退”不是恢复 timeline fallback

这里的“可回退”应明确解释为：

- repair 产物可识别
- repair 产物可清理
- repair 可按新版本重新执行

不应被理解为：

- 把 `/tasks/timeline` 再改回 EventLog fallback
- 保留页面级运行期兼容分支

## 当前事实

### 1. timeline 已经只读取任务域状态历史

[src/ui/app/pages/task-timeline-model.ts](../../src/ui/app/pages/task-timeline-model.ts) 当前直接按 `task.statusTransitions` 生成 segment / terminal：

- 若 transition 为空，则返回空 segment / 空 terminal
- 最终这类任务不会进入时间线

这条主线已经收口，不应再在页面上加写入型兼容逻辑。

### 2. 旧空历史任务当前仍被保留，但不会被 repair

[crates/exomind-runtime/src/task/store.rs](../../crates/exomind-runtime/src/task/store.rs) 目前明确保留两条测试：

- `sqlite_init_preserves_empty_status_history_from_legacy_schema`
- `sqlite_init_preserves_empty_in_progress_history_from_legacy_schema`

说明当前行为是：

- 旧 schema 读出的任务若 `status_transitions=[]`
- 任务仍可读取
- 但 store 初始化时不会自动补历史

### 3. import 链路当前没有“历史重建”步骤

[src/ui/components/MigrationDialogController.tsx](../../src/ui/components/MigrationDialogController.tsx) 当前只负责：

- 读取 legacy events / tasks / timeblocks
- 导入 RT

但导入完成后没有任何“根据旧事件重建任务状态历史”的收尾步骤。

### 4. 当前 transition 结构已有幂等与 provenance 基础字段

前后端 `TaskStatusTransition` 当前已经具备：

- `reason`
- `actorId`
- `sourceHostId`
- `operationId`
- `autoGenerated`

因此 v1 repair 不必急着再加一套全新 transition 子结构；可以优先复用这些字段来表达 repair 产物的可溯源性。

## 设计原则

### 一、单向

只允许：

- `EventLog -> Task.statusTransitions`

不允许：

- `Task.statusTransitions -> EventLog` 回写旧历史
- timeline 继续从 EventLog 读取作为兜底

### 二、一次性

同一 repair 版本对同一 scope 只能成功执行一次。

如果后续升级 repair 规则，必须显式提升 repair version，再触发新一轮重跑。

### 三、可溯源

任何 repair 生成的 transition 必须能被识别出来，而不是和原生运行时写入的 transition 混成不可区分的一团。

### 四、可回退

必须存在一种机制，可以：

1. 识别 repair 生成的 transition
2. 清理 repair 生成的 transition
3. 清除“本版本 repair 已完成”的标记
4. 按新版本重新生成

### 五、不重复

repair 不能因为：

- app 重启
- scope 重开
- 再次进入任务列表 / 时间线 / 详情页

就不断重复向同一任务追加同样的 transition。

### 六、保守优先

无法稳定推断时，宁可：

- 保持旧任务空历史
- 继续不进时间线

也不应硬编一段伪历史。

## 推荐方案

## 一、repair 的落点

### 推荐落点

把 repair 放在任务域内部的 ensure 流程：

1. runtime 打开任务 store 后，为某个 `scope_key` 第一次执行任务域读取前
2. 或 legacy import 完成后，作为已有导入链路的收尾步骤

推荐实现形态是：

- `ensure_legacy_status_history_repaired(scope_key)`

由任务域内部调用，而不是由页面直接调用。

### 不推荐落点

以下位置都不应承担 repair：

- `TaskTimelinePage`
- `task-timeline-model.ts`
- 任何只读页面组件
- 新增一个面向用户的 repair API/UI

原因很直接：

1. 会把读路径变成写路径。
2. 会把 EventLog 再次带回 timeline 的运行期依赖。
3. 会让“只认任务域状态历史”的收口再次失焦。

## 二、repair 的持久化幂等机制

### 方案

在 task SQLite 中新增一张轻量 meta 表：

```sql
CREATE TABLE IF NOT EXISTS task_meta (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

用于记录 per-scope repair version，例如：

- `legacy_status_history_repair:anonymous = v1`
- `legacy_status_history_repair:profile:<profile-id> = v1`

### 作用

这张表只承担两件事：

1. 防止同一 scope 在同一 repair version 下重复执行
2. 为将来的 rollback / regenerate 提供最小控制点

### 为什么不用页面内存态解决

因为 repair 的“不重复”必须跨：

- 重启
- 刷新
- 新窗口
- Tauri / RT 进程生命周期

所以不能只靠前端 flag 或页面内存态。

## 三、repair 产物的可溯源策略

### v1 最小策略：优先复用现有字段

repair 生成的 transition 优先复用现有字段表达 provenance：

- `operationId`：
  - `legacy-status-history-repair:v1:<scope_key>:<task_id>`
- `actorId`：
  - `system:legacy-status-history-repair`
- `autoGenerated`：
  - `true`
- `sourceHostId`：
  - 当前 runtime host id

### reason 的处理规则

`reason` 仍尽量表达真实的领域含义，而不是只写“repair”：

- 若事件能明确映射为创建：`task.create`
- 若事件能明确映射为手动状态变化：`task.transition`
- 若事件能明确映射为暂停/恢复/结束联动：`timeblock.pause` / `timeblock.resume` / `timeblock.end`

也就是说：

- **repair provenance** 由 `operationId + actorId + autoGenerated` 表达
- **领域语义** 由 `reason` 表达

### 为什么不把 `reason` 直接改成 `legacy.eventlog_repair`

因为 `reason` 当前承担的是“状态变化语义”而不是“迁移来源语义”。

若后续实践证明仅靠现有字段还不够，再考虑新增显式 `provenance` 字段；但 v1 不把 schema 变更做得更大。

## 四、repair 任务筛选规则

只处理同时满足以下条件的任务：

1. `statusTransitions` 缺失或为空
2. 任务来自当前 scope
3. 能从旧事件中找到与该任务相关的可信状态事件

明确不处理：

- 已有非空 `statusTransitions` 的任务
- 当前状态历史已经合法的任务
- 无法从事件稳定映射的旧任务

## 五、事件到状态历史的映射策略

### v1 只吃“可信任务事件”

v1 repair 只处理能稳定映射的任务事件，不做泛化猜测。

推荐优先映射：

1. `task.created`
2. `task.transitioned`
3. `task.cancelled`
4. 已能稳定识别且和任务直接绑定的 timeblock 联动事件

### 去重与排序

重建时按以下顺序处理：

1. 先按事件发生时间排序
2. 同时刻按原始事件顺序稳定排序
3. 过滤重复或自相矛盾事件
4. 最终生成 append-only transition 列表

### 合法性校验

重建出的 transition 列表必须通过现有任务状态历史校验逻辑：

- 第一条必须是 `task.create`
- 状态机路径必须合法
- 最终 `status` / `completedAt` 必须能与任务快照对齐

一旦校验不通过：

- 放弃 repair
- 保持旧任务空历史

### v1 不做的事

v1 不承诺：

- 从所有旧 EventLog 叙事文本里猜状态
- 从零散 timeblock 关联硬推完整任务历史
- 用任务快照强行补一段伪完整历史

## 六、回退与重跑机制

### rollback 定义

rollback 指：

1. 找出 `operationId` 以 `legacy-status-history-repair:v1:` 为前缀的 transition
2. 将这些 transition 从目标任务中剔除
3. 重新归一化任务快照
4. 清除该 scope 的 `task_meta` repair version 标记

### regenerate 定义

regenerate 指：

1. 先 rollback 旧 version repair 产物
2. 升级 repair version
3. 按新版本规则重跑

### 为什么需要这套机制

因为用户明确要求这条兼容路径必须：

- 可溯源
- 可回退
- 不重复

如果没有 rollback/regenerate 设计，repair 一旦算法有 bug，就只能人工修数据库，风险太高。

## 验收重点

至少覆盖以下行为：

1. 一条 `statusTransitions=[]` 的旧任务，若旧事件足够，能被补出合法历史。
2. repair 后该任务进入 `/tasks/timeline`，且 timeline 不额外依赖 EventLog fallback。
3. 同一 scope 在同一 repair version 下，多次启动不会重复追加历史。
4. rollback 后，repair 产物可被完整识别并清理。
5. 无法可靠推断的旧任务保持空历史，不伪造 transition。

## 风险

### 风险 1：事件映射不稳定

如果旧事件的 metadata 质量不足，repair 可能会生成错误历史。

应对方式：

- v1 只吃可信事件
- 映射失败就放弃 repair

### 风险 2：repair 触发点过晚或过早

若放到页面加载时，读写边界会被污染。
若放得太深、又没有 per-scope ensure，某些旧 scope 可能永远不触发 repair。

应对方式：

- 放在任务域内部 ensure 流程
- 用 `task_meta` 做 once-only 守卫

### 风险 3：无法精确区分 repair 产物

若 provenance 不清晰，将来很难 rollback。

应对方式：

- 统一 `operationId` 前缀
- 固定 `actorId`
- 固定 `autoGenerated=true`

## 最终判断

这份单向兼容方案的核心，不是“把旧 fallback 变相搬回来”，而是：

- 让旧事件只在一次性 repair 中充当输入材料
- repair 完成后，任务时间线仍只认任务域 `statusTransitions`

这样既满足：

- 比完全不兼容更好
- 不新增 UI / API 入口
- 一次性、可溯源、可回退、不重复

又不会把 `#929` 刚完成的任务时间线收口重新打散。
