# ExoMind Architecture Principles

> 架构层必读。用于命名、抽象边界、文案语义、测试描述和评审判断。

## 使用方式

只要任务涉及以下任一内容，就先回读本文件：

- 命名系统约束、行为语义、方法名、字段名
- 设计或审查“删除 / 回滚 / 取消 / 放弃 / 提案 / 承诺 / 时间推进”等动作
- 编写会影响产品语义的测试描述、Issue 文案或 UI 文案

## 双层原则命名规范

ExoMind 的每一条系统级约束都必须具备**双层表述**，缺一不可：

| 层次 | 面向 | 措辞风格 | 适用场景 |
|------|------|---------|---------|
| **架构不变量（invariant）** | 开发者 / 架构师 | 强硬，描述硬约束 | 架构文档、代码注释、评审规则 |
| **用户行为语义（affordance）** | 用户 / 产品 | 柔性，描述操作含义 | UI 文案、Issue、测试描述、方法名 |

判断标准：若一个约束只有不变量名而没有行为语义名，说明设计未完成。

## 当前核心原则

| 不变量（invariant） | 行为语义（affordance） | 对实现的含义 |
|------|------|------|
| **不可删除原则** | **删除 = 放弃** | 优先把“删除”设计成可追溯的放弃或撤销语义，而不是无痕消失 |
| **不可回滚原则** | **操作生效 = 留下痕迹** | 成功发生的动作应可追踪、可解释，避免假装从未发生 |
| **持续展开原则** | **任务在时间中推进** | 对象不只是静态状态，还要表达时间中的推进、阻塞、恢复与续接 |

## 生命判据

系统设计遵循 5 条工程否决式生命判据：

| 判据 | 含义 |
|------|------|
| **可存活区间** | 任何主体都处于资源与能量约束中，跌出区间会导致过程退化或中断 |
| **边界归因** | 任何动作都必须可归因到明确边界与责任主体 |
| **过程性存在** | 生命不是静态实体，而是时间中持续展开的过程 |
| **失败不可回滚** | 错误和后果不会因为一句“撤销”就从历史中蒸发 |
| **环境裁决** | 真正的硬约束由环境执行，而不是由主体自行宣布豁免 |

## 设计提醒

1. 不要把产品语义直接坍缩成 CRUD 语义。
2. 不要把用户行为文案和底层不变量混成一套词。
3. 若一个实现需要“删除”“回滚”“重置”“撤销”，先问它到底对应哪条 invariant / affordance。
4. 若一段逻辑会改变用户对“承诺、痕迹、推进、放弃”的理解，必须在设计和测试里显式说明。
