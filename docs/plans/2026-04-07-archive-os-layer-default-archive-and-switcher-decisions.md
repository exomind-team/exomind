## 1. 结论快照

### 1.1 核心术语

- 统一正式术语选：
  - `archive`
- `profile` 退到：
  - 展示层
  - 资料卡
  - 对外描述等较轻表面
- 第一阶段执行方式：
  - 文档和 UI 统一改成“档案 / archive”
  - 内部实现按“边界先换名”推进
- 存储迁移策略：
  - 双读旧 `profile` 键
  - 写入统一落到新 `archive` 键
- 会话字段迁移策略：
  - 从 `activeProfileId / unlockedProfileIds`
  - 迁到 `activeArchiveId / unlockedArchiveIds`

### 1.2 Tauri App 中的档案系统

- 一个 Tauri App 内部，`RT` 更像本地小型多用户 OS 的底座
- `archive` 是这个 `RT` 内的逻辑用户 / 档案体
- `ArchiveSession` 是某个档案在该 `RT` 上的本地运行会话
- `UiSession` 是外部 UI 终端连接
- `UiSession` 粒度按：
  - 每窗口 / 标签
- 第一阶段默认：
  - 同一档案在同一 `RT` 上只允许一个 `UiSession`
- 第二个终端撞上已占用档案时：
  - 拒绝连接
  - 提示占用
  - 给出候选列表供用户改选
- 旧 `UiSession` 异常失活时：
  - 通过超时自动释放

### 1.3 Tauri UI 与 RT 对接

- Tauri UI 启动时默认：
  - 自动拉起本地 RT
- UI 侧应有：
  - `RT 加载中` 表面
- 这个加载表面只负责：
  - 监控 RT 启动状态
- 第一阶段“选择档案 / 登录”页默认只看：
  - 当前本地 RT
- 如果 RT 在 UI 接入前已有 `running` 的 `ArchiveSession`：
  - 登录 / 切换器里应置顶为恢复候选

### 1.4 启动入口与默认档案

- 一个 Tauri App 第一阶段默认启动入口是：
  - 直接进入内置默认档案
- 这意味着当前“未打开档案”不再按纯空壳理解，而是：
  - 一个内置默认档案
- 这个默认档案第一阶段按：
  - 本地默认档案
- 并且它是：
  - 固定存在
  - 固定置顶特殊行
  - 不可删除
  - 不可重命名
- 用户从正式档案执行退出 / 关闭当前档案后：
  - 回到默认档案

### 1.5 档案切换器

- 其他档案的入口第一阶段放在：
  - 档案切换器弹层
- 切换器第一阶段默认动作只包括：
  - 进入
  - 切换
  - 创建
- 第一阶段不在切换器里直接做：
  - 接管会话
  - 关闭其他 running 会话
- 切换器里每条档案记录，OS 层第一阶段最小状态集合是：
  - 当前
  - 运行中
  - 已占用
  - 已锁定
- 这样做的原因是：
  - 用户需要知道有哪些档案正在 RT 后台运行，以便及时进入并管理它们
  - 后台持续运行的内容可能消耗性能，例如 Agent 会话

### 1.6 默认档案与正式档案的转换

- 默认档案可以：
  - 升级为正式个人档案
- 升级触发方式：
  - 显式升级动作
- 升级数据策略：
  - 迁移到新正式档案
- 升级完成后：
  - 当前窗口停留在新的正式档案
  - 用户体验尽量无感
  - `RT` 再生成一个新的空白默认档案，接住原默认档案的位置

### 1.7 OS 层与集体层的边界

- `OS 层` 先解决：
  - 档案术语
  - 默认档案
  - 档案切换器
  - `ArchiveSession`
  - `UiSession`
  - Tauri UI 与 RT 对接
- `集体层` 后续再解决：
  - 集体档案在切换器中的分组
  - 默认档案与正式档案在公开身份、邀请、集体接入上的差异化限制
  - 集体入口与 `MemberSeat` 的更细合同
- 在 OS 层第一阶段，默认档案先按：
  - 本地功能与同步一视同仁
- 更强的公开身份 / 集体接入限制：
  - 延后到集体层追踪

## 2. 一个 Tauri App 中，这套档案系统怎样运行

可按下面的心智模型理解：

- 一个 Tauri App 实例先确保本地 `RT` 可用
- `RT` 是底层运行时，会持有多个 `ArchiveSession`
- 应用默认先进入一个内置默认档案
- 用户在当前工作面通过侧边栏 / 账号入口打开档案切换器
- 切换器显示：
  - 默认档案
  - 其他已知档案
  - 它们的状态（当前 / 运行中 / 已占用 / 已锁定）
- 选择某个档案时：
  - 若未运行，则自动拉起对应 `ArchiveSession`
  - 若已被本 `RT` 其他窗口占用，则拒绝并提示占用
  - 若允许进入，则当前窗口对应的 `UiSession` 接入该档案
- 若用户从正式档案退出：
  - 当前窗口回到默认档案
- 若用户在默认档案中创建新正式档案：
  - 当前窗口直接切入新档案
- 若用户把默认档案升级成正式个人档案：
  - 数据迁移到新正式档案
  - 当前窗口继续停留在新正式档案
  - `RT` 补出一个新的空白默认档案

## 3. 原始问答摘录

以下内容按本轮工具问答原文整理，尽量保留原始表达。

### 3.1 `UiSession` 与单连接

Q：同一档案在同一 RT 上，第一阶段默认应允许哪种 UI 并连模型？

A：`单连接`

原始备注：

> 要更严格些，后续再考虑扩展

Q：如果同一 ArchiveSession 已被多个 UiSession 连接，其中一个 UI 切走或退出时，默认应怎样处理旧档案会话？

A：`只断当前终端`

原始备注：

> 对，这就是「一档案多UI连接」后续要考虑的

Q：第一阶段里，一个 UiSession 最合适对应什么粒度？

A：`每窗口或标签`

Q：在“同一档案同一 RT 只允许一个 UiSession”的前提下，第二个窗口/标签尝试连接同一档案时，第一阶段默认应怎么处理？

A：`拒绝并提示占用`

原始备注：

> 拒绝、提示占用，并给出一个候选列表让用户选择。
> 这或许也类似Linux系统那样，需要一个「登录」页面了

Q：如果当前唯一 UiSession 已经崩溃、断网或标签页被异常关掉，新的 UiSession 该如何重新取得连接？

A：`超时后自动释放`

Q：这条“同档案同 RT 单 UiSession”规则，第一阶段应覆盖到哪一类档案 / 座席？

A：`个人+集体都统一`

原始备注：

> 我们把这个开发计划再分两层：一个管「档案系统」即「OS层」（因为本身是类似多用户操作系统来设计的），一个管「集体协作」即「集体层」。
> 这个层次划分我们需要明确

### 3.2 Tauri UI 与 RT 对接

Q：如果用户打开 Tauri App 时，本地 RT 还没跑起来，第一阶段默认应怎样处理？

A：`自动拉起本地RT`

原始备注：

> 这方面可能也要做一个类似「RT加载中」，对标「各操作系统的启动页面」。
> 这个是纯粹在UI侧做的，主要是监控RT的启动状态

Q：第一阶段这个“选择档案 / 登录”页，默认应该面向哪一层的 RT 范围？

A：`只看当前本地RT`

Q：如果 RT 在 UI 接入之前就已经有 `running` 的 ArchiveSession，登录页第一阶段应怎样对待它们？

A：`置顶为恢复候选`

### 3.3 默认档案与启动入口

Q：你说的“未打开档案”，第一阶段更应该被理解成什么？

A：`匿名个人档案`

原始备注：

> 目前我觉得沿用目前的方式要好一些，用户可以开箱即用。
> 如果用纯OS壳态，倒不如直接替换成登录页面（定位重复了）
> 内建系统档案可以考虑一下

Q：在这个“未打开档案”状态下，第一阶段默认允许做什么？

A：`完整轻量工作面`

原始备注：

> 在目前的功能设计中，它本身就是一个内置档案。
> 我倾向于不动。后续如果要移除这个「未打开档案」的功能，不如直接以「登录界面」替代

Q：用户从这个空状态里选择或创建一个档案后，第一阶段默认应怎样进入？

A：`None of the above`

原始备注：

> 这不是空状态，这个「未打开档案」应该就是个默认用户可进入的档案，或者说是一个纯RT本地的、APP启动后默认进入的档案。
> 具体还要再讨论，主要是要不要把整个系统做成一个登录页面。设计考量主要是担心这样是过度设计，登录界面可能让原先「启动后直接进入可以工作」的用户产生交互上的认知负荷

Q：对一个 Tauri App 来说，第一阶段默认启动入口最终应是哪一种？

A：`默认进入内置档案`

Q：如果默认启动后直接进入内置档案，那么其他档案的进入入口第一阶段最适合放在哪里？

A：`档案切换器弹层`

原始备注：

> 就是现在的功能配置，允许用户以未登录状态使用外心APP

Q：这个默认进入的“未打开档案 / 内置档案”，第一阶段最应该按什么语义处理？

A：`本地默认档案`

Q：当用户从一个正式档案执行“退出 / 关闭当前档案”时，第一阶段默认应回落到哪里？

A：`回默认档案`

原始备注：

> 对。后续再单开一个issue来追踪「默认档案/统一登录」的设计决策

Q：这个本地默认档案，第一阶段最适合加什么约束？

A：`完全固定`

原始备注：

> 不允许重命名，因为目前就是这样做的，系统内置。
> 后续的「统一登录化」交给另一个issue追踪

Q：用户在默认档案里创建了一个新的正式档案后，当前窗口第一阶段默认应怎样处理？

A：`创建后立即切入新档案`

### 3.4 档案切换器

Q：在 OS 层第一阶段，档案切换器里每条档案记录最小应区分哪些状态？

A：`当前+运行+占用+锁定`

原始备注：

> 我们也要知道有哪些档案正在RT后台运行，以便及时进入并管理它们（后台持续运行如Agent会话之类的，会吃性能）

Q：切换器第一阶段默认应允许哪些会话动作？

A：`进入/切换/创建`

Q：这个内置默认档案在切换器里，第一阶段最适合怎样显示？

A：`固定置顶特殊行`

Q：第一阶段的档案切换器，个人档案与集体档案最适合怎么组织？

A：`分区同页`

原始备注：

> 这个放到「集体层」中决策。我们延后，把这个问题追踪到issue即可。
> 我们的阶段也并非要一次性做完OS层与集体层

Q：用户在切换器里点击一个集体档案时，第一阶段默认应怎样进入？

A：`直接进成员座席`

Q：切换器里每条档案记录，第一阶段最少应该显示哪些信息？

A：`名称+类型+状态`

原始备注：

> 我们在做OS层是不需要考虑这些，基本上只需沿用当前的「名称+状态」

### 3.5 `archive` 术语与迁移

Q：对这个统一承载个人/集体、可被 RT 运行、可被 UI 接入、可进入关系与邀请系统的核心对象，第一正式术语应选什么？

A：`archive`

原始备注：

> 我觉得是要这样统一一下，那先前的「沿用旧键」决策就被推翻了

Q：如果核心对象正式叫 `archive`，那么 `profile` 这个词在第一阶段最适合退到哪一层？

A：`退到展示层`

Q：一旦正式选定 `archive`，第一阶段文档与产品层面应怎样执行？

A：`文档和UI统一改`

Q：既然核心术语正式锁为 `archive`，第一阶段本地存储键最适合怎么迁移？

A：`双读旧键写新键`

Q：像 `activeProfileId / unlockedProfileIds` 这类持久状态字段，第一阶段应怎样处理？

A：`迁成archive字段`

Q：代码层第一阶段最适合怎么推进 `profile -> archive` 的符号迁移？

A：`边界先换名`

Q：在 OS 层第一阶段实现时，现有代码里大量 `profile` 概念应怎样迁移到 `archive` 语义？

A：`内外一起改名`

原始备注：

> 我们可以讨论下：这个「档案」是用「profile」还是用「archive」。
> 只看词语与我们的设计决策的贴合程度，不看我们之前已经在用什么

### 3.6 默认档案升级为正式档案

Q：这个本地默认档案，第一阶段是否应允许升级为正式个人档案？

A：`允许升级`

原始备注：

> 升级之后，RT应该会再建立一个空白的「默认档案」来接住升级后原来档案的位置

Q：如果允许升级，第一阶段最合适的触发方式是什么？

A：`显式升级动作`

原始备注：

> 对。这个「默认档案」仅限使用本地可用的功能，公开标识、同步、邀请等集体层功能，后续不做在默认档案上。
> 不过同步功能应该对这个「默认档案」一视同仁，因为这个「默认档案」很适合用于临时使用与测试

Q：默认档案升级时，第一阶段应怎样处理它已有的本地数据？

A：`迁移到新档案`

Q：对这个默认档案，第一阶段最合适的能力边界是哪一条？

A：`本地功能+同步`

原始备注：

> 对。所以在OS阶段我们先做得一视同仁，不需要区别对待。
> 只有在做「集体层」功能时再区分

Q：默认档案第一阶段最应该明确禁止哪类能力？

A：`公开身份与集体接入`

原始备注：

> 这个是在「集体层」制作时再决定的。我们在「OS层」不需要考虑

Q：默认档案升级并迁移成正式个人档案后，执行升级的那个当前窗口第一阶段默认应落在哪？

A：`停在新正式档案`

原始备注：

> 迁移应该让用户基本无感

## 5. 一句话总结

本轮之后，外心的 `OS 层` 已经收口为：**一个 Tauri App 默认进入固定内置默认档案，通过档案切换器进入其他档案；核心对象统一叫 `archive`；`RT` 管 `ArchiveSession`，窗口 / 标签管 `UiSession`；默认档案可显式升级为正式个人档案，并在升级后由 `RT` 自动补出新的空白默认档案。**
