# Governance PR Website Refresh Design

**背景**

治理 PR `#565` 已补治理文档，但官网对外宣传仍落后于当前产品与治理叙事，主要问题是：

- 首页文案仍是旧版“生命成长助手”定位，和治理草稿不一致。
- 下载页把 `macOS/Linux` 的 runtime 产物包装成桌面下载，不适合对外宣传。
- 文档页仍是 `coming soon` 占位。
- 更新日志仍停留在旧版本。
- 多处页面仍直接导向当前匿名不可访问的 GitHub 仓库。

**目标**

在不新开 PR 的前提下，直接在治理 PR worktree 中补齐官网对外宣传基础面，让外部访问者能够看到一致、可公开、可落地的产品叙事与入口。

**已确认约束**

- 继续使用现有分支 `ex/govn-governance-docs`。
- 演示图本轮不做。
- 必须本地构建成功，并更新官网页面后再推送。
- 对外页面不能继续把私有 GitHub 当主入口。

**方案对比**

## 方案 A：最小补全

只把文档页从占位改成链接集合，其他页面少改。

优点：
- 快

缺点：
- 首页、下载页、更新日志仍然和治理叙事脱节
- PR 看起来像“补丁”，不是完整的对外刷新

## 方案 B：官网宣传面一次收敛

统一刷新首页、下载页、文档页、更新日志页和公开入口；文案以 `docs/governance/README-draft.md` 为基准；只展示真实可下载平台，其它平台明确 `Coming Soon / 即将推出`。

优点：
- 用户进入官网时信息一致
- 能直接支撑对外宣传
- 风险主要集中在文案与页面层，改动边界清晰

缺点：
- 需要补测试并同时处理中英双语页

## 方案 C：顺手连发布元数据一起重构

除了官网页面，还同步改 release workflow / latest metadata 生成策略。

优点：
- 平台展示逻辑最彻底

缺点：
- 超出本轮 PR 范围
- 会把官网 PR 拉成发布链路 PR

**采用方案**

采用方案 B。

**设计要点**

## 1. 文案基线

官网首页与关于页文案以 `docs/governance/README-draft.md` 为唯一基线，突出：

- 本地优先（Local-first / 本地优先）
- 认知主权（Cognitive Sovereignty / 认知主权）
- 事件驱动 Agent 系统（Event-driven Agent System / 事件驱动 Agent 系统）
- 分布式身体与协作网络（Distributed Body / 分布式身体）

## 2. 下载页策略

- `Windows`、`Android` 保持真实下载入口。
- `macOS`、`Linux` 不再宣传为可下载桌面版，改为明确说明“即将推出 / 工程预览准备中”。
- 不依赖 GitHub Releases 作为公开兜底入口。
- 下载 API 保持兼容已有 release metadata，但官网 UI 不再把 runtime tarball 描述成正式桌面包。

## 3. 文档公开入口

将文档页改成非空公开资料页，聚合以下内容：

- 项目概览 / 快速认知
- 治理说明
- 所有制说明
- 贡献方式
- 版本与更新入口

页面可直接链接仓库中的公开文档文件路径，后续再扩展为正式 docs 站。

## 4. 更新日志

将 changelog 更新到当前版本 `v0.3.6`，并体现最近的真实里程碑，而不是旧占位文案。

## 5. 公开入口治理

- 首页 CTA、Footer、About、Docs、Download 中的 GitHub 私有入口全部下掉或降级。
- 用站内公开入口代替：`/download`、`/docs`、`/changelog`。

**测试策略**

- 先改单测，确保下载 API 行为仍兼容已有真实产物。
- 再补 E2E，覆盖首页文案、文档页非空、更新日志版本、下载页平台状态。
- 最后跑 `website:build` 与网站 E2E。
