# 已确认决策：事件引用与事件唯一链接（v1）

> **状态**：已确认，待实现
> **日期**：2026-04-13
> **关联 Issue**：#66 `feat(eventlog): 事件唯一链接 — 可分享的事件永久地址`、#67 `feat(eventlog): 事件引用 — 在新事件中引用历史事件`
> **后续关联**：#53、#256 作为下一阶段扩展，不纳入本次 v1

---

## 一、范围结论

本次 v1 只解决 **事件对事件（event -> event）** 的引用与唯一链接闭环，不顺带纳入任务、时间块、提案等对象引用。

- 本次必须闭环：
  - 新事件可引用已有事件
  - 新事件可复制唯一链接
  - 点击链接后进入记录页并定位到对应事件
  - 事件卡片可展示正向引用摘要
- 本次明确不做：
  - task / timeblock / proposal 的统一引用
  - `#ID` 短引用语法
  - `exo://` 自定义协议
  - 单独的事件详情页
  - 历史旧事件的批量回填
  - 反向引用（backlink）展示

---

## 二、数据与写入决策

### 2.1 引用模型

事件采用 **显式 `refs`** 作为结构化引用字段，不采用“仅正文解析”的模型。

- `refs` 在**创建事件时固化**
- `refs` **去重**
- `refs` **保留用户添加顺序**
- 第一个 ref 视为主引用，用于默认展示

### 2.2 正文识别规则

正文中的引用识别在 v1 只支持 **明确链接**，不支持短 ID 语法。

- 支持识别：Markdown / App URL 内链
- 不支持识别：`#e123`、`#123` 等短引用

### 2.3 旧数据策略

v1 **只支持新事件** 的结构化 `refs`。

- 历史旧事件不做启动时全量迁移
- 历史旧事件不做读时懒回填
- 原因：旧事件本身并没有唯一链接体系，强行回填会引入不必要的不确定性

## 三、链接与路由决策

### 3.1 Canonical 形式

事件唯一链接的 canonical 形式为 **绝对 App URL**。

- 基于 **当前应用 origin** 生成
- v1 不引入固定 share base
- v1 不做运行时可配置分享基址

### 3.2 路由落点

在“不做单独事件详情页”的前提下，链接统一落到 **现有记录页 + query 参数**。

- 继续使用 `/eventlog/record`
- 用 query 携带事件定位参数
- 不新增 `/eventlog/record/:eventId` 子路由
- 不使用 hash 锚点作为 canonical

### 3.3 打开行为

用户点击事件链接后：

- 进入记录页
- 自动定位到目标事件
- 自动高亮目标事件

---

## 四、输入区与引用交互决策

### 4.1 引用入口

复用现有消息操作区里的“引用”按钮，不另起一套入口。

### 4.2 点击“引用”后的输入区表现

点击已有事件下方“引用”后，输入区采用 **横幅 + 正文首行** 的混合模型。

- 输入框上方出现结构化引用横幅
- 正文顶部自动插入轻量引用文案
- 横幅支持：
  - 点击查看被引事件全文
  - 右键快速定位到被引事件
  - 右侧 `x` 关闭并移除该引用

### 4.3 删除语义

正文引用文案与结构化 `refs` **保持同步**。

- 只有当某条引用文案被**完整删除**时，才移除对应 ref
- 不因局部编辑而移除 ref
- ref 不允许重复

### 4.4 多引用顺序

多引用按**添加顺序**排列。

- 第一条引用为主引用
- 后续引用依序附加
- v1 不支持手动重排

---

## 五、事件展示决策

### 5.1 正向引用展示

事件气泡下方采用 **首条引用 + 其余计数** 的默认展示模型。

示意：

```text
引用：第一条引用标题
还有 N 条引用
```

目标：

- 保留聊天软件式低负担阅读感
- 同时不丢失多引用的表达力

### 5.2 反向引用展示

`被引用于 N 条` 不纳入本次 v1，实现顺序后置。

- 本次先把正向引用、唯一链接、记录页定位、输入区引用闭环做稳
- backlink 作为下一阶段增强功能单独推进

---

## 六、血缘参考与偏离点

`exobuffer-connector` 可直接借鉴的部分：

- 聊天式引用横幅
- 点击引用后跳转到原消息
- 复制消息链接
- 服务端生成稳定 ID

本次 ExoMind 明确不照搬的部分：

- 不沿用单一 `reply_to`
- 改为支持多引用的 `refs`
- 不把旧消息兼容当作本次 v1 范围

一句话总结：

> **ExoMind v1 采用“ExoBuffer 的聊天式引用体验 + GitHub 式可定位链接”，但底层从单 `reply_to` 升级为有序去重的多 `refs` 模型。**
