# ExoMind Issue 追踪执行章程（Agent）

> 目标：把用户的追踪请求稳定转为“查重 → 现状核查 → 新建/追加 → 关联依赖 → 回报”的标准化动作，并在问题收敛后自然升级为可执行的 issue 合约，避免重复、遗漏与语义漂移。

## 1. 适用范围

- Bug / 回归 / 体验缺陷
- 功能请求
- 架构/产品讨论
- 设计原则澄清

## 2. 强制原则（不可跳过）

1. **自主执行，不问用户要结构化信息**（最高优先级）：
   - 收到用户的自然语言描述后，**立即开始**查重、检索、核查。
   - **绝对禁止**要求用户提供预期/实际、复现步骤、平台/影响范围、关联 issue 编号、或任何表单式/清单式信息。
   - 所有 issue 正文所需的结构化字段（预期/实际/当前实现定位/关联依赖，以及适用时的已定决策/边界/完成条件）由 Agent 自行通过代码检索、issue 查重、dev 分支核查等手段填充。
   - 仅当 Agent 已完成检索和分析后仍无法判断问题核心时，允许提出**一个**最小澄清问题（具体且封闭式，例如”你说的'不对'是指 A 还是 B？”）。
   - 追踪完成后必须输出执行过程与报告供人回看。
2. **无则创建，有则追加评论**：先查重再行动。
3. **必须核查当前 dev 实现**：追踪前先看 `dev` 分支代码现状。
4. **必须包含”预期/实际”**：对立呈现需求张力。
5. **必须写明验证方式**：追踪时不仅要写“预期/实际是什么”，还要写“当前情况如何验证”“实现完后如何验证”。
6. **实际必须带当前实现定位**：写明 `dev` 短 hash + 关键文件路径；关键路径要保持项目根目录相对路径语义，在 issue / 评论正文中应以可点击 Markdown 链接展示，保证可溯源定位。
7. **强制双向关联**：新旧 issue 互链（正文 + 评论）。
8. **严格去重**：几乎同问题才追加，其他新建并互链。
9. **多问题强制拆分**：一个 issue 只追踪一个原子问题。
10. **分阶段补全，不一次写满**：
   - 新 issue 默认先满足“追踪层”，不得因信息未完全细化而阻塞创建/追加。
   - 当问题边界、方向、交互或实现约束已相对清晰时，再补全“细化层”字段。
   - 不得跳过“追踪层”直接写抽象方案；也不得在仍模糊时强行伪造完整 contract。
11. **链接必须降噪后再发布**：
   - GitHub issue / 评论正文中，禁止裸贴 `https://...`、禁止把 URL 当作链接文本、禁止出现本地绝对路径。
   - 仓库内文档、工作流、分析报告等引用，必须优先改写为**简短命名的 Markdown 链接**。
   - 本地 Markdown 文档优先使用相对路径链接；GitHub issue / 评论优先使用命名后的 GitHub 链接。

## 3. 执行 SOP

1. **抽取问题原子点**（拆分多问题）
2. **查重检索**（open + closed）
3. **核查 dev 现状**（代码/实现/行为）
   - 若用户要求“广泛搜索上下文”，必须在正文补充“上下文检索”列表（issue/PR/文档/代码路径）。
   - 对 bug / 回归，优先收集**当前情况证据**，再写 issue；不得先写推测原因再回头补证据。
4. **决策新建/追加/回归**
5. **按“追踪层”创建/追加 + 标签**
6. **添加依赖关系（GraphQL）**
7. **在适当时机补全“细化层”**
   - 适用时机：
     - 用户明确要求先细化想法/方案
     - Agent 已能稳定判断关键交互、边界与验收
     - issue 即将进入计划、实现或交付排序
   - 补全内容：
     - 已定决策
     - 边界
     - 完成条件
8. **正文降噪与发布前复核**
   - 发布前必须本地回读正文临时文件。
   - 必查是否残留：
     - 裸 `https://...`
     - 形如 `[https://...](https://...)` 的高噪音链接
     - 反引号包裹但不可点击的仓库文档路径（如 `` `docs/...md` ``、`` `.github/workflows/...yml` ``）
     - 本地绝对路径（如 `H:/...`、`C:/...`）
   - 当前仓库可优先运行 `node scripts/check-issue-link-hygiene.cjs <body-file>` 做最小机械检查。
   - 发现上述情况时，必须先改写，再执行 `gh issue create/edit/comment --body-file ...`。
9. **回报用户：决策说明 + 当前状态 + 下一步建议**
10. **同步追踪报告**：追踪完成后必须输出“执行过程与报告”，供人回看参考（即便未向用户索取结构化信息）。

## 3.1 验证优先的追踪细化方法

追踪不是“把需求翻译成 issue”，而是把问题或目标收敛成**可验证、可溯源、可接力**的对象。

每个追踪对象，至少回答两件事：

1. **当前情况如何被验证**
2. **预期情况在实现完后如何被验证**

推荐将验证分成四层理解：

- **现象层**：用户能看到什么、发生了什么、没发生什么。
- **操作层**：通过什么步骤、在哪个页面/设备/状态下能复现或验收。
- **证据层**：通过什么日志、报错、开发者工具、代码路径、issue/PR/文档拿到结论。
- **边界层**：哪些已验证，哪些未验证，哪些证据待补。

### 3.1.1 当前情况验证

“实际”不是只写一句现象，而要写清：

- 当前实现落在哪个仓库、哪个分支、哪个 `dev` 短 hash
- 当前代码对应哪些关键路径
- 当前现象是通过什么操作观察到的
- 当前结论来自哪些证据源

若证据不足，必须显式写出：

- `已验证`
- `未验证`
- `待补证据`

禁止把尚未验证的推测写成“当前事实”。

### 3.1.2 预期情况验证

“预期”不是只写一句理想行为，而要写清：

- 实现完后用户应该看到什么
- 实现完后用户不应再看到什么
- 用什么操作路径可以验收
- 需要覆盖哪些相邻场景或边界场景

对 bug，可将“实现完”特化为“修完”；对功能、设计或讨论类 issue，默认统一使用“实现完”。

### 3.1.3 验证溯源方法的填写时机

- 创建 / 追加 issue 时，`验证溯源方法` 允许先写**简版**
- 当问题边界、实现方向、复现路径或验收链路收敛后，再补全为**完整可操作版**
- 不得因为一开始拿不到完美证据而阻塞追踪；但必须明确当前证据等级与缺口

### 3.1.4 证据源优先级（推荐顺序）

Agent 追踪时，优先按以下顺序收集证据：

1. **UI / 交互现象**
2. **开发者工具**
3. **设置页调试日志**
4. **设置页实例诊断信息**
5. **Tauri 本地日志**（如 `exomind.log`）
6. **系统日志**（如 Android `logcat`）
7. **`dev` 代码路径、相关 issue / PR / 文档**

应优先使用项目当前已经存在的取证入口，而不是一上来要求新增日志能力。

### 3.1.5 对齐当前 ExoMind 代码的现成取证入口

以当前 `dev` 为例，已知可用于追踪的入口包括但不限于：

- 前端开发者工具：
  - `src/lib/debug/devtools-runtime.ts`
- 设置页调试日志面板：
  - `src/ui/app/components/settings/LogPanel.tsx`
  - `src/ui/app/config/settings/LogPanelDialog.tsx`
- 设置页实例诊断信息：
  - `src/ui/app/components/settings/settings-custom-items.tsx`
  - `src/config/dev-instance-diagnostics.ts`
- Tauri 本地日志：
  - `src-tauri/src/lib.rs`
  - 当前通过 `tauri_plugin_log` 写入 `exomind.log`

追踪 bug 时，若这些入口已经足够支持定位，应先利用这些入口验证现状，再决定是否需要新增调试日志。

## 3.2 Bug 特攻追踪法

Bug / 回归类 issue 除了遵守通用追踪法，还应优先使用“先取证，再定性”的路径。

推荐默认链路：

1. **添加调试日志**（仅在现有日志不足时）
2. **试运行**
3. **复现问题**
4. **获得日志 / 报错 / 系统记录**
5. **追溯根源**

执行要求：

- 优先复现问题，不先猜原因
- 若当前代码已有日志入口，先使用现有入口
- 仅当现有入口不足以区分问题层级时，再补最小调试日志
- “实际”里只能写已观察到的效果与证据，不写未经验证的因果判断
- 推测、怀疑、方向性判断，只能放在：
  - `未验证`
  - `待补证据`
  - 或细化阶段的讨论区

对 bug 的“实际”建议至少包含：

- `当前实现 / 现状定位`
- `观察到的现象`
- `验证溯源方法`
- `已验证 / 未验证 / 待补证据`

## 4. Issue 合约分层

### 4.1 追踪层（创建/追加时必备）

用于承接用户自然语言反馈并完成标准追踪。新 issue 或追加评论时，必须至少覆盖以下字段：

- `背景`
- `预期`
- `实际`
- `关联/依赖`

特点：
- 重点在“事实、现状、定位、关联”，不要求一开始就把方案写满。
- 适用于 bug、功能请求、产品讨论、回归、设计澄清等所有追踪入口。
- 这一层必须由 Agent 自主补齐，不得向用户索要结构化表单信息。
- `预期` 与 `实际` 下允许先写简版 `验证溯源方法`，后续再补全。

### 4.2 细化层（问题收敛后补齐）

用于把 issue 从“追踪对象”升级为“可执行合约”。当方向与边界已足够清楚时，补充以下字段：

- `已定决策`
- `边界`
- `完成条件`

特点：
- 吸收 contract 思维，减少实现前的二次翻译。
- 允许逐步补全，不要求创建 issue 当下就写完。
- `完成条件` 应尽量写成可验证的行为描述；必要时可带 `测试:`、场景、步骤或 mermaid 图，但当前不强制所有 issue 绑定测试选择器。

## 5. Issue 正文模板（追踪层 + 细化层）

```md
## 背景
- 用户反馈：
- 影响范围：

## 预期
### 目标行为
### 验证溯源方法

## 实际
### 当前实现 / 现状定位
- dev: <short-hash>
- 关键路径：
  - [src/xxx.ts](<repo-blob-url>)
  - [docs/xxx.md](<repo-blob-url>)
- 上下文检索（当用户要求“广泛搜索上下文”时必填）：
  - Issues:
    - #123
  - PRs:
    - #456
  - Docs:
    - [设计说明](<repo-blob-url>)
  - Code:
    - [src/xxx.ts](<repo-blob-url>)
### 观察到的现象
### 验证溯源方法
### 已验证 / 未验证 / 待补证据

## 已定决策（问题收敛后补）
- 决策 1
- 决策 2

## 边界（问题收敛后补）
### 要做
- 范围 1
- 范围 2

### 不做
- 非目标 1
- 非目标 2

## 完成条件（问题收敛后补）
- [ ] AC1
- [ ] AC2

或使用更接近 BDD/Contract 的写法：

场景: xxx
  假设 xxx
  当 xxx
  那么 xxx

## 关联/依赖
- 关联：
  - #123
  - #456
- 阻塞：
  - #789
- 子问题：
  - #234
```

**注意**：
- “实际”只描述已观察到的效果，不写未经验证的推测原因。
- “当前实现 / 现状定位”必须可定位到具体提交与文件。
- `验证溯源方法` 默认可简写，但必须让后续 Agent 或人类知道“应该去哪里继续验证”。
- `已验证 / 未验证 / 待补证据` 用于显式标出当前证据边界，避免把猜测写成事实。
- “已定决策”只写已经锁定的选择，不写开放问题。
- “边界”用于限制范围漂移，优先写用户可感知行为边界与关键改动边界。
- “完成条件”优先描述外部可观察行为与验收路径，而不是内部实现细节。

## 6. 追踪层与细化层的使用规则

### 6.1 何时只写追踪层

- 刚收到用户描述，问题尚未完全收敛
- 主要目标是查重、定性、关联、落 issue
- 仍存在多个可能方向，尚不宜锁定方案

### 6.2 何时补全细化层

- 用户明确进入“细化想法 / 细化需求 / 计划模式”
- Agent 已能判断主要交互、边界与完成标准
- issue 需要进入计划、实现、排期或交接

### 6.3 细化层的来源

- 可来自用户明确表态
- 可来自 Agent 对代码、issue、PR、设计讨论的归纳
- 可来自已完成的计划讨论结果

### 6.4 不强制引入的 contract 要素

- 当前不强制每个 issue 都补 `测试:` 选择器
- 当前不强制每个 issue 都写完整 step table
- 当前不要求把 issue 完全等同于外部 spec 文件

保留这些空间，是为了兼顾 ExoMind 的追踪治理场景与实现前探索阶段。

## 7. 标签规则（对齐仓库已有标签）

- 平台：`UI` / `Web` / `Tauri` / `移动端`
- 领域：`时间块` / `事件日志` / `Agent` / `sync` / `架构` / `research`
- 优先级：
  - 默认 `P2`
  - 影响面大或阻塞链路：`P1`
  - 数据丢失/系统不可用或用户明确要求：`P0`
  - 使用 `P0/P1` 必须在背景或影响范围中写明依据

## 8. 依赖关系（GraphQL 强制）

### 8.1 关系类型（优先级）

- **阻塞为主**：实现先后依赖 → `blocked by`
- **父子谨慎**：仅在领域高度相关且范围覆盖时使用
- 若适用：**父子 + 阻塞都建**
 - **自主建立依赖**：Agent 必须在追踪时直接建立依赖关系，**不得**等待用户确认；依赖是供人回看与执行排序使用的事实记录。

### 8.2 GraphQL 最小命令集

**获取 issue node id：**

```bash
gh api graphql -f query='
  query {
    repository(owner:"exomind-team",name:"exomind") {
      issue(number:123){ id }
    }
  }'
```

**添加阻塞：**

```bash
gh api graphql -f query='
  mutation($issueId:ID!,$blockingIssueId:ID!){
    addBlockedBy(input:{issueId:$issueId,blockingIssueId:$blockingIssueId}){ clientMutationId }
  }' -f issueId=<ISSUE_ID> -f blockingIssueId=<BLOCKING_ID>
```

**添加子问题：**

```bash
gh api graphql -f query='
  mutation($issueId:ID!,$subIssueId:ID!){
    addSubIssue(input:{issueId:$issueId,subIssueId:$subIssueId}){ clientMutationId }
  }' -f issueId=<ISSUE_ID> -f subIssueId=<SUB_ID>
```

### 8.3 失败兜底

GraphQL 失败时必须：
1. 在 issue 正文的“关联/依赖”区保留 Markdown 列表；
2. 追加评论记录失败原因与待补操作（命令级别）。

## 9. 引用与关联规范

- 正文可就近引用 `#编号`
- **必须**在“关联/依赖”区用 Markdown 列表聚合
- 允许并鼓励**多级 Markdown 列表**，尤其是在列举 issue、文件路径时
- 文件路径必须使用**项目根目录相对路径**，禁止绝对路径
- GitHub issue / 评论中，仓库文件、计划、报告、workflow 引用必须尽量写成**简短命名的 Markdown 链接**
- **禁止**裸贴 URL；若必须引用网络地址，链接文本应使用文件名、文档名、标题或简短语义名
- **禁止**使用 `[https://...](https://...)` 这类把 URL 直接暴露为链接文本的写法
- 本地 Markdown 文档优先使用相对路径链接；GitHub issue / 评论优先使用命名后的 GitHub 链接
- 若 `src/...`、`docs/...`、`.github/workflows/...` 这类路径本身就是必要定位信息，可直接把相对路径作为链接文本，但仍必须是 Markdown 链接
- 若文件名重复或语义不清，链接文本应改为 `目录/文件名` 或简短语义名，避免歧义
- 允许使用 **mermaid** 图表表达复杂关系（依赖/阻塞/父子）
- 新建 issue 时，旧 issue 要追加回链评论

## 10. 回报用户格式（必须）

- 决策说明（追加/新建/回归）
- 当前状态（issue 编号、状态）
- 下一步建议（可执行动作）
