## 结论先行

### 结论 1：任务时间线必须切到任务域状态历史

任务时间线不应再以 `EventLog` 或旧时间块索引作为权威读模型，而应直接读取任务域自己的状态历史结构。

目标落点应是：

- `Task.status` 表达当前快照
- `Task.statusTransitions` 表达状态历史
- 任务时间线只根据 `statusTransitions` 生成“状态变化节点”
- 时间块只提供上下文与联动来源，不再承担任务状态历史的兜底读模型角色

### 结论 2：运行期兼容回退应直接删除

这项收口不应保留以下运行期回退：

- `EventLog -> 任务状态变化节点`
- `task.timeBlockIds + completed blocks -> 任务时间线`
- “没有任务事件就回退旧时间块范式”

原因很直接：

1. 任务状态变化首先是任务域事实，不是日志域事实。
2. `EventLog` metadata 已经出现 camelCase / snake_case 漂移，不能继续承担强合同。
3. 旧回退会长期维持“双范式并存”，让统一时间块类型与间隙时间块类型永远收不了口。
4. 继续靠日志和旧索引拼时间线，本质上是在用 side-effect 重建状态机，不符合当前架构方向。

### 结论 3：黄色语义必须只表达 `suspended`

任务时间线里的黄色节点 / 黄色段落，不应再承担“时间块暂停了，但任务其实还在 `in_progress`”这种叠加语义。

收口后的规则应是：

- 黄色 = `suspended`
- 如果需要黄色，就必须有对应的任务状态变化记录把任务切到 `suspended`
- 不再用“活动覆盖层”或“时间块暂停但任务未挂起”的方式伪造黄色时间段

### 结论 4：时间块暂停 / 恢复要显式驱动任务状态变化

如果时间块暂停时任务仍保持 `in_progress`，任务时间线就无法只根据任务域数据正确表达“当前没在做”。

因此应收口为：

- 时间块 `pause`：
  - 自动把该时间块关联且当前为 `in_progress` 的任务切到 `suspended`
- 时间块 `resume`：
  - 只把“本次 pause 自动挂起的那一批任务”恢复到 `in_progress`
- 时间块 `end`：
  - 最终状态仍由结束反馈里的 task outcomes 决定
  - 不额外制造一个“先 suspended 再 completed/cancelled”的中间写入

这样任务时间线才可以真正以任务状态变化为准，而不是再次借道时间块或 EventLog 做额外解释。

## 已确认决策

### 一、任务域新增 canonical primitive

建议新增：

```ts
type TaskStatusTransition = {
  id: string
  at: number
  fromStatus: TaskStatus | null
  toStatus: TaskStatus
  reason:
    | 'task.create'
    | 'task.transition'
    | 'timeblock.pause'
    | 'timeblock.resume'
    | 'timeblock.end'
  actorId?: string
  sourceHostId?: string
  operationId?: string
  relatedTimeBlockId?: string
  relatedTimeBlockTransitionRef?: string
  autoGenerated?: boolean
}
```

第一版建议直接内嵌在任务对象内，而不是先拆独立表：

- TS：`Task.statusTransitions`
- Rust：`Task.status_transitions`
- SQLite：`tasks.status_transitions_json`

原因：

1. 和时间块 `transitions` 方案一致。
2. API 面最小。
3. 任务时间线读取直接。
4. 大多数任务状态变化次数有限，第一版没必要先做二级索引表。

补充约束：

- `id` 必须是稳定主键，用于去重、复制与导入合并。
- `operationId` 用于把一次 pause / resume / end 联动写入串起来，保证幂等。
- 当前 `BlockTransition` 还没有独立 id，因此 `relatedTimeBlockTransitionRef` 在第一版应采用稳定复合键：
  - `<blockStartId>:<transitionType>:<at>:<actorId|system>`
- 如果后续给 `BlockTransition` 增加原生 id，再把该复合键升级为显式字段映射。

### 二、任务状态变化是 canonical write，EventLog 是 derived side-effect

任何任务状态变化都应先写任务域，再派生写日志。

顺序建议固定为：

1. 更新 `Task.status`
2. 更新 `Task.updatedAt`
3. 追加一条 `Task.statusTransitions`
4. 再发 signal / 写 EventLog / 触发 UI 通知

这样可以明确：

- 任务系统自身对“状态变化”负责
- EventLog 只做审计、叙事、跨域观察
- UI 不再依赖 EventLog 才能拼出时间线

### 三、时间块暂停 / 恢复联动必须可逆但不可乱恢复

仅仅在 `pause` 时把所有关联任务设成 `suspended` 还不够；`resume` 时如果无差别恢复，会把原本就是用户手动挂起的任务也误恢复。

因此至少要记录“本次 pause 自动挂起了哪些任务”。

推荐最小方案：

- 在时间块侧记录一组 pause-resume 联动元数据
- 或在任务状态 transition 上记录 `reason = timeblock.pause` 且挂上 `relatedTimeBlockTransitionRef`
- `resume` 时只回收：
  - `reason = timeblock.pause`
  - `relatedTimeBlockTransitionRef = 本次 pause`
  - 当前状态仍为 `suspended`

第一版不要求 UI 显示“这是手动挂起还是 pause 联动挂起”，但内部数据必须能区分，否则恢复会错误。

### 四、不做运行期兼容，但允许一次性迁移回填

“删除兼容回退”和“是否保留旧数据”不是同一件事。

推荐策略是：

- 运行期只认新结构
- 若希望保留旧任务历史，可在 schema migration 或一次性脚本中：
  - 从可信的旧 `EventLog` / 任务快照中回填 `statusTransitions`
- 迁移完成后，页面和 service 不再读旧源

如果团队决定更激进，也可以不做完整回填，只保留：

- `null -> pending` 初始记录
- 当前状态快照对应的最小闭合记录

但无论采用哪一种，都不应再保留运行期 fallback。

## 落地前提

### 一、先锁定复制模型，再把 `statusTransitions` 升成权威源

当前任务复制 / 导入 / peer reconcile 仍主要是：

- 整任务快照
- 以 `updatedAt` 为主的 LWW 合并

这和 append-only 状态历史不是天然兼容的。

因此在真正实现前，必须先锁定以下前提之一：

1. **推荐的 v1 路线：**
   - 在本轮迁移窗口内，明确任务状态历史采用 `single-writer per task/profile` 前提；
   - 同时把 `TaskStatusTransition.id / operationId / sourceHostId` 先补齐，给后续 per-transition merge 留好演化空间。
2. **若不能接受 single-writer 前提：**
   - 必须先拆出 `per-transition merge / dedupe / import reconciliation` 前置工作，再进入 schema rollout。

若以上前提未锁定，就不能宣称 `Task.statusTransitions` 已经具备“复制安全的唯一权威源”资格。

### 二、先定义跨 store 一致性策略，再落 `pause/resume/end` 联动

当前 runtime 中：

- `task_store`
- `timeblock_store`

是两套独立持久化边界，不存在天然单事务。

因此 Phase 2 开始前，必须明确应用层一致性策略，至少包括：

1. `pause/resume/end` 每次联动生成统一 `operationId`
2. task transition 与 timeblock transition 的固定写入顺序
3. 失败补偿 / repair 机制
4. 幂等重试规则
5. side-effect（EventLog / signal）只在主写入成功后发出

在这套策略写清楚之前，计划不能把 `Task.statusTransitions` 直接当作已经可靠的唯一权威源。

### 三、默认只承诺最小回填，完整历史回放另起一次性工具

双盲审阅确认了一点：当前旧数据并不支持“默认完整回填”的承诺。

因此本计划应改成：

- **默认承诺：最小回填**
  - `null -> pending`
  - 当前快照对应的最小闭合记录
- **可选增强：完整历史回放**
  - 另起一次性迁移工具
  - 显式处理 camelCase / snake_case EventLog metadata 混用
  - 显式处理非空 RT profile、旧 Web 数据与 mesh peer 混合数据

也就是说：

- 不再把“从旧 EventLog 完整回填历史”写成默认可行项
- 只把它视为额外的数据保真增强项

### 四、这轮删除的是“任务时间线 fallback”，不是全面停写 `timeBlockIds`

本轮要删除的是：

- 任务时间线对 `EventLog` 的权威依赖
- 任务时间线对 `task.timeBlockIds + completed blocks` 的权威依赖

但 `timeBlockIds` 目前仍被用于：

- 任务关联块索引
- 任务耗时累计
- 任务详情 / 今日页关联展示

因此本计划不会在同一轮里宣称：

- 停写 `timeBlockIds`
- 全局删除 `timeBlockIds`

它们仍需保留到专门的“任务-时间块关联索引收口”计划中再处理。

## 风险与验收重点

### 风险 1：pause/resume 恢复集合做错

如果没有区分“自动挂起”和“用户手动挂起”，`resume` 会误把手动挂起任务恢复成 `in_progress`。

### 风险 2：边迁边保留回退，导致双范式长期并存

这会让：

- 数据源不唯一
- 时间线 bug 继续被兼容层掩盖
- 统一时间块 / gap closeout 永远无法真正关闭

### 风险 3：把结束反馈写成两段状态变化

如果先写 `suspended` 再写 `completed/cancelled`，会制造不真实的时间线节点。

正确做法是：

- `pause` / `resume` 单独表达过程状态
- `end` 只提交最终 outcome

### 风险 4：复制 / 导入仍按整任务快照合并，导致历史分叉丢失

如果 `statusTransitions` 已落地，但 replication / import 仍按整任务 LWW 覆盖：

- 不同 peer 并发追加的 transition 可能互相覆盖
- 最终时间线会丢历史分支

因此必须先锁定 Phase 0 的复制门禁。

### 风险 5：RT 接管后 UI 双写未清，导致重复状态变化

如果 runtime 已经在 `pause/resume/end` 写 task history，而 UI 某些入口仍在 `endBlock()` 后自行 `transitionTask()`：

- 会产生重复 transition
- 会产生错误 `fromStatus`
- 也可能产生双份 EventLog / signal

### 验收重点

至少覆盖以下行为：

1. 创建任务后，任务对象内能看到初始化 transition。
2. 手动切换任务状态时，任务时间线节点正常生成。
3. 时间块暂停后，关联的进行中任务自动挂起，时间线显示黄色。
4. 时间块恢复后，仅自动挂起集合恢复进行中。
5. 时间块结束后，最终状态只按 outcomes 落地。
6. 任务时间线在没有 EventLog 的情况下仍可完整工作。
7. import / backup / replication / reconcile 不会丢失 `statusTransitions`。
8. legacy data 至少能完成最小回填，不会把老用户时间线直接打残。
9. `shortcut=true` 的多步状态机是否写多条 `statusTransitions`，必须有明确测试。

## 最终判断

如果目标是让任务时间线真正完成“新时间块系统下的完全迁移”，那就不应再保留任何运行期回退。

合理路线不是继续修补：

- `EventLog` 识别
- 旧 `task.timeBlockIds`
- 旧时间块范式 fallback

而是直接切换到：

- `Task.statusTransitions` 作为唯一权威源
- 时间块 pause/resume/end 通过任务域状态变化显式留痕
- 黄色只表达 `suspended`

这条路线的成本高于小修，但它是唯一能让“统一时间块类型”“间隙时间块类型”“任务时间线”三条线真正一起收口的做法。
