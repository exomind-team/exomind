## 3. 工程判断与阶段主线

### J01 · Alpha 先完成，而不是绕过

保留两阶段目标，先修骨架的隔离、裁剪与生命周期，再验收保存。 审计发现的风险会进入任何 Beta 外壳；直接改版会扩大未闭合责任。

归属：r2 工程建议，已在此次审批范围内执行；最终产品决定以审批文件为准。

### J02 · 同步是核心检查点

通用文件在单机保存可信后，马上验证同版本两端与 EasyTier；不把跨端推迟到所有 UI/模型完成以后。 这是近期阻塞继续使用的能力；如果最后才验证，可能重走旧版可见功能很多却无法互通的路。

归属：r2 工程建议，已在此次审批范围内执行；最终产品决定以审批文件为准。

### J03 · 保留原件，压缩的是阅读负担

原件、记录、引用与总结分别存在。总结折叠和整理视图不以自动清理为前提。 “临时 inbox”描述用途，不等于获准自动删除；长期保留成本通过明确手动清理解决。

归属：r2 工程建议，已在此次审批范围内执行；最终产品决定以审批文件为准。

### J04 · 阶段门按行为通过

健康检查、UI 卡片、测试计数和演示动画均不能替代实际持久回执与双端内容。 先前验收范围过窄、默认启动误接旧 RT 与后台写入均未被小套件覆盖。

归属：由审计支持的判断。

### J05 · 原版 React 界面接真实新核心

此前审阅页的 vanilla demo 保留为历史功能示意。当前可实测目标使用原 React 组件、布局与暖石样式，服务明确接新 Rust RT；合成夹具仅用于验证，不成为虚假业务回执。

归属：r2 工程建议，已在此次审批范围内执行；最终产品决定以审批文件为准。

### J06 · 工程事实由 Agent 查证

不把端口、并发取消、Rust 选型、哈希和源码归属转成用户问卷；只请你裁定价值、用途和体验。 super-questioning 的价值门：能查的先查，问题必须能改变方案。

归属：r2 工程建议，已在此次审批范围内执行；最终产品决定以审批文件为准。

Beta 内部每门都有可恢复工程检查点，不能把“B1/B2部分能力可用”称为完整Beta验收。**首次新schema合同就要预留记录修订、时间块并发、清理痕迹、引用缺口与恢复身份**；对应用户工作流可后续实现，避免同步完成后再推翻对象。

通用文件还需要最小真实输入/回执流程，不能只做一个后端blob接口。B1先验证接纳、固定提交快照、移除/取消、失败重试与真实读取；B2随后验证原件跨端。B3先做文字与已可读材料的时间块回顾，B4再扩媒体消费与语音派生。可以提前做非阻塞设计/模拟，不提前搬入正式Beta代码。

| 层 | 证明什么 | 不能替代什么 |

每条验收记录：需求/任务ID、来源commit、候选hash、实例hostId、协议/schema、隔离目录、平台/网络路径、合成输入、请求ID、本机回执、对端读数、用户路径、实际结果、失败/未测与证据。没有明确指标时先测真实量级，再做有范围的人类体验判断，不自造“99.9%”或跨端单程延迟。

验证顺序为相关Web/类型/行为测试 → Rust/RT合同 → 真实浏览器 → 原生宿主/设备；具体门需要哪层就补哪层。直接相关既有断言与禁止行为必须包含，不以全仓无关失败挡住修复，也不以局部套件抵消关键缺口。

当前用户目标选择开发分支 `dev-0.6`，仓库 `dev` 仍是开发主线；保存点先明确归属再推送，`main`不作为本轮开发目标。不得为了此计划创建新worktree、清空dirty改动、移动失败标签、把临时报告/截图/数据库加入源码提交。后续多Agent按独立职责分工，主代理统一复核diff/测试/运行证据；本轮可以使用明确授权的Sol routing selector，不能把选择器当作可核验的实际下游模型命中记录。

### Q03 · 记错后怎么改？

**问题：** 记录保存以后，修改文字/替换附件时，你希望看到怎样的结果与历史？

关联：B0 / B1。到对应行为实施前需要决定；当前计划和无关工作不等待。

背景：

- 原件保存已定，但“保留原件”不自动决定文字是否可编辑。旧架构强调留痕，Pro 以追加事实为主。
- 直接改当前显示更自然；追加更正更容易跨端解释，却可能让简单错字的记录变乱。

已经确定：总结不覆盖原文；错误/冲突不能静默吞掉。

尚未确定：错字更正、重要事实修订、附件替换是否需要不同语义。

答案的用途：影响修订事实、引用稳定性、同步冲突和回顾来源。

| 可行路径 | 得到什么 | 代价/范围 |
|---|---|---|

| 追加一条更正 | 行为简单、原始信息清楚。 | 错字或频繁修订会增加阅读噪音。 |
| 首版原文不改，仅追加 | 先把采集/同步做稳。 | 短期编辑体验受限。 |
