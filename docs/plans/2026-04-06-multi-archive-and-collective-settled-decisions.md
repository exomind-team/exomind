## 1. 去中心化前提

- 外心不强制中心化用户服务器或注册服务器
- 任何设备、任何档案都可参与组网
- 网络传输首先发生在 `RT` 之间
- 档案系统与集体协作系统都以此为逻辑前提

---

## 2. 档案身份与会话

### 2.1 档案身份

- 档案主键是不可变 `archive_id`
- 密码、token、邀请材料只是接入层
- 个人档案与集体档案在身份层同型

### 2.2 ArchiveSession

- 多档案并活是 `v1` 基础设施
- `ArchiveSession` 是一等运行时对象
- 其作用域完全本地于 `RT`
- 不跨 `RT` 同步
- 真相落在 `RT` 本地会话元数据
- 未被明确关闭的会话，`RT` 重启后默认自动恢复

### 2.3 会话状态

- 第一阶段状态收口为：
  - `running`
  - `closed`
- 同一档案可在多个 `RT` 上各自 `running`
- 外部 UI 连接单独建模为 `UiSession / ClientSession`
- `RT` 第一阶段只跟踪 UI 连接的：
  - `connected`
  - `disconnected`

---

## 3. 前台切换与资源占用

- “前台 / 后台”是 UI 视角概念，不是 `RT` 状态机字段
- 普通“切换档案”默认只切当前 UI 连接，不默认停旧档案
- 单例资源默认前台独占：
  - 主窗口焦点
  - 全局快捷键
  - 麦克风入口
  - 托盘主入口
- UI 未连接但仍 `running` 的档案，对该 UI 而言属于后台档案
- 连接未运行档案时，默认自动拉起其 `ArchiveSession`
- 必须区分“断开 UI 连接”与“关闭 ArchiveSession”
- 最后一个 UI 断开后，默认会话继续运行
- “自动关闭切出的档案”是 UI 侧快捷策略，第一阶段默认开启
- 切档案固定流程是：
  1. 先启动 / 连接新档案
  2. 若失败则回退到旧档案
  3. 若成功再请求关闭旧档案
  4. 若关闭旧档案失败，仍停留在新档案并显式报错
- 此前说的“硬切换”重定义为 UI 当前连接与前台资源的原子切换事务

## 4. Settings 分层

### 4.1 个人档案级

- 先采用广义档案态
- 个人 UI / 交互偏好默认跟档案走

### 4.2 集体本体级

- 持有治理规则、提案门禁、route 编辑门禁等公共规则
- 跨 `RT` 同步

### 4.3 成员 × 集体视角级

- 持有成员进入某集体时的工作面偏好
- 默认继承该成员个人档案偏好
- 可局部覆写
- 覆写在该成员各 `RT` 间同步

---

## 5. 集体档案模型

- 集体档案与个人档案同层并列为工作空间
- 集体档案有自己的 `ArchiveSession`
- 但 UI 前台接入的是“成员对集体的座席”，不是抽象集体本体
- 所有行为都以明确成员身份记账

### 5.1 固定角色

- `v1` 不引入固定的“管理员 / 创建者”角色
- 任何现有成员都可发起邀请提案
- 元治理按旧规则裁决

### 5.2 成员生命周期

最少显式区分：

- `inviting`
- `approved_pending_accept`
- `active_member`
- `exited`

加入流程：

1. 成员发邀请提案
2. 集体批准
3. 生成绑定目标个人档案的加入材料
4. 带外送达
5. 被邀请者在自己的个人档案中接受
6. 成员状态流转为正式成员

### 5.3 审计浏览

- 第一阶段优先提供对象局部历史
- 不先做厚重的全局审计总控台

---

## 6. 提案门禁粒度与可见性

集体档案默认不做“所有业务写入都逐条提案”，而是明确分层：

- 集体 `eventlog` 默认可直接写，但必须强审计
- 时间块计划走提案，执行记录直写并审计
- 任务结构变更走提案，执行反馈直写并审计
- 提案默认对所有 `active_member` 可见
- 成员可见性不自动等于 Agent 可见性
- `blackboard` 默认可直接写
- 但 Phase 1 不再按“长期保留 + 强审计总池”实现
- route / edge 编辑默认走提案
- 治理设置本身也走提案

同时：

- 允许少量枚举例外类别
- 通过集体 settings 配置开关
- 不做自由规则矩阵或通用规则引擎

---

## 7. Blackboard、Network v1 与集体 Agent

### 7.1 Blackboard

- 每档案一个持久 `blackboard`
- 不按每次会话重建
- `v1` 只承载共享工作记忆、协调便笺、交接摘要
- 不承载任务、时间块等业务真相
- 也不作为公共长期记忆总池
- 在集体档案中默认对 `active_member` 可读
- Phase 1 只先测试记录、存储与读写
- Phase 1 采用时间序条目 + 追加修正
- Phase 1 语义上是临时草稿区、容量受限缓冲区
- 默认允许成员与授权 Agent 写入
- 每条记录至少归因到作者与座席 / 设备
- 每黑板有总上限
- 所有保留条目都计入占用
- 达到阈值时先预警，再阻写
- 显式提供“弹出最早条目”释放空间
- Phase 1 不做 pin / protect
- 访问方式应靠近 node / workbench，而不是先做厚重独立页面
- 交互型请求可建立正式 route，并把弹出内容作为信号回送给发起者
- 这类 route 进入档案级持久路由，并在 route editor 可见

### 7.2 Network v1

- 采用“固定节点 + 可配路由”
- route table 是档案级持久配置
- `edge` 表达“输出后默认送达给谁”
- `v1` 没有连边就不能发消息
- 无边发信必须硬失败并提示先建边
- topic 先采用预注册集合
- 通配 `*` 只用于前端观察 / 诊断
- 禁用 route 记录 `skipped`
- 目标缺失或不可用记录 `failed`
- 人类可直接改边；Agent 改边默认通过提案或明确授权流程

### 7.3 集体 Agent 默认权限

- 集体 Agent 默认采用最小权限读面
- 每个 Agent 的可读范围单独配置
- tools 层显式区分读 / 写权限
- 写权限按角色输出受限，不默认等同成员的广泛写权限
- 审计需同时记录 Agent 身份与来源成员
- 集体 Agent 第一阶段最小现实形态，默认先挂在活跃成员的座席主机

## 8. 公开标识、邀请与 bootstrap

### 8.1 公开标识

- `v1` 先只给个人档案开放公开标识
- 公开标识映射到内部 `archive_id`
- 需显式开启后才存在
- `v1` 先只支持一个主公开标识
- 主公开标识默认长期稳定，仅在用户手动停用或重置时变化

### 8.2 名片与邀请材料

- 给人看的 `PublicCard` 与公开标识、邀请码分离建模
- 导入公开标识后，先解析最小名片供人类确认
- `InviteCredential` 与公开标识分离，只在集体批准后生成

### 8.3 找被邀请者

- 系统不负责全网搜人
- 系统只解析用户已经拿到的个人公开标识
- 首次找人只支持带外导入，如复制、扫码、文件、聊天等
- 邀请默认绑定到某个具体个人档案
- 邀请发起与批准阶段不要求目标当前在线

### 8.4 邀请送达

- 默认通过带外方式送达，如复制、扫码、文件、聊天等
- 被邀请者只能用被绑定的那个个人档案接受邀请
- 旧公开标识一旦失效，新的接受动作直接拒绝

### 8.5 关系沉淀与已知档案

- 接受前不创建正式关系对象
- 接受成功后，个人关系可沉淀为档案级 `KnownArchiveEntry`
- `KnownArchiveEntry` 在同一档案的各 `RT` 间同步
- 正式关系的稳定主键为 `archive_id`
- 条目同时保存最近看到的名片快照与本地备注 / 别名
- 关系对象允许延迟验证：旧标识失效时保留关系，但标记待更新
- 新鲜度默认通过再次接触或手动校验更新

### 8.6 集体与成员关系

- 个人档案与集体档案都可各自维护档案级关系记忆
- 但集体新成员接受加入后，首先落在集体成员表
- 这不等于自动给发起成员建立私人 `KnownArchiveEntry`

### 8.7 档案 bootstrap

- 新 `RT` 接入已存在档案，默认走显式配对 / 导入
- 现有“同名同密码自动相认”逻辑直接废弃
