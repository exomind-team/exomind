# 代码评审规范

> 本规范定义 ExoMind 项目的代码评审流程、维度和标准

---

## 1. 评审触发条件

以下情况必须进行代码评审：

| 触发条件 | 说明 |
|----------|------|
| 功能开发完成 | 特性开发完成后 |
| PR 提交前 | 合并到主分支前 |
| 安全相关代码 | 认证、授权、加密等 |
| 架构变更 | 模块重构、接口变更 |
| 修复 Bug 后 | 验证修复是否彻底 |
| 重大更新后 | 用户要求全面评审时 |

---

## 2. 评审维度

### 2.1 六大核心维度

| 维度 | 权重 | 说明 |
|------|------|------|
| **功能完整性** | 25% | 需求覆盖度、功能点完整性 |
| **安全性** | 25% | 输入验证、认证授权、数据安全 |
| **代码质量** | 20% | 可读性、可维护性、DRY原则 |
| **架构设计** | 15% | 模块划分、依赖关系、设计模式 |
| **性能** | 10% | 资源使用、算法效率、扩展性 |
| **测试覆盖** | 5% | 单元测试、集成测试、E2E测试 |

### 2.2 专项评审维度

| 维度 | 适用场景 |
|------|----------|
| **UI/UX** | 前端组件、用户交互 |
| **后端接口** | API 设计、数据传输 |
| **数据库** | 存储设计、查询优化 |
| **移动端** | 响应式、性能优化 |
| **安全** | 认证、加密、漏洞 |

### 2.3 商业评审维度（可选）

| 维度 | 说明 |
|------|------|
| **市场定位** | 目标用户、竞争格局、差异化 |
| **商业模式** | 可行性、收入预测、成本结构 |
| **竞争优势** | 独特价值、技术壁垒、护城河 |
| **风险挑战** | 市场、技术、运营风险 |
| **推进策略** | 路径选择、里程碑、行动计划 |

---

## 3. 评分标准

### 3.1 总体评分

| 分数 | 等级 | 说明 |
|------|------|------|
| 90-100 | A | 优秀，可直接合并 |
| 75-89 | B | 良好，小修改后合并 |
| 60-74 | C | 中等，需较多修改 |
| <60 | D | 差，需重大重构 |

### 3.2 问题严重程度

| 标记 | 级别 | 说明 | 处理时限 |
|------|------|------|----------|
| 🔴 P0 | 阻塞 | 阻断性问题，必须修复 | 立即 |
| 🟠 P1 | 严重 | 重要功能缺陷，应修复 | 24h |
| 🟡 P2 | 中等 | 一般问题，建议修复 | 1周 |
| 🟢 P3 | 轻微 | 优化建议，可延后 | 任意 |

## 4. 评审工作流程（SubAgent 并行模式）

### 4.1 工作流程图

```
┌─────────────────────────────────────────────────────────────────────┐
│                        评审工作流程                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1. 准备阶段                                                        │
│     ├── 确认评审范围和分支                                           │
│     ├── 获取 commit hash                                            │
│     ├── 收集相关文档（SPEC、PRD、商业计划）                          │
│     └── 创建评审目录                                                 │
│                                                                     │
│     ┌─────────────────────────────────────────────────────────┐   │
│     │  2. 并行评审阶段（4个 SubAgent 同时执行）                │   │
│     │                                                         │   │
│     │  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐    │   │
│     │  │ 功能与需求   │  │ 安全性      │  │ UI/UX       │    │   │
│     │  │ 评审        │  │ 评审        │  │ 评审        │    │   │
│     │  └─────────────┘  └─────────────┘  └─────────────┘    │   │
│     │                                                         │   │
│     │  ┌─────────────┐  ┌─────────────┐                     │   │
│     │  │ 模块与设计   │  │ 商业评审    │  ← 可选            │   │
│     │  │ 评审        │  │ (战略决策)  │                     │   │
│     │  └─────────────┘  └─────────────┘                     │   │
│     └─────────────────────────────────────────────────────────┘   │
│                                                                     │
│     3. 整合阶段                                                     │
│     ├── 汇总 4 个维度的评审结果                                     │
│     ├── 生成综合评审报告                                            │
│     ├── 计算总体评分                                                │
│     └── 归档到 agent-output/review/                                │
│                                                                     │
│     4. 输出阶段（可选）                                             │
│     ├── 从报告提取问题创建 GitHub Issue                             │
│     ├── 标记优先级（P0/P1/P2）                                      │
│     └── 关联代码位置                                                │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 SubAgent 并行评审配置

| SubAgent | 评审维度 | 核心任务 |
|----------|----------|----------|
| **功能与需求评审** | 功能完整性 | 模块状态、缺失功能、测试覆盖 |
| **安全评审** | 安全性 | 输入验证、认证授权、数据安全、网络安全 |
| **UI/UX评审** | 前端体验 | 组件完整性、交互体验、视觉一致性 |
| **模块设计评审** | 架构设计 | 模块职责、接口设计、代码结构、设计模式 |

### 4.3 评审输出模板

**每个 SubAgent 输出**：
- 模块实现状态（✅/⚠️/❌）
- 缺失功能列表
- 关键代码问题（含行号）
- 改进建议

## 6. 评审报告与 GitHub Issue 的配合

### 6.1 混合模式（推荐）

**工作流程**：
```
1. 评审报告 → 放入 agent-output/review/
   └── 完整报告、详细分析

2. 提取问题 → 创建 GitHub Issue
   └── 问题清单、优先级、分配

3. 修复完成 → PR 关联 Issue
   └── 引用 Issue #10, #11

4. 状态追踪 → GitHub Projects
   └── 看板管理、里程碑
```

### 6.2 Issue 模板

```markdown
## 问题分类
- [ ] 功能缺陷 (Bug)
- [ ] 安全漏洞 (Security)
- [ ] 性能问题 (Performance)
- [ ] 代码质量 (Code Quality)
- [ ] 架构设计 (Architecture)

## 问题描述
**严重程度**：🔴 P0 / 🟠 P1 / 🟡 P2 / 🟢 P3
**模块**：
**位置**：`file:line`

```
代码片段
```

**影响**：
-

**修复建议**：
1.

**相关文件**：
- `path/to/file1`
- `path/to/file2`

**相关评审报告**：
`agent-output/review/YYYY-MM-DD-xxxxxxx/综合评审.md`
```
