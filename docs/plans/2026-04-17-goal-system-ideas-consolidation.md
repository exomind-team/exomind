# Goal System v0.4 语义收口与想法归一

> 目的：在上下文压缩前，把当前已经收敛出的 `goal-system v0.4` 方向完整落盘，作为后续继续细化 spec、更新 GitHub issue、推进实现的基线文档。

## 0. 原始想法摘录

原始表述如下，完整保留：

> ①目标是任务系统的新视图，但基于视图还有更多的东西，就是将任务从节点看成边、随后引入新的「节点」类型——目标
>
> ②每个任务都必然指向一个目标节点，但每个任务指向的目标节点是可变的——可以多个任务指向一个目标节点，也能一个目标节点发出多个任务
>
> ③任务的依赖关系天然表现在目标的连接关系中，因为其本质就是「任务指向目标」——一个任务若有上游任务，那这个任务必然基于所有上游任务节点的目标节点（不论直接还是间接），而一个任务没有上游任务（是根），则其表示为从Me节点（目标节点的根）到其终点的边。
>
> ④目标节点依托任务存在，任务不存在了，目标节点就会少一条依托，而正常时候不会存在没任务作为连边的目标节点。一条边（或者有多个起点、一个终点的超边？）唯一对应一个任务，而不会有多余冗余存在。
>
> ⑤任务之间可以用「共同目标」相关联，任务之间原本不同的目标可以经过操作变成是相同的，这时候有多个任务指向同一个目标，而这些任务的下游依赖则都表现为从这个「共同目标节点」所发出的边
>
> ⑥这时候「目标节点」其实就是先前在issue中讨论过的「随着任务自动完成的任务」，而现在这份语义恰好给「目标」承载了
>
> ⑦这个新的「目标系统架构」强化了与任务系统的联系，降低使用的认知负荷（因为更不需要维护两套任务系统了，目标系统不需要绑定任务，而只需专注目标本身，匿名目标节点会因为任务的增加而自动生成）
>
> ⑧这个新的目标系统设计，应该是与先前的目标系统设计是兼容的

## 1. 当前结论（一句话）

把现有 `goal-system` 从“与 Task 系统解耦的独立图”收口为“任务系统之上的主事实层目标图”：

- `GoalNode` 是主节点语义。
- `Task` 是严格唯一对应任务的边语义。
- `Me` 仍是根节点。
- 不再保留“匿名边”作为槽位概念，改为“匿名目标节点”。
- 多前提默认通过“共同目标”归一，不先引入超边。
- `completionRule` 继续保留为核心，用来表达“任务完成如何推进目标达成”。
- 术语上开始区分：`任务完成` 与 `目标达成`。

## 2. 这轮已经锁定的主决策

### 2.1 事实层定位

- `goal-system` 是 **RT 主事实层**，不是纯 UI 派生视图。
- `GoalsPage` 只是这套事实层的一种交互视图，不是唯一存在位置。
- 任务系统与目标系统不是两套平级真相源；目标图应成为任务系统之上的更高层语义编排面。

补充理解：

- 由任务能重建一部分目标系统，因为边与任务是一一对应的。
- 但无法完整重建目标系统节点，因为节点的排布与组织方式本身也是目标系统的事实。
- 目标系统的点边关系更新，一般应从任务系统更新，而不是完全反过来。

### 2.2 任务、边、节点的主语义

- 一个任务严格唯一对应一条边。
- 一个任务严格唯一对应一个终点目标节点。
- `GoalNode` 是目标、阶段、共同目标的承载体。
- `Task` 是从某个前提状态走向某个目标的行动路径。

这意味着：

- 旧 `TaskEdge = 槽位` 的解释需要被重写。
- 新解释更接近：`TaskEdge = 任务在目标图中的主表达`。

### 2.3 匿名语义

- **没有匿名边，只有匿名目标节点。**
- 匿名目标节点不是纯结构垃圾节点，而是“真实但待命名的 goal”。
- 自动生成的匿名节点，后续允许用户延迟命名，不要求创建当下就命名。

### 2.4 多前提的主表达

- 一版主路线不引入超边。
- 多前提默认走“共同目标归一化”。
- 当多个任务的结果需要汇聚成一个后续前提时，系统自动插入匿名的共同目标节点，然后由用户后续命名或继续调整。

当前保留判断：

- 这条路线更兼容现有普通有向图、现有布局和现有 `completionRule`。
- 但它会引出新的结构边界情况，需要后续专门讨论。

### 2.5 完成/达成语义

- `任务完成` 推进 `目标达成`。
- `completionRule` 继续保留为核心。
- 普通目标与共同目标都通过 `completionRule` 达成，不为二者拆两套完成模型。

默认理解：

- 对普通目标来说，最常见情况是它只有唯一来源边，于是表现为“其唯一任务完成，则目标达成”。
- 对共同目标来说，多入边才会形成真正的“共同目标节点”，其达成仍由入边规则纯推导。

### 2.6 goal 侧的可编辑边界

- 默认编辑链路是“任务改目标”。
- 与此同时，目标也能修改“它自己的东西”。

这里的“自己的东西”目前收口为：

- 可以改节点属性。
- 可以改局部结构。
- 可以做目标合并。
- 暂不做目标拆分。
- 不通过 goal 侧去改写“一个任务唯一指向一个终点目标”这条主语义。

### 2.7 目标合并

- 当前只考虑 **目标合并**，不考虑目标拆分。
- 合并的主目的，是让原本分散的目标语义收敛成同一个目标。
- 当前倾向是不额外生成新边，也不优先走“新建父目标”的父子结构表达。

这意味着：

- 合并更接近“二者收敛成一个目标”。
- 它不是创建一个全新的抽象上位父目标来承接原目标。

## 2A. 问答决策日志（本轮 super-questioning 收敛结果）

下面保留本轮关键问答的收敛结果，避免只剩摘要、丢掉推理细节。

### Q1. 新的 goal-system 在事实层是什么？

结论：

- 选择：`主事实层`

补充说明：

- 目标在任务之上有自己的编排。
- 目标的每条边严格唯一对应任务。
- 节点的排布方法是目标自身存储的事实。
- 由任务能重建一部分目标，因为边是一一对应的。
- 但无法完整重建目标系统的节点。
- 目标系统更新点边关系时，一般来说只能是从任务系统更新，而非反之。

### Q2. 多上游依赖主表达是什么？

结论：

- 选择：`共同目标归一`

补充说明：

- 这条路线可以接受。
- 但它可能会引发更多新情况，后续需要继续讨论补规则。

### Q3. 匿名边、任务边和真实 Task 实体的关系怎么定？

结论：

- 选择：`边是任务主表达`

补充说明：

- 新设想里不需要匿名边。
- 也应该没有匿名边的存在。
- 只有匿名节点。
- 结构上应该更简洁，但仍需要继续证明。

### Q4. 匿名节点默认更接近哪种语义？

结论：

- 选择：`待命名目标`

### Q5. task 系统和 goal 系统之间，哪边是默认编辑入口？

结论：

- 选择：`任务改目标`

补充说明：

- 与此同时，目标也能改其自己的内容。
- 这也是“目标基于任务”而不是“目标等于任务”的原因之一。

### Q6. 多个任务汇聚成同一“共同目标”时，这个节点怎么出现？

结论：

- 选择：`自动生成`

补充说明：

- 自动插入匿名目标节点即可。
- 用户可以延迟命名。
- 但这个节点必须存在。

### Q7. “目标也能改其自己的”，这里的“自己的”具体指什么？

结论：

- 选择：`可改局部结构`

补充说明：

- 除了节点归属，其他都属于“自己的东西”。
- 目标之间的拆并，不会影响任务的目标边。
- 当前只考虑目标的合并。
- 先不考虑目标拆分，因为那会影响“一个任务只对应一个目标节点作为其终点”的语义。

### Q8. 自动生成的共同目标节点怎样达成或退出？

结论：

- 选择：`由入边纯推导`

补充说明：

- 当前推理中，多入边才会形成“共同目标节点”。
- 其他情况还需要进一步探讨。

### Q9. 旧 completionRule / AND-OR 规则在新想法里怎么处理？

结论：

- 选择：`继续保留为核心`

补充说明：

- 需要为目标节点的“达成”语义留出空间。
- 潜在未解问题是：任务的完成会怎样影响目标的达成？
- 把任务关系引入目标节点间拓扑结构后，需要怎样对齐“任务的完成”与“目标的达成”？
- 当前倾向是：任务的完成自动推进目标的达成。
- 这个自动推进方式，仍以 `completionRule` 为核心，只是可能要基于新架构更新表达。

### Q10. 两个目标被“合并”为共同目标时，默认更接近哪种语义？

结论：

- 名义选项上接近：`其中一个吞并另一个`

实际补充说明：

- 二者合并成一个新目标。
- 目的在于不生成新边。
- 因为边的语义现在跟任务强绑定，没有匿名边作为“槽位”语义了。

### Q11. 不是“共同目标”的普通 goal，默认怎样达成？

结论：

- 选择：`仍靠 completionRule`

补充说明：

- 默认就是其唯一来源边的任务完成，这个目标就达成。
- 这符合“一个任务完成，代表一个目标达成”的用户语义。
- 用户即便只用任务系统，目标系统也应自动形成一个大致可用的图景，并随任务变化自动更新。

### Q12. “任务完成”和“目标达成”的关系怎么定？

结论：

- 选择：`任务完成推进目标达成`

补充说明：

- 日后术语上都用“达成”替代“目标完成”，用来区分任务与目标。
- 对共同目标来说，任务完成意味着它在达成的路上，进度更进一步。

### Q13. 本轮是否还有没问到的关键问题？

结论：

- 当前仍有两个大块未完待续：
  - 术语层
  - 演化路径

这两块明确作为下一步工作，而不是本轮继续扩散。

## 3. 对现有体系的影响

### 3.1 直接继承的东西

- `MeNode`
- `GoalNode`
- `TaskEdge`
- `completionRule`
- `Me` 作为根节点
- 目标图是普通有向图

### 3.2 需要重写解释的东西

- `TaskEdge = 任务槽位` 要改写为 `TaskEdge = 任务主表达`
- 旧“匿名边”语义废弃
- `task.statusChanged -> goal recompute` 不再只是桥接增强，而更接近主状态传播链

### 3.3 暂不纳入 v0.4 主体的东西

- 超边
- 目标拆分
- 双向等权编辑
- 彻底移除 `completionRule`

## 4. 术语层：下一步必须继续收口

这轮已经明确，“术语层”是下一步必须落实的第一优先级。

至少要统一以下几组词：

- `任务完成` vs `目标达成`
- `普通目标` vs `共同目标`
- `匿名目标节点` vs `待命名目标`
- `局部结构编辑` vs `任务事实编辑`
- `目标合并` vs `目标拆分`

当前临时默认：

- `完成` 保留给任务
- `达成` 保留给目标

## 5. 演化路径：下一步必须写清

这轮已经明确，除了术语层，下一步必须落实的就是“演化路径”。

至少要写清：
