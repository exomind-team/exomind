# 工作 Agent 审阅处理流程

## 阻塞输入

下列输入都视为阻塞项：

- `REQUEST_CHANGES`
- 新的 `[Codex Reviewer]` 评论（不区分内容，包含“未发现问题/状态同步”）
- 新的人类普通评论
- `[Codex Reviewer] ❤️ 需要人类测试`
- `🙋needs-human-test`

## 优先级规则

优先级按风险排序：

1. `REQUEST_CHANGES`
2. `[Codex Reviewer]` 新意见
3. 新的人类普通评论
4. 人测阻塞与 CI 失败

## 先回复，再决策

工作 Agent 处理审阅反馈的默认策略是：

1. 先引用原意见。
2. 先回复确认理解。
3. 再决定改代码、解释原因，还是明确无需改码。

这条规则同样适用于人类普通评论。

## 不允许沉默规则

工作 Agent 不允许对 `[Codex Reviewer]` 评论保持沉默。

- 无论评论内容是否为“未发现问题/状态同步”，都必须回复。

## 先回复，再 `cursor sync`

回复审阅者评论后必须立即执行 `cursor sync`，否则下一轮 `next-action` 会再次把同一条评论视为阻塞项。

## 无需改码时的回复要求

即便这轮无需改码，也要发结构化 `[Codex Worker]` 评论，说明：

- 为什么无需改码
- 已检查了什么
- 结论是什么

## 恢复开发边界

只有当前 `head SHA` 上没有未处理阻塞项时，才允许继续推进原始开发任务。

不允许一边欠 review 债，一边继续扩功能。

## `cursor sync` 规则

当当前这批审阅反馈 / 人类评论已经被处理并吸收后，工作 Agent 应运行一次 `cursor sync`，把当前评论/审阅集合写入已处理游标。

否则同一批反馈会在下一轮继续被识别为“新阻塞项”。
