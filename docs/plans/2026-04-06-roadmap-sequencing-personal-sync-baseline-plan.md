# 2026-04-06 路线顺序与个人同步基线计划

> 状态：已收口阶段顺序
>
> 目的：把“哪些主题先做、哪些主题并行、哪些主题后置”从聊天判断收口成一份稳定路线文档。

---

## 1. 路线摘要

近期总路线先不以“完整集体档案系统”作为第一交付，而先收口一个更贴近现实开发收益的里程碑：

1. **第一里程碑：个人同步基线**
2. **第二主线：信号网络 v1**
3. **第三主线：单 Agent 时间块闭环**
4. **之后再推进更强的多档案 / 集体档案主线**

并行但不抢主线关闭条件的主题：

- `Web API Agent` 持久化：放在信号网络之后
- 集体记账独立系统：并行产品化设计与实现
- 对外文档 / 宣传描述：只跟随已验证里程碑推进
- `Agent` 能量双计量：放在单 Agent 闭环之后接成治理 / 调度层

---

## 2. 第一里程碑：个人同步基线

### 2.1 目标

在信号网络、集体档案、完整多 Agent 体系全部完成前，先把个人档案的跨端同步做成一个真实可用、可验证、能直接反哺后续开发过程的基线。

### 2.2 范围

第一里程碑覆盖以下数据域：

- `EventLog`
- `TimeBlock`
- `Task`
- `Settings`
- `Proposal`

其中 `Proposal` 在这一阶段只收口到：

- 草案内容一致
- 列表一致
- 状态一致

不把“审批执行后的业务副作用”强行塞进同一关闭条件。

### 2.3 验收梯子

个人同步基线不是单跳关闭，而是分层验收：

1. **桌面标准链路**
   - 以 `Web + Desktop` 作为标准起步拓扑
   - `Tauri manager` 与 `Tauri MCP` 作为桌面真实验收标配
   - 允许用 `Windows ↔ Windows` 或 `Web + Desktop` 先建立基础证据
2. **`Windows ↔ Android` 真机链路**
   - 作为里程碑关闭前必须补过的真实跨设备链路
3. **`Android ↔ Android` 近场链路**
   - 明确纳入同一基线的最终关闭条件
   - 包括手机热点 / 近场接续场景

也就是说，第一里程碑不是“桌面先绿就算完成”，而是必须走完整个验收梯子。

## 3. 个人同步基线之后的主线顺序

### 3.1 信号网络 v1

个人同步基线完成后，下一主线是：

- 固定节点
- 可配边
- 预置连边
- 内建领域节点

不把 `Web API Agent` 持久化绑成同一轮主线。

### 3.2 单 Agent 时间块闭环

在信号网络 v1 上，优先验证：

- `timeblock.completed`
- 总结
- 建议
- `pending proposal`

这条闭环是信号网络的关键用户叙事。

### 3.3 多档案 / 集体档案主线

多档案、`ArchiveSession`、成员座席、集体档案与治理门禁，仍然是长期主线，但不再作为近期第一交付来卡住前面的同步与网络里程碑。

---

## 4. 并行但不并批的主题

### 4.1 Web API Agent 持久化

- 放在信号网络 v1 之后
- 不与信号网络骨架捆绑为同一关闭条件

原因：

- 先有统一的节点 / 路由 / 存储与通信壳层
- 后续再把 `API Agent`、终端 Agent 等更稳妥地接成信号节点

### 4.2 集体记账独立系统

- 作为独立系统并行推进
- 先做独立产品与数据壳层
- 后续再讨论如何并入外心

### 4.3 对外文档 / 宣传生成

- 只跟随已验证里程碑推进
- 不允许宣传文案反向定义尚未验证的内部架构

### 4.4 Agent 能量双计量

- 放在单 Agent 关键闭环之后
- 第一阶段优先承担运行调度，不与信号网络 v1 同批关闭
- 采用“运行资源 + 模型资源”双账本同界面，而不是单一总指标

---

## 5. 一句话总结

近期总路线应按“**个人同步基线先落地 → 信号网络 v1 → 单 Agent 时间块闭环 → 再抬升到更强的多档案 / 集体主线**”推进；`API Agent` 持久化、集体记账与对外叙事都要继续推进，但不与当前第一里程碑绑成同一关闭条件。
