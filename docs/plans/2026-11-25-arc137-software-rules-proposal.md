## 建议进入 Skill 的正文

**何时使用**　设计或审阅软件的可配置行为、存储放置策略、输入和通知通道、自动化接管方式，或决定哪种行为成为推荐默认值时使用。项目私有的阈值、具体按键、网络名称和界面布局归产品自己的配置或宿主规则。

1. **先描述用户有理由作出的不同选择。** 对每个会改变结果的选择写明对象、作用范围、所有者、可用条件、切换代价与恢复方法。例：选择让某台设备长期保留原件，和选择本次从哪台下载，分别影响保留策略与传输任务。
2. **让变化有稳定入口。** 同一个策略有一个权威表示，UI、CLI 和 Agent 使用同一动作与状态。用户可以查看当前有效值和来源，修改、恢复推荐值，跨环境限制有解释。入口按场景提供，常用任务使用简洁默认路径，低频选项在相关位置展现。一个清楚的模式切换按钮也可以承载多种工作方式。
3. **推荐值以实际任务为依据。** 保留可行的策略，再选初始可用配置。记录目标用户、样本场景、平台能力以及触发调整的证据。正式推荐可以随使用验证更新，显式选择和既有数据按迁移合同保留。例如小文件自动取件和大文件按需是可测组合，阈值应由介质成本、耗时和失联后的可用性共同决定。
4. **自动化承担已能判断的工作。** 路线切换、重复事件、可重试故障在用户设定范围内自动处理。执行者保留最后证据、截止时间和接管入口。只有当需要新的授权、不可恢复的取舍或无法保留用户意图时才打扰人。
5. **把不变量写清楚。** 能力选项必须服从身份、授权、数据完整性和宿主实际能力。配置审批者可以选择共享范围与方式，执行者必须证明持有相应权限。新策略能否只修改对应所有者，是可扩展性的日常检验。

**设计审查用例**

| 场景 | 推荐路径和替代路径 | 可证伪的评审问题 |
|---|---|---|
| 输入和模式 | 初次打开可直接记录；需要时切到专注或导出。显式按键绑定可压过自动检测 | 只用触摸能否找到入口，改了作用域后另一程序是否仍收到错误的操作？ |
| 原件与持久化 | 普通场景用推荐持有策略；有带宽或离线要求时配置指定 RT、大小条件或手动取件 | 改动设置后，运行端是否遵守，是否能分辨「希望有副本」与「已验到副本」？ |
| 逻辑提醒 | 一个客户端针对一次到期发起一次提醒，通道可独立开启；文字内容让获权工具继续处理 | 只开通知、由第三方播报能否工作？重放旧事件时是否重复响？ |
| 异常与权限 | 短暂失联按预算恢复，拒绝时给人可行动的状态。Agent 与 UI 可用合适形式读取同一个结果 | 新运行会否因可恢复错误反复打扰人？用户撤销后能否停止？ |
| 反例 | 为《所有行为可选》做出一个永久跳过授权的开关，或把每项能力都做成日常首页上的按钮 | 前者使授权合同失效，后者挤走用户真正要完成的任务。设计应同时保住操作范围与日用路径 |
