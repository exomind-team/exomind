| ECS-3 组网/发现/mDNS | **文档标注未实现，但 mesh relay 已存在** | `crates/exomind-runtime/src/mesh/mod.rs` | 生产级（mesh relay 超出文档描述） |
| ECS-4 会话管理（SSE） | 已实现 | `crates/exomind-runtime/src/routes/signals.rs` | 生产级 |

---

### Layer 2: EDS 对象同步层

**计划文档中定义的职责**：对象同步单位、delta/snapshot 格式、scope 隔离。

**现状评估**：

#### Task 域 — 最成熟

| 组件 | 实现位置 | 状态 |
|------|---------|------|
| `TaskReplicationSummary` 契约 | `task-backup.service.ts` | 生产级，有完整类型 |
| `TaskReplicationPullCursor` | `task-backup.service.ts` | 生产级 |
| `TaskReplicationPullResult` | `task-backup.service.ts` | 生产级 |
| `TaskReconciliationService`（摘要比较→pull→snapshot fallback） | `task-reconciliation.service.ts` | 生产级，有 7 个单测覆盖关键分支 |
| `TaskRtAdapter.applyReplicationSnapshot` | `task-rt-adapter.ts` | 生产级，调用 `POST /tasks/replication/upsert` |
| `TaskBackupServiceImpl`（pull/snapshot/summary 路由客户端） | `task-backup.service.ts` | 生产级 |

#### EventLog 域 — 仅快照 fallback

- **无** `EventLogReconciliationService` 或等效的摘要比较逻辑
- `RtDomainBackfillService` 中对 eventlog 只做：`exportPeerEventsAsSqliteSnapshot` → `importEventsFromSqliteSnapshot(..., 'merge')`
- **没有** `EventLogSummary` 契约（虽然文档中定义了建议结构）
- **没有** 增量 pull 路径，只有 snapshot import

#### TimeBlock 域 — 仅快照 fallback

- 与 EventLog 类似，只有 snapshot import，没有摘要比较或增量 pull
- `RtDomainBackfillService` 中对 timeblocks 也是盲跑 snapshot export/import

**判断**：EDS 对象同步层在 Task 域是生产级的（`summary→compare→pull→snapshot fallback` 全链路），但在 EventLog 和 TimeBlock 域还停留在"盲跑 snapshot"的早期阶段。

---

### Layer 3: Recovery / Reconciliation 层

**计划文档中定义的职责**：anti-entropy、bootstrap/backfill、snapshot fallback、reconnect repair。

**现状评估**：

#### Task域 — 已闭环（生产级）

`TaskReconciliationService` 实现了完整的三阶段 reconciliation 策略：
- `noop`：摘要一致则跳过
- `pull`：远端更新则走增量 pull + `applyReplicationSnapshot`
- `pull_then_snapshot`：pull 后仍 drift 则 fallback 到 SQLite snapshot merge
- `unresolved`：超出 merge 语义时显式记录，不谎称收敛

#### EventLog/TimeBlock 域 — 早期阶段

`RtDomainBackfillService` 对这两个域只做"满足前提就盲跑 snapshot import"，没有摘要比较，没有漂移检测，没有条件触发补偿。

#### PeerScopeGrant — 已实现（生产级）

`crates/exomind-runtime/src/mesh/mod.rs` 中的 `MeshState` 提供了完整的 `PeerScopeGrant` 管理：
- `upsert_scope_grant()` — 创建/刷新 grant
- `resolve_scope_key_for_peer_domain()` — 查询 grant，带唯一性检查（fail closed）
- `revoke_scope_grant()` / `revoke_all_scope_grants_for_peer()` — 生命周期撤销
- 与 `peers/interests` 一起持久化到 `mesh-state.json`

**判断**：Recovery 层在 Task 域是完整的，在 EventLog/TimeBlock 域仍是"盲跑 snapshot"模式。PeerScopeGrant 体系已完整实现并持久化。

---

### Layer 4: 投影层（Projection Layer）

**计划文档中定义的职责**：同步对象→领域对象→UI 可消费状态。

**现状评估**：
- `notifyTaskDataChanged()` 和 `notifyTimeBlockDataChanged()` 存在——但这只是通知层，不是真正的投影层
- **没有** 专门的 `DomainProjector` 抽象或框架
- **没有** 增量事件驱动的投影刷新机制（只有粗暴的全量 `notifyChanged`）

**判断**：投影层薄弱，不是独立的架构层次。

---

### Layer 5: 校验层（Validation / Audit Layer）

**现状**：
- `TaskReconciliationService` 记录 `unresolvedDrift` 标志和 `strategy` 分支——这是"显式记录未收敛"，符合原则
- 但没有独立的 validator 框架
- 没有 conflict object 建模
- 没有 audit trail 持久化

**判断**：校验层处于萌芽状态，只有 Task 域在 reconciliation 层面有基本的 drift 标记。

## 2. 关键链路完整性

### Task 同步链路（最完整）

```
本地写入 → task.replication.upserted signal（RT publish）
  → mesh relay 转发
  → 对端 SignalPool 接收
  → domain projector 消费
  → TaskRtAdapter.applyReplicationSnapshot → POST /tasks/replication/upsert
  → RT SQLite upsert_scoped()
  → notifyTaskDataChanged() → UI 刷新

重连/周期 reconciliation：
  RtDomainBackfillService.backfillConfirmedPeers()
    → reconcileScopeGrants()
    → TaskReconciliationService.reconcilePeer(peerId)
      → getTaskReplicationSummary() [本地 RT]
      → getPeerTaskReplicationSummary(peerId) [peer via local proxy]
      → summariesEqual? → noop
      → pullPeerTaskReplicationBatch() → applyReplicationSnapshot() → importTasksFromSqliteSnapshot() fallback
      → notifyTaskDataChanged()
```

**链路状态**：闭环，生产级实现，有测试覆盖。

### EventLog 同步链路

```
本地写入 → eventlog.replication.appended signal
  → mesh relay 转发
  → 对端 SignalPool 接收
  → domain projector 消费
  → RT eventlog store 写入

重连/周期：
  RtDomainBackfillService.backfillConfirmedPeers()
    → exportEventsAsSqliteSnapshot() [peer RT]
    → importEventsFromSqliteSnapshot() [本地 RT merge]
```

**链路状态**：live path 存在，reconciliation path 只有 snapshot fallback，**没有摘要比较**。

### TimeBlock 同步链路

- Active block：`active_block.replication.snapshot`（live path）
- Completed block：`timeblock.replication.completed`（live path，新增）
- Reconciliation：snapshot export/import（盲跑，无摘要比较）

**链路状态**：live path 存在，reconciliation path 薄弱。

## 4. 缺口清单

### 严重缺口（阻塞核心叙事）

1. **EventLog Reconciliation Adapter 缺失**：没有摘要比较，没有增量 pull，只有盲跑 snapshot import。当 EventLog 数据量大或 drift 是增量变化时，每轮都做全量 snapshot 不可接受。

2. **TimeBlock Reconciliation Adapter 缺失**：同样只有盲跑 snapshot import，active block 和 completed block 的 reconciliation 策略未独立实现。

3. **统一 DomainReconciliationAdapter 接口未抽象**：TS 层没有 `DomainReconciliationAdapter<TSummary, TPullCursor>` 接口，三个 domain 的 reconciliation 策略不一致。

4. **ECS-3 文档与实现严重不符**：`mesh/mod.rs` 的 mesh relay 已经是生产级实现，但 `ECS-communication-stack.md` 标注为"未实现"。这会导致后续 agent 和开发者误判系统成熟度。

### 中等缺口

5. **EventLog/TimeBlock peer-auth 路由未实现**：设计文档定义了 `/mesh/eventlog/*` 和 `/mesh/timeblocks/*` 路由，但代码中只有 task 的 peer-auth 路由（`/mesh/tasks/*` 在 auth 白名单中）。

6. **Projection Layer 不是独立架构层次**：当前只有全量 `notifyChanged()`，没有按 domain/change-type 的细粒度投影刷新。

7. **Validation/Audit Layer 薄弱**：只有 Task 域在 reconciliation 中标记 `unresolvedDrift`，没有独立的 validator 框架，没有 conflict object 建模。

8. **Reminder 域仍是 Pouch 残留**：Reminder 没有 RT backend，仍使用 Pouch adapter，没有纳入 reconciliation 框架。

### 轻微缺口

9. **DSON 未落地**：只是 greenfield 研究，不是当前开发目标。EDS 当前走的是"摘要比较 + SQLite merge"路径，不是 CRDT 路径。

10. **ECS-2 传输抽象层未正式引入**：`Transport` trait 未抽象，当前直接用 Axum + SSE。

11. **跨 RT 路由表同步未实现**（ECS-5 未来增强项）。

## 5. 综合判断

### 成型 / 部分成型 / **早期阶段**

**判断：部分成型（Phase 1-2 完成，Phase 3 局部完成）**

具体原因：

**已成型部分**：
- ECS 网络层（TCP + SSE + SignalPool + mesh relay）——生产级，代码量和测试覆盖充分
- Task 域的端到端同步链路（live signal + reconciliation + `applyReplicationSnapshot`）——生产级，链路闭环，有完整测试
- PeerScopeGrant 鉴权体系——生产级，持久化，生命周期管理，唯一性 fail closed
- Auth middleware（peer identity 注入 + 精确白名单）——生产级
- `TaskReplicationSummary` / `TaskReplicationPullCursor` / `TaskReplicationPullResult` 契约——生产级

**部分成型部分**：
- EventLog/TimeBlock 的 live replication（signal path 存在）
- `RtDomainBackfillService` 作为协调层（调度点正确，但内部 reconciliation 逻辑只有 snapshot fallback）
- ECS-3 mesh relay（代码生产级，但文档标注"未实现"）

**早期阶段部分**：
- EventLog Reconciliation（无摘要比较，无增量 pull）
- TimeBlock Reconciliation（无摘要比较，无增量 pull）
- 统一 DomainReconciliationAdapter 接口
- Projection Layer（无细粒度投影框架）
- Validation/Audit Layer（无独立框架）

**一句话定性**：

> Task 域的 EDS 同步架构已成型（摘要比较→增量 pull→snapshot fallback 全链路），但 EventLog 和 TimeBlock 域仍停留在"盲跑 snapshot"的早期阶段；ECS 网络层整体生产级但文档严重滞后；Projection 和 Validation 层仍是缺口。EDS 架构的"核心叙事"（跨设备数据同步）以 Task 域为代表已可验证闭环，但全量多域覆盖还需要 Phase 2-3 的工作。
