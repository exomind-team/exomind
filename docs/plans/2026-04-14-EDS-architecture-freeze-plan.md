## 一、文档定位与优先级

本计划用于冻结 EDS 的目标态架构口径，供后续实现、评审、拆 issue、验收时统一参照。

它的职责不是复述当前代码已经做到了什么，而是明确：

1. EDS 的正式分层是什么
2. 哪些数据必须进入 DSON 对象同步底座
3. 哪些数据不进入 DSON，但仍属于 EDS 统辖范围
4. 五个核心业务域的目标态是什么
5. 后续实现者不应再自行决定的关键合同是什么

如与现有代码实现冲突，以本计划为准；如与更旧的探索性方案冲突，以本计划为准。

## 二、核心冻结决策

### 2.1 DSON 的唯一性定义

`DSON` 是 **EDS 的唯一对象同步底座**。

这里的“唯一”不是指“所有数据都长成同一种结构”，而是指：

- 所有需要跨 RT 同步的对象数据，都只能依赖这一套对象同步底座
- 不允许再为不同内容类型分别长出第二套对象同步内核
- 不同数据语义可以在 DSON 之上有不同治理方式，但不能另起同步底层

因此，后续“同步轨道”的区分只与：

- 是否需要同步
- 能否复制
- 怎样同步

有关，而**不与“内容属于哪一个业务域”直接绑定**。

### 2.2 Pin 是一级概念

`Pin` 是 EDS 的一级概念，并采用以下主从关系：

1. 先判断对象或字段是否被 Pin
2. 再决定它采用什么同步策略
3. 最后才决定它通过什么同步方式落地

换言之，`Pin` 在前，`同步策略` 与 `同步方式` 在后。

### 2.3 本地写入是否经过 DSON

冻结口径如下：

- **凡需要跨 RT 同步的数据，本地写入也必须经 DSON**
- **凡本质上绑定某个 RT 的数据，可以不经 DSON**

因此，是否走 DSON 的判断标准不是“这次是不是远端同步”，而是“这类数据是否属于可跨 RT 同步的对象底座”。

### 2.4 EDS 覆盖范围

本计划正式覆盖五个目标域：

- `Task`
- `EventLog`
- `TimeBlock`
- `Proposal`
- `Reminder`

其中 Reminder 不能再只作为附注或边角问题存在，必须在完整 EDS 中拥有正式定位。

## 三、EDS 正式分层

完整 EDS 分层固定为四层：

```text
Domain / UI / Runtime Consumer
        ↑
EDS Governance Layer
        ↑
DSON Store
        ↑
Storage Adapter
```

### 3.1 Storage Adapter

Storage Adapter 只负责 JSON 持久化接口。

它有两端语义：

- 面向持久化端：唯一真相源落点
- 面向操作端：供 DSON / 治理层读写 JSON 数据

冻结要求：

- 真相源只能落在持久化端
- DSON merge 态不是最终真相
- UI read model 也不是最终真相

### 3.2 DSON Store

DSON Store 只负责对象同步底座能力：

- 文档身份
- delta
- causal context
- merge
- 对象级结构同步

它不负责：

- 业务对象最终可用性
- Pin 缺失时的用户语义
- 冲突是否需要人工介入
- UI 直接消费态

### 3.3 EDS 治理层

`EDS Governance Layer` 是 DSON 之上的总治理层。

它内部统领以下子职责：

- `CRL`
- `Projection`
- `Validation`
- `Pin 依赖治理`
- `ConflictObject / 审计留痕`

它对上的主职责是：

- 暴露业务 JSON 结构
- 暴露同步状态
- 暴露同步操作
- 屏蔽 DSON primitive、CRDT 元数据与 Pin 内部存储细节

### 3.4 对外接口风格

治理层对 Domain / UI / Runtime Consumer 统一暴露 **JSON 门面**。

冻结要求：

- 上层只能面对 JSON 业务对象和同步状态
- 不暴露 `OrMap / OrArray / MvReg`
- 不暴露 CRDT 内部因果元数据
- 不暴露 Pin 的底层持久化细节

## 四、数据分类法与 Pin 模型

本计划正式引入 EDS 数据分类法。

### 4.1 四类数据

| 类别 | 含义 | 是否进入 DSON | 说明 |
|------|------|---------------|------|
| `Unpinned` | 可在各 RT 间完整复制 | 是 | 标准跨端对象 |
| `Pinned-To-One-RT` | 可持久，但完整体归属于某一 RT | 否（完整体）/ 可部分进入 | 可能以投影形式出现在其他 RT |
| `Runtime-Only` | 运行期瞬时状态 | 否 | 不是长期对象，不参与对象复制 |
| `Hybrid` | 同一对象内含可同步字段与 Pin 字段 | 是（同步部分） | 需正式依赖契约 |

### 4.2 特定 RT Pin 与不可复制运行态的区别

这两类数据必须严格区分：

- `Pinned-To-One-RT`
  - 可持久
  - 有归属 RT
  - 可能存在跨端可见的投影
  - 完整体不能在每个 RT 都持有

- `Runtime-Only`
  - 是执行期状态
  - 不是长期对象本体
  - 即便跨端可观察，也不意味着它应被复制为持久对象

### 4.3 字段级 Pin

本计划允许 **字段级 Pin**。

也就是说，同一对象内可以同时存在：

- 进入 DSON 同步的字段
- 被 Pin 到某个 RT 的字段

这不是异常情况，而是正式支持的模型。

### 4.4 单对象双层视图

对混合对象，领域上仍视为**一个对象**，但在 EDS 内部必须区分：

- `同步字段集`
- `Pin 字段集`

不采用“一有混合字段就强制拆成两个对象”的默认策略。

## 五、Pin 依赖契约与残缺态

字段级 Pin 会带来一个关键问题：

> 对象同步到了本地，但它依赖的 Pin 字段或 Pin 子对象并不由当前 RT 持有，此时该对象应如何存在？

本计划冻结如下合同。

### 5.1 显式残缺态

当同步对象依赖的 Pin 部分不在当前 RT 上时：

- 对象仍然可以在本地落地
- 但必须进入**显式残缺态**
- 不允许伪装成完整对象

推荐的语义口径：

```text
PinState =
  Owned(value)
  NotOwned(runtime_id)
```

### 5.2 正式依赖契约

这种“同步对象依赖 Pin 部分”的关系必须进入正式架构合同。

治理层必须明确定义：

- 依赖引用如何声明
- 缺失态如何表达
- 对象何时视为“可完整使用”
- 对象何时只是“受限可用”
- 投影给 UI 时哪些字段可见、哪些字段隐藏
- 后续若发生迁移/归属转移，如何从 `NotOwned` 变为 `Owned`

### 5.3 典型例子：Codex 会话

以 RT 上运行的 Codex 会话为例：

- 可同步字段：
  - 会话名称
  - 可见活跃状态
  - 可展示的工作目录描述
- Pin 字段：
  - 进程 ID
  - PTY 句柄
  - RT 本地控制状态

因此：

- 手机 RT 可以看见这条会话的同步投影
- 但不会持有桌面 RT 上的完整运行态
- 对手机 RT 而言，该对象是一个带 `NotOwned(...)` 成分的混合对象

## 六、Schema 合同

### 6.1 全字段显式覆盖

冻结规则：

- 只要进入 DSON 的持久字段，就必须在 Schema 中显式声明
- 未声明字段默认非法
- 不允许“先让字段存在，后补策略”

### 6.2 FieldType 到 DSON primitive 的正式映射

本计划要求后续实现阶段正式给出并遵守一张映射表，至少覆盖：

| `FieldType` | DSON primitive | 说明 |
|-------------|----------------|------|
| `String` | `MvReg` | 标量并发值 |
| `Number` | `MvReg` | 标量并发值 |
| `Bool` | `MvReg` | 标量并发值 |
| `Timestamp` | `MvReg` | 标量并发值，业务语义另定 |
| `Object` | `OrMap` | 结构化对象 |
| `Array` | `OrArray` 或受治理层约束的组合结构 | 视数组语义决定 |

### 6.3 LWW 语义

`LWW` 的底层排序语义固定为：

- 按 DSON / CRDT 元数据排序
- 不按业务字段值排序

因此：

- `updated_at`
- `trigger_at`
- 其他业务时间字段

都只是业务数据，不是 DSON 底层排序依据。

### 6.4 AtomicGroup 是硬约束

凡存在跨字段语义依赖的字段组，必须建模为 `AtomicGroup`。

冻结要求：

- CRL 不允许输出违反组内语义的不合法中间态
- 不允许先做字段级独立 merge、再靠下游补救

## 七、冲突治理合同

### 7.1 自动裁决原则

自动裁决采取“宁严勿松”的总原则：

- 只有当规则绝对明确、可解释、不会制造假正确时，才允许自动裁决
- 其余情况必须显式升级为：
  - `UserRequired`
  - `Escalate`
  - 或未收敛状态

### 7.2 ConflictObject 的范围

`ConflictObject` 只用于承载**需要人工介入**的冲突。

冻结范围：

- 持久化 `UserRequired`
- 持久化 `Escalate`
- 自动裁决默认不生成独立 `ConflictObject`

### 7.3 自动裁决的留痕方式

自动裁决不进入 ConflictObject，并不等于无痕。

冻结要求：

- 自动裁决通过治理层审计留痕记录
- 审计留痕与 ConflictObject 分离
- ConflictObject 只为人工冲突服务

## 八、五域目标态

### 8.1 Task

`Task` 是标准 mutable object 域。

目标态要求：

- 进入 DSON
- 明确声明所有持久字段
- 用 `AtomicGroup` 表达跨字段终态语义
- 支持 `MergeAll / RecursiveOr / Nested` 等不同粒度

### 8.2 EventLog

`EventLog` 必须进入统一对象同步底座。

冻结口径：

- 它在语义上属于“追加事实流”
- 但不能因此长出第二套对象同步内核
- 可在 DSON 内部做追加流优化
- 外部仍视为 EDS 统一对象轨的一种特殊语义

### 8.3 TimeBlock

`TimeBlock` 只有一个统一数据结构。

冻结口径：

- 不再区分“活跃时间块”和“已完成时间块”两种独立数据结构
- “活跃时间块”只是统一时间块结构中的一种特殊状态
- 统一结构中由字段状态表达其当前是否活跃

### 8.4 Proposal

`Proposal` 作为正式对象域纳入完整 EDS。

冻结口径：

- 不是边缘域
- 不是后补专题
- 必须拥有完整 schema 与正式冲突治理合同

### 8.5 Reminder

`Reminder` 当前冻结为**独立对象域**。

冻结口径：

- 不并入 `TimeBlock`
- 必须在完整 EDS 里拥有正式归宿
- 允许后续继续讨论其细节治理方式，但当前不能缺席

## 九、本地写路径与迁移范围

### 9.1 本地写路径

本地写入采用“按数据类型分流”的冻结口径：

- 可跨 RT 同步的数据：
  - 本地写也必须经 DSON
- RT 绑定数据：
  - 可以绕过 DSON

不允许把“这是本地写”当作绕过 DSON 的理由。

### 9.2 迁移范围

`migration wizard` 只负责五域从旧存储到目标态的迁移：

- `Task`
- `EventLog`
- `TimeBlock`
- `Proposal`
- `Reminder`

以下数据不纳入本轮 migration 范围：

- RT 绑定数据
- 运行态瞬时对象
- 非 DSON 对象轨的数据

## 十一、验收标准

当以下问题都能从正式架构文档中直接回答时，视为这份冻结计划已落实成功：

1. 什么数据必须进入 DSON，什么数据不进入？
2. `Pin`、同步策略、同步方式三者的先后关系是什么？
3. 当同一对象同时含同步字段与 Pin 字段时，系统如何表达？
4. 当 Pin 依赖不在本 RT 上时，对象如何存在？
5. `Storage Adapter`、`DSON Store`、`EDS 治理层` 各自负责什么？
6. `ConflictObject` 和自动裁决审计日志的边界是什么？
7. 五个业务域的目标态是否都已被正式定义？
8. “活跃时间块”是否仍被误当成独立数据结构？

若以上任一问题仍需实现者自行判断，则本计划仍不算冻结完成。
