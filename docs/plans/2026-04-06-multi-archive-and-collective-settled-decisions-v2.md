## 1. 本轮方法立场

- 这轮不是对旧有架构做局部改良，而是对既有技术选择与设计决策做彻底复审后的**搬迁式重构**
- 目标不是“让旧骨架继续活下去”，而是形成一套可承载后续新功能的新骨架
- 旧代码与旧文档的主要价值，不在于继续兼容其实现形状，而在于保留其中已经验证过的：
  - 对象语义
  - 系统不变量
  - 理论与设计决策
  - 失败教训

## 2. 必须保留与必须抛弃

### 2.1 必须保留

- 对象语义与不变量
- 已验证的理论与设计决策
- 先前调研中已经摸清的领域冲突规则与失败经验

### 2.2 必须抛弃

- `profile / user / scopeKey / anonymous` 旧作用域心智继续作为底层 canonical primitive
- UI 持有 runtime 真相与长期 side effects
- UI、运行时、存储、计算混合持有业务主权
- 计算职责与存储职责继续揉在同一层里

## 3. 新骨架的硬边界

后续总架构必须强制分层：

- `EDS` 负责存储
- `RT` 负责计算
- `ECS` 负责联网与连接性
- `Web / Tauri App` 负责用户呈现与 UI/UX

这些边界不再作为“倾向”，而是作为后续技术选择与实现评审的硬约束。

## 4. 路线与主攻方向

- 第一优先不是页面替换，而是先形成**总路线图**
- 这轮路线图的总战略轴是：
  - 跨设备一致性
  - `ECS / EDS / signal network` 作为共同基础
- 第一主攻方向是：
  - 底层真相源
- 推进顺序固定为：
  1. 从核心能力需求出发
  2. 再做技术选择
  3. 再收口宏观架构
  4. 最后才进入 UI/UX

## 5. 技术选择原则

- 可重新审视到技术选型层，已有技术选项不享有豁免权
- 即使是现成且常见的机制，例如 `WebSocket`，也不是当然前提
- 但新的技术选择必须满足：
  - 可搬迁
  - 可替换
  - 不把未来再次重构锁死在当前选择上

## 6. 兼容与迁移原则

- 至少保留“旧数据单向导入新骨架”的义务
- 不做长期双写
- 不做长期双向兼容
- 不做长期 bidirectional shim
- 允许出现明显断裂，只要断裂换来更干净的新骨架

## 7. 阶段性验证标准

- 第一条端到端验证切片是：
  - 对象同步闭环
- 第一阶段完成标准不是“旧功能全兼容”，而是：
  - 新骨架已经能够承载新功能

## 8. 超级提问后新增锁定事项

### 8.1 主架构与主内核

- 新骨架现在就先锁**对象同步骨架**
- 当前主倾向不是“先只锁硬边界再慢慢看”，也不是“先做过渡骨架再反推”
- 当前主同步内核方向锁定为：
  - `CRDT-first Object Store`
- 目标起点是：
  - 无头外心
  - `DSON` 作为 `CDS` 基座
  - `ECS` 通过 `iroh` 等机制承担互联
- 可以分阶段建设
- 但不接受“先按另一套核心做出来，后面再回头重构主内核”

### 8.2 第一条闭环与首阶段验收

- 第一条“对象同步闭环”优先选择：
  - `EventLog / TimeBlock`
- 第一阶段最不能妥协的验收口径是：
  - 无头单机先成立
- 即使没有完整 UI 和完整 ECS，`RT / EDS` 也要能独立跑通对象闭环与治理动作

### 8.3 EDS / ECS 首阶段落点

- 首个可实现的 `EDS` 基座采用：
  - `SQLite-backed EDS interface`
- `SQLite` 是第一适配者，而不是临时旁路
- `DSON` 当前先按“包壳后的 `JSON` 对象格式”理解
- 第一阶段底层存储接口只要求能稳定存取：
  - `JSON` 值
  - 对象元数据
- `ECS` 第一阶段采取：
  - 先本地无头，`ECS` 做窄接口
- `ECS` 不得反过来阻塞主骨架重建

### 8.4 旧数据与默认匿名用户

- 旧数据导入最低义务只兜：
  - `RT SQLite`
- 旧 `PouchDB` 不在新架构正式位置中
- 最多只支持原先基于 `PouchDB` 的 `JSON` 数据一次性导入
- 新系统导出的 `JSON` 不承诺兼容旧版
- 当前 `anonymous` 历史数据应抽象并映射为：
  - 新系统中的默认档案
- 新骨架不再额外保留“默认用户”这一层对象
- 默认档案升级为正式个人档案时：
  - 按同主体转正处理
- 默认档案第一阶段能力边界是：
  - 本地功能
  - `EDS` 对象能力
  - 后续可升级
- 它不承接集体功能

### 8.5 集体语义与治理主队列

- 集体档案语义在第一阶段：
  - 骨架预留但不落地
- 当前只预留已知接口，例如档案类型等
- `Proposal` 第一阶段应尽早进入主路径，承担治理主队列角色
- 提案的理论定位是：
  - 待批准的 `RT` 动作
- 它不仅控制代码合并式操作，也可控制事件日志、时间块、任务等运行时功能

### 8.6 Apply 权威、共享层与 UI 角色

- 远端同步、恢复、重放进入本机后的唯一最终 `apply authority` 是：
  - `RT`
- `Blackboard` 必须保持为独立共享层
- 但其落地顺序后置
- 第一阶段里，它更多作为测试 `ECS / EDS` 稳定性、存储空间、算力跟踪等能力的服务型节点
- 首阶段 UI 只做：
  - 最小治理 / 调试壳

### 8.7 Proposal 的最小技术合同

- `Proposal` 第一阶段采用：
  - 显式命令对象
- 每个提案都包装为明确的 `RT command / action`
- “批准”与“执行”显式拆两段
- 批准后默认自动进入执行，但执行不是必然成功
- 第一阶段最小状态机采用：
  - `draft`
  - `in_review`
  - `approved`
  - `executing`
  - `executed`
  - `execution_failed`
  - `rejected`
- 第一阶段必须进入 `Proposal` 主队列的是：
  - 结构变更
  - 重要运行动作
- 这些 `RT` 命令在技术上可与信号池机制对接：
  - 提案被批准后，再向事件日志、时间块等 `RT` 能力发送与 UI 点击等效的信号

### 8.8 旧 JSON 的迁移方式

- 对旧 `Pouch / JSON` 数据，第一阶段只承诺：
  - 一次性导入工具
- 不承诺双向兼容
- 不承诺新格式回导旧版

### 8.9 对象骨架、三层主权与 ECS 窄接口

- 第一阶段明确采用：
  - 源对象与投影分离
- 三层主权关系固定为：
  - `EDS` 持久真相
  - `RT` 投影索引 / 热点缓存
  - `UI` 纯交互临时态
- `RT` 缓存默认按：
  - 投影索引缓存
  - 热点对象缓存
 处理
- `UI` 本地态严格收缩到纯交互临时态
- `CRDT-first Object Store` 采用：
  - 统一外壳 + 分对象规则
- `object_id` 全局唯一
- `archive_id` 只做归属 / scope
- 每个可同步对象第一阶段最低必须自带：
  - `object_id`
  - `archive_id`
  - `object_type`
  - `schema_version`
  - 因果元数据
  - `author / actor`
  - 终态 / `tombstone`
- 不可逆动作默认收口为：
  - 统一终态或 `tombstone`
- 远端对象进入本机后采用：
  - 分层入库后验证
- 底层可先保存原始对象 / 历史
- 上层只暴露验证通过对象
- `ECS` 第一阶段只管：
  - peer identity
  - 连接
  - 发现
  - 投递
  - 重连
- `ECS` 不承担对象真相、收敛与数据恢复主权
- `iroh` 第一阶段落在：
  - 传输 / 连接层
- 恢复明确拆两步：
  - 连接恢复归 `ECS`
  - 数据重新一致归 `EDS`

## 9. 当前仍未锁定的问题

以下问题保留到综合决策和后续提问中继续收口：

- `DSON / CDS` 的正式对象边界与接口形态
- `Proposal` history、审计与动作集的精确定义
- `Blackboard` 的 owner、scope 与删除痕迹
- 在一致性、可恢复性、可治理性、可替换性与实现可行性之间，主排序怎样定

## 10. 一句话总结

本轮新增决策的核心不是“如何温和升级旧系统”，而是：**抛掉旧作用域、旧主权归属与旧兼容前提，只搬走那些已经被证明正确的语义、不变量与设计成果，用它们重建一套可继续生长的新骨架。**
