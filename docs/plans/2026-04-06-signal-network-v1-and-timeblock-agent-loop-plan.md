# 2026-04-06 信号网络 v1 与单 Agent 时间块闭环计划

> 状态：已收口子计划

> 目的：把 `Theme A + Theme B` 中已经形成稳定判断的部分，从总索引中拆成可继续实现的子计划。

## 1. 计划摘要

信号网络第一阶段先不追求动态工作流系统，而收口为：

- 固定节点
- 可配边
- 内建领域节点
- 特殊共享 `blackboard`
- 边可全 CRUD、节点只读

在这个骨架上，优先验证一个单 Agent 关键闭环：

- `timeblock.completed`
- 自动总结
- 自动建议
- 自动创建 `pending proposal`

---

## 2. 统一语义基线

### 2.1 `node / actor / Agent`

后续文档统一按以下原则表述：

- `node`、`actor`、`Agent` 都是**方法论概念**
- 它们都不是对底层程序本体的硬分类
- 同一个底层运行体可以同时被多个视角理解

其中：

- `node` 强调：
  - 网络中的位置
  - 路由关系
  - 工作台 / 可视化中的承载点
- `actor` 强调：
  - 消息收发
  - 信号输入 / 输出
  - 参与连边传播
- `Agent` 强调：
  - 调度
  - 记忆
  - 提案
  - 资源 / 能量治理

因此：

- 不再把 `actor` 或 `Agent` 写成“程序先天类型”
- `v1` 文档默认采用**节点优先**的表述
- 只有在需要强调消息参与时，才补充“它在这里按 `actor` 视角理解”

### 2.2 route / edge

- route table 是**档案级持久配置**
- `edge` 对用户表达的是：
  - 这个节点输出后，默认下一步送达给谁
- `edge` 在网络层同时表达：
  - 只有建边才允许通信

`v1` 默认规则固定为：

- **无边发信即拒绝**
- 拒绝时要给出“去建边 / 看路由”的明确提示

### 2.3 topic 与投递规则

- 第一阶段先采用**预注册 topic**
- 通配 `*` 只用于：
  - 前端观察
  - 调试 / 诊断
- `*` 不作为通用业务兜底路由

当 route 状态异常时：

- 禁用 route：
  - 保留连边
  - 投递记录记为 `skipped`
- 目标缺失或目标当前不可用：
  - 投递记录记为 `failed`
  - 结果需要对用户 / workbench 可见

### 2.4 v1 范围

第一阶段只收口到：

- 固定节点
- 可配边
- 预注册 topic
- 投递结果可观测

不进入 `v1` 的内容：

- `if` / 条件控制节点
- 节点动态生成
- 自动建边
- 临时直发覆盖层
- 用户自定义节点系统

### 2.5 节点 CRUD

`v1` 中的“信号网络 CRUD”解释为：

- **边全 CRUD**
- **节点只读**

节点来源先收口为内建 registry，而不是用户自定义节点系统。

边编辑表面第一阶段收口为：

- **workbench / route editor**

## 3. 第一批进网对象

这些对象在第一阶段以**内建领域节点**进入网络：

- 事件日志
- 时间块
- 任务
- 提案
- 黑板

其中：

- `blackboard` 在这里是**特殊共享节点**
- 需要强调消息传播时，可按 `actor` 视角理解
- 它承载的是：
  - 协调便笺
  - 交接摘要
  - 共享工作痕迹
- 它不承载的是：
  - 业务真相数据库
  - Agent 私有长期记忆池

---

## 4. 单 Agent 关键用户叙事

### 4.1 触发点

第一条必须跑通的内置预置连边是：

- `timeblock.completed`

### 4.2 默认产出

单 Agent 第一阶段默认产出：

- 总结
- 建议
- `pending proposal`

### 4.3 接入方式

这条闭环在网络中以**内置预置连边**进入，而不是用户临时搭建。

### 4.4 `blackboard` 与记忆边界

在这条单 Agent 闭环里：

- `blackboard` 默认只收：
  - 摘要痕迹
  - 交接 / 协调说明
- 不收：
  - 完整私有推理过程
  - Agent 私有长期记忆正文

当前默认边界是：

- Agent 长期记忆先保持私有
- 只有蒸馏后的共享内容才写入 `blackboard`

### 4.5 档案范围

第一阶段默认在：

- **个人档案**

中启用。

集体档案适配后置。

### 4.6 投递可观测性

这条闭环产生的投递结果至少要可区分：

- 正常送达
- `skipped`
- `failed`

并在 workbench / 调试表面可回看。

## 5. 明确后置的主题

以下内容不进入这份子计划的关闭条件：

- `Web API Agent` 持久化
- 长期记忆细化
- 控制节点
- 动态 teammate / subAgent 编排
- 集体档案中的这条闭环适配

---

## 6. 最小验收方向

至少应能稳定回答并验证：

- route table 是档案级持久配置
- 内建领域节点可读、边可 CRUD
- 边编辑第一阶段走 workbench / route editor
- 无边发信会硬失败，并提示先建边或检查路由
- 只有预注册 topic 可用于业务投递
- `*` 只用于前端观察 / 调试，不作为业务兜底
- 禁用 route 会保留连边，但投递记录为 `skipped`
- 目标缺失或不可用时，投递记录为 `failed`
- `timeblock.completed` 会沿预置连边产出总结、建议与 `pending proposal`
- `blackboard` 只收到摘要 / 交接痕迹，不吞并 Agent 私有长期记忆

---

## 7. 一句话总结

信号网络 `v1` 不是“自由工作流编辑器”，而是“**固定领域节点 + 可配边 + 可观测投递规则 + 一个必须跑通的单 Agent 时间块闭环**”；只有先把这个骨架做稳，后面的 `API Agent` 持久化、多 Agent 协作与更强编排能力才有可靠挂点。
