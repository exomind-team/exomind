## 2. 多 Agent 第一阶段：新增已定决策

对应既有文档：

- [2026-04-06-multi-agent-task-governance-phase1-plan.md](./2026-04-06-multi-agent-task-governance-phase1-plan.md)

对应既有 issue：

- [#846](https://github.com/exomind-team/exomind/issues/846)

### 2.1 宿主形态

第一阶段默认采用：

- `coordinator` 常驻
- `proposer`、`reviewer`、`retrospector` 按需实例化

不采用：

- 四角色都只是单一治理 Agent 的内部逻辑模式
- 四角色全部长期常驻

### 2.2 主治理队列

第一阶段任务治理默认改为：

- **提案优先**

也就是说：

- `coordinator` 默认围绕提案主队列调度
- 任务更多作为被提案驱动、引用或执行的对象

不采用：

- “任务为主，提案只是门禁分支”
- 独立治理队列优先

### 2.3 人工升级表面

当 `coordinator` 无法裁决、或角色执行失败时，第一阶段默认：

- **统一转成提案表面处理**

当前明确不做：

- 特殊治理节点
- 另一套独立人类治理面

用户补充理由：

- “先不搞节点特殊化，后者涉及的问题会特别多”

### 2.4 提案进入评审链

当前收口为：

1. `proposer` 先产出 `pending`
2. `coordinator` 把草稿送进评审链
3. `reviewer` 参与预审 / 预裁决
4. 再进入等待人类 UI 终审的阶段

### 2.5 `in_review` 的语义

第一阶段明确固定为：

- `in_review` = **等待人类 UI 终审**

不再理解为：

- Agent 内部评审中的中间态
- 只有人类已经点开后才算进入 review

### 2.6 `reviewer` 的新定位

本轮关键修正：

- `reviewer` 不是最终审批人
- `reviewer` 更像：
  - 预审者
  - 预裁决者
  - 为人类终审准备意见的人

用户原话要点：

- “评审者预裁决并推到 `in_review` 状态，这个审阅必须要人在 UI 中做”

### 2.7 UI “退回”与状态机修正

本轮新增的关键修正有三条：

1. UI 中的“退回”必须同步回提案状态
2. 现有 `Rejected` 不能再按真正终态理解
3. 第一阶段应新增：
   - `changes_requested`

并且用户进一步补充：

- `rejected` 更适合改名为 `cancelled`
- 因为有些时候用户不是退回 / 否决，而是取消

### 2.8 被退回后的修订路径

第一阶段默认采用：

- 在**同一提案**上修订
- 修订后再重送审

不采用：

- 复制成新提案重提
- 只通过评论追加修订说明

### 2.9 `retrospector` 的默认落点

即使在“提案优先”的治理模型下，第一阶段仍保持：

- `retrospector` 只落 `eventlog`

不默认：

- 直接评论到提案
- 自动新建复盘提案

### 2.10 本轮对多 Agent 的一句话更新

多 Agent 第一阶段已从“固定四角色的任务治理”进一步收口为：

- **`coordinator` 常驻 + 其余角色按需实例化**
- **提案优先的治理主队列**
- **人类 UI 终审**
- **需要新增 `changes_requested` 的提案状态机**

## 3. 双计量第一阶段：新增已定决策

对应既有文档：

- [2026-04-06-agent-energy-and-dual-metering-phase1-plan.md](./2026-04-06-agent-energy-and-dual-metering-phase1-plan.md)

对应既有 issue：

- [#848](https://github.com/exomind-team/exomind/issues/848)

### 3.1 双账本治理面纳入范围

第一阶段默认只把以下对象纳入双账本治理面：

- **显式登记的 Agent**

不默认扩大到：

- 所有 actor
- 所有 runtime 组件

### 3.2 actor 节点的资源追踪

用户新增的重要补充：

- 即便 actor 节点不自动进入 Agent 双账本治理面
- 仍需要追踪它们使用的：
  - 存储资源
  - 计算资源
  - 其他“时空”资源

也就是说：

- “是否进入双账本治理面”
- “是否追踪运行资源”

这两件事要分开理解。

### 3.3 模型账本真相源

第一阶段默认采用：

- **RT 侧 invocation 记录**

用户新增补充：

- 这些 invocation 记录在存储上属于：
  - **RT 信号网络节点的状态信息**
- 应与：
  - `RT` 信号节点
  - 其相关状态存储
 统一放在一起考虑

不采用：

- Agent 自报为真相
- RT 与 Agent 双源并存后再对账

### 3.4 人工“补能 / 唤醒”的语义

第一阶段默认：

- 只影响**运行能量**

不直接影响：

- token / cost 账本
- 模型资源异常历史

### 3.5 actor 节点资源表面

本轮收口为：

- actor 节点的时空资源默认放在：
  - **节点详情 / 拓扑检查器**

不默认：

- 和 Agent workbench 混成一张总表
- 只藏在纯 diagnostics 底层

### 3.6 模型账本保留粒度

第一阶段默认采用：

- 保留原始 invocation 记录
- 同时保留 turn 聚合

不采用：

- 只留 turn 聚合
- 只留累计 counters

### 3.7 本轮对双计量的一句话更新

双计量第一阶段已进一步收口为：

- **显式登记 Agent 才进入双账本治理面**
- **actor 节点仍追踪时空资源**
- **模型账本真相源在 RT**
- **invocation 原始记录与 turn 聚合都保留**
- **节点级资源看节点详情，Agent 级双账本看 workbench / diagnostics**

## 4. 对外文档工作流：新增已定决策

对应既有文档：

- [2026-04-06-remaining-themes-second-round-settled-plan.md](./2026-04-06-remaining-themes-second-round-settled-plan.md)

对应既有 issue：

- [#847](https://github.com/exomind-team/exomind/issues/847)

### 4.1 证据包最小要求

当 Agent 为已验证里程碑生成对外文档草案时，第一阶段默认必须附带：

- 对应 issue
- 验收证据
- `covered / not-covered` 边界说明

不采用：

- 只挂 issue 链接
- 一上来就要求过重的完整归档包

### 4.2 草案默认落点

第一阶段默认：

- **先发 issue 评论**

再由人工同步到：

- README
- Release 说明
- 其他真实对外表面

不默认：

- 直接生成 README / Release 补丁作为第一审阅面
- 先写独立临时 docs 文件

### 4.3 语言策略

第一阶段默认：

- 中文正文优先
- 必要时附英文摘要

不默认：

- 每次都中英双份
- 英文优先

## 5. “普通使用者手册 / 操作指南”子分支：新增已定决策

### 5.1 主题定位

用户新增澄清：

- 这条线属于“对外叙事 / 宣传”的一个**子模块**
- 它不是孤立的新大主题

当前至少拆成两个并行子分支：

1. 开发手册 / 开发进度追踪
2. 普通使用者手册 / 操作指南

### 5.2 追踪方式

“普通使用者手册 / 操作指南”第一阶段默认采用：

- **单开专门 issue**

不继续完全挂在：

- `#847`

也不只靠现有文档自然积累。

### 5.3 第一阶段范围

这条用户手册子分支第一阶段优先覆盖：

- 上手
- 核心日常流
- 常见排障

当前不优先做：

- 全量功能百科
- 单独的多端互联深度专项手册作为唯一主线

### 5.4 现有用户手册文档的处理方式

现有文档：

- `src/docs/user-guide.md`

第一阶段默认采用：

- **作为种子继续演进**

而不是：

- 视为废弃样稿整体放弃
- 只抽片段不保留整体脉络

### 5.5 新增的工作流方向

用户新增了一个很重要的后续扩展方向：

- 这个用户手册子分支，后续可能不仅仅是“写文档”
- 而是要构建一条工作流：
  - 从代码
  - 到功能
  - 到文档
  - 再到用户使用手册
  - 再到网页

并且用户明确指出：

- 这条线会进一步涉及：
  - **构建系统**

这条判断当前先记为：

- 已明确提出的后续设计方向

但本轮尚未继续细化其：

- 构建触发机制
- 产物转换链
- 自动化边界

### 5.6 本轮对用户手册子分支的一句话更新

“普通使用者手册 / 操作指南”现已被明确为：

- 对外叙事 / 宣传下的并行子分支
- 需要单开专门 issue
- 第一阶段优先做“上手 + 核心日常流 + 常见排障”
- 以 `src/docs/user-guide.md` 为种子演进
- 后续可能上升为“代码 -> 功能 -> 文档 -> 用户手册 -> 网页”的构建工作流主题
