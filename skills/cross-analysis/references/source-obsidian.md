# Obsidian

本文件是 `Obsidian` 的本地化搜索指南，不是产品百科。

它的目标是帮助 Agent 在遇到相关目的时，快速判断：

- 这个参考源值不值得纳入交叉分析
- 应该先从哪些入口开始检索
- 哪些主题适合参考它
- 哪些主题不应把它当作主参考

## 适合优先参考的目的

当用户目的涉及以下方向时，优先考虑 `Obsidian`：

- 本地优先笔记
- Markdown 笔记工作流
- 双链 / 链接型知识组织
- 个人知识库结构
- 图谱视图如何辅助笔记探索
- Canvas / 白板式知识组织
- 插件生态如何扩展个人知识工作流

## 不要把它当成主参考的情况

以下场景里，`Obsidian` 通常不应作为唯一主参考：

- 强实时多人协作
- 完整开源应用源码级实现对照
- 服务端优先或云原生知识系统
- 严格数据库驱动而非文件驱动的信息系统

说明：

- 这里的判断是“参考价值边界”，不是产品优劣判断。
- 对源码级实现问题，`Obsidian` 更适合作为“产品与生态参考”，而不是“完整核心应用源码参考”。

## 优先检索入口

### 1. 官方产品入口

- 官网：`https://obsidian.md/`

适合先回答：

- 产品主张是什么
- 本地优先、私有存储、开放格式这些定位是否明确
- 官方主推的能力面有哪些

优先关注：

- 本地存储
- Markdown / open file formats
- Links / Graph / Canvas
- Plugins / Sync / Publish

### 2. 官方帮助文档

- 用户帮助：`https://obsidian.md/help/`

适合先回答：

- 用户功能是怎样组织的
- 某个具体功能在产品里如何命名
- 相关概念的官方术语是什么

如果目的是“本地化笔记”“知识组织”“图谱视图”“Canvas”，优先从帮助文档检索这些关键词：

- vault
- markdown
- links
- graph
- canvas
- properties
- tags
- daily notes

### 3. 官方开发文档

- 开发文档：`https://docs.obsidian.md/`

适合先回答：

- 插件与主题扩展的官方入口是什么
- API、主题、CSS、扩展点怎样组织
- 如果要分析“生态可扩展性”，应该先看哪条路线

### 4. GitHub 组织与仓库

优先看这些仓库：

- 组织页：`https://github.com/obsidianmd`
- 发布与插件/主题索引：`https://github.com/obsidianmd/obsidian-releases`
- API 类型定义：`https://github.com/obsidianmd/obsidian-api`

如果目的是：

- 看生态边界：先看 `obsidian-releases`
- 看插件接口：先看 `obsidian-api`
- 看开发方式：先从开发文档继续跳转到 sample plugin 模板

### 5. 官方论坛

- 论坛：`https://forum.obsidian.md/`

适合先回答：

- 社区常见需求集中在哪里
- 哪些能力是核心功能，哪些更多由插件生态承接
- 用户和开发者围绕哪些问题反复讨论

优先关注这些板块：

- Help
- Knowledge management
- Developers: Plugin & API
- Share & showcase
- Custom CSS & Theme Design

## 面向常见目的的检索路线

### 目的：本地化笔记 / 本地优先知识库

建议路线：

1. 官网看产品定位
2. 帮助文档确认 vault、Markdown、links 等官方术语
3. 再决定是否需要补论坛里的工作流讨论

重点想确认的问题：

- 是否本地存储
- 是否使用开放文件格式
- 链接与图谱在组织中的位置
- 离线与私有性是否是核心主张

### 目的：知识组织 / 双链 / 图谱视图

建议路线：

1. 官网看 Links / Graph / Canvas 的产品表述
2. 帮助文档确认这些功能的实际边界
3. 论坛或 showcase 看社区如何把这些能力组合成工作流

重点想确认的问题：

- 图谱是核心组织工具，还是辅助探索视图
- 双链与标签、属性之间怎样配合
- Canvas 与笔记链接体系是什么关系

### 目的：插件生态 / 自动化扩展

建议路线：

1. 开发文档
2. `obsidian-api`
3. `obsidian-releases`
4. 论坛 Developers: Plugin & API

重点想确认的问题：

- 扩展能力由哪些 API 提供
- 插件生态的分发与兼容性边界是什么
- 官方鼓励的扩展方式是什么

## 适合从 Obsidian 借鉴什么

通常适合借鉴：

- 本地优先的产品定位表达
- Markdown 与开放格式的长期可迁移叙事
- 链接、图谱、Canvas 并存的知识组织方式
- 核心能力与插件生态的边界划分
- 社区工作流如何围绕核心能力生长

## 不要急着从 Obsidian 借鉴什么

通常不要直接从它推导：

- 完整核心应用的源码实现细节
- 强实时协作架构
- 云端知识服务后端方案
- 对大型结构化数据库场景的通用做法

## 一句话判断

如果用户目的是：

- “本地优先笔记怎么做”
- “Markdown 知识库怎么组织”
- “双链、图谱、Canvas 这些能力如何组合”
- “插件生态怎样支撑个人知识工作流”

那么 `Obsidian` 应该进入优先参考源集合。
