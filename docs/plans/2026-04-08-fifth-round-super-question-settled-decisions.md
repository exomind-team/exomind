## 2. `#865` 普通用户手册 / 官网 `/docs`

对应既有文档：

- [2026-04-07-fourth-round-user-manual-phase1-settled-decisions.md](./2026-04-07-fourth-round-user-manual-phase1-settled-decisions.md)

对应既有 issue：

- [#865](https://github.com/exomind-team/exomind/issues/865)

### 2.1 新增已定决策

- 手册进入可发布链的单一触发点默认收口为：
  - **验收通过**
- 当前阶段的操作性代理值可先采用：
  - **对应 issue 关闭**
- 一个功能进入普通用户手册主链的最低门槛固定为：
  - 代码已实现
  - 已有验收证据
  - 用户叙事已写清
- `/docs` 第一阶段承接 canonical 内容的方式固定为：
  - **人工镜像到现有官网**
- 当前 P0 目标固定为：
  - **内容上线**
- 当前不把以下内容当成第一阶段强门禁：
  - 自动导出
  - 自动排版
  - 自动同步
- canonical 内容源从当前单文件种子稿演进为：
  - **总索引 + 分文档**
- 当前种子稿里已经存在、但不属于最小主线的内容，如多端配对 / 设备互联，应先移到：
  - **进阶 / 附录**
- `/docs` 第一版最小结构固定为：
  - **5 入口首页 + 已完成正文**
- 当前 5 个入口中，第一版最小必须有正式正文的只有：
  - `3 分钟上手`
  - `常见问题 / 排障`
- `核心概念` 第一阶段先只保留：
  - **入口级摘要**
- 未完成的入口在 `/docs` 首页上应：
  - **显示出来**
  - **明确标注“即将上线”**
- 英文 `/en/docs` 第一阶段固定为：
  - **保留英文占位页**
- 文档过时后的默认策略固定为：
  - **允许后补**
- 用户明确补充：
  - 现在先不把“文档债追踪机制”当成首要主题
  - 先有初步文档，再讨论同步治理
- 正文页被视为“已完成，可上线”的最低口径固定为：
  - 有明确用户路径
  - 有操作步骤
  - 有边界说明
  - 有排障内容
- 普通用户手册与官网 `/docs` 第一阶段都需要显式展示：
  - **已验证 / 实验 / 非核心 / 即将上线** 这类状态标识
- 标识表面默认采用：
  - **正文内直接标识**

## 3. `#847` 已验证里程碑 -> 对外文档草案包

对应既有 issue：

- [#847](https://github.com/exomind-team/exomind/issues/847)

### 3.1 新增已定决策

- 第一阶段默认先产出的不是 README patch，也不是 release 文案文件，而是：
  - **issue 评论草案包**
- 这批草案包的集中承载位置固定为：
  - **`#847`**
- 不采用：
  - 每个来源 issue 各发一份
  - 每轮单开临时 docs issue
- 草案包的组织粒度固定为：
  - **里程碑汇总**
- 不采用：
  - 单 issue 为主的零散草案模式
- 进入这类汇总包的来源对象固定收口为：
  - **用户可感知的里程碑 issue**
- 不要求：
  - 所有已关闭 issue 都强行入包
- 第一阶段的汇总触发方式固定为：
  - **人工发起**
- 也就是说：
  - 不是每次 issue 关闭都自动追加
  - 而是维护者判断“这批已经能对外说明”后，再整理一轮
- 草案包正文结构固定为：
  1. 里程碑摘要
  2. 证据链接
  3. `covered / not-covered`
  4. README 草稿
  5. Release / build 草稿
- 第一阶段默认覆盖的公开表面固定为：
  - `README / README-zh`
  - `Release / build 说明`
- website 继续后置，不进入当前最小关闭条件
- 草案包的人工审阅通过动作固定为：
  - **在 `#847` 中用明确评论确认**
- 语言策略继续固定为：
  - **中文优先，必要时补英文**

  - A：`README + Release`
- Q：草案包正文结构怎么组织？
  - A：`摘要 + 证据 + 边界 + 文案草稿`

## 4. `#845` 独立集体记账系统

对应既有文档：

- [2026-04-06-independent-collective-bookkeeping-system-plan.md](./2026-04-06-independent-collective-bookkeeping-system-plan.md)

对应既有 issue：

- [#845](https://github.com/exomind-team/exomind/issues/845)

### 4.1 新增已定决策

- 为后续并回 ExoMind，第一阶段最应该优先稳定的不是 UI，而是：
  - **领域事件模型 + 本地 API**
- 文件格式重要，但不是第一优先稳边界
- UI 工作面贴近旧系统重要，但不作为未来并回 ExoMind 的核心锚点
- 身份模型第一阶段明确采用：
  - **完全独立**
- 也就是说：
  - 当前不预留 `archive`
  - 不预留 `member`
  - 不把外心主仓身份语义强塞进独立系统
- 最低归因固定为：
  - **操作者文本 + 设备 + 时间**
- 这里的“操作者”第一阶段不是稳定成员 ID，而是：
  - 最小可读的文本归因
- GitHub 私有仓库同步的产品地位固定为：
  - **可替换传输层**
- 它不是未来必须保留的领域语义核心
- 第一阶段仓库归属策略改为：
  - **计划一旦稳定，尽快独立仓库**
- 不再默认长期留在 ExoMind 主仓中推进实现

### 4.2 本轮问答快照

- Q：为了后续并回 ExoMind，最值得优先稳定哪一层？
  - A：`领域事件模型 + 本地 API`
- Q：独立系统第一阶段的人与集体身份模型如何和 ExoMind 对齐？
  - A：`完全独立，不预留`
  - 用户补充：第一阶段不需要区分用户、档案等内容，只是读写
- Q：独立记账系统第一阶段的代码归属怎么规划？
  - A：`尽快单独仓库`
- Q：GitHub 私有仓库同步后续应被视为什么？
  - A：`可替换传输层`
- Q：什么时候拆仓？
  - A：`计划后即拆`
- Q：最低归因保留到什么程度？
  - A：`操作者文本 + 设备 + 时间`

## 5. `#846` 多 Agent 第一阶段治理

对应既有文档：

- [2026-04-06-multi-agent-task-governance-phase1-plan.md](./2026-04-06-multi-agent-task-governance-phase1-plan.md)

对应既有 issue：

- [#846](https://github.com/exomind-team/exomind/issues/846)

### 5.1 新增已定决策

- 在 proposal-first 前提下，`coordinator` 的默认排优先级收口为：
  - **先处理会阻塞人类决策或执行的提案**
- `reviewer` 永远不拥有：
  - **最终通过提案** 的权力
- `approved` 在第一阶段只能由：
  - **人类 UI 终审**
 产生
- Agent 内部的预审 / 预裁决不会直接生成 `approved`
- `reviewer` 的职责进一步收口为：
  - 评论
  - 证据复核
  - 退回
  - 把提案推进到等待人类 UI 终审
- 争议升级节奏从“无法决定就交人”进一步收口为：
  - 允许固定多轮退回-修订循环
  - 当前默认值为 **3 轮**
- “1 轮”的默认计数方式固定为：
  - 一次 `changes_requested -> proposer 修订 -> 再次送审`
- 当达到 3 轮仍不收敛时，第一阶段默认：
  - **强制进入人类终审**
- 治理痕迹默认落在：
  - **提案评论 / 提案历史**
- 不默认落到：
  - 黑板
  - eventlog 主表

### 5.2 本轮问答快照

- Q：proposal-first 下 `coordinator` 默认怎样排优先级？
  - A：`人工阻塞优先`
- Q：如果 `reviewer` 与 `proposer` 反复来回，何时升级给人类？
  - A：`固定多轮后升级`
  - 用户补充：大概确定为 3 轮；并且 reviewer 不能自行决定提案通过
- Q：治理痕迹默认应落在哪个表面？
  - A：`提案评论 / 历史`
- Q：“3 轮”默认按哪种方式计数？
  - A：`退回-修订循环`
- Q：达到 3 轮仍未收敛时默认怎样升级？
  - A：`强制进入人类终审`

## 6. `#848` Agent 双计量治理面

对应既有文档：

- [2026-04-06-agent-energy-and-dual-metering-phase1-plan.md](./2026-04-06-agent-energy-and-dual-metering-phase1-plan.md)

对应既有 issue：

- [#848](https://github.com/exomind-team/exomind/issues/848)

### 6.1 新增已定决策

- 双计量治理面的默认纳入方式进一步纠偏为：
  - **凡是 RT 托管、且被视作 Agent 节点的，都默认进入双计量治理面**
- 因此旧说法里的：
  - “显式登记 Agent 才进入双计量治理面”
  在当前阶段需要被视作过时表述
- 与此同时，第一阶段仍保留：
  - 一个**默认开启的“纳入双计量”开关**
  - 方便未来尚未完全实现的 Agent 节点类型
- 但这个开关的主要作用不再是“决定常规 Agent 是否入表”，而是：
  - 作为扩展治理接口的一部分
- 第一阶段配置接口的主要用途固定为：
  - **阈值 / 告警 / 策略**
- Agent 自己读取双账本状态的接口固定为：
  - **只读工具 / API**
- 不默认：
  - 自动注入上下文
  - 通过黑板读取
- diagnostics / workbench 第一阶段默认显示：
  - **粗粒度状态告警**
- 例如：
  - 低能量
  - 高频唤醒
  - 休眠
  - 异常调用
- 不先把 invocation / turn 明细和趋势图表直接堆成主界面
- 当终端 Agent 后续具备 Agent 节点语义后，默认也应：
  - **自动纳入双计量治理面**

### 6.2 本轮问答快照

- Q：一个 Agent 被纳入双计量治理面，默认通过什么方式“显式登记”？
  - A：`RT 托管即登记`
  - 用户补充：这更接近“Agent 节点”的定义；API Agent 与终端 Agent 最终都需要配置接口
- Q：Agent 自己读取双账本状态，默认最适合走什么接口？
  - A：`只读工具 / API`
- Q：diagnostics / workbench 第一阶段默认显示多细的告警？
  - A：`粗粒度状态告警`
- Q：既然 RT 托管的 Agent 默认都进双计量治理面，那配置接口第一阶段主要配什么？
  - A：`阈值 / 告警 / 策略`
  - 用户补充：再加一个默认开启的“纳入双计量”开关，这样能对尚未实现的 Agent 节点有用
- Q：终端 Agent 后续具备 Agent 节点语义后，应怎样进入双计量治理面？
  - A：`默认自动纳入`

## 7. `#860` 集体 Agent 的同步边界

对应既有 issue：

- [#860](https://github.com/exomind-team/exomind/issues/860)

### 7.1 新增已定基线

这条主题仍是**问题定义层**，不是最终实现方案。但本轮已经补出了当前最重要的边界基线：

- 集体 Agent 第一默认更接近：
  - **汇聚管理层**
- 它主要是：
  - 对各成员座席 Agent 的统一编排 / 管理层
- 它不是：
  - 某个固定 RT 上跨设备同步的单一执行实例
- 若未来把“集体 Agent”纳入同步系统，第一阶段最该同步的是：
  - **定义 / 权限 / 任务队列**
- 更精确地说，是三层分法：
  1. **所有 RT 共享的**
     - Agent 定义
     - 权限配置
     - 待处理任务 / 提案 / 队列
  2. **RT 侧留引用的**
     - 对共享对象的本地挂载
     - 订阅
     - 调度引用
  3. **只留在本地的**
     - 正在执行中的 Agent 实例
     - 终端会话
     - 进程上下文
     - 临时执行态
- 归因语义固定为：
  - **集体 Agent + 来源座席 / RT**
- 也就是说：
  - 既保留“代表哪个集体 Agent 执行”
  - 也保留“实际落在哪个成员座席 / 哪个 RT 执行”

### 7.2 本轮问答快照

- Q：当前“集体 Agent”更接近哪种关系模型？
  - A：`汇聚管理层`
- Q：如果以后把“集体 Agent”纳入同步系统，第一阶段最应同步什么？
  - A：`定义 / 配置 / 任务队列`
  - 用户补充：要区分“所有 RT 共享的”“在 RT 侧留引用的”“只留在本地的”
- Q：当某个成员座席上的 Agent 代表集体执行动作时，默认怎样归因？
  - A：`集体 Agent + 来源座席`
- Q：对“所有 RT 共享的”那一层，第一阶段最应包含哪些对象？
  - A：`定义 / 权限 / 任务`
- Q：对“在 RT 侧留引用的”那一层，第一阶段最应怎样理解？
  - A：`共享对象的本地挂载`
- Q：对“只留在本地的”那一层，第一阶段最明确不应跨 RT 同步的是哪类东西？
  - A：`执行实例 / 终端上下文`
