# 2026-04-06 多 Agent 任务治理第一阶段计划

> 状态：已收口阶段边界
>
> 目的：把多 Agent 主题从“抽象愿景”收口到近期第一阶段的具体边界。

---

## 1. 计划摘要

多 Agent 不进入当前第一主线的关闭条件，但其第一阶段方向已经明确：

- **先做任务治理**
- **采用固定四角色编制**
- **采用 proposal-first 主队列**
- **人类入口与终审先落在提案表面**
- **不做动态持久 teammate**

这意味着多 Agent 第一阶段不是“通用自治框架”，而是一个围绕任务治理的受约束协作系统。

---

## 2. 第一阶段产品故事

多 Agent 第一阶段最先承接的故事是：

- 任务治理

而不是：

- 多模态服务员优先
- 通用 teammate 框架优先
- 统一服务员前台优先

其原因是：

- 更贴近外心已有任务 / 提案 / 汇报结构
- 更容易形成可见验收
- 不会过早把系统拖进泛化自治框架

---

## 3. 第一阶段固定角色编制

第一阶段固定为四种角色：

- `coordinator`
- `proposer`
- `reviewer`
- `retrospector`

### 3.1 `coordinator`

- 常驻
- 负责分派、节奏控制、状态推进
- 先承担争议裁决入口

### 3.2 `proposer`

- 按需唤起
- 负责形成或修订提案内容
- 不直接越权改写已完成提案

### 3.3 `reviewer`

- 按需唤起
- 负责评审、评论、退回与预裁决
- 负责把提案推进到等待人类终审的 `in_review`
- **不负责代写 / 代改提案正文**
- **也不负责直接批准提案**

### 3.4 `retrospector`

- 按需唤起
- 独立于 `reviewer`
- 负责执行完成后的复盘，而不是提案评审

---

## 4. 角色职责合同

### 4.1 `coordinator`

第一阶段中：

- 分派与门禁优先
- 控节奏
- 决定交给哪个角色处理
- 默认优先推进会阻塞人类决策或执行的提案
- 遇到争议先做第一层裁决

如果 `coordinator` 仍无法决定：

- 再升级给人类

### 4.2 `proposer`

负责：

- 起草建议
- 形成 `pending proposal`
- 收到退回后修订提案

不负责：

- 直接代执行任务副作用
- 越过评审链直接把草案变成完成态

### 4.3 `reviewer`

负责：

- 评论
- 证据复核
- 退回为 `changes_requested`
- 将提案推进到等待人类终审的 `in_review`

不负责：

- 重写提案
- 代替 `proposer` 修正文案
- 直接把提案标记为 `approved`

### 4.4 `retrospector`

第一阶段触发点优先收口为：

- 执行完成后
- 尤其是时间块结束后

默认读取：

- `eventlog`
- `timeblocks`
- `tasks`

当前明确不做：

- 提案系统本身的复盘闭环

默认输出为：

- 一条结构化 retrospective record

第一阶段落点收口为：

- 以一条 “Agent summary” 消息落到 `eventlog`
- 语义上绑定到已完成的时间块
- 可引用相关任务与事件

默认后续产出只到：

- 建议

不默认自动生成：

- 新任务
- 新提案

---

## 5. 提案流转合同

第一阶段提案流转固定为：

1. `proposer` 生成 `pending proposal`
2. `coordinator` 负责把草稿送入评审链
3. `reviewer` 做预审与证据复核
4. `reviewer` 只能：
   - 推进到 `in_review`
   - 退回为 `changes_requested`
5. `in_review` 的正式语义固定为：
   - **等待人类 UI 终审**
6. 只有人类 UI 可以把提案推进到：
   - `approved`
   - `cancelled`

退回后的规则：

- 由 `proposer` 在**同一提案**上修订
- 一次 `changes_requested -> proposer 修订 -> 再次送审` 记为 1 轮
- 默认允许最多 **3 轮**退回-修订循环
- 达到 3 轮仍未收敛时：
  - 强制进入人类终审
  - 不再让 Agent 角色继续内部往返

如果提案已经到达完成态，再要改动时：

- 必须创建新提案

---

## 6. 协作介质

四角色之间第一阶段默认主要通过以下对象协作：

- 任务
- 提案
- 黑板
- 事件日志
- 时间块

补充边界：

- `blackboard` 只承接摘要 / 交接 / 协调便笺
- 不把“大量自由直接对话”作为第一阶段默认主流程
- `coordinator` 的分派、退回、升级与终审准备痕迹默认挂在：
  - **提案评论 / 提案历史**

---

## 7. 人类入口

第一阶段默认：

- **人类从任务 / 提案表面进入**

而不是：

- 先做统一“服务员聊天入口”

这意味着：

- 近期优先强化任务治理工作面
- “面向人的多模态服务员”明确后置到下一阶段

---

## 8. 与当前主线的关系

多 Agent 第一阶段建立在以下前提之后：

- 个人同步基线已建立
- 信号网络 `v1` 已有骨架
- 单 Agent 关键闭环已跑通

它不应提前混入基础信号语义讨论。

---

## 9. 当前不纳入第一阶段的内容

以下主题明确后置：

- 统一服务员前台
- 通用 teammate 框架
- 动态生成并持久化的 subAgent 网络
- 多设备下的复杂分布式裁决最终方案
- 多模态服务员的完整体系

---

## 10. 最小验收方向

至少应能稳定回答并验证：

- `coordinator / proposer / reviewer / retrospector` 四角色合同明确
- `coordinator` 常驻，其余角色按需唤起
- 主队列采用 proposal-first
- 人类入口与终审先落在提案表面
- `reviewer` 只能评论 / 退回 / 推进到 `in_review`，不能直接批准提案
- `approved` 只能由人类 UI 终审产生
- 退回后的提案由 `proposer` 在同一提案上修订并重新送审
- 达到 3 轮退回-修订循环仍不收敛时，会强制进入人类终审
- 已完成提案的后续变更必须新开提案
- 争议先由 `coordinator` 裁决，无法决断时再交给人类
- 治理痕迹默认挂在提案评论 / 提案历史
- `retrospector` 在时间块完成后可读取 `eventlog + timeblocks + tasks`
- `retrospector` 的第一阶段输出是落入 `eventlog` 的结构化复盘记录，而不是自动新建任务 / 提案

---

## 11. 一句话总结

多 Agent 的第一阶段不是“造一个泛化 Agent 社会”，而是“**先做一个由 `coordinator / proposer / reviewer / retrospector` 组成的固定角色任务治理协作层**”；只有这条线稳定之后，才值得继续抬升到更强的服务员体系和动态 teammate 编排。
