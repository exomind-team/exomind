# 2026-04-17 提案系统通用化讨论纪要

## 背景

本纪要用于固化本轮围绕“提案系统通用化”的问答与阶段性结论，作为后续继续讨论、补充设计与追踪 issue 的本地上下文锚点。

当前讨论已经形成两个明确方向：

- 短期救急：补充当前软件急需的提案能力，例如新增 `edit_task` 提案类型。
- 中长期演化：将提案系统从“少数硬编码提案类型”推进为“面向 RT 动作目录的通用授权执行关口”，并在后续重构中进一步抽象。

相关 issue：

- `#921`：短期方向，补充 `edit_task` 提案类型
- `#922`：长期方向，将提案系统演化为可组合的 RT 动作授权关口
- `#906`：重构/迁移主线，后续 signal-source / signal network 方向的重要承载 issue

## 本轮已确认的核心结论

### 1. 通用化的第一站不是继续扩对象枚举，而是先做 RT 动作目录

本轮讨论确认，提案系统的近期泛化目标应当优先落在“RT 动作目录”这一层，而不是继续围绕对象类型、提案对象枚举或 workflow-first 方案扩展。

也即：

- 先把“系统到底能做哪些动作”抽出来，形成清晰的动作能力面。
- 提案系统对用户呈现的，不再只是少数固定提案类别，而是“对某个 RT 动作的授权执行请求”。

### 2. 提案的默认单位应为单步动作

本轮讨论确认，提案系统默认以“单步动作”作为最小执行单位，而不是一开始就强推多步 workflow。

这意味着：

- 当前阶段先把每一个动作做清楚、做可授权、做可审计。
- 复合动作、工作流、策略编排等能力可作为后续叠加层，而不是当前设计的入口。

### 3. 当前优先级排序：能力覆盖优先于审批可理解性

本轮讨论明确，当前最主要的目标是先提升能力覆盖面，让系统能表达并执行更多真实需要的 RT 动作。

审批可理解性仍然重要，但排序次于能力覆盖：

- 第一优先级：系统能不能覆盖真实需要执行的动作。
- 第二优先级：这些动作如何被用户清楚理解、审批和追溯。

### 4. 权限边界按“动作 + 作用域”定义

本轮讨论确认，提案系统的授权边界不宜只按对象类型划分，而应按“动作 + 作用域”定义权限。

即授权语义更接近：

- 谁可以执行什么动作
- 这个动作允许作用于哪些对象/范围

这比单纯的“能不能改任务”更精确，也更适合后续通用化。

### 5. 失败语义采用强原子单步

本轮讨论确认，当前提案动作的失败语义应采用“强原子单步”。

也即：

- 一个提案默认对应一个单步动作。
- 该动作要么成功，要么失败，不做部分成功的灰色状态设计。
- 复杂补偿、半成功、多阶段提交等机制不作为当前阶段主线。

## 已明确排除或暂不优先的方向

### 1. 当前轮不以 workflow-first 作为核心推进方向

虽然长期来看，复合动作与工作流会是重要方向，但本轮结论是：不以 workflow-first 作为当前提案系统通用化的主入口。

### 2. 当前轮不继续围绕对象枚举做主要扩展

当前不优先继续扩展“又增加一种对象、又增加一种提案类别”的模式，因为这会持续放大硬编码类型分裂，而不能真正解决表达能力问题。

## 分阶段路线

### 近期路线：先服务当前软件的急需功能

当前系列应先满足现实中的紧急需求，以当前 ExoMind 软件为主战场：

- 先建立 RT 动作目录
- 先支持更多现实需要的提案类型
- 先把提案系统从“少数固定类型”推进到“面向动作的授权关口”

这一路线的主要目标，是让当前系统尽快具备更强的实用性和可操作性。

### 远期路线：在 `#906` 重构中向 signal-source / signal network 演化

本轮也形成了较明确的长期判断：

- 在后续 `#906` 迁移/重构阶段，signal-source / signal network 更可能成为底层统一抽象。
- 当前提案系统的 RT 动作目录，可以视为面向未来抽象过渡的一层现实落脚点。

因此，长期方向不是否定当前 RT 动作目录，而是：

- 先用 RT 动作目录解决当前软件的真实问题
- 再在重构中将其提升、重组或吸收到更统一的 signal-based 抽象体系中

## 对“提案系统通用化”本质的当前表述

本轮讨论下，可将提案系统的本质暂时表述为：

“提案系统是一个让用户做门卫、以用户授权为前提、从而获得对 RT 各类动作进行受控增删改查权限的行动关口。”

按这个理解：

- “点击执行”不只是点一个硬编码提案类型
- 而是对某个 RT 动作表达式进行授权与触发
- 后续还可以继续向可复合、可配置、可整合的动作系统推进

## 当前仍保留为后续讨论的问题

- RT 动作目录如何组织、命名、分层，才能既服务当前实现，又不阻碍未来统一抽象。
- signal network 与其他底层建模方式（例如更偏 ECS 风格的组织方式）如何衔接，仍需在后续重构语境中再讨论。
- 复合动作、批处理动作、工作流动作应在何时以及以何种抽象进入系统，当前尚未定案。

## 作为后续讨论的约束

后续若继续展开提案系统设计，应默认继承以下约束：

- 短期优先服务当前软件的现实功能缺口
- 默认动作单位为单步
- 默认失败语义为强原子
- 权限边界按“动作 + 作用域”设计
- 不再把“新增一个提案类型枚举”作为长期主路线
- 长期目标与 `#906` 的 signal-source / signal network 方向保持兼容
