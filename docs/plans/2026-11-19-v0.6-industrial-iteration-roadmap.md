# v0.6 工业化迭代路线图

## 目标与边界

用户要求先把反复返工转成可证明的约束，再逐步引入意图编排和自动检查。
本轮只做最小闭环，不搭建全套 Agent 平台。跟踪复用
[#568](https://github.com/exomind-team/exomind/issues/568)。

产品次序不变：同步/多端时间块/文件传输等核心缺陷 → 关键 P1 → Beta
余项。工业化检查服务于这条主线，不以「框架完工」阻塞产品修复。

## Beta26 环境与多连接主线

用户于 2026-11-21 批准采用增量方案 B：以“稳定外心环境 + 可多条连接 +
档案 membership”替换当前把 route 直接挂在 `(profile, device)` 上的单层模型。
详细设计见
[Beta26 环境与多连接设计](2026-11-21-beta26-environments-connections-design.md)。

实施顺序：

1. 状态闭包、邀请候选、自动复制、主动扫描和 Windows 任务栏身份；
2. 环境、连接、端点、邀请投递和同步尝试持久层；
3. 双侧连接启停、显式拒绝、手动测试和同步路径日志；
4. 一键邀请/接受以及无复制主路径；
5. PC 双 Host、EasyTier、Android 模拟器，最后再做物理平板矩阵。

### 长期选项 C：完整连接督导器

只有在上述真实模型通过后，才评估 T3 式单一 supervisor、持续 route 预检、
抖动退避、优先后台探测和自动回切。该长期选项要求：

- 多路真实故障矩阵和移动端后台数据；
- 连接测试、同步拨号和 discovery 的成本分别预算；
- 前后台/切网唤醒不产生竞争重连；
- 连接失败可定位到 transport、identity、membership 或数据阶段；
- 用户主动关闭始终优先于自动恢复。

本轮不照搬 T3 的 provider/thread/project/MCP OAuth 或整个客户端架构，只学习
稳定环境身份、可变路线、显式授权和唯一重连所有者的工程规律。

## 2026-11-22 日用界面反馈与后续架构顺序

本节记录 Beta 日用实测提出的 UI 反馈，以及暂不并入当前缺陷修复的两项架构投入。
当前消息操作栏/导出模式重整属于近期交互修复；它要先稳定动作语义和显式模式，
不实施全局命令注册表或命令面板。历史 Beta 差距见
[Beta 执行路线](2026-11-13-v0.6-beta-execution.md) 中的「Ctrl+K 命令面板」与「语音」项。

### 本轮原则收敛：默认降噪与模式可发现性

这组反馈的共同目标不是简单“少放按钮”，而是让日常主线安静，同时让低频但重要的任务在需要时找得到。依据 ARC P02／P03／P06／P07／P09／P11／P12／P13／P16／P17／P20／P21，按 `arc-ui-design` 的 I20「可发现入口与模式内操作隔离」落地；不新增通用 P 原则，也不把某一张工具栏截图或按钮尺寸变成全局规范。

执行合同：

1. **日常操作与专用模式分开**：记录浏览时保留少量主操作；批量选择／导出由记录区内稳定可见、视觉次级的入口进入。进入后再显示选择、移除、导出等模式内动作，并提供清晰退出。命令面板可补充快捷到达，不能成为唯一入口。
2. **模式与对象选择分开**：选区属于消息／记录对象；进入、退出或重排模式不得静默清空或改变选区含义。需要清空时给出明确动作与反馈。
3. **内容本身保留语义**：消息正文继续支持文本选择、链接与长按；通过独立命名的操作控件呈现菜单，不用点击气泡空白区这种会与正文交互冲突的隐式手势。
4. **屏幕空间优先给主要任务**：手机窄屏和软键盘下先保证输入、发送和附件入口完整；低频工具可进入可滚动的次级区域，但不能被裁掉或挤压主要输入。
5. **关系、状态和恢复就近呈现**：引用给出足够上下文和档案内直达；暂存、校验、事件提交、系统打开分别显示真实阶段；失败保留正文并提供对应恢复路径。主题颜色复用语义 token，特殊表面可保留自己的布局。

### UI 与同步分轨验收

- **UI 轨**：日常记录↔选择导出、消息引用与气泡、窄屏输入、附件状态／系统打开、更正弹层、档案切换／管理、浮窗入口分别走实际任务；重点检查信息噪声、入口可发现性、键盘／触摸等价与真实状态反馈。
- **同步轨**：设备身份／成员资格、事件事实、时间块投影、原件字节与 SHA 结果独立核对。UI 显示“已加入”不能替代同步 ACK，UI 呈现“原件完整”也不能替代接收端 hash。
- **候选验收**：源代码与单测通过只证明对应层；同一 Beta26 候选另做 Android 软键盘／实触摸／系统 Sharesheet／系统打开，以及隔离桌面 Beta26 与测试档案的跨设备验证。当前旧候选或模拟视口不冒充新候选通过。
- **明确不纳入**：用户决定直接禁用 GKD 规则；本轮不修改外心以适配该规则。

当前批次已有若干 UI 源码改动与单测结果，但尚未在修复后的 Beta26 候选上完成实机／真窗复核；未验项目维持待验，不以源码状态替代接受结论。

### D1：可拓展命令系统与全局命令面板

- **排期**：当前 Beta 现场缺陷与候选验收收口之后，作为独立架构阶段进入设计和实现；
  不阻塞当前消息操作、导出模式、移动端输入和浮窗缺陷修复。
- **范围**：统一命令身份、上下文/能力条件、来源扩展点、注册与发现、执行回执、
  键盘/触摸的独立唤起，以及类似 VS Code 的全局命令面板。
- **与本轮 UI 的关系**：命令面板和上下文操作不是互斥入口。当前先把「复制、引用、
  更正、选择导出」等事件动作按语义分清，默认/导出模式分开，保持就地入口的
  可发现性；后续由命令系统复用这些动作身份和执行结果，不能把已有必要操作一律
  藏入命令面板，也不能因增加面板再次把两种模式混成一排按钮。
- **验收边界**：没有焦点事件时只开放全局命令；事件上下文命令需标明目标消息和作用；
  无权限/无选中对象/执行失败有真实状态与恢复；注册扩展不得越过命令原有授权。

### D2：跨提供商语音接入

- **排期**：在 D1 的命令/动作接口稳定后设计语音统一接缝，再实现桌面与移动端的
  提供商适配器；它与当前消息工具栏修复分开验收。
- **范围**：适配 MOSS、火山、DeepSeek 等提供商，并允许通过明确版本化的外部 API
  格式增加适配器；重点验证手机上的授权、录音/音频路由、后台恢复、取消与文本回执。
- **安全与产品边界**：密钥使用专门的私密设置/安全存储，不进入命令参数回显、事件正文、
  普通诊断或剪贴板；录音许可、发送目标与最终事件提交仍由用户可见、可控制的状态确定。
- **验收边界**：统一接口须表达流式/非流式能力、取消、超时、错误类别和来源；提供商
  不可用时仍能手动输入和保存，未确认的识别结果不能伪装成已记入事件日志。

### 顺序决策

1. 收口当前实测缺陷，并完成对应的 Web/Native/设备候选验证；不把 D1/D2 混入 Beta 修复。
2. 先建立 D1 的动作注册与全局命令发现，使已有动作可复用；必要的就地操作仍保留。
3. 再把 D2 语音接入同一动作/命令边界，逐个验证提供商、权限与移动端体验。

这样先固定动作是什么、作用于哪个对象和何时提交，再决定各入口如何暴露；新增命令面板
将扩展可达性，不会推翻当前默认态降噪与导出模式分离。
