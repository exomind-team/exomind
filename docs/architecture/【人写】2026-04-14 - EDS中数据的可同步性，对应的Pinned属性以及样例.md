# EDS中数据的可同步性，对应的Pinned属性以及样例

## 核心定义

类型定义：RT-Only即Pinned属性，应该是数据的「可同步性」属性的一部分，分为「当前可无缝跨端同步Unpinned|单RT持有且当前不可迁移Pinned」
特征阐释：这个属性标记了「虽然数据最终都要落盘在RT上，但哪些数据可以被跨端共享读写且不会有毁灭性冲突（如一条事件日志，或带有充足环境信息不会因换RT就改变意思的信号值，即Unpinned），哪些是与具体的RT绑定而无法自由挪动（如只在特定RT上有效的Agent会话id，或操作系统的某个进程，即Pinned）」。
相互转化：与此同时，这两个属性还是可以转化的。Unpinned一定程度上会被Pin，Pin经过一些方法可以转换成Unpinned，这中间往往意味着数据自身的变化。

## 举例说明

假设设备：有两台Windows电脑A、B，有一台Android手机C。

### Pinned

A上的RT（简称RT-A，以此类推还有）现在有一个Codex会话，这个会话的信息包括：会话历史、会话id、会话工作目录、会话配置，Rust结构体如：Session { id, history, work_dir, config }。因为只有在A上才能以id加载history并在work_dir上运行相同的Codex，这些数据只有在A上才能真正发挥作用
因此：数据只在RT-A上有意义，在设计上就需要做成Pinned。RT-A在启动一个Codex会话时，所创建的session = Session { id, history, work_dir, config }只保证本地可用，而正因如此需要把这个Session标记为Pinned类型，从而session不需要参与CRDT同步（不需要经过DSON层与冲突解决层，直接与存储适配层交互）进而只会留在RT-A中， 不与其他RT共享。
为什么叫Pinned？因为这些信息的语义、它的作用被一个RT（及其背后的物理设备）给「钉住了」，意义被钉在RT上，在同步系统视角下，无法保证能完整迁移到其他RT中，RT也不承诺这数据直接复制到其他RT上能用。
如果RT-A上的Codex会话只把上边这些id、历史记录、工作目录路径

### Unpinned

而后有了一个「Codex会话打包工具」，能把整个会话（包括历史、id、整个工作目录文件夹、整个配置文件）打包成一个结构体archive = SessionArchive { id, history_data, work_dir_archive, config_data }即「会话存档」。这份会话存档可以在任何RT中部署，所有的语义都包含在内，能跨RT通用（当然会有某些RT无法执行的问题，但本质特征是「可以被迁移到其他RT上了」至少是「在数据自身跨RT流动后，耗损程度可控可接受的情况下」）
因此：这个SessionArchive是一个典型的Unpinned数据类型——因为所有能达到其目标（建立有对话历史、配置一样、在相应工作目录文件夹工作的Codex）的数据都不会在「迁移到另一个RT」中失去意义。
会话存档如此，事件日志如此（天然可复制，只增不改），任务集也是如此（需要在多设备间同步，并且可能会修改标题或描述）。

### 中间状态如何定义？

那是不是Pinned状态的数据，就一定不能在RT中迁移呢？对于上述的「Codex会话」的例子，就能找出一个可能的途径：

1. 解绑：把Pinned状态的数据通过一种「Unpin」过程，转换成Unpinned的数据。在Codex会话的例子中就是：RT-A把会话历史、压缩后的工作目录文件夹、会话配置与会话id等数据都打包成一个「能在别的RT上重放出基本上相同的Codex会话」的数据包
2. 同步：再把Unpinned的数据，同步到其他RT上（这时候就经过正常的CRDT/DSON同步），实现Pinned数据的间接共享。在Codex会话的例子中就是：RT-A把打包后的Codex会话存档发给RT-B，这时候RT-B就获得了这个Codex会话存档，并有了运行相同（相同工作目录、相同对话历史）Codex会话的能力
3. 重绑：这些Unpinned的数据无法直接被执行，需要经过「Pin」过程被再度绑定成原始Pinned数据，实现Unpinned数据的「激活」（而激活的代价就是不能直接同步）。在Codex会话的例子中就是：要把压缩包重新解压成会话历史文件、工作目录文件夹等，而解压出的历史文件、工作目录文件夹就只能被当前RT所访问了；因此当RT-B解压「会话存档压缩包」并启动Codex会话时，这个Codex会话就会变成在RT-B上的Pinned数据，而RT-A与RT-C均不能直接同步

因此，通过Pinned--Unpin->Unpinned--共享->Unpinned--Pin->Pinned的全过程，本来Pinned的数据经过这一对「Unpin-Pin」的可逆过程，可以实现间接同步。

但要注意，这样的间接同步还是不等于直接同步，终究不是万能的。因为：

0. 根本原因：转换成的Unpinned数据≠转换前的Pinned数据，不能发挥Pinned数据的作用（如：Codex会话压缩包无法被直接执行，Codex CLI运行环境不认压缩包）。而如果一个Unpinned的数据能与Pinned的数据发挥同样的作用，那就根本不需要这么繁琐的过程（因为本身就能作为Unpinned数据四处流转，举例说明如事件日志列表，能Pin是能Pin，但在Pin之前就能无损在设备间同步）。总而言之：「能在RT之间传递」只是「能在不同RT上发挥其原有功能」的必要条件而非充分条件。
1. 不保证一定能Unpin：Pinned数据并不总是能经由Unpin转换为Unpinned数据（如：正在运行的Codex会话中，操作系统进程无法被Unpin）
2. 不保证一定能(re-)Pin：Unpinned数据不一定能被另一个RT运行，其「间接同步」只是一种可能性，而非必然性。

### 一些数据的默认Pinned状态：到底是怎样控制的？

结论先行：

- 通用来说：这些状态由数据结构定义。我们的数据结构预设了一些数据默认要参与同步（如事件日志、时间块、任务），而另一些数据默认不参与同步。因为同步本身是由「同步之后能在某个目的上有相同效果」定义的，而其中的「目的」与「效果」

### 信号网络「管理其他设备上的终端」的功能，如何在这层体系中实现？

结论先行：

- 通用来说：最终的数据类型、数据结构并不一定是完全的Pinned或完全的Unpinned，而是部分字段（内部数据）Pinned作为「对接本地的部分」、部分字段（另一部分数据）Unpinned作为「外部引用的部分」。其他RT通过共享Unpinned的数据以间接控制Pinned的数据。
- 举例说明：对于在电脑A上的RT-A启动的Codex会话，有关「Codex进程id」是Pinned的，有关「Codex会话ID」「当前Codex会话状态」「PTY连接地址」等描述性、引用性信息则是Unpinned的。对于有权控制RT-A的Codex会话的RT-B，可以通过发送Unpinned的信号「对Codex会话ID为{id}、PTY地址为{link}的会话输入文本{content}」就可以同步到RT-A中，并让RT-A对着指定进程id（只有RT-A自己持有）的Codex CLI进程传递文本{context}并通过PTY地址{link}持续向RT-B的「PTY终端UI」呈现Codex会话中的内容，以此实现对RT-A中终端（不仅仅是Codex会话）的管理

### 对于「多RT唯一持有」的问题

结论先行：

- 通用来说：这是一个更高层次的「UniquePinned数据」的问题，建立在我们文档所讲解的「Pinned/Unpinned」抽象之上，且具体细节需要更多问题讨论来明确。
    - 具体而言，这是在同步层要锁死的，并且需要更多的讨论来明确「如何做到严格保持只有唯一一个RT持有」。
    - 因为在Unpin后的Unpinned数据可以被其他多个RT所同步（只要做了，就能基本上无损同步并存留多个备份），所以我们可能需要一个在CRDT同步之上的「连接」机制来保证通道的唯一性（只在两个RT之间做Unpinned数据的传输，传输后传出方销毁、传入方Pin；但这样子做依然可能会出现「传出方与传入方得到了两份Pinned数据」的情况，不能确保销毁）。
- 举例说明：一个Codex会话、一个中心化服务器（如各类中心化服务端）从RT-A到RT-B上运行时，只会在一个RT上运行，以类似「接力」的方式做Pinned数据的迁移（依然是Pinned的，但只是被Pin在的RT不同）
    - 也许「先Unpin并同步到RT-B上，再在RT-A销毁，再让RT-B启动」这个执行链条能基本保证整个「Pinned数据唯一性交接」进而维护数据的「UniquePinned性质」，但过程中只要一个地方断线、断裂，就可能有「两个RT同时运行本来要UniquePinned的数据，进而使数据不再UniquePinned」的状况。特别是对于随时可能在任何时候、任何环节断开连接的分布式网络而言，本身需要一个强稳定性来保证数据的UniquePinned性质不被破坏。
    - 破局点也许在于：对于要保证UniquePinned的数据d而言，虽然「在RT-A与RT-B同时存在」会破坏其UniquePinned性，但「RT-A与RT-B都不存在d」并不会破坏其UniquePinned性，而d可以被Unpin后的数据d_u还原（随时可以？可重复？需要探索）
