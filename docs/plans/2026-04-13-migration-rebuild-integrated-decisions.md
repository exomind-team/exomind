## 1. 这轮工作的性质已经锁定

- 这不是对旧架构做补丁式改良，而是**搬迁式重构**
- 搬迁的对象不是旧实现的壳，而是已验证的：
  - 对象语义
  - 不变量
  - 设计决策
  - 失败教训
- 这轮默认允许明显断裂，不以“旧入口尽量无感兼容”作为首要目标
- 旧数据需要承担**单向导入**义务，但不承担长期双向兼容义务

## 2. 新骨架的硬边界已经锁定

后续架构必须满足以下硬分层：

- `EDS` 负责存储
- `RT` 负责计算
- `ECS` 负责联网与连接性
- `Web / Tauri App` 负责用户呈现与 UI/UX

因此，以下旧前提已经被否决：

- UI 持有 runtime 真相
- UI 持有长期业务 side effects
- 存储与计算职责混层
- `profile / user / scopeKey / anonymous` 继续做底层 canonical scope

## 3. Archive OS 与多档案心智已经锁定

### 3.1 核心对象与主键

- 核心对象正式术语统一为 `archive`
- 稳定主键是不可变 `archive_id`
- 个人档案与集体档案在身份层同型

### 3.2 会话边界

- `ArchiveSession` 是某个 `RT` 上某个档案的本地运行会话
- `UiSession` 是外部 UI 终端连接
- `前台 / 后台` 是 UI 概念，不是 RT 状态机字段
- 第一阶段 RT 侧最小状态收口为 `running / closed`
- 第一阶段 UI 连接侧最小状态收口为 `connected / disconnected`

### 3.3 默认档案与切换器

- 一个 Tauri App 第一阶段默认直接进入固定存在的本地默认档案
- 默认档案不可删除、不可重命名、固定置顶
- 默认档案可显式升级为正式个人档案
- 升级完成后，当前窗口停在新正式档案，RT 自动补出新的空白默认档案
- 档案切换器第一阶段至少区分：
  - 当前
  - 运行中
  - 已占用
  - 已锁定

## 4. 集体协作与治理边界已经锁定

### 4.1 集体档案与成员关系

- 集体档案与个人档案同层并列
- 集体档案有自己的 `ArchiveSession`
- UI 前台接入的是成员对集体的座席，而不是抽象集体本体
- 所有行为都必须按明确成员身份记账

### 4.2 治理与写入门禁

- 不采用“所有业务写入全部逐条提案”的极端模型
- 采用分层门禁：
  - 集体 `eventlog` 默认直写，但强审计
  - 时间块计划走提案，执行记录直写并审计
  - 任务结构变更走提案，执行反馈直写并审计
  - route / edge 编辑走提案
  - 治理设置本身走提案
- 不做通用规则引擎，只允许少量枚举式例外与开关

### 4.3 Blackboard 边界

- `blackboard` 是每档案一个持久对象
- 它承载共享工作记忆、协调便笺、交接摘要
- 它不是业务真相 carrier
- 它不是长期保留、强审计总池
- Phase 1 采用时间序条目 + 追加修正 + 容量上限 + 显式弹出

## 5. 搬迁策略已经锁定

### 5.1 保留什么

- 领域对象语义与不变量
- Archive OS、`ArchiveSession / UiSession` 边界
- proposal-first、blackboard、route / edge 等已收口的产品与架构合同
- durable runtime、跨设备一致性、signal network 的已验证经验

### 5.2 抛掉什么

- `profile / user / scopeKey / anonymous` 旧作用域心智
- UI-owned runtime worker、scheduler、projector、repair coordinator
- 旧页面和旧 store 对 layout / runtime / navigation / persistence 的主权
- 旧兼容桥继续成为未来主干

### 5.3 兼容窗口怎样做

- 允许短期兼容读取旧数据
- 所有迁移默认朝新骨架**单向导入**
- 兼容层必须可删除，不能成为永久层

## 6. 主骨架与首阶段落点已经进一步锁定

### 6.1 主骨架

- 新骨架现在就先锁**对象同步骨架**
- 当前不采用“先只锁硬边界，继续长期比较对象同步内核”的路线
- 当前主同步内核方向锁定为：
  - `CRDT-first Object Store`
- 当前技术起点约束是：
  - 无头外心
  - `DSON` 作为 `CDS` 基座
  - `ECS` 以 `iroh` 等机制承担互联
- 可以分阶段分别建设
- 但不接受“先按另一套核心做出来，后面再回头改主内核”

### 6.2 第一条对象同步闭环

- 第一条“对象同步闭环”优先选择：
  - `EventLog / TimeBlock`
- 选择理由不是“它们最终一定是全部核心”，而是：
  - 它们更接近底层基础数据结构
  - 更适合先验证对象同步骨架与治理动作的基本闭环

### 6.3 首阶段验收口径

- 第一阶段最不能妥协的验收口径是：
  - 无头单机先成立
- 即使没有完整 UI 和完整 ECS，`RT / EDS` 也要能独立跑通：
  - 对象闭环
  - 治理动作

### 6.4 EDS / ECS 首阶段落点

- 首个可实现的 `EDS` 基座采用：
  - `SQLite-backed EDS interface`
- 新架构正式存储层中没有 `PouchDB` 的位置
- `SQLite` 不是权宜之计，而是第一适配者
- `ECS` 第一阶段采用：
  - 先本地无头，`ECS` 做窄接口
- `ECS` 不得反过来阻塞主骨架重建

## 7. 总路线图的主攻顺序已经锁定

- 总战略轴：
  - 跨设备一致性
  - `ECS / EDS / signal network` 共同基础
- 第一主攻方向：
  - 底层真相源
- 推进顺序：
  1. 核心能力需求
  2. 技术选择
  3. 宏观架构
  4. UI/UX

## 8. 旧数据、默认匿名用户与集体预留已经锁定

- 旧数据导入最低义务只兜：
  - `RT SQLite`
- 旧 `PouchDB` 最多只作为：
  - 一次性 `JSON` 导入源
- 新系统的 `JSON` 导出不承诺兼容旧版
- 当前 `anonymous` 历史数据应抽象并映射为：
  - 新系统中的默认匿名用户 / 默认档案
- 集体语义在第一阶段：
  - 骨架预留但不落地
- 当前只预留已知接口，例如档案类型等

## 9. Proposal、Apply 权威、Blackboard 与 UI 角色已经锁定

### 9.1 Proposal

- `Proposal` 第一阶段尽早进入主路径
- 它承担治理主队列角色
- 它的理论定位是：
  - 待批准的 `RT` 动作
- 第一阶段的最小技术合同采用：
  - 显式命令对象
- 每个提案都包装为明确的 `RT command / action`
- 批准后由 `RT` 执行并留历史
- 在技术上，这些命令可通过信号池机制发往事件日志、时间块等 `RT` 能力，语义上等价于 UI 点击，但主权不再属于 UI

### 9.2 Apply 权威

- 远端同步、恢复、重放进入本机后的唯一最终 `apply authority` 是：
  - `RT`

### 9.3 Blackboard

- `Blackboard` 必须保持为独立共享层
- 但其落地顺序后置
- 第一阶段里，它更偏向：
  - 用于测试 `ECS / EDS` 稳定性
  - 用于测试 actor 节点可跟踪的存储空间与算力等资源
  - 作为服务型节点验证共享层边界

### 9.4 UI

- 首阶段 UI 只做：
  - 最小治理 / 调试壳

## 10. 阶段性完成标准已经锁定

- 第一条端到端验证切片：
  - `EventLog / TimeBlock` 对象同步闭环
- 第一阶段完成标准：
  - 新骨架可承载新功能

这意味着第一阶段的胜负手不在“旧页面迁得多快”，而在“新骨架是否真正拿回真相源、作用域原语和运行时主权”。

## 11. 当前明确不再回退的否决项

后续讨论中，不再回退到以下立场：

- 继续把旧代码视为必须原位改良的主体
- 继续让 UI 拥有 runtime 的长期职责
- 继续把 `profile` 体系视为未来主对象，只做 rename 美化
- 继续用长期双写、长期双向 shim 换“平滑迁移”
- 先做页面外壳，再反向逼底层补能力

## 12. 基于现有决策，仍需继续提问收口的问题

下面这些问题尚未锁定，而且会直接改变路线图，因此必须进入后续提问：

### 12.1 对象同步骨架的正式形态

- `CRDT-first Object Store` 的正式对象结构、对象日志、验证层、投影层分别长什么样
- `DSON / CDS` 的最小接口边界与命名如何落定
- `EventLog / TimeBlock` 在该骨架中分别属于原生对象、投影对象，还是命令驱动对象

### 12.2 ECS 窄接口的最小合同

- `ECS` 在第一阶段到底只承担哪些互联职责
- `iroh` 对应的是 transport、peer identity、还是更高层的同步承载
- 首阶段哪些同步/恢复能力必须故意不依赖 `ECS`

### 12.3 默认匿名用户与默认档案模型

- 默认匿名用户 / 默认档案在新骨架中是一个对象、两个对象，还是一组视图关系
- 它与未来正式个人档案的升级关系怎样进入 `EDS / RT` 合同
- 旧 `anonymous` 数据如何映射成新对象而不再保留旧作用域语义

### 12.4 Proposal history 与动作集

- `Proposal` 的最小历史模型、审计字段、状态机与动作集如何定义
- “批准”与“执行”在事件与对象层是否显式拆开
- 哪些 `RT command` 第一阶段必须进入提案门禁，哪些暂不进入

### 12.5 Blackboard 的 owner 与 scope

- `Blackboard` 的第一 owner 到底是 `archive`、`archive session`，还是成员座席
- 它的 scope、资源记账、删除痕迹、与私有 workspace 的蒸馏边界怎样落定

### 12.6 选择标准的主排序

- 架构候选筛选时，以下维度的主排序怎样定：
  - 一致性与恢复性
  - 可治理与不可静默丢失
  - 可替换与可搬迁
  - 实现可行性

## 13. 一句话总结

当前已经定下来的不是“如何修旧系统”，而是：**抛掉旧作用域、旧主权和旧兼容前提，把已经验证过的语义、不变量与设计合同搬进一套新的、以底层真相源为先的新骨架。**
