## 调查原则

1. 用户反馈、源码事实、自动化测试结果和设备实机结果分别记账。
2. 同一现象可归并根因，但不能用一条修复关闭同组所有反馈。
3. 不降低设备身份、证书 pin、本地草稿或原件校验来换取“看起来成功”。
4. 所有异步操作必须有可见状态和可执行的下一步；不能停在没有结果的等待态。
5. 低频操作可以渐进披露，但不能只靠 hover、长按、空白点击或命令面板发现。
6. 进入专用模式后可以公开该模式的动作；模式切换不能静默丢失用户选区。

## β26 日用新增反馈：旧档案切换到手机新档案时无恢复动作

> 级别：用户标记为影响同步稳定性的致命问题。仅记录，不派工、不开始 β27。

- **设备状态**：PC 打开的是旧档案；手机打开的是新档案“2026-11-24”。
- **用户预期**：重新建立设备连接，并把手机“2026-11-24”档案同步到 PC。
- **现场结果**：PC 从虚拟局域网检测到已有设备后，显示“当前档案的设备授权已变化或被撤销”，当前画面没有能继续到用户预期操作的可用动作。
- **根因**：未知。现有画面只证明档案/设备授权状态不匹配以及恢复路径没有指向用户目标；不能仅凭截图断定邀请失效、设备身份变化或历史数据丢失。
- **证据**：本轮随消息附图。截图包含邀请内容与凭据字段；本记录不复制、不解析、不复述这些值。
- **影响边界**：当前反馈描述的是从 PC 旧档案切换并接入手机新档案的流程受阻；没有证据表明任何一端的历史被覆盖或删除。
- **后续记录要求**：在用户授权进入下一轮前仅作为 β26 问题台账。将来若开始调查，需分别查明当前 PC 档案、目标手机档案、设备身份/授权关系和可恢复动作，并验证双端历史与原件未丢失；不得为了连接成功覆盖档案或放宽身份验证。

### 本轮补充：虚拟局域网地址与签名邀请

- 用户报告：手机原始邀请的结构、签名和 schema 检查通过，但其中列出的连接地址都 timeout；手动把虚拟局域网地址追加到 `offer.candidates`、沿用原签名后，流程转为“当前档案的设备授权已变化或被撤销”。用户同时表示旧档案数据已由本人删除。此条不推断应用曾覆盖或删除数据。
- 源码确认邀请签名覆盖整个 `PeerInvitationOffer`，其中包括 `candidates`；改变候选地址却保留原签名应验证失败。这是身份完整性约束，不应允许客户端忽略签名错误。
- 源码另有接收端“更换连接地址”字段。它把地址作为独立的拨号提示传给 join 路径；Host 可优先拨该地址，同时仍用原邀请 issuer 的 TLS fingerprint 校验身份。预期现场路径是保留手机原邀请原文，在 PC 的地址提示字段输入虚拟局域网地址，再检查并确认加入。
- 当前产品的目标语义是：加入动作以邀请中的 profile ID 为目标；旧档案保留，成员资格确认后将新档案加入本机列表并切换到它。因此不应要求先删旧档案或先回到“未配置档案”。
- 档案选择器现状：切换动作只接受本机档案列表中的 profile ID；初次启动的空档案状态存在，但选中档案后没有“暂不选择/回到未配置状态”的入口。虽然目标加入流程不应要求清空选择，这个退出当前档案的恢复入口缺失仍是用户反馈，不代表需要删除或归档现有数据。
- **尚未解释**：为什么现场出现的旧档案授权变化提示让用户无法辨认它是否阻断新档案加入；也未确认用户是否使用过独立拨号地址字段、该字段实测结果如何。源码只能证明存在该控制与其设计边界，不能证明本轮实机流程成功。
- 附图只作为交互状态证据；邀请 secret、signature、地址与 fingerprint 均不摘录、不复用。
- **手机热点状态补充**：用户报告 PC 已改接手机热点。最新界面截图显示邀请结构/签名与 schema 通过，连接来源报告“安全身份可达，尚未加入”，成员资格仍待确认。此证据只证明连接候选已通过 TLS 身份检查；不代表成员资格已接受、档案已切换或历史/原件已同步。用户表示将自行完成后续确认。

## 横向 UI 原则候选

这组原则用于后续复核并反馈给 `arc-ui-design`，当前只记录：

1. **状态闭包**：用户动作必须到达成功、失败、取消或明确待查证状态。
2. **单一事实投影**：开放端口、已验证设备、已加入成员、已同步数据是四种不同状态。
3. **渐进披露但不隐藏入口**：日常界面安静，低频操作仍可通过可命名控件、键盘或触摸发现。
4. **模式与选区分离**：进入或退出选择导出等模式，不静默清掉已选对象。
5. **内容优先于管理细节**：图片先显示内容；文件名、大小、打开和下载在需要时展开。
6. **可逆但不含糊**：继续输入取消预发送时要保留原文和附件；危险动作必须说明不可逆范围。
7. **路径与身份可审计**：地址、证书、设备、档案和运行时身份分别呈现，不用一个“连接成功”掩盖差异。

## 建议的调查顺序

这只是进入 β27 后可提出的顺序，不是当前派工：

1. 先做只读源码追踪和最小复现，固定状态机与 evidence owner；
2. 区分平台无关问题与 Android Tauri/IME/通知渠道/System Sharesheet 专属问题；
3. 对同步问题同时记录 TCP 可达、TLS 身份、协议 hello、应用设备 ID 和档案成员五层事实；
